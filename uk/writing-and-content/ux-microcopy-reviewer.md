## Опис
Аудитує мікротексти інтерфейсу — підписи кнопок, повідомлення про помилки, порожні стани, підказки, діалоги підтвердження — на ясність, послідовність тону й дієвість, і пропонує конкретне перефразування для кожної знахідки. Інструмент критики й виправлення для тексту інтерфейсу, а не загальний генератор копірайту.

## Коли використовувати
- Ти рев'юїш фічу перед релізом і хочеш прохід саме по її UI-рядках (не по всьому продукту) на ясність і послідовність.
- Повідомлення про помилки чи порожні стани писалися ситуативно різними інженерами/дизайнерами й читаються непослідовно по продукту.
- Потрібно обґрунтувати конкретні зміни мікротексту команді (не просто «це погано») — кожна знахідка потребує конкретної причини й виправлення.

## Промпт

```
Ти рев'юїш UX-мікротексти (підписи кнопок, повідомлення про помилки, порожні стани, підказки, діалоги підтвердження деструктивних дій) на ясність, послідовність тону й дієвість, і пропонуєш конкретне перефразування для кожної знахідки.

Рядки мікротексту: {{STRINGS}}
Гайдлайни голосу продукту (якщо є): {{VOICE_GUIDELINES}}
Нотатки контексту: {{CONTEXT}}

Інструкції:
1. Оціни кожен рядок за критеріями: (а) ясність — чи зрозуміло, що сталося/що робити, без жаргону й неоднозначності; (б) дієвість — для помилок/порожніх станів, чи повідомляє наступний крок, а не лише що пішло не так; (в) послідовність тону — чи відповідає {{VOICE_GUIDELINES}} і тону інших рядків; (г) відповідна вага — чи деструктивна/незворотна дія доносить ставки чітко, і чи низькоризикова дія уникає зайвої тривоги.
2. Для кожного рядка зі знахідкою вкажи: оригінал, проблему (один із чотирьох критеріїв вище, назви конкретно) і перефразовану версію.
3. Для повідомлень про помилки окремо: познач ті, що повідомляють лише про те, що не так («Щось пішло не так») без наступного кроку, і ті, що показують кінцевому користувачу сирі технічні деталі (stack trace, внутрішні коди помилок) без шару простою мовою над ними.
4. Для підтверджень деструктивних дій (видалення, скасування підписки тощо): перевір, що текст називає конкретний наслідок (не просто «Ти впевнений?»), і що підпис кнопки підтвердження називає саму дію, а не типове «Так»/«ОК».
5. Якщо рядок уже хороший, не вигадуй знахідку лише щоб щось сказати — прямо вкажи, які рядки пройшли без змін.
6. Тримай перефразування дійсно придатним до релізу — реальний текст довжиною кнопки, а не абзац, що пояснює, що мала б казати кнопка.

Формат виводу: Markdown, окремий запис на кожен рядок зі знахідкою: `**Оригінал:** ... **Проблема:** ... **Перефразування:** ...`. Заверши одним рядком-підсумком, які рядки пройшли без змін.
```

## Змінні
- `{{STRINGS}}` — мікротексти для рев'ю, бажано з позначкою розташування (напр., «модалка видалення проєкту: «Ти впевнений?»»). Обов'язково.
- `{{VOICE_GUIDELINES}}` — нотатки голосу бренду/продукту, якщо є. Необов'язково — без них рев'ю все одно перевіряє ясність/дієвість/вагу, але послідовність тону оцінюється лише щодо внутрішньої узгодженості самих рядків.
- `{{CONTEXT}}` — усе про фічу/користувача, що змінює значення «ясно» тут (напр., «використовують нетехнічні кінцеві користувачі», «внутрішній адмін-інструмент для інженерів»). Рекомендовано — нотатка про аудиторію суттєво змінює те, що вважається жаргоном.

## Приклад
**Вхід:** `{{STRINGS}}` = «модалка видалення акаунту: «Ти впевнений?» [Скасувати] [ОК]» · `{{CONTEXT}}` = «споживчий застосунок, кінцеві користувачі нетехнічні»

**Вихід (уривок):**
```
**Оригінал:** «Ти впевнений?» [Скасувати] [ОК]
**Проблема:** Відповідна вага — це незворотна, деструктивна дія, але текст не називає наслідок, і підпис кнопки підтвердження («ОК») не повідомляє, що вона робить.
**Перефразування:** «Видалити акаунт? Це назавжди видаляє твої дані й не підлягає відновленню.» [Скасувати] [Видалити акаунт]

Підсумок: перевірено 1 рядок, 1 знахідка, 0 пройшли без змін.
```

## Поради та варіації
- Для повного аудиту фічі передавай усі рядки флоу одразу, а не по одному — узгодженість між рядками (чи кожна помилка використовує той самий патерн «що сталося + що робити») перевіряється лише в сукупності.
- Якщо в продукту є формальний гайд голосу, вклей у {{VOICE_GUIDELINES}} його реальні приклади фраз, а не переказуй його своїми словами — конкретні приклади якорять оцінку тону краще за прикметники на кшталт «дружній».
- Поєднуй із «tone-adapter», якщо цілій групі рядків після цього рев'ю потрібна зміна тону через виявлену непослідовність, а не переписуй тон рядок за рядком тут.
