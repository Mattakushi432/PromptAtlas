## Опис
Генерує рубрику оцінювання — критерії, пороги проходження/провалу і крайні випадки для перевірки — для оцінки якості виводу AI-агента на конкретній задачі, щоб прогони оцінювались послідовно різними рев'юерами (чи LLM-суддею) замість довільного «на око», яке дрейфує між оцінювачами й із часом.

## Коли використовувати
- Налаштовуєш harness для оцінювання агента і потрібна конкретна рубрика для оцінки, а не розмите відчуття «виглядає правильно».
- Різні люди в команді оцінюють вивід одного й того самого агента непослідовно, і потрібен спільний письмовий стандарт для узгодження.
- Збираєшся внести зміну в агента (промпт, інструмент, модель) і хочеш мати рубрику заздалегідь, щоб порівняти прогони до/після за тими самими об'єктивними критеріями.

## Промпт

```
Ти генеруєш рубрику оцінювання виводу AI-агента на конкретній задачі.

Задача, яку виконує агент: {{TASK}}
Приклад хорошого виводу: {{GOOD_EXAMPLE}}
Приклад поганого чи провального виводу, якщо є: {{BAD_EXAMPLE}}
Хто використовуватиме цю рубрику для оцінки виводів (людина-рев'юер чи LLM-суддя): {{SCORER}}

Інструкції:
1. Виведи 4-6 критеріїв оцінки безпосередньо з того, що відрізняє {{GOOD_EXAMPLE}} від {{BAD_EXAMPLE}} (якщо надано), чи з реальних вимог {{TASK}} — не загальний список «точність, ясність, корисність», відірваний від цієї конкретної задачі. Кожен критерій має бути перевірним лише за виводом, без потреби заглядати у внутрішні міркування агента.
2. Для кожного критерію визнач, як конкретно виглядає прохід, достатньо чітко, щоб два різні оцінювачі погодились щодо того самого виводу — уникай суб'єктивних формулювань на кшталт «хороший тон» без уточнення, що означає «хороший» для цієї задачі.
3. Визнач принаймні 2 крайні випадки, специфічні для {{TASK}}, які наївна рубрика пропустила б — випадки, коли вивід виглядає поверхово правильним, але провалюється при уважному розгляді (напр., числова відповідь, яка правдоподібна, але неправильна; відповідь, що відповідає на інше питання, ніж поставлене; правильна відповідь, подана з фальшивою впевненістю, коли насправді правильною відповіддю було «я не знаю»).
4. Визнач загальний поріг проходження/провалу: ця задача бінарна (прохід/провал), потребує зваженого балу за критеріями, чи будь-який провал критичного критерію (напр., фактична помилка) автоматично провалює вивід незалежно від того, наскільки добре оцінені інші критерії? Обґрунтуй вибір, зважаючи на реальні ставки {{TASK}}.
5. Якщо {{SCORER}} — LLM-суддя, додай явні інструкції для цього судді, як послідовно застосовувати кожен критерій (напр., що робити, коли критерій неоднозначний для конкретного виводу) — LLM-судді потрібна та сама однозначна рубрика, що й людині, можливо навіть більше, оскільки він не може поставити уточнювальне питання.
6. Познач будь-який критерій, який був би дорогим чи повільним для перевірки в масштабі (напр., що вимагає перевірки людиною за зовнішнім джерелом), і запропонуй, чи варто лишити його лише для ручної вибіркової перевірки, чи виключити з рутинного автоматизованого оцінювання.

Формат виводу: таблиця Markdown зі стовпцями: Критерій | Визначення проходу | Вага/Критичний?. Далі — список «Крайні випадки для перевірки» і абзац, що формулює загальну логіку проходження/провалу.
```

## Змінні
- `{{TASK}}` — конкретна задача, яку виконує агент і яка оцінюється. Обов'язково.
- `{{GOOD_EXAMPLE}}` — реальний чи репрезентативний приклад якісного виводу. Обов'язково — критерії, виведені з реального прикладу, значно конкретніші за критерії, вигадані абстрактно.
- `{{BAD_EXAMPLE}}` — реальний чи репрезентативний приклад провального виводу, якщо є. Необов'язково, але суттєво покращує здатність рубрики ловити режими відмов, що реально трапляються.
- `{{SCORER}}` — хто застосовує цю рубрику (людина-рев'юер проти LLM-судді). Обов'язково — інструкції відрізняються для кожного.

## Приклад
**Вхід:** `{{TASK}}` = «Агент підсумовує тред тікета підтримки клієнтів у примітку передачі на 2-3 речення для наступного агента.» `{{GOOD_EXAMPLE}}` = «"Клієнт повідомляє про збої входу з учорашнього оновлення застосунку, підтверджено лише на iOS. Уже пробували перевстановлення (без ефекту). Потрібна ескалація на інженерів, а не стандартна відповідь скидання пароля."» `{{BAD_EXAMPLE}}` = «"У клієнта якісь проблеми із застосунком, потрібна допомога."» `{{SCORER}}` = «LLM-суддя, запускається автоматично на кожному новому підсумку.»

**Вихід (уривок):**
```
| Критерій | Визначення проходу | Вага/Критичний? |
|---|---|---|
| Конкретність | Називає реальний симптом (не «якісь проблеми») і реальну зачеплену область продукту. | Критичний — {{BAD_EXAMPLE}} провалюється саме тут. |
| Обізнаність про попередні дії | Вказує, що вже пробували, якщо тред показує спробу виправлення, щоб наступний агент не повторював її. | Висока |
| Правильний сигнал маршрутизації | Якщо проблема потребує ескалації понад стандартний playbook (за змістом треду), підсумок явно про це каже, а не звучить рутинно. | Критичний |
| Дисципліна довжини | 2-3 речення, не більше — довший «підсумок» знищує саму мету примітки передачі. | Середня |

### Крайні випадки для перевірки
- Тред, де заявлена клієнтом проблема й реальна першопричина (видима з пізніших повідомлень) розходяться — підсумок має відображати діагностовану причину, а не лише початкове формулювання клієнта.
- Тред, який уже вирішений до передачі — підсумок має прямо про це сказати, а не описувати це як відкриту проблему, що потребує дії.

Загальний прохід/провал: провал будь-якого Критичного критерію автоматично провалює підсумок незалежно від інших балів, оскільки розмита чи неправильно маршрутизована передача активно витрачає час наступного агента, а не просто субоптимальна.
```

## Поради та варіації
- Поєднуй із «Рев'юєром слідів використання інструментів» (agents-and-automation, вже випущений), коли рубрика, згенерована тут, позначає повторюваний збій — рев'юєр слідів може допомогти визначити, чи причина в помилці планування, проблемі інструменту, чи прогалині промпту.
- Переглядай рубрику щоразу, коли з'являється новий режим відмови в продакшні, який поточні крайні випадки не передбачали — рубрика це живий документ, а не одноразовий артефакт, особливо на ранньому етапі життя агента.
- Для {{SCORER}} = LLM-суддя періодично звіряй власне оцінювання судді з людським на вибірці — судді-моделі можуть розвинути власні систематичні сліпі зони, яких сама рубрика не ловить.
