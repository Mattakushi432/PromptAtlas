## Опис
Планує перенесення наявної no-code автоматизації (zap у Zapier, воркфлоу n8n, сценарій Make) на іншу no-code платформу чи на власний код — зіставляючи кожен крок з його еквівалентом на цілі, позначаючи кроки без прямого еквівалента й вибудовуючи послідовність переходу, що не створює розриву, коли ні стара, ні нова автоматизація не працює надійно.

## Коли використовувати
- Ти оцінюєш чи вже вирішив перенести робочу автоматизацію з поточної no-code платформи (вартість, обмеження функцій, прив'язка до постачальника, перевага команди) і хочеш конкретну карту того, що переноситься напряму, а що потребує переробки.
- No-code автоматизація переросла свою платформу (впирається в ліміти виконання, потребує логіки, яку кроки платформи не підтримують), і наступний крок — власний код, а не більший план на тій самій платформі.
- Ти консолідуєш автоматизації, побудовані на різних платформах різними людьми, на одну платформу і потребуєш плану міграції для кожної окремої автоматизації, а не просто політичного рішення стандартизувати.

## Промпт

```
Ти плануєш міграцію no-code автоматизації на нову платформу чи на власний код.

Наявна автоматизація, описана крок за кроком (тригер, потім кожна дія/фільтр/розгалуження по порядку): {{CURRENT_AUTOMATION}}
Вихідна платформа: {{SOURCE_PLATFORM}}
Ціль: {{TARGET}} (конкретна no-code платформа, чи «власний код» плюс намічена мова/рантайм)
Чому відбувається міграція (вартість, ліміти, брак функцій, навички команди, консолідація, інше): {{MIGRATION_REASON}}

Інструкції:
1. Зіставляй кожен крок {{CURRENT_AUTOMATION}} з його еквівалентом на {{TARGET}}: тип тригера, кожну дію, кожен фільтр/умовне розгалуження. Для міграцій між платформами назви конкретну функцію цільової платформи (нод/модуль/додаток), що відповідає. Для міграції на власний код назви бібліотеку/виклик API, що замінює кожен no-code крок.
2. Познач кроки без прямого еквівалента: специфічні для платформи функції (вбудована політика повторів, нативна інтеграція конкретного додатка, помічник форматування), яких немає на {{TARGET}} і які потребують явного дизайну заміни, а не просто позначки «інше». Запропонуй заміну конкретно.
3. Визнач поведінку, яка могла б мовчки змінитись, навіть де існує «прямий еквівалент»: різний тайм-аут за замовчуванням, поведінка повторів, гарантії порядку виконання між паралельними гілками чи ліміти швидкості між {{SOURCE_PLATFORM}} і {{TARGET}}. Це найризикованіший клас багів міграції, бо нічого не видає помилку — автоматизація просто починає поводитись трохи інакше.
4. Вибудуй послідовність переходу, щоб уникнути розриву: рекомендуй запускати стару й нову автоматизацію паралельно (нова — у режимі сухого прогону/без запису в продакшн) проти реальних подій тригера протягом визначеного вікна перевірки, перш ніж вимикати стару, замість жорсткого перемикання. Вкажи, що порівнювати між виводами двох прогонів для підтвердження еквівалентності, і тригер відкату (яка помічена різниця означає «зупинись, повернись до старої автоматизації»).
5. Зверни увагу на все специфічне для {{MIGRATION_REASON}}, що змінює план — напр., якщо причина — досягнення ліміту виконання, план має підтвердити, що нова платформа/код справді вирішує цей ліміт, а не просто відтворює ту саму стелю під іншою назвою.

Формат виводу: Markdown-план міграції із секціями: Покрокове зіставлення, Кроки без прямого еквівалента й заміни, Ризики мовчазної зміни поведінки, План переходу (Паралельний прогін → Перевірка → Перехід → Тригер відкату), Примітки щодо {{MIGRATION_REASON}}.
```

## Змінні
- `{{CURRENT_AUTOMATION}}` — наявна автоматизація, описана крок за кроком. Обов'язково.
- `{{SOURCE_PLATFORM}}` — платформа, на якій вона зараз працює. Обов'язково.
- `{{TARGET}}` — цільова платформа чи «власний код» плюс мова/рантайм. Обов'язково.
- `{{MIGRATION_REASON}}` — чому відбувається міграція. Обов'язково — визначає, що план має конкретно перевірити як дійсно вирішене.

## Приклад
**Вхід:** `{{CURRENT_AUTOMATION}}` = «Тригер: новий рядок у Google Sheet (подання форми замовлення). Дія 1: фільтр — продовжувати, лише якщо 'Сума замовлення' > $500. Дія 2: створити запис в Airtable. Дія 3: надіслати повідомлення в Slack у #big-orders.» `{{SOURCE_PLATFORM}}` = «Zapier» `{{TARGET}}` = «n8n (self-hosted)» `{{MIGRATION_REASON}}` = «Вартість — цінова модель Zapier за завдання стає дорогою за поточного обсягу; self-hosted n8n не має вартості за виконання.»

**Вихід (уривок):**
```
### Покрокове зіставлення
- Тригер (новий рядок Sheet) → нод n8n Google Sheets Trigger, режим опитування (тригер Sheets у n8n не має миттєвого варіанту тригера Zapier для Sheets — див. Ризики мовчазної зміни поведінки).
- Фільтр (Сума замовлення > $500) → нод IF n8n з тим самим числовим порівнянням.
- Створення запису Airtable → нод Airtable n8n, операція Create — прямий еквівалент, та сама модель авторизації (API-ключ/OAuth).
- Повідомлення Slack → нод Slack n8n, операція Send Message — прямий еквівалент.

### Ризики мовчазної зміни поведінки
Тригер Zapier «New Spreadsheet Row» для Google Sheets — майже миттєвий (у більшості випадків на основі вебхука); вбудований тригер Sheets у n8n опитує з інтервалом (зазвичай кожні 1-5 хвилин залежно від конфігурації). Це означає, що сповіщення про великі замовлення в Slack, які на Zapier були майже в реальному часі, тепер відставатимуть до величини інтервалу опитування на n8n — узгодь із командою, чи прийнятна ця затримка для #big-orders, чи налаштуй найкоротший практичний інтервал опитування й стався до цього як до усвідомленого компромісу, а не недогляду.

### План переходу
Запусти n8n паралельно на 2 тижні (покриває звичайну варіацію обсягу замовлень) із діями Airtable/Slack, спрямованими на тестові призначення (дублікат бази Airtable, приватний тестовий канал Slack), а не продакшн, порівнюючи: чи кожне замовлення, що пройшло фільтр $500 на Zapier, також з'являється у тестовому виводі n8n з тією самою обчисленою сумою? Тригер відкату: будь-яке замовлення, яке n8n пропустить чи обробить двічі під час вікна перевірки — розслідуй і виправ, перш ніж чіпати продакшн-автоматизацію Zapier.

### Примітки щодо причини міграції
Причина — вартість, а не брак функцій — перед переходом підтверди, що реальна вартість інфраструктури self-hosted n8n (хостинг, час на обслуговування) справді нижча за вартість за завдання Zapier за поточного й прогнозованого обсягу замовлень, а не просто нижча за виконання; self-hosting зміщує вартість із за-завдання на фіксовану інфраструктуру + час операцій, що може програвати Zapier за низького обсягу, навіть вигравши за високого.
```

## Поради та варіації
- Відрізняється від уже випущеного «Конструктора рецептів no-code автоматизації» (`no-code-automation-recipe-builder`): той промпт будує рецепт зовсім нової автоматизації з мети, сформульованої звичайною мовою; цей починає з наявної, вже робочої автоматизації і планує її перенесення на іншу платформу — це інша задача (зіставлення й перевірка еквівалентності, а не оригінальний дизайн).
- Цей промпт зосереджений саме на міграції no-code-до-no-code чи no-code-до-власного-коду — для міграції вихідного коду між мовами програмування/фреймворками це турбота категорії `coding` (промпт міграції мови/фреймворку), а не цей; тримай їх окремо, а не намагайся змусити один промпт покривати і no-code, і перенесення вихідного коду.
- Якщо {{TARGET}} — власний код, очікуй, що крок 2 (без прямого еквівалента) спливатиме частіше, ніж у міграції між платформами — no-code платформи вбудовують багато неявної поведінки (повтори, логування, оновлення токена авторизації), яку власний код має реалізувати явно; не дозволяй плану применшувати цей розрив лише тому, що «це просто код, ми можемо побудувати що завгодно».
