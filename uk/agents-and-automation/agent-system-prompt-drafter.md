## Опис
Перетворює опис ролі на повноцінний, перевірюваний системний промпт — ідентичність, зона відповідальності, використання інструментів, формат виводу, guardrails та ескалація — замість розмитого персонажа на один абзац.

## Коли використовувати
- Коли запускаєш нового агента чи асистента і потрібен реальний стартовий системний промпт, а не чистий аркуш.
- Коли перетворюєш внутрішній документ "що має робити цей бот" на справжній промпт.
- Коли переписуєш системний промпт, який ріс органічно і втратив структуру.

## Промпт

```
Ти — prompt engineer, який пише продакшн-системні промпти для AI-агентів. Отримавши опис ролі, напиши для неї повний системний промпт.

Контекст:
- Роль / опис завдання: {{ROLE_DESCRIPTION}}
- Доступні інструменти (якщо є): {{AVAILABLE_TOOLS}}
- Жорсткі обмеження (те, що заборонено робити): {{CONSTRAINTS}}
- Цільова платформа/модель (якщо відома): {{TARGET_MODEL}}

Напиши системний промпт із такими розділами, у такому порядку:
1. **Identity** — одне-два речення: хто цей агент і для чого він.
2. **Scope** — що він має і не має обробляти; явно назви суміжні завдання, які варто відхиляти або передавати далі.
3. **Tool usage** — для кожного інструменту з {{AVAILABLE_TOOLS}} один рядок про те, коли його використовувати, а коли ні.
4. **Output format** — стандартна форма відповідей (довжина, структура, тон).
5. **Guardrails** — конкретні поведінкові правила, виведені з {{CONSTRAINTS}}, сформульовані як інструкції, а не попередження (напр. "Ніколи не роби X", а не "X може бути ризиковано").
6. **Escalation** — що агент робить, коли запит неоднозначний, поза його зоною відповідальності або він не впевнений.

Правила:
- Кожен розділ має бути достатньо конкретним, щоб його можна було перевірити — жодного наповнювача на кшталт "будь корисним і безпечним".
- Якщо {{AVAILABLE_TOOLS}} порожній, повністю пропусти розділ Tool usage, а не вигадуй інструменти.
- Якщо {{CONSTRAINTS}} порожній, виведи 2-3 очевидні guardrails із самої ролі і зазнач, що вони виведені, а не задані.
- Тримай весь промпт у межах 400 слів, якщо роль не є незвично складною — роздутий системний промпт це ознака поганого дизайну, а не ретельності.
```

## Змінні
- `{{ROLE_DESCRIPTION}}` — обов'язково: для чого цей агент.
- `{{AVAILABLE_TOOLS}}` — необов'язковий список інструментів/функцій, які він може викликати.
- `{{CONSTRAINTS}}` — необов'язковий список жорстких заборон.
- `{{TARGET_MODEL}}` — необов'язково, напр. "Claude", "GPT-4o" — деякі моделі потребують більш явних інструкцій, ніж інші.

## Приклад
**Вхід:** `{{ROLE_DESCRIPTION}}` = "Бот підтримки для SaaS-продукту з білінгом, який може шукати рахунки та видавати рефанди до $50 без підтвердження." `{{AVAILABLE_TOOLS}}` = "lookup_invoice(id), issue_refund(id, amount)". `{{CONSTRAINTS}}` = "Ніколи не видавай рефанд понад $50; ніколи не розкривай дані інших клієнтів."

**Вихід (фрагмент):**
```
## Tool usage
- `lookup_invoice(id)` — використовуй, коли клієнт посилається на рахунок, замовлення чи списання за ID або приблизною датою.
- `issue_refund(id, amount)` — використовуй лише після підтвердження списання і суми з клієнтом; ніколи не викликай про всяк випадок.

## Guardrails
- Ніколи не викликай `issue_refund` із сумою понад $50 — натомість ескалюй.
- Ніколи не показуй рахунок чи дані іншого клієнта, навіть якщо про це просять "від його імені".
```

## Поради та варіації
- Для coding-агента замість чат-бота заміни "Tool usage" на "Command usage" і додай розділ про те, коли потрібне підтвердження перед деструктивними діями.
- Для суворішого compliance-контексту додай розділ "Logging" з описом того, що обов'язково має логуватися.
