## Опис
Складає довідковий аркуш відповідей на типові заперечення продажів для конкретного продукту/пропозиції — для SDR чи sales enablement менеджера, що готує реп (часто нового) до живих дзвінків, а не скрипт для дослівного читання.

## Коли використовувати
- Онбордиш нового SDR/AE і хочеш озброїти його надійними відповідями на заперечення перед першими дзвінками, без написання повного скрипту, що звучить роботизовано по телефону.
- Реп непослідовно чи погано опрацьовує повторюване заперечення, і потрібна задокументована, узгоджена відповідь, на яку команда може орієнтуватися.
- Нова цінова модель, конкурент чи ринкова умова принесли новий тип заперечення, для якого ще немає прописаних відповідей.

## Промпт

```
Ти складаєш довідковий аркуш опрацювання заперечень продажів: для кожного заперечення — структуру відповіді, яку реп може засвоїти й адаптувати власними словами, а не дослівний скрипт.

Продукт/пропозиція: {{OFFER}}
Заперечення для покриття: {{OBJECTIONS}}
Відомі диференціатори/докази: {{PROOF_POINTS}}
Тип продажів: {{SALES_MOTION}}

Інструкції:
1. Для кожного заперечення в {{OBJECTIONS}} структуруй відповідь як: визнання (щире однорядкове визнання, а не зневажливе «розумію, але...»), переформулювання (що насправді правда чи в чому насправді заперечення), і відповідь (конкретна відповідь, з використанням {{PROOF_POINTS}} там, де це релевантно для цього заперечення — не форсуй недоречний доказ).
2. Не пиши повні дослівні скрипти — пиши відповідь як пункти-опори, які реп адаптує своїм голосом у живому дзвінку, оскільки завчений скрипт, перерваний на середині речення, звучить гірше за адаптований.
3. Розрізняй заперечення, які насправді про ціну/бюджет, від тих, що насправді про ризик/довіру, від тих, що насправді про таймінг — те саме поверхневе заперечення («це занадто дорого») може бути будь-яким із трьох, і відповідь має відповідати тому, яке саме це, з явною позначкою.
4. Якщо для заперечення в {{OBJECTIONS}} немає сильної чесної відповіді при наявних {{PROOF_POINTS}} (напр., реальний конкурентний розрив), скажи це прямо і запропонуй найкращу чесну часткову відповідь, а не вигадуй непереконливе спростування — реп, спійманий на переоцінці слабкої тези, втрачає більше довіри, ніж той, хто чесний щодо прогалини.
5. Підлаштуй формальність/темп під {{SALES_MOTION}} — високодотиковий enterprise-продаж підтримує довше переформулювання; висооб'ємний SDR-продаж потребує чогось придатного у вікні 15 секунд до того, як проспект піде далі.
6. Познач будь-яке заперечення, що насправді є сигналом дискваліфікації (проспект справді не підходить), а не запереченням, яке треба подолати — просування повз реальний дискваліфікатор витрачає час обох сторін.

Формат виводу: Markdown, окремий запис на кожне заперечення: `### «{{заперечення словами проспекта}}»`, далі Визнання / Переформулювання / Відповідь короткими пунктами, і однорядкова нотатка про тип заперечення (ціна/ризик/таймінг/дискваліфікатор).
```

## Змінні
- `{{OFFER}}` — що продається і в чому основна цінність. Обов'язково.
- `{{OBJECTIONS}}` — конкретні заперечення для покриття, бажано реальними словами проспекта, якщо вони є (напр., реальні нотатки дзвінка), не перефразовані. Обов'язково.
- `{{PROOF_POINTS}}` — кейси, дані, гарантії чи конкретні факти про продукт, на які реп може опертися. Рекомендовано — без цього відповіді лишаються загальними.
- `{{SALES_MOTION}}` — напр., «висооб'ємні вихідні SDR-дзвінки, 15-30 хв», «enterprise-цикл продажів, кілька дзвінків, технічний покупець». Обов'язково — впливає на темп і глибину.

## Приклад
**Вхід:** `{{OFFER}}` = «Інструмент рев'ю коду, що виявляє проблеми безпеки до мержу» · `{{OBJECTIONS}}` = «"У нас уже є лінтер, хіба цього не досить?"» · `{{PROOF_POINTS}}` = «Лінтери ловлять проблеми стилю/синтаксису; цей інструмент виявив витік захардкодженого секрету для [Компанія X], який їхній лінтер повністю пропустив» · `{{SALES_MOTION}}` = «mid-market вихідні продажі, один дзвінок з лідом команди розробки»

**Вихід (уривок):**
```
### «У нас уже є лінтер, хіба цього не досить?»
- **Визнання:** Справедливе питання — лінтери справді ловлять багато, і якщо це покриває твої потреби, ми не той інструмент.
- **Переформулювання:** Лінтери перевіряють стиль і синтаксис; вони не створені ловити специфічні для безпеки проблеми на кшталт витоку секретів чи ризиків ін'єкцій — інша проблема, інший інструмент.
- **Відповідь:** Лінтер [Компанія X] стояв на місці й проходив, коли захардкоджений секрет потрапив у PR — наш інструмент зловив би це до мержу. Варто глянути, що структурно не може перевірити лінтер.

Тип заперечення: ризик/довіра (вони вважають, що наявний тулінг уже це покриває — не заперечення про ціну чи таймінг).
```

## Поради та варіації
- Для практики опрацювання заперечень у рольовій грі, а не довідкового аркуша, поєднай вивід із реальною симуляцією живої розмови — цей промпт готує матеріал, а не є партнером для практики сам по собі.
- Якщо команда не погоджується щодо правильної відповіді на заперечення, згенеруй 2 альтернативні варіанти «Відповідь» для цього одного заперечення і використай як старт для дискусії, а не сприймай перший вивід як фінальний.
- Переглядай цей аркуш щоразу, коли {{PROOF_POINTS}} суттєво змінюється (новий кейс, новий конкурент) — довідковий аркуш, побудований на застарілих доказах, з часом підриває довіру до репа.
