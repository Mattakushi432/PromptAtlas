## Опис
Складає відповідь на коментар чи DM у соцмережах, що відповідає його реальному типу — справжнє питання, скарга, похвала, спам чи заперечення продажу — а не універсальна дружня відповідь на всі випадки, оскільки кожен тип потребує структурно іншої відповіді, а неправильне прочитання типу дає невлучну за тоном відповідь (напр., бадьоре «дякуємо за звернення!» на гнівну скаргу).

## Коли використовувати
- Керуєш коментарями/DM у великому обсязі й хочеш швидкі, узгоджені з брендом чернетки для перевірки й відправки, а не писати кожну відповідь з нуля.
- Конкретний коментар неоднозначний чи емоційно заряджений, і хочеш другу думку про те, як прочитати його реальний намір перед відповіддю.
- Тренуєш нового спільнотного менеджера і хочеш приклади відповідей, що демонструють різні патерни відповідей, реально потрібні різним типам коментарів.

## Промпт

```
Ти складаєш відповідь на коментар у соцмережах, відповідну його реальному типу. Ти не переходиш за замовчуванням до одного загального тону «дуже дякуємо!» незалежно від того, чим коментар реально є — скарга, питання й похвала кожні потребують структурно іншої відповіді.

Текст коментаря/DM: {{COMMENT}}
Платформа: {{PLATFORM}}
Голос бренду: {{BRAND_VOICE}}
Релевантний контекст (відома проблема, політика, деталь продукту, на яку відповідь може потребувати посилатись): {{CONTEXT}}

Інструкції:
1. Спочатку класифікуй реальний тип коментаря: справжнє питання, скарга/негативний досвід, похвала/позитив, спам/нерелевантне, чи заперечення продажу/вагання — вкажи класифікацію, оскільки структура відповіді повністю залежить від правильності цього.
2. Для справжнього питання: відповідай прямо й конкретно, використовуючи {{CONTEXT}}, якщо релевантно — не ухиляйся в «напиши нам у DM!», якщо питання має публічну відповідь, що також допомогла б іншим читачам, які бачать тред.
3. Для скарги: визнай конкретну проблему (не загальне «шкода це чути»), і переводь розмову в DM/підтримку лише якщо це реально необхідно для усунення несправностей, специфічних для акаунту — негайне переведення кожної скарги в DM може читатись як спроба сховати проблему, а не вирішити її.
4. Для похвали: відповідай конкретно на те, що похвалили, не загальним «дуже дякуємо! 🙏» — конкретне визнання читається як щира увага, загальне — як відповідь бота.
5. Для спам/нерелевантних коментарів: рекомендуй не відповідати (чи мінімально, якщо норми платформи очікують якогось визнання), а не складай щиру відповідь на контент, що цього не заслуговує.
6. Для заперечення продажу чи вагання («задорого», «чи це працює для X випадку»): адресуй реальне заперечення конкретною, чесною інформацією з {{CONTEXT}} — не заклеюй реальне обмеження розмитим позитивом, оскільки потенційний клієнт, що пізніше виявить обмеження, почуватиметься обманутим.
7. Відповідай довжиною й тоном нормам {{PLATFORM}} і {{BRAND_VOICE}} — відповідь, доречно коротка в X, може відчуватись зневажливою на платформі, де довші, тепліші відповіді є нормою.

Формат виводу: Markdown. Спочатку вкажи класифікацію, потім складену відповідь, потім однорядкову примітку про те, чому цей тип/структура відповіді підходить коментарю (корисно для тренування чи швидкої перевірки перед відправкою).
```

## Змінні
- `{{COMMENT}}` — реальний текст коментаря чи DM для відповіді. Обов'язково.
- `{{PLATFORM}}` — конкретна платформа, оскільки норми тону/довжини різняться. Обов'язково.
- `{{BRAND_VOICE}}` — вказівки голосу/особистості бренду. Обов'язково.
- `{{CONTEXT}}` — будь-який релевантний бекграунд, який відповідь могла б потребувати (відомий збій, політика повернень, специфікація продукту). Необов'язково, але на практиці потрібно для чогось понад загальну відповідь, щоб вона була точною, а не розмитою.

## Приклад
**Вхід:** `{{COMMENT}}` = «Це зламалось буквально після 2 використань. Абсолютна витрата грошей, не купуйте» `{{PLATFORM}}` = «Instagram» `{{BRAND_VOICE}}` = «Теплий, прямий, без корпоративного жаргону» `{{CONTEXT}}` = «Продукт має річну гарантію, що покриває виробничі дефекти; email підтримки — support@brand.com»

**Вихід (уривок):**
```
Класифікація: Скарга/негативний досвід

Відповідь: «Це не той досвід, який ми хочемо, щоб ти мав, і цього не мало б статись після 2 використань — це схоже на дефект, і він покривається річною гарантією. Можеш написати support@brand.com з номером замовлення? Ми оформимо заміну.»

Чому це підходить: визнає конкретну проблему (зламалось після 2 використань), а не загальне вибачення, вказує конкретний шлях вирішення (гарантія + конкретний email), а не розмите «ми розберемось», і переводить у приватний канал лише тому, що дія, специфічна для акаунту (оформлення заміни), реально цього вимагає — не як спосіб уникнути публічної розмови.
```

## Поради та варіації
- Поєднуй із «Переписувачем конструктивних коментарів рев'ю» (coding, вже випущений), якщо потрібно пом'якшити власні внутрішні нотатки про різкий коментар перед поширенням з командою — той промпт побудований для тону код-рев'ю, але патерн переформулювання застосовний до будь-якого переписування різкого в конструктивне.
- Для коментаря, що справді неоднозначний між двома типами (напр., читається і як скарга, і як питання), адресуй обидва у відповіді, а не форсуй єдину класифікацію — явно відзнач неоднозначність, а не обирай одну інтерпретацію, ігноруючи іншу.
- Веди постійний довідковий документ {{CONTEXT}} для повторюваних проблем (відомий баг, поширені питання про політику), щоб відповіді лишались послідовними серед різних людей, що керують коментарями, а не лише точними для будь-якої окремої відповіді.
