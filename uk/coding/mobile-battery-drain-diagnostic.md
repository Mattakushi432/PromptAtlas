## Опис
Діагностує ймовірні причини надмірного розряду батареї/навантаження CPU в мобільному застосунку з патернів коду та/або даних профайлера — відрізняється від діагностики крашів і загального профілювання продуктивності, сфокусована конкретно на фоновій активності та енергонеефективних патернах. Для застосунку, який користувачі чи звіти про енергію магазину застосунків позначили як такий, що розряджає батарею.

## Коли використовувати
- Користувачі повідомляють, що застосунок швидко розряджає батарею, чи він позначений у налаштуваннях батареї iOS / статистиці використання батареї Android як топовий споживач.
- Рев'ю коду, що використовує локацію, фонову обробку чи мережу перед релізом, щоб рано виловити енергонеефективні патерни.
- Розслідування регресії, де використання батареї погіршилося після конкретного релізу.

## Промпт

```
Ти діагностуєш ймовірні причини надмірного розряду батареї/навантаження CPU в коді мобільного застосунку — енергоспецифічний аналіз, не загальний дебаг продуктивності чи крашів.

Підозрюваний код/область фічі (локація, фонові завдання, мережа, рендеринг тощо): {{CODE_OR_FEATURE}}
Платформа: {{PLATFORM}}
Дані профайлера, якщо доступні (Xcode Energy Log, Android Battery Historian тощо): {{PROFILER_DATA}}

Інструкції:
1. Перевір на надмірну активність: фонові завдання, таймери чи оновлення локації, що спрацьовують частіше, ніж фіча фактично потребує, не даючи пристрою переходити в стани низького споживання. Розрізняй безперервне/високочастотне трекінг локації (значна вартість батареї) від значних змін чи геофенс-базованої локації (значно дешевше), і познач, якщо код використовує дорогий режим без явної потреби в такій точності/частоті.
2. Перевір на опитування замість push: мережевий запит у циклі на таймері замість push-сповіщень/websockets для даних, що змінюються нечасто — опитування тримає радіомодуль активним значно довше, ніж оновлення на основі подій.
3. Перевір на відсутність використання API керування енергією платформи: неповагу до Low Power Mode iOS чи лімітів часу фонових завдань, невикористання API Android, що враховують Doze/App Standby (WorkManager з відповідними обмеженнями замість сирих фонових сервісів чи wake lock'ів, утримуваних довше за необхідне).
4. Перевір на важку для CPU роботу в busy-loop чи надмірно частому тригері: безперервне опитування сенсорів, необмежені обробники скролу/анімації, що роблять важку роботу на кожен кадр, чи фоновий потік, що виконує повторювану роботу, яку можна було б батчувати чи дебаунсити.
5. Перевір на невивільнені wake lock'и чи фонове виконання, що переживає своє призначення — wake lock, отриманий, але не звільнений на шляху помилки, є поширеним, важким для виявлення джерелом розряду.
6. Для кожної знахідки оціни ймовірну серйозність (оновлення локації щосекунди — більша справа, ніж неефективне одноразове обчислення) і дай конкретне виправлення, використовуючи фактичне енергоефективне API платформи для цього випадку використання.
7. Якщо надано {{PROFILER_DATA}}, обґрунтуй знахідки на його фактичних доказах (яка підсистема — CPU, радіо, GPS, дисплей — показана як найбільший споживач), а не вгадуй широко.

Формат виводу: Markdown, один запис на знахідку, ранжовано за ймовірним впливом, кожен з: що відбувається, чому це розряджає батарею, і конкретне виправлення.
```

## Змінні
- `{{CODE_OR_FEATURE}}` — код чи область фічі, підозрювана в спричиненні розряду. Обов'язково.
- `{{PLATFORM}}` — "iOS" чи "Android" (з версією, якщо релевантно). Обов'язково — API керування енергією специфічні для платформи.
- `{{PROFILER_DATA}}` — фактичний вивід профілювання енергії. Необов'язково, але перетворює широку підозру на цілеспрямований діагноз.

## Приклад
**Вхід:** `{{PLATFORM}}` = "Android", `{{CODE_OR_FEATURE}}` = foreground-сервіс, що запитує оновлення локації щосекунди безперервно, навіть коли застосунок у фоні, а фіча ("друзі поруч" на карті) не потребує посекундної точності.

**Вихід (фрагмент):**
```
### Знахідка: Безперервні оновлення локації щосекунди — ВИСОКИЙ вплив
Запит оновлень локації з GPS-точністю щосекунди тримає радіомодуль і чіп GPS активними майже безперервно — одна з найбільших вартостей батареї, яку може накласти застосунок. Для фічі "друзі поруч" посекундна точність, вкрай малоймовірно, потрібна.

Виправлення: значно збільш інтервал запиту локації (напр., 30-60 секунд), використовуючи `FusedLocationProviderClient` з відповідним `Priority` (напр., `PRIORITY_BALANCED_POWER_ACCURACY` замість `PRIORITY_HIGH_ACCURACY`), і повністю припини запитувати оновлення, коли застосунок у фоні, якщо фонова локація не є основною фічею за згодою користувача — розглянь `LocationRequest.Builder` з довшим `setMinUpdateIntervalMillis` і пріоритетом, свідомим до батареї.
```

## Поради та варіації
- Для iOS попроси конкретно перевірити налаштування `desiredAccuracy` і `distanceFilter` у `CLLocationManager`, і чи міг би `significantLocationChangeMonitoring` замінити безперервні оновлення для описаного випадку використання.
- Поєднуй з реальним виводом Battery Historian (Android) чи Energy Log Xcode (iOS) для діагнозу, обґрунтованого на фактично виміряному споживанні підсистем, а не лише виведенні з патернів коду.
