## Опис
Рекомендує конкретну стратегію версіонування API (шлях URL, заголовок, media-type чи взагалі без версій) з урахуванням твоїх реальних обмежень — контроль над клієнтами, темп релізів, частота ламаючих змін — а не загальний список підходів до версіонування. Для команди, що ось-ось ухвалить це рішення, а не досліджує теорію версіонування.

## Коли використовувати
- Побудова нового публічного чи партнерського API з потребою вирішити підхід до версіонування до того, як перший клієнт інтегрується.
- Внутрішнє API починає мати зовнішніх споживачів і потребує реальної стратегії версіонування замість "ми просто скажемо людям, коли щось зламається".
- Перегляд наявного підходу до версіонування, що спричиняє тертя (підтримується забагато версій, чи ламаючі зміни потрапляють без попередження).

## Промпт

```
Ти рекомендуєш конкретну стратегію версіонування API на основі наданих обмежень — не загальний огляд усіх підходів.

Контекст API (хто його споживає — лише внутрішньо, кілька відомих партнерів, чи публічно; як часто очікуються ламаючі зміни): {{API_CONTEXT}}
Обмеження (напр., "клієнти не можуть легко швидко оновлюватися", "ми контролюємо всіх клієнтів", "потрібно підтримувати старі версії мобільного застосунку роками"): {{CONSTRAINTS}}
Поточний підхід, якщо є (необов'язково): {{CURRENT_APPROACH}}

Інструкції:
1. Зваж основні стратегії саме з урахуванням наданих обмежень: версіонування за шляхом URL (/v1/, /v2/), версіонування на основі заголовків (кастомний заголовок чи media type в Accept), і формальна відсутність версіонування (лише адитивні зміни з політикою депрекації для всього іншого).
2. Рекомендуй одну основну стратегію, з обґрунтуванням, прив'язаним напряму до {{API_CONTEXT}} і {{CONSTRAINTS}} — напр., "оскільки ви контролюєте всіх клієнтів і можете форсувати оновлення, відсутність формального версіонування зі строгою дисципліною адитивних змін має нижчі накладні витрати, ніж підтримка паралельних версій".
3. Якщо ламаючі зміни очікуються рідко, віддавай перевагу стратегії, що уникає накладних витрат на підтримку кількох живих версій; якщо вони очікуються часто чи контроль над клієнтами слабкий, віддавай перевагу стратегії, що дає клієнтам явний контроль над тим, коли вони приймають зміни.
4. Визнач, що вважається "ламаючою зміною" для рекомендованої стратегії (напр., видалення поля, зміна типу поля, зміна обов'язковості), щоб команда мала конкретну межу, а не просто назву стратегії.
5. Рекомендуй політику депрекації разом зі стратегією версіонування: як версії виводяться з експлуатації, скільки попередження отримують клієнти, і як депрекація повідомляється (заголовки, changelog, прямий контакт для відомих партнерів).
6. Якщо надано {{CURRENT_APPROACH}} і воно спричиняє конкретну проблему, адресуй цю проблему напряму в рекомендації, а не пропонуй непов'язану ідеальну стратегію.

Формат виводу: Markdown з розділами: Рекомендована стратегія (з обґрунтуванням), Що вважається ламаючою зміною, Політика депрекації.
```

## Змінні
- `{{API_CONTEXT}}` — хто споживає API і як часто очікуються ламаючі зміни. Обов'язково.
- `{{CONSTRAINTS}}` — фактори, що обмежують вибір (швидкість оновлення клієнтів, розмір команди, потреби зворотної сумісності). Обов'язково.
- `{{CURRENT_APPROACH}}` — наявна стратегія, якщо переглядаєш її. Необов'язково.

## Приклад
**Вхід:** `{{API_CONTEXT}}` = "публічне API, яке споживають сторонні розробники, що будують інтеграції, ламаючі зміни трапляються кілька разів на рік", `{{CONSTRAINTS}}` = "сторонніх розробників не можна змусити оновлюватися за нашим графіком".

**Вихід (фрагмент):**
```
## Рекомендована стратегія
Версіонування за шляхом URL (`/v1/...`, `/v2/...`). Оскільки сторонні розробники контролюють свій власний графік оновлень і їх не можна змусити мігрувати, їм потрібен явний, стабільний спосіб продовжувати використовувати старіший контракт, поки ви розвиваєте API. Версіонування за шляхом також найлегше виявляється/дебажиться для зовнішніх розробників, що читають документацію чи URL у рядку логу, що важливо, коли ви не контролюєте їхній тулінг.

## Що вважається ламаючою зміною
Видалення чи перейменування поля, зміна типу поля, додавання нового обов'язкового поля запиту, чи зміна семантики наявних статус-кодів. Додавання нових необов'язкових полів чи нових ендпойнтів не є ламаючим і не потребує підвищення версії.

## Політика депрекації
Підтримуй попередню мажорну версію мінімум 12 місяців після релізу нової; повідомляй про депрекацію через заголовок відповіді (`Deprecation: true`, `Sunset: <date>`) плюс запис у changelog, і напряму надсилай email власникам зареєстрованих API-ключів за 3 місяці до виведення з експлуатації.
```

## Поради та варіації
- Для суто внутрішнього API, де ти контролюєш кожного клієнта, явно попроси надати більшу вагу "без версіонування, лише адитивно" — це часто правильна відповідь, яку недооцінюють, якщо промпт за замовчуванням мислить у категоріях enterprise-API.
- Якщо замість REST йдеться про GraphQL, зазнач, що депрекація на рівні поля (директива `@deprecated`) замінює більшість потреби в версіонуванні всього API — попроси про цю альтернативу явно.
