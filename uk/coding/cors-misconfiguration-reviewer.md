## Опис
Рев'юїть конфігурацію CORS (Cross-Origin Resource Sharing) бекенду на конкретні помилки, що перетворюють зручну фічу на діру для витоку авторизаційних даних — відображені origin'и, комбінацію wildcard із credentials та надто широке кешування preflight — а не на загальний рев'ю безпеки API.

## Коли використовувати
- Налаштовуєш чи рев'юїш CORS-заголовки для API, що обслуговує браузерні клієнти, і хочеш підтвердити, що конфігурація випадково не дозволяє будь-якому origin читати автентифіковані відповіді.
- Сканер безпеки чи пентест позначив «помилку конфігурації CORS», і потрібно зрозуміти, яке саме налаштування є проблемою і чому, а не просто що вона десь є.
- Додаєш новий frontend-origin (новий піддомен, сайт партнера) до дозволеного списку і хочеш перевірити, що зміна не розширює доступ понад задумане.

## Промпт

```
Ти рев'юїш конфігурацію CORS бекенду на конкретні режими відмови, що дозволяють недовіреному origin читати дані, до яких він не мав би доступу.

Конфігурація CORS (заголовки/код middleware чи конфіг): {{CORS_CONFIG}}
Чи автентифіковані запити (cookies, заголовки Authorization) покладаються на цей API: {{USES_CREDENTIALS}}
Відомі легітимні origin'и, які мають бути дозволені: {{ALLOWED_ORIGINS}}

Інструкції:
1. Перевір на wildcard `Access-Control-Allow-Origin: *` разом із `Access-Control-Allow-Credentials: true` — ця комбінація невалідна за специфікацією, і браузери її відхиляють, але перевір, чи код натомість досягає еквівалентного небезпечного ефекту, безумовно відображаючи заголовок `Origin` запиту назад, дозволяючи credentials, — це браузери приймають, і це дозволяє будь-якому сайту читати автентифіковані відповіді.
2. Якщо існує дозволений список origin'ів, перевір, як він звіряється: перевірка на підрядок чи незаякорений regex (напр., збіг будь-якого origin, що містить «example.com») можна обійти origin, контрольованим атакувальником, на кшталт `evil-example.com.attacker.net` чи `example.com.attacker.net`. Підтверди, що звірка точна чи належно заякорена звірка суфікса проти {{ALLOWED_ORIGINS}}.
3. Перевір, що значення `Access-Control-Allow-Methods` і `Access-Control-Allow-Headers` не ширші за те, що реально потрібно {{ALLOWED_ORIGINS}} — надто дозвільна preflight-відповідь сама по собі не зливає дані, але розширює, що зможе зробити скомпрометований чи зловмисний дозволений origin.
4. Перевір `Access-Control-Max-Age`: дуже довга тривалість кешування preflight означає, що вже відкликаний origin чи змінена політика лишається фактично чинною в браузерах, що вже закешували preflight, аж до її завершення.
5. Якщо {{USES_CREDENTIALS}} true, підтверди, що дозволений список не походить із чогось, на що може вплинути атакувальник (напр., відлуння значення, похідного від `Referer`, чи довіра до origin, переданого як параметр запиту) — джерелом істини має бути фіксований список на стороні сервера.
6. Познач будь-який origin у конфігурації, якого немає в {{ALLOWED_ORIGINS}}, і запитай, чи він навмисний (напр., залишковий staging/localhost-запис, випадково доставлений у продакшн).

Формат виводу: Markdown. Для кожної знахідки: конкретний рядок/налаштування, сценарій експлуатації в одному реченні, серйозність (critical/high/medium), і виправлення. Заверши однорядковим вердиктом: безпечно за поточної конфігурації, або небезпечно — поки [конкретне виправлення].
```

## Змінні
- `{{CORS_CONFIG}}` — реальні заголовки CORS, конфігурація middleware, чи специфічний для фреймворку код налаштування CORS. Обов'язково.
- `{{USES_CREDENTIALS}}` — чи браузерні клієнти API надсилають cookies чи заголовки авторизації через origin (true/false). Обов'язково — серйозність кожної знахідки тут залежить від того, чи задіяні credentials.
- `{{ALLOWED_ORIGINS}}` — список origin'ів, які мають бути легітимно дозволені. Обов'язково.

## Приклад
**Вхід:** `{{CORS_CONFIG}}` = «Express middleware: `res.header('Access-Control-Allow-Origin', req.headers.origin); res.header('Access-Control-Allow-Credentials', 'true')`» `{{USES_CREDENTIALS}}` = «true — API викликається з cookie сесії з браузерного застосунку» `{{ALLOWED_ORIGINS}}` = «https://app.example.com, https://admin.example.com»

**Вихід (уривок):**
```
### Знахідка: відображений Origin + credentials = будь-який сайт може читати автентифіковані відповіді
Middleware відображає назад будь-який заголовок `Origin`, який надсилає запит, як дозволений origin, із увімкненими credentials. Будь-який сайт, який відвідує залогінений користувач, може зробити credentialed-запит до цього API з JavaScript і прочитати відповідь, оскільки браузер прийме цей origin як «дозволений».
Серйозність: critical.
Виправлення: заміни відображення на точну звірку проти фіксованого дозволеного списку (https://app.example.com, https://admin.example.com); відлунюй Origin запиту назад лише коли він збігається із записом у цьому списку, інакше зовсім не встановлюй заголовки CORS.

Вердикт: небезпечно — поки відображення origin не замінено на звірку з дозволеним списком.
```

## Поради та варіації
- Цей промпт передбачає браузер-орієнтований API; якщо {{USES_CREDENTIALS}} false, і API обслуговує лише публічні, нечутливі дані для будь-якого origin, дозвільна wildcard-конфігурація може бути навмисним і розумним вибором — не позначай це як знахідку без цього контексту.
- Поєднуй із «Рев'юєр потоку автентифікації» (coding, вже випущений), коли той самий API також має логіку автентифікації, варту рев'ю — той промпт широко покриває коректність логіну/сесії/токена; цей вузько сфокусований на шарі контролю крос-origin доступу.
- Для API за CDN чи API-шлюзом, що теж встановлює заголовки CORS, перевір обидва шари — коректна конфігурація на рівні застосунку може бути мовчки перевизначена чи здубльована конфігурацією на рівні інфраструктури, породжуючи заголовок, якого код застосунку ніколи не задумував.
