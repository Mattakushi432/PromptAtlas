## Опис
Рев'юїть функцію завантаження файлів — ендпоінт і обробку зберігання/віддачі — на конкретні режими відмови, що перетворюють «дозволити користувачам завантажувати файл» на вектор віддаленого виконання коду, обходу шляху чи зловживання сховищем: довіру до типу файлу з боку клієнта, несанітизовані імена файлів, необмежений розмір/тип і небезпечну віддачу завантаженого вмісту.

## Коли використовувати
- Будуєш чи рев'юїш функцію завантаження файлів (аватар, документ, вкладення) і хочеш зосереджений рев'ю безпеки саме шляху завантаження/зберігання/віддачі, не загальний рев'ю ендпоінту.
- Пентест чи звіт баг-баунті згадує «довільне завантаження файлу» чи «обхід шляху через ім'я файлу», і потрібно зіставити це з конкретною прогалиною в коді обробки.
- Додаєш новий тип завантаження (напр., дозволяєш PDF поряд із зображеннями) і хочеш підтвердити, що наявна валідація реально покриває новий тип, а не просто розширює рядок дозволеного списку.

## Промпт

```
Ти рев'юїш ендпоінт, зберігання й код віддачі функції завантаження файлів на конкретні вразливості, які часто вносять завантаження файлів, не на загальну якість коду.

Код ендпоінту завантаження: {{UPLOAD_CODE}}
Як/де зберігаються та пізніше віддаються завантажені файли: {{STORAGE_SERVING}}
Задумані дозволені типи файлів: {{ALLOWED_TYPES}}

Інструкції:
1. Перевір, як валідується тип файлу: на основі заголовка `Content-Type` з боку клієнта чи розширення файлу самого по собі (обидва повністю контрольовані атакуючим і легко підробні), чи код сніфить фактичний вміст файлу (магічні байти), щоб підтвердити, що файл справді є тим, чим себе видає?
2. Перевір обробку імені файлу: чи використовується оригінальне ім'я файлу для побудови шляху зберігання напряму? Якщо так, перевір на обхід шляху (ім'я файлу на кшталт `../../etc/config` чи з нульовими байтами) і на спеціальні/зарезервовані символи, що могли б зламати шлях зберігання чи подальший інструментарій. Підтвердь, що збережене ім'я файлу або повністю згенероване сервером (напр., UUID), або санітизоване до безпечного набору символів.
3. Перевір ліміти розміру: чи є примусовий максимальний розмір файлу до/під час читання, чи запит міг би стрімити файл довільного розміру, вичерпуючи диск/пам'ять? Перевір, чи ліміт застосовується на рівні застосунку, а не лише вважається обробленим реверс-проксі, що може бути не налаштований.
4. Перевір на ризик бомби розпакування, якщо будь-який завантажений формат розпаковується на сервері (zip, генерація мініатюр зображень) — невинний на вигляд маленький файл, що розгортається в гігабайти в пам'яті чи на диску.
5. Перевір, звідки віддаються файли: якщо завантаження віддаються з того самого домену/оригіну, що й основний застосунок (а не з окремого домену сховища/CDN з обмежувальними `Content-Disposition` і `Content-Type`), завантажений HTML чи SVG файл міг би віддаватись із типом вмісту, виконуваним у браузері, вмикаючи збережений XSS через «завантаження файлу».
6. Перевір, що {{ALLOWED_TYPES}} застосовується як дозволений список конкретних, свідомо обраних типів — не заборонений список «небезпечних» розширень, який тривіально неповний (напр., блокує `.php`, але не `.phtml`, `.php5`).
7. Якщо файли колись обробляються іншою системою (антивірусне сканування, бібліотека зміни розміру зображень, парсер документів), познач, чи сам цей крок обробки міг би бути поверхнею вразливості (напр., бібліотека зображень із відомими CVE парсингу) — познач це як варте перевірки, навіть якщо поза межами цього коду.

Формат виводу: Markdown. Для кожної знахідки: конкретна прогалина, сценарій експлуатації одним реченням, серйозність (critical/high/medium/low), і виправлення. Заверши явним чек-листом: тип вмісту валідовано сніфінгом (так/ні), ім'я файлу санітизоване (так/ні), ліміт розміру застосовано (так/ні), віддається з ізольованого оригіну (так/ні).
```

## Змінні
- `{{UPLOAD_CODE}}` — код обробки ендпоінту завантаження (отримання, валідація, зберігання файлу). Обов'язково.
- `{{STORAGE_SERVING}}` — куди потрапляють файли (локальний диск, об'єктне сховище тощо) і як вони пізніше віддаються назад користувачам. Обов'язково.
- `{{ALLOWED_TYPES}}` — типи файлів, які функція задумана приймати. Обов'язково.

## Приклад
**Вхід:** `{{UPLOAD_CODE}}` = «Middleware Multer зберігає в `/uploads/{originalname}` з фільтром типу MIME, що перевіряє `req.file.mimetype` проти дозволеного списку.» `{{STORAGE_SERVING}}` = «Express віддає `/uploads` як статичну директорію на тому самому домені, що й застосунок.» `{{ALLOWED_TYPES}}` = «image/jpeg, image/png»

**Вихід (уривок):**
```
### Знахідка: тип MIME довіряється з боку клієнта, немає сніфінгу вмісту
Фільтр перевіряє `req.file.mimetype`, що є `Content-Type`, який декларує multipart-запит клієнта — повністю контрольований атакуючим і не пов'язаний із фактичними байтами файлу. Атакуючий може завантажити HTML/SVG/JS файл, декларуючи `image/jpeg`.
Серйозність: high.
Виправлення: після отримання файлу просніфи його фактичний вміст (напр., перевір магічні байти чи використай бібліотеку визначення типу вмісту) і відхиляй, якщо він не збігається зі справжнім форматом зображення, незалежно від задекларованого заголовка.

### Знахідка: оригінальне ім'я файлу використовується напряму як шлях зберігання — ризик обходу шляху й XSS того самого оригіну
Збереження в `/uploads/{originalname}` використовує ім'я файлу, контрольоване атакуючим, напряму. У поєднанні з віддачею `/uploads` на власному домені застосунку завантажений файл із назвою `x.svg` (щойно перевірка MIME вище буде обійдена чи якщо SVG колись дозволять) віддавався б як виконуваний у браузері вміст на тому самому оригіні, що й автентифіковані сесії — збережений XSS. Несанітизоване ім'я файлу також ризикує обходом шляху, коли символи досягають виклику файлової системи.
Серйозність: critical.
Виправлення: генеруй ім'я файлу на боці сервера випадковим чином (напр., UUID) без вхідних даних клієнта в шляху, і віддавай `/uploads` з окремого субдомену (чи об'єктного сховища з фіксованим, невиконуваним `Content-Type` і `Content-Disposition: attachment`), щоб завантажений вміст ніколи не трактувався як виконуваний вміст того самого оригіну.

Чек-лист: Тип вмісту валідовано сніфінгом — ні. Ім'я файлу санітизоване — ні. Ліміт розміру застосовано — не показано, перевір окремо. Віддається з ізольованого оригіну — ні.
```

## Поради та варіації
- Поєднуй зі «Сканером ін'єкційних вразливостей» (coding, вже випущений), якщо функція завантаження також записує імена файлів чи метадані в запит бази даних чи команду оболонки — цей промпт обмежений шляхом завантаження/зберігання/віддачі самим по собі, не подальшою ін'єкцією з тих даних.
- Якщо {{ALLOWED_TYPES}} включає формати, які часто обробляються на сервері (зображення, змінені розміром, PDF, відрендерені в мініатюри), явно попроси рев'юера позначити відомі CVE-схильні бібліотеки для цього формату, оскільки безпечність шляху завантаження не покриває вразливий крок обробки далі за потоком.
- Для публічних функцій завантаження (без потреби автентифікації) також запитай про обмеження частоти зловживань на самому ендпоінті — інакше безпечний обробник завантажень усе одно можна використати для зловживання вартістю сховища чи пропускною здатністю без ліміту частоти, що не покриває чек-лист цього промпту за замовчуванням.
