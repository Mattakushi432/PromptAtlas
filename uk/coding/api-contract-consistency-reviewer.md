## Опис
Перевіряє набір API-ендпоінтів на внутрішню узгодженість — нейминг, пагінацію, форму помилок, статус-коди, версіонування — а не коректність реалізації окремого ендпоінта. Створено для тімліда, який робить рев'ю дизайну API перед публікацією контракту або мерджем ендпоінтів, спроєктованих різними людьми.

## Коли використовувати
- Перед публікацією документації API, коли ендпоінти писали різні розробники чи команди в різний час.
- Рев'ю нової партії ендпоінтів на відповідність вже усталеним конвенціям існуючого API.
- Періодичний аудит узгодженості на API, що постійно росте.

## Промпт

```
Ти перевіряєш набір API-ендпоінтів на внутрішню узгодженість, а не на коректність чи безпеку реалізації окремого ендпоінта — вважай, що кожен ендпоінт працює; твоє завдання — чи узгоджені вони між собою.

Ендпоінти (шляхи, методи, форма запиту/відповіді):
{{API_ENDPOINTS}}

Style guide чи існуючі конвенції (необов'язково — якщо не надано, визнач домінантну конвенцію із самих ендпоінтів і вважай відхилення від неї неузгодженістю): {{STYLE_GUIDE}}

Перевір узгодженість за такими вимірами:
1. Нейминг — регістр (snake_case чи camelCase), множина у назвах ресурсів, дієслова у шляхах.
2. Вкладеність ресурсів — однакова глибина та патерн для вкладених ресурсів.
3. Пагінація — однаковий стиль пагінації (курсор чи offset), однакові назви параметрів, однакова форма відповіді (envelope) для всіх list-ендпоінтів.
4. Відповіді з помилками — однакова форма об'єкта помилки, однакові назви полів для коду/повідомлення помилки, узгоджене використання HTTP статус-кодів для еквівалентних типів збоїв.
5. Версіонування — однаковий механізм версіонування (шлях URL, заголовок), застосований однаково скрізь.
6. Автентифікація — однакові конвенції заголовків/токенів на ендпоінтах, що вимагають авторизації.

Для кожної знайденої неузгодженості назви конкретні ендпоінти, процитуй суперечливі фрагменти, оціни серйозність (MINOR — косметична; MODERATE — заплутає користувачів API; MAJOR — зламає клієнтський код чи спричинить реальні баги) і дай конкретне виправлення (яку сторону змінити і на що).

Якщо надано менше двох ендпоінтів, скажи, що для порівняння недостатньо даних, і зупинись — не вигадуй конвенцію, з якою порівнювати.

Заверши вердиктом: повністю узгоджено, або кількість неузгодженостей за рівнями серйозності.
```

## Змінні
- `{{API_ENDPOINTS}}` — два або більше визначень ендпоінтів (шлях, метод, форма запиту/відповіді). Обов'язково.
- `{{STYLE_GUIDE}}` — явний style guide API, з яким звіряти. Необов'язково; без нього базою слугує домінантний патерн серед самих ендпоінтів.

## Приклад
**Вхід:** `{{API_ENDPOINTS}}` = `GET /users?page=2&per_page=20`, що повертає `{ users: [...], total_count, page }`, і `GET /orders?cursor=abc123&limit=20`, що повертає `{ data: [...], next_cursor }`.

**Вихід (фрагмент):**
```
1. Пагінація — MAJOR. `/users` використовує offset-пагінацію (`page`/`per_page`) з envelope на ключах `users`/`total_count`/`page`; `/orders` використовує курсорну пагінацію (`cursor`/`limit`) з envelope на ключах `data`/`next_cursor`. Дві різні моделі пагінації в одному API змушують кожен клієнт окремо обробляти list-ендпоінти. Виправлення: стандартизувати один стиль пагінації (курсорна зазвичай безпечніша при масштабуванні) і одну форму envelope для всіх list-ендпоінтів.

Вердикт: знайдено 1 неузгодженість рівня MAJOR.
```

## Поради та варіації
- Встав OpenAPI/Swagger специфікацію напряму як `{{API_ENDPOINTS}}` — переформатовувати заздалегідь не потрібно.
- Для GraphQL-схеми попроси перевіряти нейминг полів, узгодженість connection/edge-патерну та узгодженість підходу error-as-data проти throw — замість REST-специфічних вимірів.
