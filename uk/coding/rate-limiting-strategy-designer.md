## Опис
Проєктує стратегію обмеження частоти запитів (rate limiting) для API-ендпоінта — вибір алгоритму, конкретні ліміти та поведінку відповіді — з огляду на патерн трафіку та ризики зловживання. Для проєктування цього до запуску ендпоінта, а не для аудиту вже наявного в продакшні лімітера.

## Коли використовувати
- Додаєш новий публічний чи партнерський API-ендпоінт, який ще не має обмеження частоти.
- Ендпоінт дорогий в обслуговуванні (важкі обчислення, вартість стороннього API) і потребує захисту до запуску.
- Вирішуєш, за якою віссю прив'язувати ліміти (per-user, per-IP, per-API-key) для конкретного патерну доступу.

## Промпт

```
Ти проєктуєш стратегію rate limiting для API-ендпоінта перед запуском — а не рецензуєш чи дебажиш вже наявну.

Опис ендпоінта (що він робить, приблизна вартість обслуговування одного запиту): {{ENDPOINT_DESCRIPTION}}

Звичайний патерн трафіку (типова форма запитів від легітимних користувачів): {{TRAFFIC_PATTERN}}

Побоювання щодо зловживання (що реально турбує — скрейпінг, credential stuffing, зловживання вартістю, відмова в обслуговуванні): {{ABUSE_CONCERN}}

Надай:
1. Рекомендований алгоритм (fixed window, sliding window, token bucket чи leaky bucket) з обґрунтуванням, прив'язаним саме до наданого патерну трафіку — а не рекомендацію за замовчуванням.
2. Конкретні числа лімітів (запитів за часове вікно) і вісь, за якою їх прив'язувати (per-IP, per-authenticated-user, per-API-key, глобально) — з обґрунтуванням, чому саме ця вісь підходить під заявлене побоювання щодо зловживання.
3. Поведінку відповіді: що відбувається, коли клієнт перевищив ліміт — жорстке блокування з 429 і заголовком `Retry-After`, чи м'якше зниження якості/дроселювання — і чому.
4. Примітку про залишковий ризик: від чого ця стратегія НЕ захищає (наприклад, розподілене зловживання з багатьох IP/акаунтів), щоб її не подавали як повне рішення.

Якщо описаний патерн трафіку природно "сплесковий" з легітимних причин (наприклад, приймач вебхуків, що отримує пакетну доставку, чи функція масового завантаження), поясни, чому наївні ліміти fixed-window зламали б легітимне використання, і скоригуй алгоритм/ліміти відповідно, замість того щоб брати число за замовчуванням.
```

## Змінні
- `{{ENDPOINT_DESCRIPTION}}` — що робить ендпоінт і приблизна вартість запиту. Обов'язково.
- `{{TRAFFIC_PATTERN}}` — як виглядає нормальне, легітимне використання (стабільне, сплескове, за розкладом). Обов'язково — це визначає вибір алгоритму.
- `{{ABUSE_CONCERN}}` — конкретний сценарій зловживання, від якого захищаємось. Обов'язково — правильна вісь прив'язки повністю залежить від цього.

## Приклад
**Вхід:** `{{ENDPOINT_DESCRIPTION}}` = "ендпоінт пошуку, що запускає повнотекстовий запит проти великого індексу", `{{TRAFFIC_PATTERN}}` = "стабільний низький обсяг для більшості користувачів, час від часу легітимні швидкі виклики автокомпліту при швидкому наборі тексту", `{{ABUSE_CONCERN}}` = "скрейпінг повного набору результатів через автоматизовану пагінацію".

**Вихід (фрагмент):**
```
Алгоритм: sliding window log чи token bucket, не fixed window — трафік автокомпліту природно сплесковий у коротких вікнах, а fixed window або пропустить сплеск точно на межі вікна (подвоївши задуманий ліміт), або хибно задроселить легітимний швидкий набір тексту.

Ліміти: 60 запитів/хвилину на автентифікованого користувача (достатньо щедро для сплесків автокомпліту), плюс жорсткіший ліміт 500 запитів/годину на користувача як другу стелю для вловлювання стійкого скрейпінгу, що тримається нижче похвилинного ліміту. Прив'язка за user ID, а не IP — скрейпінг через один акаунт тут реалістичніша загроза, а лімітування за IP зашкодило б користувачам за спільним корпоративним NAT.

Відповідь: 429 з Retry-After для похвилинного ліміту (відновлюваний, клієнт має відступити); для погодинної стелі — знизити розмір сторінки результатів замість жорсткого блокування, оскільки це, ймовірно, реальний активний користувач, а не атакуючий.

Залишковий ризик: це не зупиняє скрейпінг, розподілений між багатьма безкоштовними акаунтами — це потребує лімітування швидкості створення акаунтів чи виявлення аномалій, що виходить за межі rate limiting на рівні ендпоінта.
```

## Поради та варіації
- Для справді публічного, неавтентифікованого ендпоінта попроси спроєктувати і IP-based, і cost-based (наприклад, тригер CAPTCHA) резервний рівень, оскільки лімітування лише за IP слабке проти розподіленого зловживання.
- Поєднуй з `caching-strategy-advisor`, коли побоювання щодо зловживання насправді про вартість обчислень — інколи кеш поглинає навантаження ефективніше за жорсткіший ліміт.
