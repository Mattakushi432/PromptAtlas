## Опис
Генерує покроковий план профілювання для конкретного повільного ендпойнта чи шляху коду — що інструментувати, в якому порядку, і що кожен результат сказав би — для моменту до існування даних профілювання. Відрізняється від «Розшифровувача результатів навантажувального тестування» (розшифровує результати постфактум): це методологія для отримання цих даних насамперед.

## Коли використовувати
- Відомо, що ендпойнт повільний, але його ще не профілювали, і потрібен систематичний план, а не випадкове додавання таймінг-логів.
- Онбординг розробника, що новий у профілюванні, з потребою в конкретній методології для реального повільного ендпойнта, не абстрактна теорія профілювання.
- Рішення, який інструмент/техніка профілювання фактично доречні для конкретного підозрюваного типу вузького місця перед витратою часу на неправильний.

## Промпт

```
Ти генеруєш покроковий план профілювання для конкретного повільного ендпойнта/шляху коду — методологію для дотримання, що видає дані, потрібні для діагностики фактичного вузького місця, не сам діагноз (оскільки даних профілювання ще не існує).

Опис повільного ендпойнта/операції (що вона робить, приблизно наскільки повільно, будь-які наявні підказки): {{SLOW_OPERATION}}
Стек/мова: {{STACK}}
Що вже пробували чи виключили, якщо є: {{ALREADY_TRIED}}

Інструкції:
1. Почни з найгрубшого вимірювання спочатку: загальний wall-clock час, розбитий на основні фази (напр., парсинг запиту, час запиту БД, бізнес-логіка, серіалізація, мережа) — перед детальним профілюванням будь-якої окремої фази встанови, яка фаза фактично домінує в загальному часі, оскільки профілювання неправильної фази витрачає зусилля.
2. На основі описаних симптомів висуни гіпотезу про 1-2 найімовірніші домінуючі фази (напр., "якщо цей ендпойнт робить важкий join БД, час бази даних — перший підозрюваний") і рекомендуй вимірювати їх спочатку, а не суцільне "профілюй усе".
3. Для тієї фази, що виявиться домінуючою, рекомендуй конкретну техніку/інструмент профілювання, доречний для неї: профайлер CPU (flame graph) для коду, обмеженого обчисленнями, профайлер запитів БД/EXPLAIN для часу запиту, розподілене трасування (якщо система багатосервісна) для міжсервісної затримки, трасування I/O/мережі для часу зовнішнього виклику.
4. Впорядкуй план так, щоб результат кожного кроку визначав, чи потрібен наступний крок — це дерево рішень, не плоский чекліст: "якщо домінує час БД, перейди до кроку 3a (профілювання запитів); якщо домінує час коду застосунку, перейди до кроку 3b (профілювання CPU)".
5. Для кожного кроку профілювання вкажи, який конкретний сигнал у результаті підтвердив би чи виключив би цю фазу як вузьке місце — не просто "запусти профайлер", а який патерн у виводі шукати.
6. Познач будь-яку техніку вимірювання, що могла б спотворити результат (напр., профайлер debug-збірки, що додає накладні витрати, які змінюють відносні таймінги, профайлер, що працює в середовищі, яке не відповідає характеристикам навантаження продакшену), щоб план враховував валідність вимірювання.
7. Якщо {{ALREADY_TRIED}} виключає деякі гіпотези, пропусти ці кроки в плані, а не включай їх заради повноти.

Формат виводу: Markdown як нумерований, розгалужений план — кожен крок називає інструмент/техніку, що шукати в результаті, і який наступний крок зробити на основі результату.
```

## Змінні
- `{{SLOW_OPERATION}}` — повільний ендпойнт/операція і доступний контекст. Обов'язково.
- `{{STACK}}` — мова/фреймворк/інфраструктура, оскільки інструменти профілювання специфічні для стеку. Обов'язково.
- `{{ALREADY_TRIED}}` — що вже було виміряно чи виключено. Необов'язково, але уникає надлишкових кроків.

## Приклад
**Вхід:** `{{SLOW_OPERATION}}` = "ендпойнт генерації звіту займає 3-5 секунд, немає ідей, яка частина", `{{STACK}}` = "Python / Django / PostgreSQL".

**Вихід (фрагмент):**
```
## Крок 1: Грубий розбір фаз
Додай таймінг навколо трьох основних фаз: (a) отримання даних з БД, (b) обчислення звіту в Python, (c) серіалізація/рендеринг відповіді. Використай `time.perf_counter()` навколо кожної фази, чи `django-silk`/`django-debug-toolbar` Django для швидкого вбудованого розбору без ручної інструментації.
→ Шукай: яка фаза становить більшість з 3-5с. Перейди до 2a, якщо домінує час БД, 2b, якщо домінує обчислення Python, 2c, якщо домінує серіалізація.

## Крок 2a: Домінує час БД → профілювання запитів
Увімкни лог запитів Django чи використай SQL-панель `django-debug-toolbar`, щоб побачити кожен виданий запит і його індивідуальний таймінг. Шукай конкретно: патерн N+1 (багато малих запитів замість одного), чи один конкретний запит, що займає непропорційну частку часу БД.
→ Якщо знайдено N+1: це виправлення `select_related`/`prefetch_related`, не проблема глибокого профілювання — зупинись тут.
→ Якщо знайдено один повільний запит: перейди до `EXPLAIN ANALYZE` на цьому конкретному запиті для діагностики на рівні індексу/плану.

## Крок 2b: Домінує обчислення Python → профілювання CPU
Використай `cProfile` (чи `py-spy` для семплування з нижчими накладними витратами в запуску, ближчому до продакшену), щоб отримати flame graph того, де витрачається час CPU всередині фази обчислення.
→ Шукай: одну функцію, що споживає непропорційну частку семплів — це твоя ціль оптимізації.
```

## Поради та варіації
- Для підозрюваного сповільнення, пов'язаного з пам'яттю (не сирим часом CPU) поряд із затримкою, зазнач це окремо — розбір фаз цього промпту сфокусований на часі; поєднуй з «Мисливцем за витоками пам'яті», якщо також підозрюється тиск виділення/GC.
- Коли план видасть фактичні дані профілювання, передай результати в свіжий аналіз (чи «Розшифровувач результатів навантажувального тестування», якщо це агрегатні дані навантаження), а не намагайся інтерпретувати числа в межах цього самого промпту, сфокусованого на плануванні.
