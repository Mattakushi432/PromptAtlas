## Опис
Ранжує гіпотези першопричини продакшн-інциденту на основі симптомів, логів і таймлайну — ширший, системний аналіз, ніж для одного нестабільного тесту чи стек-трейсу, призначений для того, хто веде інцидент чи пише постмортем.

## Коли використовувати
- Активна реакція на інцидент, потрібен структурований спосіб міркувати про кілька сигналів під тиском часу.
- Написання постмортему, коли потрібен систематичний прохід по доказах перед тим, як зупинитися на "тій самій" першопричині.
- Передача інциденту, що триває, іншому інженеру, з потребою підсумувати поточні зачіпки.

## Промпт

```
Ти допомагаєш проаналізувати першопричину продакшн-інциденту на основі симптомів і доказів нижче. У реальних інцидентах часто присутні кілька сприятливих факторів — не звужуй до однієї причини, якщо докази підтримують більше однієї.

Опис інциденту: {{INCIDENT_SUMMARY}}
Таймлайн подій (деплої, алерти, зміни конфігурації, зміни трафіку — все відоме): {{TIMELINE}}
Спостережувані симптоми: {{SYMPTOMS}}
Логи/метрики/фрагменти помилок: {{LOGS_OR_METRICS}}
Контекст архітектури системи (необов'язково): {{SYSTEM_CONTEXT}}

Інструкції:
1. Побудуй короткий наратив, впорядкований за часом, того, що відомо про те, що сталося, розрізняючи підтверджені факти від того, що поки лише припускається.
2. Згенеруй гіпотези першопричини, і для кожної: сформулюй причинний ланцюг, який вона передбачає (що сталося → що це спричинило → що це спричинило → спостережуваний симптом), які докази її підтримують і які докази їй суперечили б.
3. Ранжуй гіпотези за тим, наскільки добре вони пояснюють УСІ спостережувані симптоми, а не лише один — гіпотеза, що пояснює 3 з 4 симптомів і вимагає збігу для четвертого, ранжується нижче тієї, що пояснює всі 4 чисто.
4. Познач будь-яку кореляцію, що трактується як причинність (напр., "деплой стався приблизно тоді ж" — це зачіпка, а не доказ) і скажи, що потрібно для її підтвердження (напр., перевірка, чи diff деплою правдоподібно спричиняє цей симптом).
5. Визнач, яких даних бракує, щоб найефективніше розрізнити топові гіпотези — найцінніший наступний доказ для збору.
6. Не декларуй остаточну першопричину, якщо докази не підтримують її впевнено — скажи, яка гіпотеза лідирує і чому, і що потрібно для її підтвердження.

Формат виводу: Markdown із розділами: Таймлайн, Гіпотези (ранжовано, кожна з доказами за/проти), Найцінніший наступний доказ для збору.
```

## Змінні
- `{{INCIDENT_SUMMARY}}` — короткий опис інциденту (що зламалося, вплив на користувачів). Обов'язково.
- `{{SYMPTOMS}}` — спостережувані ефекти (помилки, затримка, неправильні дані тощо). Обов'язково.
- `{{TIMELINE}}` — відомі події з таймстемпами: деплої, зміни конфігурації, алерти, сплески трафіку. Обов'язково — часто це найсильніший сигнал.
- `{{LOGS_OR_METRICS}}` — реальні рядки логів, частота помилок чи показники дашбордів. Необов'язково, але дуже цінно.
- `{{SYSTEM_CONTEXT}}` — відповідна архітектура (залучені сервіси, залежності). Необов'язково.

## Приклад
**Вхід:** `{{INCIDENT_SUMMARY}}` = "частота помилок при оформленні замовлення злетіла до 40%", `{{TIMELINE}}` = "14:02 деплой payment-service v2.3.1, 14:05 частота помилок починає рости", `{{SYMPTOMS}}` = "500-і помилки від payment-service, обсяг трафіку не змінився".

**Вихід (фрагмент):**
```
## Гіпотези (ранжовано)
1. **Деплой payment-service v2.3.1 вніс регресію** — ВИСОКА впевненість.
   Причинний ланцюг: деплой о 14:02 → початок помилок о 14:05 (відповідає швидкості роловту) → 500-і саме від payment-service, а не вищерозташованих сервісів → узгоджується з "трафік не змінився" (виключає причину, пов'язану з навантаженням).
   Докази за: часова кореляція щільна (3 хв), помилки ізольовані до задеплоєного сервісу.
   Не перевірено: не підтверджено, що diff деплою дійсно зачіпає шлях коду, що падає.

## Найцінніший наступний доказ для збору
Дістань diff для v2.3.1 і перевір, чи зачіпає він шлях коду, що видає 500-і — це підтвердить чи спростує гіпотезу №1 майже миттєво.
```

## Поради та варіації
- Для активного інциденту попроси постійно оновлювати ранжований список у міру надходження нових доказів, а не перезапускати аналіз щоразу з нуля.
- Для фінального тексту постмортему попроси розділити "першопричину", "сприятливі фактори" і "чому не помітили раніше" на окремі розділи, коли розслідування вже завершилося.
