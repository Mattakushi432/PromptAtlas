## Опис
Позначає нечіткі, оманливі чи неузгоджені назви ідентифікаторів у файлі та пропонує конкретні кращі назви — вузький прохід лише по іменуванню, не загальні запахи коду чи структура. Для швидкого, сфокусованого покращення читабельності.

## Коли використовувати
- Логіка файлу в порядку, але назви (`data`, `temp`, `flag2`, `handleThing`) ускладнюють розуміння.
- Рецензування PR, де неузгоджене іменування (змішування `userId`/`user_id`/`uid` для того самого поняття) створює плутанину.
- Підготовка файлу для нового контриб'ютора з бажанням, щоб назви самі несли більше пояснення.

## Промпт

```
Ти аудитуєш лише назви ідентифікаторів — змінних, функцій, класів, параметрів — не логіку, структуру чи інші запахи коду. Тримайся вузько сфокусовано на іменуванні.

Код:
{{CODE}}

Конвенція іменування для дотримання (необов'язково, напр., "camelCase, булеви з префіксом is/has"): {{NAMING_CONVENTION}}

Інструкції:
1. Познач назви, що не розкривають намір: загальні назви (`data`, `temp`, `obj`, `flag`, `handleThing`), які можуть означати багато речей, і назви, що вимагають читання реалізації для розуміння.
2. Познач оманливі назви: назву, що натякає на щось, чого код насправді не робить (напр., `getUser`, що також має побічний ефект запису в базу даних — назва обіцяє чисте читання).
3. Познач неузгодженість: те саме поняття, назване по-різному в різних місцях (`userId` проти `user_id` проти `uid` для явно того самого значення), чи та сама назва, використана для концептуально різних речей.
4. Познач назви, що порушують задану {{NAMING_CONVENTION}}, якщо вона надана (напр., булева без префікса is/has/should/can).
5. Для кожної позначеної назви запропонуй конкретну заміну, не просто "обери кращу назву" — і коротко обґрунтуй, чому заміна чіткіша.
6. Не позначай назви, які вже чіткі, лише щоб наповнити звіт — добре названий файл має повернутися з небагатьма знахідками чи взагалі без них.
7. Не чіпай логіку, лише назви — якщо помітиш баг під час читання, не звітуй про нього тут (цей промпт лише про іменування).

Формат виводу: Markdown, один запис на позначену назву: `оригінал` → `пропозиція`, з реченням-причиною.
```

## Змінні
- `{{CODE}}` — код для аудиту іменування. Обов'язково.
- `{{NAMING_CONVENTION}}` — правила іменування проєкту для звірки. Необов'язково.

## Приклад
**Вхід:** `{{CODE}}` = функція з параметром `d`, що використовується як відсоток знижки, і функція `checkUser(u)`, яка насправді створює користувача, якщо його не існує.

**Вихід (фрагмент):**
```
- `d` → `discountPercent` — одна літера не дає жодного натяку, що це відсоток, а не сума чи флаг.
- `checkUser` → `getOrCreateUser` — поточна назва натякає на чисту перевірку/читання, але функція має побічний ефект (створює запис користувача); назва має це відображати.
```

## Поради та варіації
- Для великого файлу попроси звітувати лише про топ-10 найважливіших проблем іменування (назви, використані в найбільшій кількості місць), а не вичерпний список.
- Поєднуй з реальним style guide проєкту як `{{NAMING_CONVENTION}}` для впровадження внутрішніх правил, а не загальних порад щодо іменування.
