## Опис
Проєктує схему оцінки вартості запиту, щоб відхиляти дорогі GraphQL-запити перед виконанням — проактивний дизайн захисту, відмінний від «Аудит продуктивності GraphQL-резолверів» (coding, вже випущений) із постфактумним рев'ю вже повільних резолверів: цей промпт проєктує саму модель вартості й точку забезпечення, для запобігання виконанню дорогих запитів узагалі, не діагностику, чому конкретний був повільним постфактум.

## Коли використовувати
- Гнучка форма запитів твого GraphQL API означає, що клієнти можуть будувати глибоко вкладені чи сильно дублюючі запити, дорогі незалежно від ефективності окремих резолверів, і хочеш захист на рівні прийняття запиту.
- У тебе був (чи хочеш запобігти) інцидент, де один зловмисний чи випадковий запит поклав API, запросивши величезний обсяг даних через на вигляд легітимні вкладені поля.
- Проєктуєш публічний доступ до API (сторонні розробники, не лише власний фронтенд) і потрібен захист на основі вартості, оскільки не можеш контролювати, які запити побудують зовнішні клієнти.

## Промпт

```
Ти проєктуєш схему оцінки вартості запиту для GraphQL API: спосіб оцінити вартість запиту перед виконанням і відхиляти запити понад поріг. Ти проєктуєш модель оцінки й точку забезпечення конкретно для реальної структури цієї схеми — ти не пропонуєш загальне рішення «просто обмеж глибину запиту» без перевірки, чи цього достатньо для реальної форми ризику схеми.

Структура схеми (ключові типи, зв'язки, особливо поля списку/з'єднання): {{SCHEMA_STRUCTURE}}
Відомі дорогі резолвери чи операції: {{EXPENSIVE_OPERATIONS}}
Типи клієнтів (внутрішній фронтенд, сторонні споживачі API тощо): {{CLIENT_TYPES}}

Інструкції:
1. Спроєктуй формулу оцінки вартості, доречну {{SCHEMA_STRUCTURE}} — сам по собі простий ліміт глибини часто недостатній, оскільки не враховує ширину (неглибокий, але дуже широкий запит із багатьма полями списку може бути таким самим дорогим, як глибокий) — запропонуй оцінку, що враховує і глибину, і мультиплікативну ширину полів списку (вартість поля списку має множити вартість вибраних під ним підполів, оскільки кожен елемент списку спричиняє цю вартість підвибору).
2. Признач вищі вагові коефіцієнти полям, пов'язаним конкретно з {{EXPENSIVE_OPERATIONS}} (напр., поле, що запускає дорогий джойн бази даних чи виклик зовнішнього API, має коштувати більше за поле, що читає з простого кешованого пошуку) — однорідна вартість на поле пропускає реальний розподіл витрат по схемі.
3. Спроєктуй, де в життєвому циклі запиту обчислюється вартість: ідеально до початку виконання (статичний аналіз AST запиту проти моделі вартості), не після того, як резолвери вже почали виконуватись, оскільки мета — відхиляти дорогі запити до того, як вони споживають ресурси, не просто вимірювати вартість постфактум.
4. Спроєктуй поріг і його забезпечення за {{CLIENT_TYPES}} — внутрішній фронтенд-клієнт, що робить відомий, перевірений набір запитів, може розумно мати вищий чи інший поріг, ніж недовірений сторонній споживач API, чиї форми запитів не контролюються чи не рев'юяться.
5. Спроєктуй відповідь відхилення дієвою, не просто голою помилкою: скажи клієнту приблизно чому запит відхилено (напр., яка частина запиту найбільше спричинила вартість), щоб легітимні клієнти могли скоригувати свій запит, а не наштовхнутись на непрозору стіну.
6. Познач будь-яку частину {{SCHEMA_STRUCTURE}}, де вартість справді важко оцінити статично (напр., поле, чия реальна вартість залежить від runtime-даних, не знаних лише з форми запиту, на кшталт пошукового поля з сильно варіативною вартістю обробки результатів) — для них зазнач, що саму статичну оцінку вартості, можливо, потрібно доповнити runtime-запобіжником (жорсткий таймаут виконання), а не покладатись лише на оцінку до виконання.

Формат виводу: Markdown із `## Модель вартості` (формула оцінки й підхід ваги полів), `## Точка забезпечення`, `## Стратегія порогу за типом клієнта`, `## Дизайн відповіді відхилення`, і секція `## Прогалини` для всього, що самого статичного аналізу не покриває.
```

## Змінні
- `{{SCHEMA_STRUCTURE}}` — ключові типи й зв'язки схеми, особливо будь-які поля списку/з'єднання, що могли б бути вкладені чи запитані в масштабі. Обов'язково.
- `{{EXPENSIVE_OPERATIONS}}` — які конкретно поля/резолвери відомо непропорційно дорогі (зовнішні виклики, дорогі джойни, обчислювані поля). Обов'язково — без цього модель вартості за замовчуванням переходить на однорідну вагу, що зазвичай не відображає реальність.
- `{{CLIENT_TYPES}}` — хто запитує цей API і наскільки довірені/перевірені їхні патерни запитів. Обов'язково — стратегія порогу сильно залежить від цього.

## Приклад
**Вхід:** `{{SCHEMA_STRUCTURE}}` = «Тип User має з'єднання `posts` (пагінований список), кожен Post має з'єднання `comments`, кожен Comment має поле `author` (ще один User) — тож запити можуть вкладати User -> posts -> comments -> author довільно» `{{EXPENSIVE_OPERATIONS}}` = «Поле `comments` запускає неіндексований запит на великій таблиці; `author` на Comment робить додатковий раунд-тріп до бази даних, не покритий наявним батчингом» `{{CLIENT_TYPES}}` = «Внутрішній фронтенд (перевірені запити) і публічний API для сторонніх розробників (неперевірений)»

**Вихід (уривок):**
```
## Модель вартості
Базова вартість на поле, помножена через межі списку/з'єднання: з'єднання `posts`, що запитує N елементів, множить вартість усього вибраного під ним на N (обмежене реальним аргументом `first`/`limit` запиту, не припущеним максимумом, щоб уникнути надмірного покарання запиту, що явно запитує мало елементів). `comments` отримує вищу базову вагу, зважаючи на вартість його неіндексованого запиту; `author` на Comment отримує підвищену вагу, зважаючи на додатковий небатчений раунд-тріп, поки це не виправлено на рівні резолвера.

## Точка забезпечення
Статичний розрахунок вартості проти розпарсеного AST запиту до початку виконання, використовуючи задекларовану вагу кожного поля й запитані розміри списку з аргументів запиту — відхиляти перед запуском будь-якого резолвера, якщо загальна оцінена вартість перевищує поріг клієнта.

## Стратегія порогу за типом клієнта
Внутрішній фронтенд: щедрий поріг, оскільки його запити перевірені кодом і не зміняться без деплою — обмеження вартості тут запобіжна сітка для випадкових регресій, не основний захист. Сторонній API: суттєво жорсткіший поріг, оскільки ці запити неперевірені, і запити ворожої форми (глибоко вкладені ланцюжки User->posts->comments->author) — основний ризик, який цей дизайн має запобігти.

## Дизайн відповіді відхилення
При відхиленні повертай, який конкретний шлях поля спричинив найбільше вартості (напр., «comments.author, вкладений під posts, перевищив дозволений множник»), а не голе «запит занадто дорогий» — дозволяє легітимному сторонньому розробнику зрозуміти, що реструктурувати.

## Прогалини
Оцінка вартості тут припускає, що розміри списку походять з явних аргументів запиту (first/limit) — якщо будь-яке поле з'єднання взагалі не має забезпечених аргументів пагінації, це окрема, більш термінова проблема (необмежені запити списків), яку варто виправити перед тим, як покладатись лише на оцінку вартості для цього поля.
```

## Поради та варіації
- Якщо {{EXPENSIVE_OPERATIONS}} виявляє, що більшість концентрації вартості походить з малої кількості конкретних резолверів, часто варто виправити ці резолвери напряму (батчинг, кешування, індексування) паралельно з — не замість — додавання захисту на основі вартості; модель вартості — запобіжна сітка, не заміна виправлення реально виправної неефективності резолвера.
- Для схеми, що часто змінюється, спроєктуй призначення ваги полів як підтримуваний, перевірюваний артефакт (не одноразовий розрахунок) — ваги варто переглядати щоразу, як додається нове дороге поле, подібно до того, як {{EXPENSIVE_OPERATIONS}} потрібно оновлювати з часом.
- Поєднуй із «Аудит продуктивності GraphQL-резолверів» (coding, вже випущений) при дослідженні, чому конкретні поля опинились у {{EXPENSIVE_OPERATIONS}} насамперед — той промпт діагностує продуктивність на рівні резолвера; цей проєктує контроль допуску на рівні запиту, побудований навколо тих знахідок.
