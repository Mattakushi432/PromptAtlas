## Опис
Радить щодо компромісів стиснення відповідей (gzip/brotli, рівень стиснення, що стискати) для реальних характеристик навантаження конкретного API — інструмент підтримки рішень для конкретної ситуації, не загальна рекомендація «просто увімкни gzip», що ігнорує, що реально подається.

## Коли використовувати
- Вирішуєш, чи/як додати стиснення до API, і хочеш, щоб компроміси були продумані для реального патерну твого трафіку, не універсальне значення за замовчуванням.
- Розміри відповідей зросли, і хочеш перевірити, чи налаштування стиснення досі відповідають поточному міксу навантажень.
- Дебажиш неочікувано високе використання CPU й підозрюєш налаштування стиснення (занадто агресивний рівень, стиснення вже стиснутого контенту) як можливу причину.

## Промпт

```
Ти радиш щодо стратегії стиснення відповідей для реальних характеристик навантаження конкретного API. Ти міркуєш на основі того, що реально подається — ти не даєш загальну пораду «увімкни gzip», не пов'язану з конкретними компромісами.

Характеристики навантаження (типовий розмір, тип контенту, структура): {{PAYLOAD_INFO}}
Профіль трафіку (запити/сек, типи клієнтів): {{TRAFFIC_PROFILE}}
Поточне налаштування (якщо є): {{CURRENT_SETUP}}

Інструкції:
1. Рекомендуй, чи взагалі варте стиснення, зважаючи на {{PAYLOAD_INFO}} — дуже малі відповіді (кілька сотень байт) часто не вартують накладних витрат CPU на стиснення відносно збережених байтів; вкажи приблизний поріг розміру, нижче якого вигода стиснення маргінальна для описаного типу контенту.
2. Порівняй gzip проти brotli для конкретної ситуації: brotli зазвичай стискає краще, але коштує більше CPU на вищих рівнях якості й має менш універсальну підтримку клієнтів за gzip — рекомендуй, зважаючи на мікс клієнтів {{TRAFFIC_PROFILE}} і те, чи CPU чи пропускна здатність тут більш обмежений ресурс, не загальну заяву «brotli краще».
3. Рекомендуй рівень стиснення, доречний обсягу запитів {{TRAFFIC_PROFILE}} — високий рівень стиснення обмінює час CPU на менший вивід, що важить по-різному при низькому обсязі запитів (вартість CPU незначна, максимізуй стиснення) проти високого обсягу запитів (вартість CPU накопичується, налаштування середнього рівня, що балансує розмір і CPU, часто краще за максимальний рівень).
4. Перевір, чи {{CURRENT_SETUP}} (якщо надано) стискає контент, що вже стиснутий (зображення, відео, вже стиснуті ассети, деякі бінарні формати) — стиснення вже стиснутих даних марнує CPU для незначної чи нульової вигоди розміру і поширена неправильна конфігурація, варта явного позначення, якщо присутня.
5. Для JSON/текстового API конкретно зверни увагу, що структура відповіді має значення: сильно повторюваний JSON (напр., багато об'єктів з однаковими ключами) стискається дуже добре, тоді як уже компактні чи високоентропійні навантаження (напр., бінарні дані у форматі base64, вбудовані в JSON) стискаються погано — врахуй це в оцінці економії розміру, а не припускай однорідні коефіцієнти стиснення.
6. Якщо {{TRAFFIC_PROFILE}} вказує, що CPU вже вузьке місце, явно зваж це проти економії пропускної здатності — стиснення не безкоштовне, і рекомендація без перевірки запасу CPU може обміняти одне вузьке місце на інше.

Формат виводу: Markdown із `## Рекомендація` (увімкнути/скоригувати/лишити як є), `## Вибір алгоритму` (gzip/brotli, з обґрунтуванням), `## Рівень стиснення`, і `## Позначки` (напр., стиснення вже стиснутого контенту, якщо знайдено в {{CURRENT_SETUP}}).
```

## Змінні
- `{{PAYLOAD_INFO}}` — типовий розмір відповіді, тип контенту, і приблизна структура. Обов'язково.
- `{{TRAFFIC_PROFILE}}` — обсяг запитів і що відомо про типи клієнтів (браузери, мобільні застосунки, сервер-сервер), оскільки підтримка стиснення клієнтом різниться. Обов'язково.
- `{{CURRENT_SETUP}}` — поточна конфігурація стиснення, якщо існує для рев'ю. Необов'язково — пропусти для свіжої рекомендації, коли нічого аудитувати.

## Приклад
**Вхід:** `{{PAYLOAD_INFO}}` = «JSON API-відповіді, типово 50-200КБ, сильно повторювана структура (масиви подібних об'єктів)» `{{TRAFFIC_PROFILE}}` = «~500 запитів/сек, мікс браузерних і мобільних клієнтів, CPU наразі при ~40% середнього використання» `{{CURRENT_SETUP}}` = «Стиснення наразі не увімкнено»

**Вихід (уривок):**
```
## Рекомендація
Увімкни стиснення. 50-200КБ значно вище порогу, де стиснення варте вартості CPU, і описана сильно повторювана структура JSON має добре стискатись (часто 70-90% зменшення розміру для такого повторюваного-за-ключами JSON).

## Вибір алгоритму
Gzip як базовий (майже універсальна підтримка клієнтами в браузерах і типових мобільних HTTP-клієнтах), з brotli як додатковою опцією, якщо серверний стек підтримує узгодження контенту й значна частка клієнтів заявляють підтримку brotli — кращий коефіцієнт стиснення brotli варто захопити там, де підтримується, але gzip має лишатись резервним, зважаючи на змішану базу клієнтів.

## Рівень стиснення
Середній рівень стиснення (не максимальний), зважаючи на ~500 запитів/сек і 40% середнього використання CPU — є запас для вартості CPU стиснення, але максимальний рівень стиснення на кожному запиті при цьому обсязі ризикує суттєво підняти використання CPU за спадаючу віддачу розміру понад налаштування середнього рівня.

## Позначки
Жодних — немає поточного стиснення для аудиту на проблему «стиснення вже стиснутого контенту».
```

## Поради та варіації
- Якщо доступні реальні виміри розмірів навантаження до/після та CPU після впровадження рекомендації, подай їх назад як оновлений {{CURRENT_SETUP}}, щоб перевірити на здоровий глузд, чи реальний коефіцієнт стиснення й вартість CPU відповідали оцінці — припущення про повторювану структуру не завжди точно тримаються на практиці.
- Для API, що обслуговує справжній мікс типів навантаження (частина сильно стискається JSON, частина майже нестискається бінарна), розглянь запуск цього промпту окремо на ендпоінт/категорію типу контенту, а не одна загальна рекомендація для всього API.
- Цей промпт покриває конкретно стиснення відповідей — для зменшення розміру навантаження в джерелі (видалення непотрібних полів, пагінація, вибір полів) це окреме питання дизайну схеми/API, яке цей промпт не покриває.
