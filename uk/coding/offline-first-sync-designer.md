## Опис
Проєктує стратегію офлайн-синхронізації даних для мобільного застосунку — модель локального сховища, чергу синхронізації, розв'язання конфліктів — для фічі, що має працювати без з'єднання і узгоджувати зміни пізніше. Рівень архітектури, відрізняється від будь-якого промпту краш/продуктивність для однієї платформи.

## Коли використовувати
- Побудова фічі, що має працювати офлайн (збір даних у полі, нотатки, управління завданнями), і потрібен реальний дизайн синхронізації перед початком реалізації.
- Наявний "переважно онлайн" застосунок доопрацьовується підтримкою офлайн і потребує плану обробки переходу.
- Дебаг проблем неузгодженості даних, що ведуть до саморобної реалізації синхронізації без чітких правил розв'язання конфліктів.

## Промпт

```
Ти проєктуєш стратегію офлайн-синхронізації для фічі мобільного застосунку — локальне сховище, механіку синхронізації, розв'язання конфліктів — як конкретну архітектуру, не загальні принципи offline-first.

Опис фічі (які дані, які операції — create/edit/delete): {{FEATURE_DESCRIPTION}}
Міркування щодо кількох пристроїв/користувачів (необов'язково — напр., "той самий користувач на двох пристроях", "кілька користувачів редагують спільні дані"): {{CONCURRENCY_CONTEXT}}
Платформа/стек: {{PLATFORM}}

Інструкції:
1. Рекомендуй підхід локального сховища, відповідний формі даних і платформі (напр., SQLite/Room/Core Data для структурованих реляційних даних, локально-перший двигун синхронізації на кшталт WatermelonDB/Realm, якщо екосистема підходить) — обґрунтуй проти конкретної форми даних, не вибір за замовчуванням.
2. Спроєктуй чергу синхронізації: як локальні зміни відстежуються під час офлайну (патерн change log/outbox зазвичай надійніший за диффінг повного локального проти віддаленого стану), і як черга обробляється, коли повертається з'єднання — включно з обробкою часткової відмови (деякі операції в черзі успішні, інші падають; черга не має бути all-or-nothing).
3. Спроєктуй розв'язання конфліктів явно для описаного сценарію конкурентності: last-write-wins просте, але мовчки втрачає дані — рекомендуй його лише там, де фіча і {{CONCURRENCY_CONTEXT}} роблять це прийнятним компромісом (напр., власні нотатки одного користувача на власних пристроях, низька ймовірність колізії). Для дійсно конкурентних редагувань кількома користувачами рекомендуй злиття на рівні полів, підхід на основі CRDT, чи явне виведення конфлікту користувачу, на основі того, що відповідає фактичній структурі даних і наскільки виправдана складність частотою колізій.
4. Явно адресуй видалення: жорстке локальне видалення, що синхронізується як видалення, може погано конкурувати з паралельним редагуванням на іншому пристрої — рекомендуй записи soft-delete/tombstone, що правильно синхронізуються і згодом збираються сміттярем, а не негайне жорстке видалення.
5. Адресуй тригери синхронізації: при повторному з'єднанні, періодично, при переході застосунку на передній план, чи через push — і зазнач компроміс між свіжістю синхронізації і використанням батареї/трафіку.
6. Зазнач, який видимий для користувача фідбек потрібен для стану синхронізації в очікуванні чи невдалої синхронізації — тиха відмова фонової синхронізації є поширеним джерелом звітів про баги "мої дані зникли"; UI має чесно представляти несинхронізований/конфліктний стан.
7. Якщо {{CONCURRENCY_CONTEXT}} не надано, за замовчуванням обирай випадок одного користувача з низькою ймовірністю колізії, але явно познач це припущення, оскільки воно суттєво змінює рекомендовану стратегію конфліктів.

Формат виводу: Markdown з розділами: Локальне сховище, Черга синхронізації та обробка, Розв'язання конфліктів, Обробка видалення, Тригери синхронізації, Видимий для користувача стан синхронізації.
```

## Змінні
- `{{FEATURE_DESCRIPTION}}` — які дані й операції потребують офлайн-підтримки. Обов'язково.
- `{{PLATFORM}}` — мобільний стек (нативний iOS/Android, React Native, Flutter). Обов'язково — доступні бібліотеки локального сховища/синхронізації різняться.
- `{{CONCURRENCY_CONTEXT}}` — скільки користувачів/пристроїв можуть паралельно редагувати ті самі дані. Необов'язково, але суттєво впливає на рекомендацію стратегії конфліктів.

## Приклад
**Вхід:** `{{FEATURE_DESCRIPTION}}` = "застосунок списку завдань, де користувачі створюють/редагують/завершують/видаляють завдання", `{{CONCURRENCY_CONTEXT}}` = "той самий користувач на телефоні й планшеті, без спільного/колаборативного редагування", `{{PLATFORM}}` = "React Native".

**Вихід (фрагмент):**
```
## Розв'язання конфліктів
З урахуванням редагування одним користувачем крізь пристрої (не колаборативного), last-write-wins на завдання, за ключем серверного таймстемпа `updated_at`, є прийнятним компромісом — вікно колізії (той самий користувач редагує те саме завдання на двох пристроях протягом секунд одне від одного, офлайн на обох) вузьке і малозначуще для списку завдань. Це БУЛО Б неприйнятним, якби {{CONCURRENCY_CONTEXT}} включав кількох різних користувачів, що редагують спільні завдання — це потребувало б натомість злиття на рівні полів чи явного виведення конфлікту.

## Обробка видалення
Впровадь м'які видалення: поле таймстемпа `deleted_at` замість жорсткого видалення рядка. Це уникає гонки, де Пристрій A видаляє завдання офлайн, поки Пристрій B редагує те саме завдання офлайн — при синхронізації і видалення, і редагування можуть бути побачені й узгоджені (напр., видалення перемагає, чи редагування виводиться користувачу), а не одна операція мовчки падає проти рядка, якого більше не існує.
```

## Поради та варіації
- Для фічі з реальним багатокористувацьким колаборативним редагуванням (напр., спільні документи) явно попроси підхід на основі CRDT чи OT і назви конкретні бібліотеки (напр., Yjs, Automerge), а не саморобне злиття полів, оскільки коректну логіку конкурентного злиття легко тонко зіпсувати з нуля.
- Якщо доопрацьовуєш офлайн-підтримку в наявному лише-онлайн застосунку, попроси також позначити, які наявні ендпойнти API/моделі даних потребували б зміни для підтримки черги синхронізації (напр., потреба в стабільному `updated_at` і способі отримати "зміни з X", а не повні дампи ресурсів).
