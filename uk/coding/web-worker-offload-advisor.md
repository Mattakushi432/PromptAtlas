## Опис
Визначає роботу, що блокує головний потік у фронтенд-коді — важкі обчислення, парсинг великого JSON, обробку зображень/даних — і радить, що винести у Web Worker, включно з дизайном інтерфейсу обміну повідомленнями й тим, що має лишитись у головному потоці. Відрізняється від «Аудитора продуктивності фронтенду» (coding, вже випущений) із його широким аудитом Core Web Vitals і «Радника з розбиття бандла» (coding, вже випущений) із фокусом на час завантаження через код-сплітинг: цей промпт вузько зосереджений на винесенні потоку під час рантайму для коду, який вже завантажений і виконується.

## Коли використовувати
- Користувачі скаржаться на ривки, замерзання UI чи затримку вводу під час конкретної операції (обробка великих даних, парсинг файлів, маніпуляції із зображеннями), і ти підозрюєш блокування головного потоку, а не мережеве очікування.
- Плануєш додати обчислювально важку фічу (клієнтську пошукову індексацію, трансформацію даних, криптографію) і хочеш заздалегідь вирішити, чи їй місце в головному потоці, чи у воркері.
- Профілював сторінку і знайшов довгі завдання головного потоку, але потрібна допомога у виборі, які саме частини цієї роботи реально безпечно й варто винести з потоку.

## Промпт

```
Ти визначаєш роботу, що блокує головний потік у фронтенд-коді, і радиш, що винести у Web Worker, включно з інтерфейсом для безпечного цього виконання.

Код чи опис профілю повільної операції: {{OPERATION_CODE}}
Фронтенд-фреймворк/контекст: {{FRAMEWORK}}
Спостережений симптом (ривки, затримка вводу, тривалість довгого завдання, якщо відома): {{SYMPTOM}}

Інструкції:
1. Визнач, які саме частини {{OPERATION_CODE}} прив'язані до CPU й незалежні від DOM (чисте обчислення, парсинг, трансформація даних) проти тих, що потребують прямого доступу до DOM/window (рендеринг, читання layout, більшість браузерних API) — лише перші можна винести у Worker, оскільки Worker не має доступу до DOM.
2. Для незалежних від DOM частин порадь інтерфейс обміну повідомленнями: які дані перетинають межу `postMessage` у кожному напрямку, і познач, якщо вхідні/вихідні дані достатньо великі, щоб вартість серіалізації (structured clone) могла звести нанівець вигоду від виносу — якщо так, порадь `Transferable`-об'єкти (напр., `ArrayBuffer`) замість звичайного об'єкта, де застосовно.
3. Якщо залежна й незалежна від DOM робота зараз переплетена в одній функції, опиши, як їх розділити: воркер робить важке обчислення й повертає результат; головний потік застосовує цей результат до DOM.
4. Радь стратегію розбиття на шматки лише якщо повний винос неможливий (напр., потрібні прогресивні результати для чутливого UI) — не радь її як перший вибір, коли можливий чистий повний винос, оскільки розбиття додає складність, яка звичайному воркеру не потрібна.
5. Зверни увагу на конкретний життєвий цикл: вартість створення воркера (не створюй новий на кожну операцію, якщо вона виконується повторно — переви користуй постійний воркер чи пул воркерів), і завершення/прибирання, якщо воркер більше не потрібен після одного використання.
6. Якщо {{FRAMEWORK}} має конкретний патерн інтеграції воркерів (напр., Comlink для чистішого RPC-стилю викликів, вбудований хук фреймворку для воркерів), порадь його замість сирого шаблонного коду `postMessage`, коли це суттєво зменшує складність коду.
7. Познач те, що явно НЕ варто виносити у воркер — напр., роботу, що вже достатньо швидка, щоб накладні витрати на обмін повідомленнями звели вигоду в мінус, чи роботу, що потребує синхронного вимірювання DOM посеред обчислення.

Формат виводу: Markdown. Секція «Винести у воркер» (що, і контракт повідомлень в/із) і секція «Лишити в головному потоці» (що, і чому), після чого мінімальний ескіз коду файлу воркера й місця виклику в головному потоці.
```

## Змінні
- `{{OPERATION_CODE}}` — код, функція чи опис профілювальника повільної операції. Обов'язково.
- `{{FRAMEWORK}}` — фронтенд-фреймворк/збірковий інструментарій (React, Vue, ванільний, Vite тощо), оскільки налаштування воркера й збирання різняться за інструментом. Обов'язково.
- `{{SYMPTOM}}` — що реально спостерігалось (замерзання скролу, затримана реакція на клік, конкретна тривалість довгого завдання з профілювальника). Необов'язково, але допомагає визначити пріоритет, яка частина коду реально винна, якщо є кілька кандидатів.

## Приклад
**Вхід:** `{{OPERATION_CODE}}` = «`applyFilters(rows)` парсить CSV-рядок на 50 тис. рядків в об'єкти, виконує багатопільний фільтр/сортування, потім викликає `setState` для перерендеру таблиці.» `{{FRAMEWORK}}` = «React, Vite» `{{SYMPTOM}}` = «Введення в поле фільтра замерзає на ~800мс на кожне натискання, за вкладкою DevTools Performance»

**Вихід (уривок):**
```
### Винести у воркер
Парсинг CSV + фільтр + сортування — усе чиста трансформація даних без доступу до DOM — це ~800мс завдання, що блокує. Контракт повідомлень: головний потік надсилає `{ csvString, filterCriteria }`; воркер повертає `{ filteredSortedRows }` як звичайний масив (розмір тут не виправдовує Transferable-об'єкти).

### Лишити в головному потоці
`setState(filteredSortedRows)` і власне перерендер таблиці — це вимагає узгодження React і оновлень DOM, що не може виконуватись у воркері.

worker.js:
self.onmessage = (e) => {
  const { csvString, filterCriteria } = e.data;
  const rows = parseCsv(csvString);
  const result = filterAndSort(rows, filterCriteria);
  self.postMessage({ filteredSortedRows: result });
};

Головний потік: перевикористовуй один екземпляр воркера, створений один раз (не на кожне натискання клавіші); на кожну зміну поля фільтра дебaунси виклик postMessage і онови стан в обробнику onmessage воркера.
```

## Поради та варіації
- Поєднуй із «Аудитором продуктивності фронтенду» (coding, вже випущений), коли ривки — один симптом серед кількох проблем Core Web Vitals — той промпт дає ширшу діагностику; цей проєктує конкретне виправлення, щойно блокування головного потоку підтверджене як причина.
- Якщо операція має торкатись великих бінарних даних (зображення, аудіобуфери), завжди схиляйся до `Transferable`-об'єктів чи `SharedArrayBuffer`, де доступно — наївний `postMessage` великого `ArrayBuffer` копіює його за замовчуванням і сам може стати вузьким місцем.
- Для операцій, що мають виконуватись на кожне натискання клавіші чи подію скролу, поєднуй винос у воркер із дебаунсингом/тротлінгом тригера в головному потоці — винос обчислення, яке все ще запускається занадто часто, лише переносить ривки, а не прибирає їх.
