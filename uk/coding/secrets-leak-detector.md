## Опис
Виловлює ймовірні захардкоджені секрети та облікові дані в коді — API-ключі, паролі, токени, рядки з'єднання — з рейтингом впевненості для кожної знахідки, для загального коду застосунку (будь-якою мовою). Відрізняється від перевірки секретів у «Рев'ювері Terraform», специфічної для IaC: це для звичайного вихідного коду, тестів, конфігів і скриптів.

## Коли використовувати
- Рев'ю PR чи файлу перед комітом/мерджем, особливо такого, що торкається конфігурації, налаштування середовища чи сторонніх інтеграцій.
- Аудит наявної кодової бази (особливо старої, чи успадкованої від іншої команди) на секрети, закомічені колись.
- Підготовка репозиторію до опенсорсингу чи ширшого внутрішнього доступу з потребою пройтися по всьому, що не має бути видимим.

## Промпт

```
Ти скануєш код на ймовірні захардкоджені секрети та облікові дані — не загальне рев'ю безпеки, лише ця одна категорія.

Код/файли для сканування: {{CODE}}
Контекст (необов'язково — напр., "це код тестової фікстури", "це конфіг-файл лише для локальної розробки"): {{CONTEXT}}

Інструкції:
1. Познач значення, що відповідають поширеним патернам секретів: API-ключі (специфічні для провайдера префікси на кшталт `sk-`, `AKIA`, `ghp_` тощо, де впізнавані), паролі, присвоєні як звичайні рядкові літерали, JWT-токени, матеріал приватного ключа (`-----BEGIN PRIVATE KEY-----` чи подібне), рядки з'єднання бази даних з вбудованими обліковими даними, секрети OAuth-клієнта, секрети підпису webhook.
2. Познач рядки з високою ентропією, присвоєні змінним із назвами, що натякають на облікові дані (`token`, `secret`, `key`, `password`, `auth`), навіть якщо вони не відповідають відомому патерну провайдера — підозрілий випадковий рядок у підозрілій змінній усе одно вартий позначення, навіть без розпізнаного префіксу.
3. Розрізняй ФАКТИЧНИЙ захардкоджений секрет від посилання на нього: `process.env.API_KEY` чи `os.environ["API_KEY"]` не є витоком (це читання зі середовища, що правильно); `const API_KEY = "sk-abc123..."` є витоком. Не позначай сам патерн назви змінної — позначай фактично вбудоване значення.
4. Оцінюй впевненість для кожної знахідки: HIGH (відповідає відомому формату ключа провайдера, чи однозначно має форму облікових даних), MEDIUM (рядок високої ентропії в змінній із натякаючою назвою, правдоподібно, але не точно), LOW (може бути секретом чи нечутливим випадковим ID/токеном — познач для людського судження).
5. Розрізняй реальні секрети від плейсхолдерів/прикладних значень, явно не живих облікових даних (`"your-api-key-here"`, `"xxxxxxxx"`, значення у файлі `.env.example`, явно призначені як шаблон) — зазнач їх окремо як "не витік" замість позначення з тією самою критичністю.
6. Якщо {{CONTEXT}} вказує, що це тестовий код/фікстура, все одно позначай реалістично виглядаючі секрети з HIGH впевненістю (тестові фікстури іноді випадково містять реальні облікові дані, скопійовані з реального середовища), але зазнач нижчу апріорну ймовірність.
7. Для кожної реальної знахідки рекомендуй конкретне усунення: перенести в змінну середовища/менеджер секретів, і зазнач, що виявлений секрет має бути РОТОВАНИЙ, не просто видалений з коду (оскільки він, можливо, вже в історії git).

Формат виводу: Markdown, один запис на знахідку: розташування значення, рівень впевненості, і виправлення — за яким слідує окремий розділ "Не позначено (плейсхолдери)" для всього, що виглядало як секрет, але оцінено як нечутливе.
```

## Змінні
- `{{CODE}}` — код/файли для сканування. Обов'язково.
- `{{CONTEXT}}` — тип цього файлу (тест, конфіг, продакшн-код). Необов'язково, але допомагає відкалібрувати впевненість.

## Приклад
**Вхід:** `{{CODE}}` = конфіг-файл з `const STRIPE_SECRET_KEY = "sk_live_51H..."` і окремо `const STRIPE_PUBLISHABLE_KEY = process.env.STRIPE_PK`.

**Вихід (фрагмент):**
```
### HIGH впевненість — `STRIPE_SECRET_KEY`
Значення `sk_live_51H...` точно відповідає формату живого секретного ключа Stripe, захардкоджене як рядковий літерал.
Виправлення: негайно перенеси в змінну середовища/менеджер секретів. Оскільки цей ключ закомічений у код (ймовірно, в історії системи контролю версій), його потрібно РОТУВАТИ в дашборді Stripe — саме лише видалення з файлу не інвалідує вже виявлений ключ.

### Не позначено
`STRIPE_PUBLISHABLE_KEY` читається з `process.env`, не захардкоджений — це посилання, не витік. (Також публічні ключі Stripe за задумом призначені для видимості на клієнті і не секретні за дизайном, на відміну від ключа вище.)
```

## Поради та варіації
- Поєднуй з реальним виводом інструмента сканування секретів (gitleaks, trufflehog, GitHub secret scanning) як додатковий контекст — цей промпт найсильніший у поясненні знахідок і відділенні реальних витоків від плейсхолдерів/хибних спрацьовувань, які сканери часто надмірно позначають.
- Для перевірки перед опенсорсингом явно попроси також позначати внутрішні хостнейми, імена/email співробітників і внутрішні URL поряд із секретами, оскільки ця перевірка часто відбувається одночасно.
