## Опис
Перевіряє фронтенд-код на готовність до інтернаціоналізації — захардкожені рядки, ручне форматування дат/чисел, плюралізацію і припущення про верстку, що ламаються при перекладі — перед виходом продукту в нові локалі. Відрізняється від `accessibility-auditor` (доступність, не локалізація) і `responsive-layout-debugger` (розмір екрана, не довжина/напрямок тексту).

## Коли використовувати
- Продукт ось-ось запускається в новій локалі і потрібен прохід для пошуку неінтернаціоналізованого коду.
- Рецензуєш новий фронтенд-код на готовність до i18n перед мерджем, у кодбейзі, що вже підтримує кілька локалей.
- Розслідуєш, чому UI конкретної локалі виглядає зламаним (верстка, форматування) порівняно з типовою.

## Промпт

```
Ти проводиш аудит фронтенд-коду на готовність до інтернаціоналізації — не доступність, не адаптивну верстку під розмір екрана, а конкретно те, що ламається, коли той самий UI має працювати іншою мовою чи локаллю.

Код (компонент чи сторінка): {{CODE}}

Цільові локалі (необов'язково — конкретні мови/регіони, для яких планується, корисно для позначення RTL чи специфічних потреб форматування): {{TARGET_LOCALES}}

Познач:
1. Захардкожені рядки, видимі користувачу, не пропущені через шар i18n/перекладу (буквальний рядок, переданий напряму в JSX/шаблон замість ключа перекладу/виклику функції).
2. Конкатенацію чи інтерполяцію рядків, що припускає конкретний порядок слів (наприклад, побудова речення конкатенацією перекладених фрагментів) — це ламається в мовах з іншою граматикою/порядком слів і має використовувати єдиний перекладний шаблонний рядок з плейсхолдерами замість цього.
3. Вручну відформатовані дати, числа чи валюту (саморобна логіка форматування) замість locale-aware API форматування (наприклад, `Intl.DateTimeFormat`, `Intl.NumberFormat`), що автоматично адаптується до локалі користувача.
4. Відсутню чи некоректну обробку плюралізації — текст, що працює для однини/множини англійською, але не враховує мови з іншими правилами плюралізації (у деяких мовах більше двох форм множини).
5. Припущення верстки, що ламаються при розширенні тексту — багато мов помітно довші за англійську для того самого значення, тож фіксовані за шириною контейнери чи припущення про відсутність обрізання — ризик — і, якщо {{TARGET_LOCALES}} включає RTL-мову (арабська, іврит), чи використовує верстка логічні властивості (start/end) замість захардкожених left/right.

Для кожної знахідки процитуй конкретний код і конкретно вкажи, що ламається (спотворене речення, обрізана кнопка, неправильна форма множини), а не загальну примітку "це не локалізовано".

Якщо код вже пропускає все через шар перекладу і коректно використовує locale-aware форматування, чесно скажи це як прохідний вердикт, замість того щоб вигадувати незначні знахідки.
```

## Змінні
- `{{CODE}}` — компонент чи сторінка для аудиту. Обов'язково.
- `{{TARGET_LOCALES}}` — конкретні локалі, для яких планується, якщо відомо. Необов'язково; без них застосовуються загальні принципи готовності до i18n без деталей RTL/плюралізації для конкретної локалі.

## Приклад
**Вхід:** `{{CODE}}` = React-компонент, що рендерить `` `У вас ${count} ${count === 1 ? 'новий файл' : 'нових файлів'}` ``, і дату, показану через ручне форматування рядка `${month}/${day}/${year}`, `{{TARGET_LOCALES}}` = "іспанська, арабська".

**Вихід (фрагмент):**
```
Знахідка: плюралізація зроблена вручну як бінарна перевірка `count === 1 ? '...' : '...'`. Це працює лише для count=1 ("1 новий файл") і випадково виглядає прийнятно для великих чисел ("5 нових файлів"), але дає граматично неправильний результат для 2-4 ("2 нових файлів" замість коректного "2 нових файли") — авторський код мовчки згорнув українську трикомпонентну систему числівникових форм (1 / 2-4 / 5+) до двокомпонентної, характерної для англійської. Іспанська та арабська мають ще інші правила плюралізації — арабська, зокрема, кілька форм множини залежно від числа. Виправлення: використай підтримку плюралізації бібліотеки i18n (наприклад, ICU MessageFormat через бібліотеку типу `i18next` чи `FormatJS`), що дозволяє кожній локалі визначати власні правила множини замість хардкоду двокомпонентної логіки.

Знахідка: дата відформатована вручну як `${month}/${day}/${year}`, хардкоджучи порядок дати (MM/DD/YYYY). Це не просто неперекладений текст — це активно неправильний формат для більшості локалей, включно з іспаномовними, які зазвичай використовують DD/MM/YYYY. Виправлення: використай `Intl.DateTimeFormat(locale).format(date)`, щоб формат автоматично адаптувався під локаль користувача.

Знахідка: у показаному коду верстки не видно врахування RTL — з арабською серед цільових локалей перевір, чи відступи/вирівнювання використовують логічні CSS-властивості (`margin-inline-start` замість `margin-left`), а не припускають LTR-верстку.
```

## Поради та варіації
- Для кодбейзу, що ще не використовує бібліотеку i18n, попроси також порекомендувати бібліотеку, відповідну для фреймворка у використанні (наприклад, `react-i18next`, `next-intl`, `FormatJS`), а не лише позначати прогалини без шляху вперед.
- Запускай це на цілій сторінці/флоу, а не одному компоненті, готуючись до реального запуску локалі — баги плюралізації і формату дати часто розсіяні по багатьох маленьких компонентах, а не сконцентровані в одному місці.
