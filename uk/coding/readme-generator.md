## Опис
Генерує README проєкту з опису кодової бази — що це, як налаштувати, як запустити — видає щось, що новий відвідувач дійсно може використати, не загальний шаблон. Для проєкту, якому потрібен README з нуля чи сильно застарілий, що потребує переписання.

## Коли використовувати
- Старт нового проєкту з потребою в README до появи першого контриб'ютора/користувача.
- Наявний README сильно розсинхронізувався (неправильні кроки налаштування, відсутні нові фічі) і потребує переписання, обґрунтованого на фактичній поточній кодовій базі.
- Підготовка проєкту до опенсорсингу чи ширшого внутрішнього поширення з потребою в README, що дійсно орієнтує незнайомця.

## Промпт

```
Ти пишеш README для реального проєкту, обґрунтований на наданих деталях — не загальний шаблон із секціями-плейсхолдерами.

Опис проєкту (що він робить, для кого, технологічний стек): {{PROJECT_DESCRIPTION}}
Кроки налаштування/встановлення (фактичні команди, потрібні для запуску): {{SETUP_STEPS}}
Ключові фічі чи приклади використання (необов'язково): {{USAGE_INFO}}
Наявний README для перегляду, якщо є (необов'язково): {{EXISTING_README}}

Інструкції:
1. Почни зі стислого опису того, що робить проєкт і для кого — незнайомець має зрозуміти призначення проєкту в перших двох реченнях, без потреби читати далі.
2. Напиши інструкції налаштування/встановлення як точні, готові до копіювання команди в порядку, в якому їх треба виконувати, не прозу з описом загальної ідеї налаштування — включи версії передумов (версія мови/рантайму, потрібні зовнішні сервіси) там, де вони мають значення.
3. Включи "швидкий старт" чи мінімальний приклад використання, що доводить когось від свіжого clone до бачення того, що воно фактично працює, перш ніж занурюватися в повну документацію фіч — це часто найцінніший окремий розділ для перших п'яти хвилин нового користувача.
4. Якщо {{USAGE_INFO}} описує конкретні фічі, документуй ті, що типовому користувачу дійсно потрібні спочатку, не вичерпний дамп фіч — посилайся на повнішу документацію для глибини, якщо вона існує, а не запихуй усе в README.
5. Не заявляй можливості, покриття тестами чи стабільність, не обґрунтовані наданою інформацією — README, що переоцінює те, що фактично є, підриває довіру при першому зіткненні з прогалиною.
6. Якщо надано {{EXISTING_README}}, збережи будь-які частини, що досі точні, замість того щоб переписувати все з нуля, але виправ усе, що фактично застаріло (перейменовані команди, видалені фічі, змінені кроки налаштування).
7. Включай стандартні завершальні розділи (License, Contributing) лише якщо дійсно застосовні — не наповнюй порожніми розділами заради вигляду завершеності.

Формат виводу: Markdown, структурований як: Назва + однорядковий опис, Швидкий старт, Встановлення, Використання, (необов'язково) Фічі, (необов'язково) Contributing/License.
```

## Змінні
- `{{PROJECT_DESCRIPTION}}` — що таке проєкт і його технологічний стек. Обов'язково.
- `{{SETUP_STEPS}}` — фактичні команди, потрібні для встановлення/запуску. Обов'язково.
- `{{USAGE_INFO}}` — ключові фічі чи приклад використання. Необов'язково, але суттєво покращує корисність README.
- `{{EXISTING_README}}` — наявний README для перегляду замість повної заміни. Необов'язково.

## Приклад
**Вхід:** `{{PROJECT_DESCRIPTION}}` = "CLI-інструмент для пакетного зміни розміру зображень, написаний на Go", `{{SETUP_STEPS}}` = "go install github.com/example/imgresize@latest", `{{USAGE_INFO}}` = "imgresize --width 800 ./photos/*.jpg".

**Вихід (фрагмент):**
```markdown
# imgresize

CLI-інструмент для пакетної зміни розміру зображень з командного рядка.

## Швидкий старт

```sh
go install github.com/example/imgresize@latest
imgresize --width 800 ./photos/*.jpg
```

Це змінює розмір кожного JPEG у `./photos` до ширини 800px, зберігаючи співвідношення сторін.

## Встановлення

Потребує Go 1.21+.

```sh
go install github.com/example/imgresize@latest
```
```

## Поради та варіації
- Для бібліотеки (не застосунку) заміни "Встановлення"/"Використання" на "Встановлення" (команда пакетного менеджера) і "API" чи "Приклад" з показом мінімального фрагмента коду, що використовує бібліотеку, оскільки аудиторія й форма швидкого старту відрізняються від CLI/застосунку.
- Якщо в проєкту є супутній сайт документації, явно попроси, щоб README залишався коротким і посилався для глибини, а не дублював вміст сайту документації вбудовано.
