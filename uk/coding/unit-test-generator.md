## Опис
Пише готові до запуску юніт-тести — включно з крайовими випадками, а не лише happy path — з сигнатури та реалізації функції, у конкретному тест-фреймворку. Для розробника, який хоче реальний перший чернетковий варіант тестів, а не чекліст того, що варто протестувати.

## Коли використовувати
- Щойно написав функцію і хочеш покриття тестами перед тим, як рухатися далі, за test-after підходом.
- Успадкував непокритий тестами легасі-код і потрібен базовий набір тестів перед безпечним рефакторингом.
- Практикуєш TDD і хочеш стартовий набір тест-кейсів для критики й доопрацювання перед реалізацією.

## Промпт

```
Ти пишеш юніт-тести. Згенеруй повний, готовий до запуску тестовий файл для функції нижче, використовуючи вказаний тест-фреймворк — не псевдокод, не опис того, що варто тестувати.

Функція/модуль для тестування:
{{FUNCTION_CODE}}

Мова та тест-фреймворк: {{LANGUAGE_AND_FRAMEWORK}}
Наявні конвенції тестових файлів для відповідності (необов'язково, напр., іменування, стиль setup/teardown): {{TEST_CONVENTIONS}}

Інструкції:
1. Спочатку протестуй happy path: типові валідні вхідні дані та очікувані результати.
2. Протестуй крайові випадки, специфічні для логіки цієї функції: порожні/null/undefined вхідні дані, граничні значення (нуль, від'ємне число, максимальний розмір), невідповідність типів, якщо мова допускає це під час виконання, та будь-який ввід, що потрапить в іншу гілку коду.
3. Якщо функція має побічні ефекти (I/O, мутація, зовнішні виклики), тестуй їх явно — не тестуй лише значення, що повертається, якщо функція робить більше, ніж обчислення.
4. Якщо функція може кинути виняток/відхилити проміс, протестуй, що вона робить це за правильних умов, і що вона НЕ робить цього за валідних.
5. Використовуй описові назви тестів, що формулюють поведінку, яка тестується (напр., `returns empty array when input list is empty`), а не `test1`, `test2`.
6. Якщо не можеш визначити коректний очікуваний результат для якогось випадку лише з коду (логіка функції неоднозначна чи виглядає багованою), не вигадуй його — напиши тест із коментарем `// TODO: confirm expected behavior` замість того щоб вгадувати.
7. Групуй пов'язані тести блоками `describe`/`context` (чи еквівалентом фреймворку), а не одним плоским списком.

Вивід: один повний тестовий файл, готовий до запуску, з необхідними імпортами.
```

## Змінні
- `{{FUNCTION_CODE}}` — вихідний код функції/модуля для тестування. Обов'язково.
- `{{LANGUAGE_AND_FRAMEWORK}}` — напр. "TypeScript / Vitest", "Python / pytest", "Go / testing package". Обов'язково.
- `{{TEST_CONVENTIONS}}` — наявний стиль тестів проєкту для відповідності. Необов'язково.

## Приклад
**Вхід:** `{{FUNCTION_CODE}}` = функція `calculateDiscount(price, percentOff)`, що кидає виняток при від'ємній ціні, `{{LANGUAGE_AND_FRAMEWORK}}` = "TypeScript / Vitest".

**Вихід (фрагмент):**
```ts
describe('calculateDiscount', () => {
  it('applies the percentage discount to a valid price', () => {
    expect(calculateDiscount(100, 20)).toBe(80);
  });

  it('throws when price is negative', () => {
    expect(() => calculateDiscount(-10, 20)).toThrow();
  });

  it('returns the original price when percentOff is 0', () => {
    expect(calculateDiscount(100, 0)).toBe(100);
  });
});
```

## Поради та варіації
- Для TDD-підходу попроси згенерувати тести лише з *сигнатури функції та докстрінга*, до існування реалізації — це дасть тести проти задуманого контракту, а не фактичного коду.
- Якщо кодова база мокає певним специфічним чином (напр., власний модуль test-utils), встав наявний тестовий файл як `{{TEST_CONVENTIONS}}`, щоб вивід точно відповідав стилю.
