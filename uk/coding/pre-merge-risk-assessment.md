## Опис
Оцінює радіус ураження diff'у та ризик мерджу/деплою — не якість коду — для того, хто вирішує, коли і наскільки обережно мерджити, а не що виправляти. Відрізняється від рев'ю коректності: результат — рівень ризику та рекомендація щодо деплою, а не список багів.

## Коли використовувати
- Рішення, чи безпечно мерджити diff прямо перед вихідними чи періодом високого навантаження.
- Триаж бекlogу відкритих PR, щоб зрозуміти, які потребують додаткової обережності (поетапний рол-аут, feature flag, деплой поза робочими годинами).
- Брифінг чергового інженера про те, що щойно задеплоїли і що може піти не так.

## Промпт

```
Ти оцінюєш ризик деплою diff'у, а не рецензуєш якість коду чи шукаєш баги. Вважай, що код уже коректний; твоє завдання — оцінити, що станеться, якщо він виявиться неправильним.

Diff:
{{DIFF}}

Контекст системи (необов'язково — частиною чого є цей код, його трафік/критичність): {{SYSTEM_CONTEXT}}

Контекст деплою (необов'язково — таймінг, доступні інструменти відкату): {{DEPLOY_CONTEXT}}

Оціни за цими вимірами:
1. Радіус ураження — що зламається, якщо в цьому diff'і є баг: одна функція, одна фіча, один сервіс чи щось наскрізне (автентифікація, білінг, цілісність даних, спільна інфраструктура)?
2. Відновлюваність — чи можна це чисто відкотити (revert безпечний), чи це включає міграцію, запис даних або зовнішній побічний ефект (надіслано email, списано платіж), який відкат не може скасувати?
3. Виявність — якщо це зламається, чи станеться це гучно (помилка, краш, алерт), чи тихо (неправильні дані, деградований UX, який ніхто одразу не помітить)?
4. Поверхня зміни — це маленька, ізольована зміна, чи вона зачіпає спільний/критичний код, від якого залежить багато іншого?
5. Попередня стабільність — чи є в diff'і щось (конкурентність, таймінг, зовнішні виклики) з патернами, відомими як нестабільні чи важкі для вичерпного тестування?

Для кожного виміру дай оцінку (LOW/MEDIUM/HIGH) і причину одним реченням, обґрунтовану реальним вмістом diff'у — а не загальними формулюваннями про ризик.

Об'єднай у загальний рівень ризику (LOW/MEDIUM/HIGH/CRITICAL) і конкретну рекомендацію: безпечно мерджити і деплоїти звично; мерджити, але деплоїти за флагом/поетапним рол-аутом; мерджити, але уникати деплою до [умова]; або не мерджити без [конкретне пом'якшення, напр., план відкату чи додатковий моніторинг].

Якщо diff занадто малий чи без контексту, щоб оцінити вимір, познач "недостатньо контексту" замість того щоб вгадувати.
```

## Змінні
- `{{DIFF}}` — diff для оцінки. Обов'язково.
- `{{SYSTEM_CONTEXT}}` — частиною чого є змінений код і наскільки він критичний/високонавантажений. Необов'язково, але покращує оцінку радіуса ураження.
- `{{DEPLOY_CONTEXT}}` — таймінг деплою, доступні інструменти відкату/флагів. Необов'язково.

## Приклад
**Вхід:** `{{DIFF}}` = міграція, що додає `NOT NULL` колонку до великої таблиці `orders` зі значенням за замовчуванням, обчисленим під час запису, `{{SYSTEM_CONTEXT}}` = "таблиця orders, ~50 млн рядків, читається/записується на кожному оформленні замовлення".

**Вихід (фрагмент):**
```
1. Радіус ураження: HIGH — це напряму зачіпає таблицю orders, залучену в кожне оформлення замовлення; блокування чи збій тут вплине на всі покупки, а не на одну фічу.
2. Відновлюваність: MEDIUM — саме додавання колонки відкотне, але якщо воно блокує таблицю під час міграції, це вікно не можна скасувати постфактум.

**Загальний ризик: HIGH.** Рекомендація: не мерджити без плану міграції, що уникає блокуючого лока таблиці (напр., спочатку додати колонку nullable, зробити backfill, потім додати обмеження), і відрепетируваного відкату для кроку міграції.
```

## Поради та варіації
- Для команди без поетапних рол-аутів прибери опцію рекомендації "за флагом" і попроси обирати лише між "безпечно мерджити" і "не мерджити без X".
- Передай реальний runbook чергового як `{{DEPLOY_CONTEXT}}`, щоб пропозиції пом'якшення посилалися на реальні інструменти, а не загальні поради.
