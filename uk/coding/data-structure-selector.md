## Опис
Рекомендує, яка структура даних чи алгоритм підходить для описаної задачі, з обґрунтуванням, прив'язаним до фактичних патернів доступу задачі — вибір дизайну наперед, відрізняється від «Аналізатора складності Big O» (аналізує наявний код постфактум). Для рішення, що обрати перед написанням розв'язку.

## Коли використовувати
- Початок розв'язання задачі (практика для співбесіди чи реальний код) з невпевненістю, яка структура даних зробила б її здійсненною.
- Рев'ю власного вибору структури даних перед фіксацією реалізації, щоб рано виловити неефективний вибір.
- Навчання розпізнавати, які характеристики задачі вказують на яку структуру даних, з часом розвиваючи інтуїцію розпізнавання патернів.

## Промпт

```
Ти рекомендуєш структуру даних/алгоритм для описаної задачі, з обґрунтуванням, прив'язаним до фактичних вимог задачі — не огляд кожної можливої опції.

Опис задачі (які операції потрібні, приблизно скільки даних, будь-яка вимога продуктивності): {{PROBLEM_DESCRIPTION}}

Інструкції:
1. Визнач конкретні операції, які задача фактично вимагає, і як часто кожна використовується: пошук, вставка, видалення, запити діапазону, впорядкований обхід, знаходження мін/макс, перевірка належності — саме суміш потрібних операцій визначає правильну структуру, не сам поверхневий опис задачі.
2. Рекомендуй конкретну структуру даних (не розпливчасту категорію) — напр., "хеш-мапа" дієвіше за "якась структура швидкого пошуку", а "min-heap" дієвіше за "структура для знаходження мінімумів".
3. Обґрунтуй вибір проти конкретних операцій, визначених у кроці 1: сформулюй, яка операція є вузьким місцем для наївного підходу, і як рекомендована структура конкретно це адресує (напр., "відсортований масив підтримує бінарний пошук за O(log n), але вставка — O(n); якщо вставки часті, збалансоване BST чи skip list тримає обидва на O(log n)").
4. Якщо кілька структур підійшли б, але з різними компромісами, назви топ-2 і сформулюй конкретний компроміс між ними (напр., хеш-мапа для O(1) середнього пошуку проти впорядкованої структури, якщо також потрібна впорядкована ітерація), а не обирай одну мовчки, коли вибір дійсно залежить від деталі, яка не надана.
5. Познач, якщо описана задача має поширений іменований патерн (два вказівники, sliding window, union-find, топологічне сортування), щоб той, хто розв'язує, міг звернутися до стандартної техніки патерну, а не винаходити її заново.
6. Якщо масштаб задачі достатньо малий, що "очевидна" проста структура підходить, а витонченіша була б передчасною оптимізацією, прямо про це скажи, а не завжди рекомендуй теоретично оптимальну структуру незалежно від фактичної потреби.
7. Коротко зазнач результуючу часову/просторову складність для основних операцій, коли рекомендована структура використовується, щоб вплив вибору був конкретним.

Формат виводу: Markdown з розділами: Визначені ключові операції, Рекомендована структура (з обґрунтуванням), Альтернатива (якщо є реальний компроміс), Результуюча складність.
```

## Змінні
- `{{PROBLEM_DESCRIPTION}}` — задача, включно з тим, які операції потрібні і приблизно скільки даних. Обов'язково.

## Приклад
**Вхід:** `{{PROBLEM_DESCRIPTION}}` = "потрібно обробляти потік чисел і в будь-який момент мати змогу швидко повідомити поточну медіану".

**Вихід (фрагмент):**
```
## Визначені ключові операції
Часта вставка (по одному числу за раз, потоково) і часті запити "знайти медіану", перемежовані зі вставками — не одноразове сортування з подальшими статичними запитами.

## Рекомендована структура
Дві купи: max-heap, що тримає меншу половину чисел, побачених досі, і min-heap, що тримає більшу половину, збалансовані за розміром (різняться щонайбільше на 1). Медіана завжди на вершині однієї (чи середнє обох вершин, якщо розміри рівні).

## Результуюча складність
Вставка: O(log n) на число (push/pop купи для перебалансування). Запит медіани: O(1) (просто зазирнути на вершину(и)). Це перемагає повторне сортування на кожному запиті (O(n log n) на запит) чи наївну єдину відсортовану структуру з O(n) вставкою.
```

## Поради та варіації
- Конкретно для практики співбесід попроси також назвати "родину патернів", до якої належить задача (напр., "це класичний патерн двох куп / підтримки медіани"), щоб розвинути розпізнавання для схоже сформульованих майбутніх задач, не лише розв'язок цієї однієї.
- Якщо фактичний масштаб даних дуже великий (не вміщається в пам'ять, потребує зовнішніх/розподілених структур), прямо про це скажи — це повністю змінює відповідь від вибору структури даних у пам'яті до питання системного дизайну.
