## Опис
Перевіряє поведінку повторів, backoff, підписів і порядку доставки в системі вихідних вебхуків — для бекенд-інженера, що будує чи рецензує систему, яка надсилає події на зовнішні URL підписників. Відрізняється від `api-error-handling-auditor`, що охоплює власну вхідну ідемпотентність API сервісу, а не гарантії, дані підписникам вебхуків.

## Коли використовувати
- Вперше будуєш систему доставки вебхуків і хочеш перевірити її на відомі пастки надійності.
- Підписники повідомляють про пропущені, продубльовані чи неупорядковані події вебхуків.
- Додаєш вебхуки в продукт і вирішуєш, які гарантії доставки реально обіцяти в документації.

## Промпт

```
Ти рецензуєш систему вихідної доставки вебхуків на надійність — конкретно, що відбувається, коли ендпоінт підписника повільний, видає помилки чи тимчасово недоступний, і чи реально дотримуються гарантії, дані підписникам.

Код доставки вебхуків: {{WEBHOOK_CODE}}

Необхідні гарантії доставки (at-least-once vs. best-effort, чи важливий порядок для подій, що надсилаються): {{DELIVERY_GUARANTEES_NEEDED}}

Перевір:
1. Повтори і backoff — при збої підписника (відповідь 5xx, таймаут, відмова з'єднання), чи є стратегія повторів, і чи використовує вона backoff (експоненційний чи інший), а не щільні повтори? Чи є обмежений максимум (кількість спроб чи загальна тривалість), щоб постійно мертвий ендпоінт підписника не намагався повторити нескінченно?
2. Підпис payload — чи підписаний кожен вебхук-payload (наприклад, HMAC з секретом на кожного підписника), щоб ендпоінт-отримувач міг перевірити, що запит реально прийшов від тебе і не був підроблений чи змінений під час передачі?
3. Підтримка ідемпотентності на боці підписника — чи включає кожна доставка стабільний ID доставки чи ID події, щоб підписник, що отримав ту саму подію двічі (через повтор після відповіді, яка була відправлена, але загублена при передачі), міг дедуплікувати на своєму боці?
4. Порядок — якщо {{DELIVERY_GUARANTEES_NEEDED}} стверджує, що порядок важливий, чи реально механізм доставки зберігає порядок (наприклад, однопотокова доставка на кожного підписника, чи номер послідовності, який підписники можуть використати для перевпорядкування) — чи паралельна доставка/повтори можуть спричинити прихід подій не в тому порядку, в якому вони сталися?

Для кожної прогалини конкретно вкажи, що могло б піти не так для підписника (подвійно оброблене списання на його боці, перезапис свіжого стану застарілою подією через неправильний порядок) — а не просто "це порушує best practice".

Якщо {{DELIVERY_GUARANTEES_NEEDED}} стверджує best-effort/без гарантії порядку, не позначай відсутність строгого порядку чи обмежених повторів як дефект — оцінюй реалізацію відносно того, що реально обіцяно, а не максимального стандарту.
```

## Змінні
- `{{WEBHOOK_CODE}}` — код вихідної доставки вебхуків. Обов'язково.
- `{{DELIVERY_GUARANTEES_NEEDED}}` — що реально обіцяно підписникам (at-least-once чи best-effort, потрібен порядок чи ні). Обов'язково — стандарт рев'ю повністю залежить від цього.

## Приклад
**Вхід:** `{{WEBHOOK_CODE}}` = функція доставки, що робить POST payload'у події без заголовка підпису, повторює 3 рази негайно при збої без затримки, і не включає ID події в payload, `{{DELIVERY_GUARANTEES_NEEDED}}` = "доставка at-least-once, порядок не потрібен".

**Вихід (фрагмент):**
```
Знахідка: немає підпису payload. Серйозність: HIGH. Підписники не мають способу перевірити, що вебхук реально прийшов з цієї системи, а не є підробленим запитом до їхнього ендпоінта — це прогалина безпеки для будь-якого підписника, що діє на основі вмісту вебхука (наприклад, тригерить повернення коштів на подію "refund.issued").
Виправлення: додай заголовок HMAC-підпису, обчислений з секретом на кожного підписника, і задокументуй процес верифікації для підписників.

Знахідка: повтори спрацьовують негайно, 3 рази, без backoff. Серйозність: MEDIUM. Проти ендпоінта підписника, що бореться (наприклад, коротко перевантажений), щільні негайні повтори додають навантаження саме тоді, коли це найменш корисно, і 3 спроби загалом — мало для заявленої гарантії at-least-once проти довшого простою.
Виправлення: експоненційний backoff (наприклад, 1с, 30с, 5хв, ...) з довшим загальним вікном повторів (наприклад, 24 години), перш ніж здатись і показати збій.

Знахідка: немає ID події/доставки в payload. Серйозність: MEDIUM з огляду на те, що at-least-once — заявлена гарантія — повтори очікувані, але без ID підписники не мають способу виявити і дедуплікувати вебхук, який вони вже успішно обробили один раз.
Виправлення: включи стабільний, унікальний ID події в кожен payload, згенерований один раз на логічну подію, незмінний при повторах тієї самої доставки.
```

## Поради та варіації
- Для системи, якій також потрібно показувати статус доставки підписникам (наприклад, дашборд з невдалими доставками), попроси додатково перевірити, чи стан збою/повтору реально зберігається і доступний для запитів, а не лише повторюється в пам'яті і губиться при перезапуску процесу.
- Якщо порядок реально важливий (наприклад, події переходу стану), попроси конкретно оцінити, чи паралельна доставка між підписниками все ще зберігає порядок на кожного підписника, навіть якщо загальна пропускна здатність паралелізована.
