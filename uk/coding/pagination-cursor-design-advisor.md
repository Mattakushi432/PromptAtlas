## Опис
Проєктує схему пагінації на основі курсора для конкретного патерну доступу до даних — кодування курсора, розв'язання нічиїх і стабільність під конкурентними вставками/видаленнями — перед запуском ендпоінта. Відрізняється від `api-contract-consistency-reviewer`, що перевіряє узгоджене застосування стилю пагінації наявного API по ендпоінтах, а не те, як спроєктувати реальну механіку нового курсора з нуля.

## Коли використовувати
- Будуєш новий ендпоінт зі списком з пагінацією і вирішуєш між offset і курсорною пагінацією.
- Уже обрав курсорну пагінацію і треба спроєктувати, що саме кодує курсор.
- Список з пагінацією показує дублікати чи пропущені елементи, коли рядки вставляються/видаляються, поки користувач гортає сторінки.

## Промпт

```
Ти проєктуєш реальну механіку схеми пагінації на основі курсора для конкретного ендпоінта — не просто рекомендуєш "використай курсорну пагінацію" як категорію, а конкретний дизайн того, що містить курсор і як він поводиться.

Порядок сортування (за чим сортується список): {{SORT_ORDER}}

Мутабельність даних (необов'язково — як часто рядки вставляються чи видаляються в цьому наборі даних, поки користувач реалістично може гортати сторінки, наприклад, здебільшого статичний каталог vs. живий стрічковий фід): {{DATA_MUTABILITY}}

Спроєктуй:
1. Що має кодувати курсор — зазвичай значення ключа сортування останнього елемента поточної сторінки плюс розв'язувач нічиї (унікальний, стабільний ID), а не просто offset/індекс, щоб пагінація залишалась стабільною, коли рядки вставляються чи видаляються деінде в наборі (схема на основі offset пропускає чи дублює елементи під конкурентними мутаціями; правильно спроєктований курсор — ні).
2. Явне розв'язання нічиї, якщо основний ключ сортування не гарантовано унікальний — наприклад, сортування за `created_at`, де кілька рядків можуть мати точно той самий таймстамп; без розв'язувача нічиї рядки з ідентичними значеннями ключа сортування можуть пропускатись чи дублюватись між сторінками.
3. Що відбувається з пагінацією користувача, якщо рядки вставляються чи видаляються попереду його поточної позиції курсора під час гортання, з огляду на {{DATA_MUTABILITY}} — вкажи реальну гарантію, яку дає цей дизайн (наприклад, "правильно закодований курсор не пропустить і не продублює раніше побачені елементи, але новий вставлений елемент попереду курсора може або не може з'явитись залежно від того, де він сортується відносно позиції курсора — вкажи яке саме").
4. Чи має курсор бути непрозорим (наприклад, base64-кодований, не призначений для парсингу чи конструювання клієнтом), щоб внутрішнє кодування могло змінюватись пізніше без зламу споживачів API, які інакше могли б стати залежними від його буквальної структури.

Виведи: дизайн курсора (що він кодує і як конструюється/декодується), конкретний приклад значення курсора і що він представляє, і явне твердження про те, яку гарантію стабільності це дає при описаній мутабельності даних.

Якщо {{SORT_ORDER}} не на індексованій колонці, познач це як окрему проблему продуктивності, незалежну від самого дизайну пагінації — коректність курсорної пагінації не виправляє відсутній індекс, і неіндексоване сортування буде повільним незалежно від того, наскільки добре спроєктований курсор.
```

## Змінні
- `{{SORT_ORDER}}` — за чим сортується список з пагінацією. Обов'язково.
- `{{DATA_MUTABILITY}}` — як часто змінюються базові дані, поки користувач може гортати сторінки. Необов'язково; без нього дизайн за замовчуванням припускає значущу мутабельність і проєктує на стабільність незалежно.

## Приклад
**Вхід:** `{{SORT_ORDER}}` = "сортовано за `created_at` спадаюче (найновіші першими)", `{{DATA_MUTABILITY}}` = "живий стрічковий фід — нові рядки вставляються постійно, наявні рядки ніколи не видаляються".

**Вихід (фрагмент):**
```
Кодування курсора: курсор має кодувати (created_at, id) останнього елемента поточної сторінки — самого лише created_at недостатньо, оскільки кілька подій активності можуть мати той самий таймстамп при високій швидкості вставки, тож id слугує розв'язувачем нічиї (за умови, що id — монотонно зростаюче чи інакше стабільне унікальне значення). Приклад курсора (до непрозорого кодування): {"created_at": "2026-08-30T14:22:01.500Z", "id": 48213} — закодуй цей JSON у base64, щоб клієнт трактував його як непрозорий токен.

Побудова запиту: запит наступної сторінки стає `WHERE (created_at, id) < (:cursor_created_at, :cursor_id) ORDER BY created_at DESC, id DESC LIMIT :page_size` — саме складене порівняння (а не дві окремі умови WHERE) правильно обробляє випадок розв'язання нічиї.

Гарантія стабільності: оскільки це фід лише-на-вставку (за заявленою мутабельністю даних), сортований найновіші-першими, нові рядки завжди вставляються "попереду" (новіші за) будь-яку позицію курсора, яку зараз тримає користувач — користувач, що гортає назад у часі, ніколи не побачить дублікат чи не пропустить раніше побачений елемент, і не побачить, як щойно вставлені елементи ретроактивно з'являються на вже отриманих сторінках, оскільки ті сторінки завжди містять лише елементи, старіші за курсор на момент отримання.

Примітка про індексацію: цей дизайн пагінації вимагає складеного індексу на (created_at, id) для хорошої продуктивності — підтверди наявність цього індексу, оскільки неіндексоване сортування на великій, постійно зростаючій таблиці фіду буде повільним незалежно від того, наскільки коректна вищеописана логіка курсора.
```

## Поради та варіації
- Для здебільшого статичного набору даних ({{DATA_MUTABILITY}} вказує на низьку мутацію) гарантії коректності мають менше практичного значення, але дизайн під них все одно коштує мало додатково і убезпечує ендпоінт на майбутнє, якщо припущення про мутабельність пізніше зміняться.
- Якщо API потребує двонапрямної пагінації (і "наступний", і "попередній"), попроси явно розглянути, чи те саме кодування курсора чисто підтримує реверс напрямку, чи потрібно повертати окремий "попередній курсор" разом із "наступним курсором" у відповіді кожної сторінки.
