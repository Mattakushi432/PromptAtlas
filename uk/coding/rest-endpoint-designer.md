## Опис
Проєктує набір REST-ендпойнтів — методи, шляхи, статус-коди, форми запиту/відповіді — з опису фічі простою мовою. Для старту нової API-поверхні з нуля, не для рев'ю чи документування наявної.

## Коли використовувати
- Старт нової фічі, якій потрібне REST API, з бажанням отримати міцний перший чернетковий варіант контракту ендпойнтів перед написанням коду реалізації.
- Узгодження фронтенд- і бекенд-команди щодо форми API перед тим, як будь-яка сторона почне будувати.
- Рев'ю того, чи запропонований набір ендпойнтів послідовно дотримується конвенцій REST перед релізом.

## Промпт

```
Ти проєктуєш REST API ендпойнти з опису фічі. Видавай конкретний контракт ендпойнтів, а не прозу з описом загальних принципів REST.

Опис фічі: {{FEATURE_DESCRIPTION}}
Наявні конвенції API для дотримання (необов'язково — напр., структура URL, патерн автентифікації, стиль пагінації, вже використовувані деінде): {{EXISTING_CONVENTIONS}}
Вподобання іменування ресурсів (необов'язково): {{NAMING_PREFERENCES}}

Інструкції:
1. Визнач ресурс(и), що випливають з фічі, і моделюй ендпойнти навколо ресурсів та їхніх зв'язків, використовуючи іменники в URL (не дієслова) і стандартні HTTP-методи для дій (GET/POST/PUT/PATCH/DELETE).
2. Для кожного ендпойнта вкажи: метод, шлях (з позначеними параметрами шляху), призначення одним рядком, форму тіла запиту (якщо застосовно), форму тіла відповіді, і повний набір реалістичних статус-кодів (не лише 200 — включи фактичні випадки помилок, з якими ця операція може зіткнутися: 400 валідація, 401/403 автентифікація, 404 не знайдено, 409 конфлікт де застосовно, 422 для семантичних помилок валідації).
3. Обробляй колекції правильно: ендпойнти списків мають підтримувати пагінацію (вкажи стиль пагінації — курсорну чи offset — і чому, з урахуванням ймовірного розміру/патерну доступу ресурсу), і параметри фільтрації/сортування, якщо фіча це передбачає.
4. Будь послідовним щодо форми обгортки відповіді у всіх ендпойнтах (або завжди обгортай у конверт з метаданими, або ніколи — не змішуй).
5. Якщо надано {{EXISTING_CONVENTIONS}}, дотримуйся їх точно, а не переходь до загальних best practices REST там, де вони конфліктують.
6. Познач будь-яку частину опису фічі, неоднозначну щодо володіння ресурсом чи кардинальності (напр., "чи може користувач мати кілька X, чи рівно один?"), замість того щоб мовчки обирати одну інтерпретацію.
7. Познач будь-який ендпойнт, що не вписується чисто в ресурсну модель REST (дія, більше схожа на RPC-виклик, напр., "надіслати лист скидання пароля"), і спроєктуй її як дію під-ресурсу (`POST /users/{id}/password-reset`), а не форсуй незграбну ресурсну форму.

Формат виводу: таблиця чи список Markdown, один запис на ендпойнт, у порядку, в якому клієнт зазвичай їх використовує (create → read → update → delete, колекція перед елементом де релевантно).
```

## Змінні
- `{{FEATURE_DESCRIPTION}}` — що фіча має дозволяти робити користувачам/клієнтам. Обов'язково.
- `{{EXISTING_CONVENTIONS}}` — усталені патерни API (автентифікація, пагінація, форма конверта, версіонування). Необов'язково, але тримає нові ендпойнти узгодженими з наявними.
- `{{NAMING_PREFERENCES}}` — стиль іменування ресурсів, якщо в команди є свій (множинні іменники, конкретний регістр тощо). Необов'язково.

## Приклад
**Вхід:** `{{FEATURE_DESCRIPTION}}` = "користувачі можуть створювати, переглядати і скасовувати підписки на доставку їжі; кожен користувач може мати максимум одну активну підписку".

**Вихід (фрагмент):**
```
| Метод | Шлях | Призначення | Тіло запиту | Успіх | Помилки |
|---|---|---|---|---|---|
| POST | /users/{userId}/subscription | Створити нову підписку | `{ planId, deliveryDay }` | 201 + об'єкт підписки | 400 (невалідний план), 401, 409 (у користувача вже є активна підписка) |
| GET | /users/{userId}/subscription | Отримати активну підписку користувача | — | 200 + об'єкт підписки, або 404, якщо немає | 401, 403 |
| DELETE | /users/{userId}/subscription | Скасувати активну підписку | — | 204 | 401, 404 (немає активної підписки для скасування) |
```

## Поради та варіації
- Для публічного API попроси явно додати заголовки rate-limit і стратегію версіонування до контракту.
- Якщо команда використовує GraphQL замість цього, цей промпт не переноситься напряму — див. промпт дизайну схеми натомість; ресурсно-дієслівна модель REST не мапиться на модель запит/мутація GraphQL.
