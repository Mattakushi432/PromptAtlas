## Опис
Генерує реальні скрипти налаштування і конфіги, які новий розробник запускає, щоб отримати робоче локальне середовище — а не текстовий документ. Відрізняється від онбординг-гайду по всьому репозиторію: тут результат — це виконувані інструменти бутстрапу (скрипти, `.env.example`, крок верифікації), а не документація процесу чи культури.

## Коли використовувати
- Онбординг досі виглядає як "спитай когось у Slack, як це запустити локально".
- Стандартизація локального налаштування в команді, де в кожного середовище розповзлося по-своєму.
- Перед написанням повного онбординг-гайду, щоб спочатку вирішити технічний бутстрап.

## Промпт

```
Ти — інженер з developer experience, що створює виконувані інструменти для налаштування локального середовища, а не текстовий гайд.

Опис стеку (мови/рантайми, сервіси, бази даних, необхідні змінні середовища): {{STACK_DESCRIPTION}}

Цільові операційні системи для підтримки: {{OS_TARGETS}}

Наявні нотатки з налаштування (необов'язково — будь-які неформальні інструкції, що вже існують, навіть неповні): {{EXISTING_SETUP_NOTES}}

Створи:
1. Скрипт бутстрапу (або набір скриптів, по одному на ОС за потреби), що: перевіряє/встановлює потрібні версії інструментів, піднімає локальні сервіси відповідно до стеку (переважно через Docker Compose, якщо підходить), і гучно падає з чітким повідомленням, якщо якоїсь передумови бракує, замість того щоб тихо продовжувати.
2. Файл `.env.example`, що перелічує кожну обов'язкову змінну середовища з коментарем inline, що пояснює її призначення і де взяти реальне значення (навіть якщо це "спитай колегу про спільні dev-креденшли").
3. Крок верифікації — одна команда, яку новий розробник може запустити, щоб реально підтвердити, що середовище працює (наприклад, звертається до health-ендпоінта, запускає smoke-тест), а не просто "команди встановлення завершились з кодом 0".
4. Явний список "чого це НЕ автоматизує" — все, що вимагає людської дії (запит доступу до сховища секретів, приєднання до Slack-каналу, додавання в хмарний акаунт), треба позначити як ручний крок, а не видавати за автоматизований.

Якщо стек має ОС-специфічні залежності (нативні скомпільовані бібліотеки, платформо-специфічні інструменти), явно розгалуж логіку скрипта по ОС і скажи про це — не видавай мовчки скрипт, що працює лише на одній платформі, стверджуючи підтримку всіх {{OS_TARGETS}}.
```

## Змінні
- `{{STACK_DESCRIPTION}}` — мови/рантайми, сервіси, бази даних і необхідні змінні середовища. Обов'язково.
- `{{OS_TARGETS}}` — які операційні системи має підтримувати налаштування (наприклад, "лише macOS і Linux", "macOS, Linux і Windows через WSL"). Обов'язково.
- `{{EXISTING_SETUP_NOTES}}` — наявні неформальні інструкції з налаштування, на яких можна побудувати результат замість початку з нуля. Необов'язково.

## Приклад
**Вхід:** `{{STACK_DESCRIPTION}}` = "Node.js 20 API, PostgreSQL 15, Redis, потрібні DATABASE_URL, REDIS_URL, JWT_SECRET", `{{OS_TARGETS}}` = "macOS і Linux".

**Вихід (фрагмент):**
```
#!/usr/bin/env bash
set -euo pipefail

command -v node >/dev/null || { echo "Потрібен Node.js 20 — встанови через nvm"; exit 1; }
...

docker compose up -d postgres redis

# .env.example
DATABASE_URL=postgres://dev:dev@localhost:5432/app_dev   # локальний Postgres з docker-compose; дій не потрібно
JWT_SECRET=                                                # спитай колегу про спільний dev JWT secret — не генеруй свій, токени мають бути перевірні для всіх локальних середовищ команди

Верифікація: запусти `npm run dev:healthcheck` — це звертається до GET /health і підтверджує, що і Postgres, і Redis доступні, а не просто що процес запустився.

НЕ автоматизує: додавання до спільного 1Password vault команди для JWT_SECRET; VPN-доступ, якщо API має звертатись до staging-сервісу.
```

## Поради та варіації
- Для полігльотного монорепо попроси створити один верхньорівневий bootstrap-скрипт, що делегує до скриптів налаштування кожного сервісу, замість одного монолітного скрипта.
- Передай реальний `.env` команди (зі значеннями, прихованими, але ключами на місці) як `{{EXISTING_SETUP_NOTES}}`, щоб згенерований `.env.example` не пропустив жодної змінної.
