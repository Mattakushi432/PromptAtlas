## Опис
Розшифровує мобільний краш-звіт (iOS crash report, Android ANR/tombstone, символізований чи ні) і пропонує ймовірні причини — специфічні для мобільних платформ формати крашів і режими відмов, відмінні від загальних серверних/мовних трейсів у «Розшифровувачі стек-трейсів». Для реального краша, який мобільному розробнику потрібно провести через триаж.

## Коли використовувати
- Прийшов краш-звіт з інструмента звітності про краші (Crashlytics, Sentry, App Store Connect), і потрібна інтерпретація перед тим, як взагалі можна почати дебаг.
- Символізація неповна чи недоступна, і потрібно працювати з частково читабельним нативним стек-трейсом.
- Триаж пачки краш-звітів, щоб зрозуміти, які з них насправді та сама першопричина проти окремих проблем.

## Промпт

```
Ти розшифровуєш мобільний краш-звіт і визначаєш ймовірні першопричини — враховуючи специфічні для мобільних платформ типи й формати крашів, а не трактуючи це як загальний стек-трейс.

Краш-звіт/лог: {{CRASH_LOG}}
Платформа: {{PLATFORM}}
Контекст застосунку (відповідний код поруч з крашем, якщо доступний): {{RELEVANT_CODE}}

Інструкції:
1. Визнач тип краша і що він фундаментально означає: для iOS розрізняй виняток Swift/Objective-C (EXC_CRASH, часто примусове розгортання nil, вихід за межі масиву, чи неперехоплений NSException) від нативного краша, пов'язаного з пам'яттю (EXC_BAD_ACCESS, часто use-after-free чи висячий вказівник, особливо в коді, що торкається мостування Objective-C чи небезпечних вказівників); для Android розрізняй необроблений виняток Java/Kotlin (видимий у звичайному стек-трейсі) від нативного краша (tombstone, що потребує NDK-символізації) від ANR (Application Not Responding — головний потік був заблокований, не краш як такий).
2. Пройдися по стек-трейсу від фрейму краша вниз (чи вгору, за конвенцією платформи), пояснюючи, що робив кожен фрейм, і зазнач, чи символізація виглядає неповною (сирі адреси пам'яті замість назв функцій) — скажи, що потрібно для повної символізації (файл dSYM для iOS, відповідні NDK-символи для Android), якщо це явно відсутнє.
3. Для краша, пов'язаного з nil/null, визнач конкретну змінну/властивість, що була nil, і поміркуй чому, на основі показаного шляху коду — краш через примусове розгортання чи оператор `!!` потребує розгляду фактичної логіки обробки опціоналів, не просто рефлекторної відповіді "додай перевірку на nil".
4. Для краша, пов'язаного з тредингом (оновлення UI з фонового потоку, гонка станів на спільному стані), визнач конкретне порушення потокобезпеки, що випливає зі стек-трейсу.
5. Конкретно для ANR поміркуй, що блокує головний потік — синхронний мережевий виклик, важке обчислення, конкуренцію за блокування — а не трактуй це як стек-трейс краша.
6. Ранжуй ймовірні причини за тим, наскільки добре вони відповідають конкретним доказам у логу, і скажи, які додаткові дані (довший стек-трейс, частота краша/розподіл по пристроях, хлібні крихти, що ведуть до нього) допомогли б підтвердити топову гіпотезу.

Формат виводу: Markdown з розділами: Тип краша, Розбір стек-трейсу, Імовірні причини (ранжовано), Наступні кроки.
```

## Змінні
- `{{CRASH_LOG}}` — текст краш-звіту/логу. Обов'язково.
- `{{PLATFORM}}` — "iOS" чи "Android" (і версія, якщо релевантно). Обов'язково — формати крашів і типові причини суттєво різняться.
- `{{RELEVANT_CODE}}` — вихідний код поруч з місцем краша, якщо стек-трейс можна зіставити з ним. Необов'язково, але різко покращує точність діагнозу.

## Приклад
**Вхід:** `{{PLATFORM}}` = "iOS", `{{CRASH_LOG}}` = краш EXC_BAD_ACCESS всередині completion handler'а, що захоплює `self` і звертається до властивості після ймовірного вивільнення view controller'а.

**Вихід (фрагмент):**
```
## Тип краша
EXC_BAD_ACCESS — порушення доступу до пам'яті, не виняток рівня Swift. Це зазвичай означає, що код звернувся до вже вивільненої пам'яті (висяче посилання), що поширено в асинхронних completion handler'ах, які захоплюють `self` без належної обробки часу життя.

## Імовірні причини (ранжовано)
1. **Найімовірніше:** completion handler сильно захоплює `self` і викликається після вивільнення view controller'а (напр., користувач перейшов геть до завершення асинхронного виклику), і handler потім звертається до властивості на тепер невалідному `self`.

## Наступні кроки
- Перевір, чи completion handler використовує `[weak self]` і чи належно захищається від nil `self` перед використанням.
- Якщо він уже використовує `[weak self]`, шукай інше висяче посилання в тому самому scope (захоплений делегат, захоплений closure-локальний об'єкт), а не сам `self`.
```

## Поради та варіації
- Для пачки схожих краш-звітів попроси визначити, чи вони мають спільну першопричину на основі схожості стек-трейсу, щоб уникнути триажу того самого бага кілька разів під різними ID звіту.
- Якщо краш-лог повністю несимволізований (лише сирі hex-адреси) і dSYM/символи недоступні, будь явним, що діагноз моделі неминуче обмежений — запитай, що пріоритезувати виправити на боці тулінгу (налагодження символізації), перш ніж подальший аналіз логу стане корисним.
