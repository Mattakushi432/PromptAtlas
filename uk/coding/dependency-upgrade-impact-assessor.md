## Опис
Оцінює вплив breaking changes при мажорному оновленні версії залежності відносно того, як вона реально використовується в кодбейзі, і формує план оновлення. Для планових мажорних оновлень — відрізняється від `dependency-cve-triage`, що тріажує ризик безпеки конкретної відомої вразливості, а не заплановане підвищення версії.

## Коли використовувати
- Плануєш мажорне оновлення версії ключового фреймворка чи бібліотеки.
- Вирішуєш, чи безпечно зробити оновлення в одному PR, чи потрібно поетапно через проміжні версії.
- Оцінюєш обсяг ручного тестування, реально потрібний для оновлення, порівняно з тим, що спіймають інструменти автоматично.

## Промпт

```
Ти оцінюєш вплив оновлення залежності через межу мажорної версії, спираючись на те, як вона реально використовується в цьому кодбейзі — а не загальне резюме "ось що змінилось".

Залежність: {{DEPENDENCY_NAME}}
Поточна версія: {{CURRENT_VERSION}}
Цільова версія: {{TARGET_VERSION}}
Контекст використання (як залежність реально використовується в кодбейзі — ключові API, що викликаються, патерни, на які покладаються): {{USAGE_CONTEXT}}

Якщо в тебе є надійні знання про breaking changes саме цього оновлення, використай їх. Якщо не впевнений щодо точних breaking changes для цього конкретного діапазону версій, скажи це явно і попроси вставити changelog/migration guide, замість того щоб вигадувати правдоподібно звучні breaking changes для версії бібліотеки, яку насправді не знаєш впевнено.

З огляду на breaking changes (відомі чи надані):
1. Зістав кожну breaking change з {{USAGE_CONTEXT}} — познач ті, що реально стосуються того, як цей кодбейз використовує залежність, і явно зазнач, які задокументовані breaking changes НЕ стосуються, бо цей кодбейз не використовує той API/патерн.
2. Запропонуй послідовність оновлення — чи стрибати напряму до {{TARGET_VERSION}}, чи проходити через проміжні версії (релевантно, коли власні migration guide залежності рекомендують поступове оновлення для великих стрибків версій).
3. Класифікуй, що потребує ручного тестування, а що, ймовірно, спіймає type-checker, лінтер чи тестовий набір автоматично — це визначає, скільки часу закладати на ручну верифікацію.

Виведи: список breaking changes "стосується цього кодбейзу" (з тими, що не стосуються, явно виключеними, а не тихо пропущеними — зазнач, що їх перевірили і виключили), потім рекомендацію послідовності, потім оцінку обсягу тестування.
```

## Змінні
- `{{DEPENDENCY_NAME}}` — залежність, що оновлюється. Обов'язково.
- `{{CURRENT_VERSION}}` / `{{TARGET_VERSION}}` — діапазон версій для оновлення. Обов'язково.
- `{{USAGE_CONTEXT}}` — як залежність реально використовується в кодбейзі (ключові API, патерни, конфігурація). Обов'язково — саме це перетворює загальний changelog на оцінку впливу, специфічну для кодбейзу.

## Приклад
**Вхід:** `{{DEPENDENCY_NAME}}` = "React", `{{CURRENT_VERSION}}` = "17", `{{TARGET_VERSION}}` = "18", `{{USAGE_CONTEXT}}` = "використовує ReactDOM.render у корені застосунку, немає використання React.Suspense чи lazy-компонентів, немає сторонніх бібліотек класових компонентів з відомими несумісностями, використовує React Testing Library для тестів".

**Вихід (фрагмент):**
```
Стосується цього кодбейзу:
- `ReactDOM.render` депрекейтний на користь `createRoot` — цей кодбейз використовує його в корені застосунку, тож ця зміна обов'язкова, а не опціональна рутина. Виправлення механічне (заміна кореневого API), але змінює поведінку рендерингу (автоматичний батчинг застосовується ширше), і саме це варте ручного тестування.
- Зміни автоматичного батчингу: оновлення стану в промісах/таймаутах/нативних обробниках подій тепер батчаться за замовчуванням, чого не було в React 17. З огляду на те, що не згадано явне покладання на синхронний таймінг ре-рендеру після оновлення стану, це пункт "перевір це, не вважай безпечним за замовчуванням", а не відомо-безпечна зміна.

Виключено (перевірено, не стосується тут): зміна поведінки повторного призупинення Suspense в React 18 (межа, що призупиняється знову після того, як уже розрішилась, тепер повністю розмонтовує і перемонтовує своє піддерево, а не просто ховає його) — контекст використання стверджує, що Suspense/lazy-компоненти не використовуються, тож ця конкретна зміна поведінки тут ні на що не впливає.

Послідовність: пряме оновлення до 18 тут розумне — власний шлях оновлення React не вимагає проміжної версії для стрибка 17→18, на відміну від деяких фреймворків з більшими стрибками.

Обсяг тестування: type-checker/лінтер спіймає видалення API `ReactDOM.render` автоматично (не скомпілюється). Зміни поведінки автоматичного батчингу НЕ будуть спіймані типами — це потребує ручного/дослідницького тестування конкретно навколо коду, що читає стан одразу після тригера оновлення всередині таймауту чи callback проміса.
```

## Поради та варіації
- Встав реальний migration guide чи changelog залежності напряму в промпт разом з `{{USAGE_CONTEXT}}` для будь-якого оновлення, де точність breaking changes справді важлива — це прибирає залежність від того, чи власні знання моделі актуальні і повні.
- Для монорепо з багатьма внутрішніми споживачами залежності запускай це окремо для `{{USAGE_CONTEXT}}` кожного споживача, а не один прохід на весь репозиторій — різні частини великого кодбейзу часто зачіпаються зовсім різними підмножинами breaking changes.
