## Опис
Проєктує скрипт заповнення даними (seed), що наповнює локальне чи демо-середовище реалістичним, референційно узгодженим обсягом даних. Відрізняється від `test-fixture-generator`, що генерує невеликі, прицільні тестові дані для одного конкретного unit/integration тесту: це для наповнення цілого середовища для ручного дослідження, демо чи локальної розробки, у більшому масштабі, зі збереженими зв'язками між таблицями.

## Коли використовувати
- Свіже локальне середовище стартує повністю порожнім, і ручне введення даних, щоб зробити його придатним для роботи, виснажливе.
- Готуєш демо-середовище, яке має виглядати справді реалістично, а не просто технічно непорожнім.
- Онбординг — поєднуй це з налаштуванням середовища від `local-env-bootstrap-generator`, щоб новий розробник отримав наповнене середовище, а не лише запущене.

## Промпт

```
Ти проєктуєш скрипт заповнення даними для локального чи демо-середовища — не прицільну фікстуру для одного конкретного тесту, і не міграцію продакшн-даних.

Опис схеми (таблиці/моделі та їхні зв'язки): {{SCHEMA_DESCRIPTION}}

Потреби в обсязі та реалістичності (скільки даних потрібно, і чи має воно виглядати справді реалістично для демо-аудиторії, чи просто бути непорожнім для розробки): {{VOLUME_AND_REALISM_NEEDS}}

Спроєктуй скрипт заповнення (чи опиши його структуру достатньо чітко для реалізації), що:
1. Створює записи в порядку залежностей — батьки перед дітьми, з дотриманням обмежень foreign key, а не сподіванням, що база даних мовчки все впорядкує.
2. Генерує внутрішньо узгоджені дані — позиції замовлення посилаються на продукти, що реально існують у заповненому наборі продуктів; замовлення користувача посилаються на того самого заповненого користувача; жодних осиротілих чи висячих посилань.
3. Достатньо варіює дані, щоб охопити реалістичні стани, а не N ідентичних щасливих записів — включи порожні стани (користувач без замовлень), великі колекції (користувач з багатьма замовленнями) і достатньо варіативності у значеннях полів, щоб середовище не виглядало штучно однорідним.
4. Ідемпотентний і безпечно повторно запускний — повторний запуск проти вже заповненої бази даних не має провалюватись на порушеннях унікальних обмежень чи тихо створювати дублікати даних; він має або пропускати наявні записи, або явно очищати і перезаповнювати, і вкажи, який підхід використовується.

Виведи: структуру скрипта заповнення (реальний код, якщо цільова мова/ORM зрозумілі з `{{SCHEMA_DESCRIPTION}}`, інакше чіткий псевдокод), плюс коротку примітку про те, що конкретно робить згенеровані дані реалістичними, а не просто наявними.

Якщо схема має справді велику кількість взаємозалежних таблиць, запропонуй заповнення в явних, названих фазах, впорядкованих за залежностями (наприклад, "фаза 1: користувачі і продукти, без залежностей; фаза 2: замовлення, залежить від фази 1"), а не один плаский, недиференційований скрипт — це набагато полегшує дебаг часткових збоїв.
```

## Змінні
- `{{SCHEMA_DESCRIPTION}}` — таблиці/моделі та їхні зв'язки. Обов'язково.
- `{{VOLUME_AND_REALISM_NEEDS}}` — скільки даних і наскільки реалістичними вони мають виглядати. Обов'язково — швидкий сід лише для розробки і демо для стейкхолдерів мають дуже різну планку.

## Приклад
**Вхід:** `{{SCHEMA_DESCRIPTION}}` = "users, products, orders (належить user), order_items (належить order, посилається на product)", `{{VOLUME_AND_REALISM_NEEDS}}` = "має виглядати реалістично для sales-демо — приблизно 20 користувачів, 50 продуктів, варіативна історія замовлень".

**Вихід (фрагмент):**
```
Фаза 1 (без залежностей): заповни 50 продуктів з варіативними назвами/цінами/категоріями — уникай неймінгу "Product 1", "Product 2", оскільки це демо для клієнта; використай реалістично звучний генератор назв чи курований статичний список.

Фаза 2 (залежить від фази 1): заповни 20 користувачів, потім для кожного згенеруй варіативну кількість замовлень (зваж у бік 2-5 замовлень на користувача, але включи щонайменше 2 користувачів з нулем замовлень і 1 "потужного користувача" з 15+ замовленнями, щоб демо показувало реалістичний розподіл, а не однорідні дані).

Фаза 3 (залежить від фази 2): для кожного замовлення згенеруй 1-4 order_items, що посилаються лише на продукти з набору фази 1 — ніколи на випадково згенерований ID продукту, який може не існувати.

Ідемпотентність: цей скрипт перевіряє наявність запису-маркера сіду перед виконанням і завершується раніше з повідомленням, якщо вже заповнено, а не або провалюється на дублікатних унікальних обмеженнях, або тихо подвоює дані — повторний запуск вимагає явного флага `--reset`, що навмисно очищає і перезаповнює.
```

## Поради та варіації
- Для демо-середовища конкретно попроси також реалістично варіювати таймстампи (замовлення розкидані по останніх кількох місяцях, а не всі створені точно в момент запуску сіду) — набір даних з повністю ідентичними таймстампами — поширена ознака того, що дані заповнені, а не реальні.
- Поєднуй напряму з `local-env-bootstrap-generator` — той промпт налаштовує працююче середовище; цей його наповнює, і обидва результати можна з'єднати в один скрипт налаштування.
