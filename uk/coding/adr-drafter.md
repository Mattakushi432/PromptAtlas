## Опис
Перетворює хаотичне обговорення рішення (тред у Slack, нотатки зі зустрічі, чорновий запис) на формальний Architecture Decision Record — для рішення, яке вже ухвалене і потребує належного документування, а не для зважування опцій, які досі відкриті.

## Коли використовувати
- Команда щойно ухвалила підхід на зустрічі/в треді, і хтось має записати це, поки контекст не втрачено.
- Онбординг нового члена команди з бажанням заднім числом заповнити ADR для минулого рішення, яке ніколи не було формально зафіксоване.
- Стандартизація розкиданого обґрунтування рішень (в описах PR, Slack, усних знаннях команди) у журнал ADR команди.

## Промпт

```
Ти укладаєш формальний Architecture Decision Record (ADR) із сирого обговорення нижче. Рішення вже ухвалене — твоя робота — чітко його задокументувати, а не переосмислювати чи переоцінювати опції.

Сире обговорення/нотатки (нотатки зі зустрічі, тред, чорновий запис): {{RAW_DISCUSSION}}
Шаблон ADR для дотримання (необов'язково, інакше використай стандартний формат Context/Decision/Consequences): {{ADR_TEMPLATE}}
Номер/назва ADR (необов'язково): {{ADR_ID_AND_TITLE}}

Інструкції:
1. Виведи фактичне ухвалене рішення — сформулюй його як одне чітке декларативне речення, а не підсумок дебатів.
2. Напиши розділ Context: яка проблема/які сили призвели до потреби в цьому рішенні, написано так, щоб хтось із нульовим фоном щодо обговорення зрозумів, чому це було важливо. Включи релевантні обмеження (технічні, командні, часові), що сформували рішення.
3. Напиши розділ Decision: що було вирішено, сформульовано просто й достатньо конкретно, щоб бути дієвим.
4. Напиши розділ Consequences: і позитивні, і негативні — що це рішення спрощує, що ускладнює чи закриває, і будь-які відомі ризики чи борг, свідомо прийняті. Не перелічуй лише плюси; рішення без перелічених компромісів — червоний прапорець, що аналіз був неповним.
5. Переліч альтернативи, які розглядалися й були відхилені, з реченням-причиною для кожної, чому їх не обрали — навіть якщо сире обговорення згадує їх лише коротко, зафіксуй те, що є, а не пропускай їх.
6. Якщо сире обговорення залишає фактичне рішення неоднозначним (люди обговорювали опції, але фінальний вибір чітко не сформульований), прямо про це скажи, замість того щоб вгадувати, яка опція "перемогла".
7. Використовуй нейтральну, фактичну мову — ADR є історичним записом, а не переконливою презентацією на користь рішення.

Формат виводу: Markdown за шаблоном ADR (Title, Status, Context, Decision, Consequences, Alternatives Considered).
```

## Змінні
- `{{RAW_DISCUSSION}}` — неструктурований вихідний матеріал, що документує рішення. Обов'язково.
- `{{ADR_TEMPLATE}}` — конкретний формат ADR для дотримання, якщо в команди є свій. Необов'язково.
- `{{ADR_ID_AND_TITLE}}` — номер/назва запису в журналі ADR команди. Необов'язково.

## Приклад
**Вхід:** `{{RAW_DISCUSSION}}` = тред у Slack, де команда обговорювала Postgres проти DynamoDB для нового сервісу і зупинилася на Postgres через наявну експертизу команди та потребу в складних join'ах, попри кращу горизонтальну масштабованість DynamoDB.

**Вихід (фрагмент):**
```markdown
## Decision
Ми будемо використовувати PostgreSQL як основне сховище даних для нового сервісу замовлень.

## Consequences
- Позитив: наявна операційна експертиза команди з Postgres знижує ризики онбордингу й чергування; складні звітні запити з join'ами між замовленнями, користувачами та складом прості.
- Негатив: горизонтальне масштабування запису вимагатиме більш свідомої роботи (read-репліки, згодом шардинг), ніж дала б DynamoDB з коробки; це прийнятий компроміс з урахуванням поточних прогнозів трафіку.

## Alternatives Considered
- **DynamoDB** — відхилено переважно через слабшу підтримку довільних реляційних запитів, потрібних для функції звітності, попри переваги в масштабованості.
```

## Поради та варіації
- Для легкої культури ADR попроси стислу версію по одному абзацу на розділ замість повного шаблону.
- Якщо сире обговорення включає кілька переплетених рішень, попроси розділити їх на окремі чернетки ADR, а не зливати непов'язані рішення в один запис.
