## Опис
Рецензує маніфест Kubernetes на типові неправильні конфігурації — відсутні ліміти ресурсів, слабкий security context, відсутні/неправильно налаштовані проби, обробка секретів — проти норм готовності до продакшену, не перевірка синтаксису YAML. Для маніфесту перед релізом у кластер.

## Коли використовувати
- Рев'ю нового маніфесту Deployment/StatefulSet/Pod перед застосуванням до продакшн-кластера.
- Аудит наявних маніфестів на прогалини безпеки чи надійності після інциденту, що виявився наслідком неправильної конфігурації.
- Онбординг команди в Kubernetes з бажанням застосувати систематичний чекліст до їхніх перших маніфестів замість вивчення прогалин важким шляхом.

## Промпт

```
Ти рецензуєш маніфест Kubernetes на проблеми готовності до продакшену — управління ресурсами, позиція безпеки, перевірка здоров'я, обробка секретів — не синтаксис YAML чи базову валідність.

Маніфест: {{MANIFEST}}
Контекст (необов'язково — напр., "це виконує stateless API", "це обробляє платежі"): {{WORKLOAD_CONTEXT}}

Інструкції:
1. Перевір requests/limits ресурсів: чи встановлені і `requests`, і `limits` для CPU і пам'яті? Відсутні requests означають, що планувальник не може розумно розмістити под; відсутні ліміти пам'яті ризикують тим, що под споживатиме необмежену пам'ять і буде непередбачувано вбитий OOM-кілером чи виснажуватиме сусідів. Познач будь-який контейнер узагалі без специфікації ресурсів як знахідку високого пріоритету.
2. Перевір security context: чи контейнер працює від root (без `runAsNonRoot`/`runAsUser`)? Чи `allowPrivilegeEscalation` залишений на дозвільному значенні за замовчуванням? Чи збережені непотрібні Linux-можливості замість скинутих (`drop: [ALL]` плюс лише конкретно потрібні можливості)? Чи кореневу файлову систему можна записувати, коли це не потрібно (`readOnlyRootFilesystem: true` де застосовно)?
3. Перевір проби здоров'я: чи присутній `livenessProbe` (без нього Kubernetes не може перезапустити зависший контейнер) і `readinessProbe` (без нього трафік може маршрутизуватися до пода, що насправді не готовий)? Перевір, чи таймінг проби (`initialDelaySeconds`, `periodSeconds`, `failureThreshold`) правдоподібний для навантаження — надто агресивна проба для повільно стартуючого застосунку спричиняє crash-loop перезапуски здорового застосунку.
4. Перевір обробку секретів: чи секрети реферуються через `secretKeyRef`/змонтовані томи секретів, а не захардкоджені як звичайні значення змінних середовища в маніфесті? Познач будь-яке значення, схоже на облікові дані, у звичайному блоці `env`.
5. Перевір на відсутню чи надто дозвільну конфігурацію service account: чи використовується конкретний ServiceAccount (не default з широкими правами), і якщо RBAC видимий, чи він обмежений тим, що навантаженню фактично потрібно?
6. Перевір кількість реплік і стратегію оновлення для всього, описаного як критичне для продакшену в {{WORKLOAD_CONTEXT}} — Deployment з однією реплікою для критичного сервісу є єдиною точкою відмови, а стратегія `Recreate` для сервісу, що потребує деплою без простою, спричиняє простій на кожному роловуті.
7. Для кожної знахідки дай конкретне виправлення YAML, не просто "додай ліміти ресурсів".

Формат виводу: Markdown, один запис на знахідку, згруповано за категорією (Ресурси / Безпека / Проби / Секрети / RBAC / Доступність), кожен з критичністю і конкретним виправленням YAML.
```

## Змінні
- `{{MANIFEST}}` — YAML маніфесту Kubernetes для рецензування. Обов'язково.
- `{{WORKLOAD_CONTEXT}}` — що робить навантаження і його критичність. Необов'язково, але уточнює оцінки критичності (відсутня readiness-проба платіжного сервісу серйозніша за таку в batch-завданні).

## Приклад
**Вхід:** `{{MANIFEST}}` = Deployment без блоку `resources`, без `securityContext`, і env-змінна `DATABASE_PASSWORD`, встановлена на значення у відкритому вигляді.

**Вихід (фрагмент):**
```
### Секрети — CRITICAL
`DATABASE_PASSWORD` встановлена як значення у відкритому вигляді в блоці `env`, видиме будь-кому з доступом на читання до маніфесту/специфікації пода (включно через `kubectl describe`).
Виправлення:
```yaml
env:
  - name: DATABASE_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-credentials
        key: password
```
(з фактичним значенням, збереженим в об'єкті `Secret`, ідеально отриманим із зовнішнього менеджера секретів, а не закомічене в репозиторій маніфестів.)

### Ресурси — HIGH
Не вказано `resources.requests`/`resources.limits` — планувальник не має основи для рішень щодо розміщення, і контейнер може споживати необмежену пам'ять.
Виправлення: додай явні requests/limits, розміром під фактичне спостережене використання навантаження, напр. `resources: { requests: { cpu: "100m", memory: "128Mi" }, limits: { cpu: "500m", memory: "256Mi" } }`.
```

## Поради та варіації
- Для Helm-чарту замість сирого маніфесту попроси рецензувати відрендерений вивід (`helm template`), а не самі шаблони чарту, оскільки значення за замовчуванням і перевизначення можуть маскувати фактично застосовану конфігурацію.
- Поєднуй з реальним виводом інструмента policy-as-code (OPA/Gatekeeper, Kyverno, kube-score) як додатковий контекст — цей промпт найсильніший у поясненні знахідок і пріоритезації їх за реальним впливом, не в заміні автоматизованого застосування політик.
