## Опис
Аудитує розмітку UI-компонента на проблеми доступності — семантичний HTML, використання ARIA, керованість з клавіатури, керування фокусом, контраст кольору там, де можна вивести — за WCAG, з виправленням для кожної знахідки. Для конкретного компонента, що рецензується, не аудиту всього сайту.

## Коли використовувати
- Рев'ю нового чи наявного компонента перед релізом, щоб виловити прогалини доступності, які суто візуальне рев'ю пропустило б.
- Користувач екранного диктора чи інструмент доступності позначив проблему, і потрібен систематичний прохід, щоб знайти пов'язані проблеми в тому самому компоненті.
- Вивчення найкращих практик доступності через їх застосування до реального коду, який ти написав, а не абстрактних гайдлайнів.

## Промпт

```
Ти аудитуєш розмітку UI-компонента на проблеми доступності за WCAG 2.1 AA, і надаєш конкретне виправлення для кожної знахідки — не лише цитату порушеного гайдлайну.

Код компонента (HTML/JSX/шаблон): {{COMPONENT_CODE}}
Призначення/модель взаємодії компонента (необов'язково, напр., "модальне вікно, що відкривається при кліку на кнопку"): {{COMPONENT_PURPOSE}}

Інструкції:
1. Перевір використання семантичного HTML: чи інтерактивні елементи є фактичними елементами `<button>`/`<a>`, а не `<div>` з обробником кліку? Чи правильна ієрархія заголовків? Чи списки/таблиці розмічені як такі, а не div-суп, стилізований під них?
2. Перевір використання ARIA: чи `role`/`aria-*` використовуються лише там, де семантичний HTML не може виразити патерн (кастомні віджети), і не надлишково на елементах з уже коректною нативною семантикою? Познач як відсутню ARIA там, де потрібна, ТАК і неправильну/надлишкову ARIA, яку екранний диктор оголосив би заплутано.
3. Перевір керованість з клавіатури: чи можна досягти й активувати кожен інтерактивний елемент лише клавіатурою (Tab, Enter/Space, Escape для контенту, що закривається, стрілки для складених віджетів на кшталт меню/вкладок)? Познач будь-яку взаємодію лише мишею (розкриття лише при наведенні, лише клік без клавіатурного еквівалента).
4. Перевір керування фокусом: для динамічного контенту (модальні вікна, дропдауни, зміни маршруту) чи фокус переходить на новий контент належним чином, і чи повертається в розумне місце, коли він закривається? Познач будь-які проблеми пастки фокусу чи втрату фокусу до `<body>`.
5. Перевір розмітку лейблів: чи кожне поле форми має асоційований, програмно зв'язаний лейбл (не лише візуальну близькість)? Чи мають кнопки лише з іконкою доступні назви (`aria-label` чи візуально приховний текст)?
6. Якщо колір/контраст можна оцінити з наданих значень CSS, познач недостатній контраст; якщо кольори не надані, зазнач, що контраст не можна було перевірити, а не мовчки пропускай категорію.
7. Для кожної знахідки дай конкретне виправлення коду, не просто "додай відповідні ARIA-атрибути".

Формат виводу: Markdown, один запис на знахідку, згруповано за категорією (Семантичний HTML / ARIA / Клавіатура / Фокус / Лейбли / Контраст), кожен з посиланням на критерій успіху WCAG, чому це важливо (конкретний вплив на користувача, не просто "це вимагається"), і виправленням.
```

## Змінні
- `{{COMPONENT_CODE}}` — розмітка компонента для аудиту. Обов'язково.
- `{{COMPONENT_PURPOSE}}` — що робить компонент і як з ним передбачається взаємодіяти. Необов'язково, але допомагає оцінити, чи правильно застосовані патерни ARIA для задуманого типу віджета.

## Приклад
**Вхід:** `{{COMPONENT_CODE}}` = кастомний дропдаун, побудований з `<div>` з обробниками `onClick`, без підтримки клавіатури, `{{COMPONENT_PURPOSE}}` = "дропдаун у стилі select для вибору країни".

**Вихід (фрагмент):**
```
### Клавіатура
FINDING — тригер дропдауна є `<div onClick={...}>` без обробника клавіатури; користувач лише з клавіатурою взагалі не може його відкрити.
WCAG 2.1.1 (Keyboard) — уся функціональність має бути керована через клавіатурний інтерфейс.
Вплив: користувачі клавіатури та екранних дикторів взагалі не можуть обрати країну — це повністю блокує фічу для них, а не незначна незручність.
Виправлення: використай елемент `<button>` (нативно фокусований і активований Enter/Space) замість `<div>`, або якщо div має залишитися, додай `tabIndex={0}`, `role="button"` і обробник `onKeyDown` для Enter/Space.
```

## Поради та варіації
- Далі попроси також згенерувати еквівалентні автоматизовані тестові асерти (напр., використовуючи `@testing-library` + `jest-axe`) для знахідок, які механічно тестовні.
- Для бібліотеки компонентів (не однієї сторінки) попроси пріоритезувати знахідки за тим, у скількох місцях застосунку компонент, ймовірно, перевикористовується, оскільки виправлення там має непропорційний вплив.
