## Опис
Проєктує, як споживач повідомлень має обробляти чергу недоставлених повідомлень (DLQ): що запускає переміщення повідомлення туди, які метадані для тріажу додати, як сповіщати про зростання DLQ, і безпечну процедуру повторного відтворення. На відміну від «Діагноста відставання черги завдань» (coding, вже випущений), що діагностує живе, зростаюче відставання повідомлень, які ще чекають на обробку, — цей промпт проєктує обробку повідомлень, обробка яких уже остаточно провалилась.

## Коли використовувати
- Будуєш нового споживача черги і хочеш спроєктувати його стратегію DLQ заздалегідь, а не виявляти, що повідомлення мовчки відкидаються чи нескінченно повторюються, коли щось піде не так у продакшні.
- У твоєї команди є DLQ, що накопичив повідомлення, для яких ніхто не має чіткого процесу тріажу чи повторного відтворення, і потрібен конкретний дизайн, щоб узяти це під контроль.
- Вирішуєш між «повторювати нескінченно», «мовчки відкидати» і «в DLQ» для конкретного типу збою і хочеш обґрунтовану рекомендацію, а не значення за замовчуванням.

## Промпт

```
Ти проєктуєш обробку черги недоставлених повідомлень (DLQ) для конкретного споживача повідомлень, зважаючи на його режими збоїв і операційні обмеження.

Споживач і тип повідомлень: {{CONSUMER_CONTEXT}}
Поточна поведінка повторів (якщо є): {{CURRENT_RETRY_BEHAVIOR}}
Типи збоїв, з якими може зіткнутись цей споживач: {{FAILURE_TYPES}}

Інструкції:
1. Рекомендуй конкретний тригер переміщення повідомлення в DLQ: максимальну кількість спроб повтору, і/чи конкретні типи помилок, що мають одразу потрапляти в DLQ без повторів (напр., збій валідації схеми, що ніколи не вдасться при повторі, проти тимчасового таймауту, що спершу мав би повторюватись). Явно розрізни отруйні повідомлення (ніколи не вдадуться) від тимчасових збоїв (можуть вдатись пізніше) в межах {{FAILURE_TYPES}}.
2. Вкажи, які метадані додавати до повідомлення в DLQ для тріажу: оригінальне повідомлення, причину/виняток збою, кількість зроблених спроб, мітки часу першої й останньої спроби, та версію споживача/деплою, що його обробляв — достатньо, щоб тому, хто робить тріаж пізніше, не довелось відновлювати контекст із логів.
3. Рекомендуй сповіщення: яка швидкість зростання чи абсолютна кількість DLQ мала б пейджити/сповіщати когось, і чи одне недоставлене повідомлення конкретної серйозності (напр., будь-що пов'язане з платежами) мало б сповіщати негайно, а не чекати порогу об'єму.
4. Спроєктуй безпечну процедуру повторного відтворення: як тріажоване, виправлене повідомлення повторно обробляється — повторно відтворюється індивідуально після ручного перегляду, повторно відтворюється масово лише після підтвердження, що корінна причина виправлена, і як повторне відтворення уникає повторного внесення того самого збою в цикл (напр., скидання лічильника спроб без усунення корінної причини).
5. Вкажи політику збереження/закінчення терміну для самого DLQ — як довго недоставлені повідомлення зберігаються перед архівуванням чи видаленням, щоб він не ріс мовчки необмежено, але й не відкидав повідомлення до того, як хтось встиг зробити тріаж.
6. Якщо {{CURRENT_RETRY_BEHAVIOR}} вказує на необмежені повтори без DLQ сьогодні, явно познач ризик: отруйне повідомлення, що повторюється нескінченно, може блокувати подальші повідомлення в FIFO-впорядкованій черзі чи мовчки споживати місткість воркерів нескінченно.

Формат виводу: Markdown із секціями: Тригер переміщення в DLQ, Метадані для додавання, Пороги сповіщення, Процедура повторного відтворення, Політика збереження. Заверши одним рядком-підсумком, що змінюється операційно порівняно з {{CURRENT_RETRY_BEHAVIOR}} сьогодні.
```

## Змінні
- `{{CONSUMER_CONTEXT}}` — що робить споживач і які повідомлення він обробляє. Обов'язково.
- `{{CURRENT_RETRY_BEHAVIOR}}` — наявна обробка повторів/збоїв, якщо є (напр., «немає DLQ, повторює нескінченно» чи «3 повтори, потім повідомлення відкидається»). Обов'язково — дизайн змінюється залежно від поточної прогалини.
- `{{FAILURE_TYPES}}` — відомі способи, якими обробка може провалитись для цього споживача (помилки валідації, таймаути далі за потоком, конфлікти даних тощо). Обов'язково.

## Приклад
**Вхід:** `{{CONSUMER_CONTEXT}}` = «Споживач виконання замовлень, що обробляє події 'order.paid' для запуску відправки зі складу.» `{{CURRENT_RETRY_BEHAVIOR}}` = «Наразі немає DLQ — після 3 повторів із фіксованою затримкою 5с повідомлення логується й відкидається.» `{{FAILURE_TYPES}}` = «Таймаут API складу далі за потоком (тимчасовий); неправильно сформована подія без обов'язкового поля SKU (отруйна); API складу відхиляє невідомий SKU (отруйна, але потребує рішення людини).»

**Вихід (уривок):**
```
### Тригер переміщення в DLQ
- Неправильно сформовані події без обов'язкового поля: одразу в DLQ, без повторів — це ніколи не вдасться, оскільки повтор не виправляє відсутнє поле.
- Таймаут API складу: повторюй до 5 разів з експоненційним backoff (проти поточних фіксованих 3/5с, оскільки довший backoff дає тимчасовому збою більше часу минути); в DLQ після вичерпання повторів.
- Відхилення невідомого SKU: в DLQ після 1 повтору (щоб виключити тимчасове відставання синхронізації каталогу) — це потребує рішення людини, не більше повторів.

### Метадані для додавання
Оригінальний вантаж події, причина збою (категоризована: неправильна форма / таймаут / відхилений-sku), кількість спроб, мітки часу першої й останньої спроби, версія деплою споживача.

### Пороги сповіщення
Будь-яке недоставлене повідомлення з неправильною формою: сповіщай негайно (вказує на баг продюсера далі за потоком, що потенційно впливає на багато замовлень). Недоставлені повідомлення таймауту/відхиленого-sku: сповіщай, якщо кількість DLQ перевищує 10 за ковзну годину, оскільки жменька — очікуваний обсяг ручного тріажу, але сплеск вказує на системну проблему (напр., збій API складу).

### Процедура повторного відтворення
Після виправлення продюсера для неправильно сформованих подій чи виправлення синхронізації каталогу для відхилених SKU, повторно відтворюй уражені повідомлення індивідуально через інструмент тріажу, що скидає лічильник спроб і повторно публікує в живу чергу — ніколи не відтворюй масово без підтвердження конкретної корінної причини на категорію збою, оскільки масове відтворення невирішених отруйних повідомлень просто знову наповнює DLQ.

Підсумок: Замінює мовчазне відкидання після 3 спроб на категоризовану обробку — отруйні повідомлення одразу йдуть у DLQ замість витрачання повторів, тимчасові таймаути отримують більше запасу повторів, і нічого не втрачається без запису тріажу.
```

## Поради та варіації
- Поєднуй із «Діагностом відставання черги завдань» (coding, вже випущений), коли *жива* черга теж росте несподівано — той промпт діагностує, чому необроблені повідомлення накопичуються; цей промпт — для повідомлень, які вже вичерпали спроби обробки.
- Якщо {{CONSUMER_CONTEXT}} стосується впорядкованої/FIFO обробки повідомлень, явно познач у виводі ризик блокування голови черги: одне застрягле повідомлення може блокувати всі наступні повідомлення для того самого партиції/ключа, поки воно не потрапить у DLQ, що змінює, наскільки терміново тригер переміщення в DLQ має спрацьовувати.
- Для споживачів, що обробляють чутливі дані (PII, платіжні деталі), познач у кроці метаданих, чи безпечно зберігати повний оригінальний вантаж у DLQ як є, чи він потребує редагування перед зберіганням для тріажу.
