## Опис
Рецензує код Terraform/IaC на ризики та порушення найкращих практик — управління станом, ризик дрейфу, надто дозвільні security groups/IAM, захардкоджені секрети — як цілеспрямоване рев'ю інфраструктури, відрізняється від рев'ю маніфестів Kubernetes і CI-пайплайну в цій категорії. Для реальної зміни Terraform перед `apply`.

## Коли використовувати
- Рев'ю PR з Terraform перед `apply`, особливо такого, що зачіпає security groups, IAM чи конфігурацію стану.
- Аудит наявного коду Terraform на ризик дрейфу чи прогалини безпеки після успадкування репозиторію інфраструктури.
- Вивчення найкращих практик IaC через їх застосування як фідбек на реальний код, а не читання style guide.

## Промпт

```
Ти рецензуєш код Terraform на ризики та порушення найкращих практик — безпеку, управління станом, безпеку змін — не синтаксис HCL чи форматування (це робота `terraform fmt`).

Код Terraform: {{TERRAFORM_CODE}}
Хмарний провайдер: {{CLOUD_PROVIDER}}
Контекст (необов'язково — напр., "це керує продакшн VPC", "це інфраструктура нового мікросервісу"): {{CONTEXT}}

Інструкції:
1. Перевір на захардкоджені секрети чи чутливі значення (API-ключі, паролі, рядки з'єднання) у звичайному HCL, а не отримані з менеджера секретів, змінної середовища, чи позначені `sensitive = true` — познач будь-яке таке значення, навіть якщо воно виглядає як плейсхолдер, оскільки такі закомічуються в систему контролю версій.
2. Перевір дозвільність правил security group / firewall: будь-яке правило, що дозволяє вхідний трафік `0.0.0.0/0` на чутливий порт (SSH, RDP, порти бази даних, адмін-інтерфейси), є знахідкою високої критичності, якщо явно не обґрунтоване контекстом (напр., порт 443 публічного веб-сервера). Познач також надто широкі правила вихідного трафіку, не лише вхідного.
3. Перевір область дії IAM/прав: чи політики використовують wildcard-дії/ресурси (`"Action": "*"`, `"Resource": "*"`) там, де підійшла б обмежена політика? Познач будь-яку роль/політику, що надає ширший доступ, ніж описаному ресурсу правдоподібно потрібно.
4. Перевір практики управління станом: чи налаштований віддалений стан (не локальний стан, що ризикує втратою і заважає командній роботі)? Чи налаштоване блокування стану (запобігання пошкодженню стану паралельними apply)? Якщо видно, чи сам бекенд стану належно контролюється за доступом і зашифрований?
5. Перевір на ресурси з ризиком неочікуваної заміни: зміна незмінного атрибута, що змушує пересоздавати ресурс (перевір наслідки `# forces replacement`) на stateful-ресурсі (база даних, ресурс, що зберігає дані), є ризиком втрати даних, що потребує явної виноски, а не лише зазначення, що план це показав би.
6. Перевір на відсутній захист lifecycle `prevent_destroy` на критичних, важких для пересоздання ресурсах (продакшн-база даних, ресурс зі значною ручною конфігурацією), де випадкове видалення через `terraform destroy` чи неправильно налаштований `apply` було б катастрофічним.
7. Перевір на ризик дрейфу: ресурси, частково керовані поза Terraform (ручні зміни в консолі керованого Terraform ресурсу), які код не може виявити — познач, якщо контекст вказує, що це ймовірно (напр., згадки ручних гарячих виправлень).

Формат виводу: Markdown, один запис на знахідку, згруповано за категорією (Секрети / Мережева безпека / IAM / Управління станом / Ризик втрати даних / Дрейф), кожен з критичністю і конкретним виправленням HCL.
```

## Змінні
- `{{TERRAFORM_CODE}}` — код Terraform/HCL для рецензування. Обов'язково.
- `{{CLOUD_PROVIDER}}` — напр. "AWS", "GCP", "Azure". Обов'язково — типи ресурсів і моделі IAM суттєво різняться.
- `{{CONTEXT}}` — що ця інфраструктура підтримує і її критичність. Необов'язково, але уточнює критичність і допомагає оцінити, чи широке правило обґрунтоване.

## Приклад
**Вхід:** `{{TERRAFORM_CODE}}` = ресурс `aws_security_group` з правилом вхідного трафіку, що дозволяє порт 5432 (Postgres) з `0.0.0.0/0`, `{{CLOUD_PROVIDER}}` = "AWS", `{{CONTEXT}}` = "security group бази даних для продакшн-сервісу замовлень".

**Вихід (фрагмент):**
```
### Мережева безпека — CRITICAL
Правило вхідного трафіку дозволяє TCP 5432 (PostgreSQL) з `0.0.0.0/0` — порт продакшн-бази даних відкритий для всього інтернету.
Виправлення:
```hcl
ingress {
  from_port   = 5432
  to_port     = 5432
  protocol    = "tcp"
  security_groups = [aws_security_group.app_servers.id]
}
```
Обмеж правило до конкретної security group серверів застосунку, яким потрібен доступ до бази даних, а не відкритий CIDR-блок. Якщо зовнішній доступ дійсно потрібен (напр., для конкретного адмін IP), використай вузько обмежений CIDR, не `0.0.0.0/0`.
```

## Поради та варіації
- Поєднуй з фактичним виводом `terraform plan` як додатковий контекст при рецензуванні реальної зміни — план показує точно, що буде створено/змінено/знищено, що є сильнішим доказом, ніж читання самого HCL для виявлення неочікуваної заміни ресурсу.
- Для великого модуля попроси пріоритезувати знахідки за радіусом ураження (неправильна конфігурація на рівні VPC впливає на все нижче за потоком), а не рецензувати ресурси в порядку файлу.
