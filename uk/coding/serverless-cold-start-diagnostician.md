## Опис
Діагностує причини надмірної затримки холодного старту конкретної serverless-функції — для інженера, чиї холодні старти шкодять чутливому до затримки шляху. Відрізняється від інших промптів продуктивності в цій бібліотеці, що націлені на інші середовища виконання (браузер, мобільні) і типи проблем.

## Коли використовувати
- Serverless-функція (Lambda, Cloud Functions, Azure Functions тощо) має помітно повільну затримку першого виклику.
- Вирішуєш, чи платити за provisioned/reserved concurrency, чи реально виправити базову причину холодного старту.
- Холодний старт функції погіршився після додавання нової залежності, і хочеш зрозуміти чому.

## Промпт

```
Ти діагностуєш причину надмірної затримки холодного старту конкретної serverless-функції — не загальне тюнінгування продуктивності, а конкретно вартість запуску при першому виклику.

Конфігурація функції (рантайм/мова, налаштування пам'яті, приблизний розмір пакета розгортання, якщо відомо, статус підключення VPC): {{FUNCTION_CONFIG}}

Код ініціалізації (код, що виконується на рівні модуля/верхньому рівні, поза функцією-обробником, при холодному старті): {{INIT_CODE}}

Спостережений час холодного старту: {{OBSERVED_COLD_START_TIME}}

Перевір:
1. Розмір пакета розгортання і зайві залежності — роздутий бандл (невикористані бібліотеки, dev-залежності, випадково включені) збільшує час, який платформа витрачає на завантаження пакета, ще до того, як твій код взагалі почне виконуватись.
2. Що виконується на рівні модуля/верхньому рівні, а що всередині обробника — важка ініціалізація поза обробником (наприклад, відкриття з'єднання з базою даних, завантаження великого конфіг-файлу) виконується на кожному холодному старті; перевір, чи можна зробити ліниву ініціалізацію при першому використанні, чи повторно використовувати з'єднання між теплими викликами замість перестворення.
3. Підключення VPC — історично значна вартість холодного старту на деяких платформах через провіжинінг ENI, хоча це суттєво покращилось на деяких провайдерах/версіях; явно зазнач, якщо не впевнений, чи це досі стосується заявленої платформи, замість того щоб стверджувати застарілий факт як актуальний.
4. Властиві характеристики холодного старту рантайму/мови — деякі мовні рантайми мають помітно вищий базовий overhead холодного старту, ніж інші, незалежно від коду.

Ранжуй ймовірних учасників за оціночним впливом з огляду на те, що реально показано в `{{INIT_CODE}}` та `{{FUNCTION_CONFIG}}`, з конкретним виправленням для кожного пункту в ранзі.

Якщо `{{INIT_CODE}}` виглядає мінімальним, а пакет невеликий, чесно скажи це — холодний старт може домінуватись overhead'ом платформи/рантайму поза контролем коду, і тоді provisioned concurrency (платити за підтримку теплих інстансів) — реалістичне виправлення замість подальших змін коду, а рекомендувати ще більше археології коду було б витратою часу інженера.
```

## Змінні
- `{{FUNCTION_CONFIG}}` — рантайм, пам'ять, розмір пакета і статус VPC. Обов'язково.
- `{{INIT_CODE}}` — код, що виконується поза обробником при холодному старті. Обов'язково.
- `{{OBSERVED_COLD_START_TIME}}` — реально виміряна затримка холодного старту. Обов'язково — без числа "надмірна" не має якоря.

## Приклад
**Вхід:** `{{FUNCTION_CONFIG}}` = "Node.js 20, 256МБ пам'яті, підключено до VPC, розмір пакета ~45МБ", `{{INIT_CODE}}` = "імпортує повний AWS SDK v2 (не модульний v3), відкриває нове з'єднання з базою даних на рівні модуля при кожному холодному старті", `{{OBSERVED_COLD_START_TIME}}` = "~2.5 секунди".

**Вихід (фрагмент):**
```
Головний фактор: імпорт повного AWS SDK v2 замість модульного SDK v3 (чи лише конкретних клієнтів v3, що реально потрібні) — це поширена, значна причина роздутості пакета, і повний бандл v2 суттєво більший, ніж імпорт лише `@aws-sdk/client-s3` чи якогось конкретного клієнта, що реально використовується. Виправлення: мігруй на AWS SDK v3 з імпортом лише потрібних сервісних клієнтів.

Другий фактор: відкриття нового з'єднання з базою даних на рівні модуля при кожному холодному старті. Це коректно розміщено поза обробником для повторного використання між теплими викликами (добре), але на кожному холодному старті це все одно додає повну затримку встановлення з'єднання на критичний шлях. Якщо база даних підтримує це, розглянь проксі з пулінгом з'єднань (наприклад, RDS Proxy), що тримає теплі з'єднання доступними, щоб холодний інстанс Lambda підключався до вже теплого проксі, а не встановлював свіже рукостискання TCP+TLS+автентифікація щоразу.

Підключення VPC: з огляду на цю платформу (AWS Lambda) і припущення про досить нову мережеву модель Lambda (ENI Hyperplane), вартість холодного старту через VPC суттєво знизилась останніми роками — не вважай це досі домінуючим фактором, яким воно було історично, без перевірки конкретного покоління рантайму/мережі у використанні.

При 2.5с з пакетом 45МБ і виявленою проблемою SDK, виправлення на рівні коду, ймовірно, суттєво допоможуть тут — це не той випадок, коли provisioned concurrency — єдиний важіль.
```

## Поради та варіації
- Якщо холодні старти вже мінімізовані на рівні коду, а решта затримки все ще неприйнятна для сценарію використання, попроси явно оцінити компроміс вартості provisioned concurrency, а не просто рекомендувати його — "платити за N завжди теплих інстансів" має реальну грошову вартість, варту зазначення.
- Для платформи, відмінної від AWS Lambda, скажи це явно — характеристики холодного старту (особливо навколо VPC/мережі і overhead мовного рантайму) суттєво різняться між провайдерами, і слід уникати перенесення AWS-специфічних припущень.
