## Опис
Порівнює 2-3 названі технологічні опції з реальними заявленими обмеженнями твоєї команди — не загальний листикл "X проти Y" — і дає конкретну рекомендацію з обґрунтуванням, прив'язаним до цих обмежень. Для конкретного рішення, яке треба ухвалити, а не загального дослідження.

## Коли використовувати
- Вибір між конкретними технологіями (базами даних, фреймворками, чергами повідомлень) для реального проєкту з реальними обмеженнями.
- Потреба обґрунтувати вибір технології стейкхолдерам чітким, прив'язаним до обмежень обґрунтуванням, а не преференцією.
- Перегляд старого вибору технології, щоб перевірити, чи він досі відповідний, з урахуванням того, як змінилися обмеження.

## Промпт

```
Ти порівнюєш конкретні технологічні опції з явно заявленими обмеженнями — не загальне порівняння функцій. Рекомендація має випливати з наданих обмежень, а не з того, яка технологія популярніша чи "сучасніша" абстрактно.

Опції для порівняння: {{OPTIONS}}
Для чого це (реальний кейс використання): {{USE_CASE}}
Обмеження (навички команди, масштаб, бюджет, терміни, наявна інфраструктура, вимоги комплаєнсу — що застосовно): {{CONSTRAINTS}}

Інструкції:
1. Для кожної опції оцінюй її саме з урахуванням заявлених обмежень — не загальний список сильних/слабких сторін. Якщо обмеження не застосовне до конкретної опції, скажи про це, замість того щоб форсувати точку порівняння.
2. Будь явним щодо компромісів: жодна реалістична опція не виграє за кожним обмеженням. Якщо твій аналіз показує одну опцію строго кращою без недоліків, сприймай це як сигнал пошукати компроміс, який ти пропускаєш.
3. Зважуй обмеження за тим, наскільки вони дійсно важливі для цього конкретного кейсу — обмеження на кшталт "у команди нуль досвіду з X" мають більшу вагу для маленької команди з жорсткими термінами, ніж для великої команди з часом на розгін.
4. Дай конкретну рекомендацію, не лише порівняння — сформулюй, яку опцію ти б обрав з урахуванням цих обмежень і чому, одним чітким абзацом.
5. Познач будь-яке обмеження, за яким у тебе недостатньо інформації для впевненої оцінки, і скажи, що потрібно знати для більшої впевненості.
6. Якщо чесна відповідь — "вони достатньо близькі, щоб вибір не мав великого значення, обирайте за перевагою команди" — скажи це, замість того щоб фабрикувати хибну точність.

Формат виводу: таблиця Markdown, що порівнює опції за кожним обмеженням, за якою слідує розділ "Рекомендація" з абзацом обґрунтування.
```

## Змінні
- `{{OPTIONS}}` — конкретні технології, що порівнюються (2-3). Обов'язково.
- `{{USE_CASE}}` — для чого фактично буде використовуватися ця технологія. Обов'язково.
- `{{CONSTRAINTS}}` — реальні обмежувальні фактори для цього рішення. Обов'язково — без цього порівняння вироджується в загальний маркетинговий контент.

## Приклад
**Вхід:** `{{OPTIONS}}` = "PostgreSQL, MongoDB", `{{USE_CASE}}` = "зберігання каталогу товарів із часто змінюваними, напівструктурованими атрибутами по категорії", `{{CONSTRAINTS}}` = "команда має сильний досвід SQL, без досвіду NoSQL; потрібні складні звітні запити крізь категорії".

**Вихід (фрагмент):**
```
| Обмеження | PostgreSQL | MongoDB |
|---|---|---|
| Досвід команди | Сильні наявні навички SQL, мінімальний розгін | Команді знадобиться вивчати документне моделювання й aggregation pipeline з нуля |
| Напівструктуровані атрибути | Обробляється через JSONB-колонки — достатньо гнучко для варіативних полів по категорії, з можливістю додати структуру пізніше | Природна відповідність, але перевага гнучкості менша, ніж здається спочатку, з урахуванням JSONB |
| Звітність крізь категорії | Сильно — стандартні SQL join'и й агрегації | Слабше — агрегація крізь колекції незграбніша й повільніша для складної звітності |

**Рекомендація:** PostgreSQL, з JSONB для варіативних атрибутів по категорії. Вимога звітності — жорстке обмеження, з яким MongoDB справляється гірше, і це повністю уникає вартості розгону команди — аргумент "напівструктуровані дані" на користь MongoDB не витримує, коли враховано JSONB.
```

## Поради та варіації
- Для рішення build-vs-buy замість порівняння технологій адаптуй `{{OPTIONS}}` під назви вендорів/SaaS-опцій і додай рядок вартості/прив'язки до вендора в набір обмежень.
- Якщо в стейкхолдерів заявлене упередження на користь однієї опції, назви це явно як (нетехнічне) обмеження, щоб промпт не ігнорував мовчки організаційну реальність.
