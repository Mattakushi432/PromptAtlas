## Опис
Перевіряє схему чи шар запитів на ризик витоку даних між тенантами в multi-tenant застосунку — для сеньйора, що рецензує тенант-скоупінг перед випуском фічі. Вужче за загальне рев'ю безпеки: конкретно про те, чи може один тенант побачити чи вплинути на дані іншого.

## Коли використовувати
- Рев'ю запитів/ORM-коду нової фічі перед випуском у multi-tenant SaaS-продукті.
- Після онбордингу нового інженера в multi-tenant кодбейз, щоб рано зловити помилки скоупінгу.
- Розслідування, чи повідомлений баг видимості даних міг бути збоєм ізоляції тенантів.

## Промпт

```
Ти рецензуєш код конкретно на ризик витоку даних між тенантами — не загальну безпеку чи якість коду. Вважай, що сама автентифікація працює; твоє завдання — чи міг би автентифікований користувач Тенанта A коли-небудь побачити чи вплинути на дані Тенанта B.

Код схеми чи запитів: {{SCHEMA_OR_QUERY_CODE}}

Модель мультитенантності у використанні (спільні таблиці з колонкою tenant_id, схема-на-тенант, чи база-даних-на-тенант): {{TENANCY_MODEL}}

Для моделі зі спільними таблицями перевір:
1. Чи кожен запит, що читає чи пише дані з прив'язкою до тенанта, включає фільтр за тенантом (умову WHERE tenant_id = ..., чи ORM default scope, що застосовує це автоматично) — познач будь-який запит без нього, процитувавши конкретний рядок.
2. Чи зв'язки foreign key і join'и не дозволяють переходити з рядка одного тенанта до рядка іншого (наприклад, join на спільній довідковій таблиці, яка сама не прив'язана до тенанта, коли мала б бути).
3. Чи tenant_id, що використовується для скоупінгу запиту, виводиться з автентифікованої сесії/контексту авторизації, а не береться напряму з клієнтського вводу (клієнтський tenant_id можна підробити).

Для моделі схема-на-тенант чи база-даних-на-тенант перевір натомість:
1. Чи логіка маршрутизації підключення/схеми не може відкотитись до типового чи неправильного підключення тенанта на шляху обробки помилки.
2. Чи жоден код-шлях не створює конкурентне з'єднання навмисно без явної, аудитованої причини (наприклад, адмін-інструмент) — і якщо такий є, чи він захищений окремо від звичайних користувацьких код-шляхів.

Для кожної знахідки процитуй конкретний код, поясни конкретний сценарій витоку (не "це теоретично може протекти" — опиши реальну послідовність дій, що розкрила б дані Тенанта B Тенанту A), і оціни серйозність (LOW/MEDIUM/HIGH/CRITICAL — будь-яке підтверджене читання чи запис між тенантами — щонайменше HIGH).

Якщо кожен релевантний код-шлях правильно прив'язаний до тенанта, чесно скажи це як прохідний вердикт, а не вигадуй незначну знахідку, щоб виглядати ретельним.
```

## Змінні
- `{{SCHEMA_OR_QUERY_CODE}}` — визначення схеми, моделі ORM чи код запитів/репозиторіїв для рев'ю. Обов'язково.
- `{{TENANCY_MODEL}}` — як реалізована мультитенантність (спільна таблиця, схема-на-тенант, база-на-тенант). Обов'язково — перевірки суттєво різняться залежно від моделі.

## Приклад
**Вхід:** `{{SCHEMA_OR_QUERY_CODE}}` = ORM-запит `Order.where(status: 'pending')` всередині дії контролера, де `tenant_id` присутній як колонка, але не використовується у запиті, `{{TENANCY_MODEL}}` = "спільні таблиці з колонкою tenant_id".

**Вихід (фрагмент):**
```
Знахідка: `Order.where(status: 'pending')` не має фільтра за тенантом і немає доказів default scope, що застосовував би його автоматично. Серйозність: CRITICAL.
Конкретний витік: будь-який автентифікований користувач, що викликає цю дію, отримає pending-замовлення з УСІХ тенантів, а не лише свого — це не теоретичний крайній випадок, а типова поведінка запиту, як він написаний.
Виправлення: або явно додати `.where(tenant_id: current_tenant.id)`, або — краще — перевірити, чи default scope ORM насправді застосовується тут і не обходиться викликом `.unscoped` десь у ланцюжку.

Вердикт: 1 знахідка CRITICAL. Не випускати без виправлення.
```

## Поради та варіації
- Якщо ORM має механізм скоупінгу за замовчуванням (наприклад, `default_scope` у Rails, кастомний базовий клас репозиторію), попроси явно перевірити, чи скоуп реально активний саме на цьому запиті, а не вважати його гарантованим глобально — скоупи часто випадково обходяться сирим SQL чи `.unscoped`.
- Для моделі база-на-тенант передай саме middleware/код маршрутизації підключення, оскільки саме там концентрується реальний ризик, а не в окремих запитах.
