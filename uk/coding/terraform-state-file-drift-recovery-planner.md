## Опис
Планує безпечний шлях узгодження пошкодженого чи розсинхронізованого state-файлу Terraform із реальною інфраструктурою — відмінний від «Виявлення дрейфу Infrastructure-as-Code» (coding, вже випущений) із фокусом на виявленні поточного дрейфу код-проти-реальності: цей промпт обробляє сценарій відновлення з вищими ставками, де сам state-файл зламаний, втрачений чи погано розійшовся, не рутинний моніторинг дрейфу.

## Коли використовувати
- Твій state-файл Terraform пошкоджений, випадково видалений, чи розійшовся з реальною інфраструктурою настільки погано, що `terraform plan` показує тривожний, важко зрозумілий diff.
- Відновлюєшся після невдалої ручної зміни, зробленої напряму в консолі хмари, про яку Terraform не знає, і потрібен безпечний шлях назад до точності стану без знищення реальних ресурсів.
- Ось-ось запустиш ризиковану операцію зміни стану (`terraform import`, хірургія стану) і хочеш перевірений план перед торканням продакшн стану, оскільки помилки стану можуть бути руйнівними й важко оборотними.

## Промпт

```
Ти плануєш безпечний шлях відновлення для узгодження пошкодженого чи розсинхронізованого state-файлу Terraform з реальною інфраструктурою. Ти пріоритезуєш незнищення чи неосиротіння реальних ресурсів понад швидкість — кожен крок має бути обміркований щодо радіусу враження перед рекомендацією.

Опис ситуації: {{SITUATION}}
Поточний статус state-файлу: {{STATE_STATUS}}
Статус реальної інфраструктури (що реально існує, якщо відомо): {{REAL_INFRA_STATUS}}
Толерантність до ризику / обмеження (вікно обслуговування, ресурси, яких не можна торкатись): {{CONSTRAINTS}}

Інструкції:
1. Перед пропозицією будь-якої команди, що змінює стан, наполягай на резервній копії state-файлу (чи підтвердженні, що вона вже існує) — операції `terraform state` можуть бути руйнівними, і резервна копія — єдиний найвпливовіший крок безпеки, доступний перед будь-якою дією відновлення.
2. Класифікуй реальний обсяг ситуації: стан повністю втрачений (потребує повної реконструкції через `terraform import`), частково розійшовся (деякі ресурси потребують import/видалення зі стану), чи виглядає пошкодженим, але ресурси всі реальні й відстежувані (може бути відновлюваним без торкання реальної інфраструктури взагалі)? Правильний підхід суттєво різниться залежно від того, що це реально.
3. Для будь-якого ресурсу, що існує в стані, але не в реальності (чи навпаки), запропонуй конкретне виправлення з мінімальним радіусом враження: `terraform state rm` для ресурсу, що в стані, але не має відстежуватись (ніколи `terraform destroy`, що спробувало б видалити реальний ресурс), чи `terraform import` для реального ресурсу, відсутнього в стані — правильно визнач напрямок, оскільки застосування неправильного ризикує реально видалити реальну інфраструктуру.
4. Послідовуй кроки відновлення так, щоб жоден `terraform apply` не запускався проти неузгодженого стану — наполягай на запуску `terraform plan` після кожного кроку узгодження й перегляді diff перед продовженням, а не пакетуванні всіх виправлень і застосуванні наосліп в кінці.
5. Познач будь-який крок, що торкнувся б ресурсу, зазначеного в {{CONSTRAINTS}} як недоторканний, і запропонуй, як обійти його (напр., виключивши цей ресурс з поточного проходу відновлення), а не включай його в пакетну операцію, що могла б його зачепити.
6. Якщо {{REAL_INFRA_STATUS}} неповний чи невизначений, скажи це прямо й рекомендуй, які конкретні команди (`terraform state list`, запити CLI хмарного провайдера) потрібно запустити спершу, щоб отримати достатню впевненість перед продовженням — не пропонуй руйнівно-суміжні операції стану на основі припущеного, а не підтвердженого стану інфраструктури.

Формат виводу: Markdown, нумерований, послідовний план відновлення, кожен крок з: конкретною командою/дією, що вона зачіпає й не зачіпає, і контрольною точкою `terraform plan`-і-перегляд між кроками, що торкаються стану. Заверши секцією `### Перевірка`, що описує, як підтвердити, що стан тепер відповідає реальності.
```

## Змінні
- `{{SITUATION}}` — що сталось (стан пошкоджено, видалено, ручна зміна поза процесом тощо). Обов'язково.
- `{{STATE_STATUS}}` — що відомо про вміст/стан поточного state-файлу. Обов'язково.
- `{{REAL_INFRA_STATUS}}` — що реально відомо як наявне в реальній інфраструктурі. Обов'язково — планування відновлення суттєво залежить від того, наскільки це реально відомо проти припущено.
- `{{CONSTRAINTS}}` — будь-які ресурси, яких не можна торкатись, вікна обслуговування, чи нотатки толерантності до ризику. Обов'язково.

## Приклад
**Вхід:** `{{SITUATION}}` = «Інженер вручну видалив і перестворив S3-бакет напряму в консолі AWS, щоб виправити термінову проблему, обходячи Terraform» `{{STATE_STATUS}}` = «Стан досі посилається на оригінальний бакет за його старим ID ресурсу» `{{REAL_INFRA_STATUS}}` = «Новий бакет існує з тією самою назвою, але іншим базовим ID ресурсу; старого бакета більше немає» `{{CONSTRAINTS}}` = «Продакшн-бакет, не може мати простою, вікно обслуговування не потрібне для операцій стану лише для читання»

**Вихід (уривок):**
```
1. **Спочатку резервуй стан.** Підтверди, що резервна копія стану існує (чи запусти `terraform state pull > backup.tfstate`) перед будь-якою подальшою дією — це не обговорюється, зважаючи на залучений продакшн.
2. **Класифікуй:** Частково розійшовся — один конкретний ресурс (S3-бакет) не синхронізований; решта стану вважається незачепленою до підтвердження на кроці 3.
3. **Підтверди обсяг:** Запусти `terraform state list` і звір із відомою реальною інфраструктурою, щоб підтвердити, що жоден інший ресурс не був зачеплений ручною зміною понад цей бакет.
4. **Прибери застарілу референцію:** `terraform state rm aws_s3_bucket.this` — це лише видаляє старий (тепер неіснуючий) бакет із відстеження Terraform; не намагається нічого видалити, оскільки ресурс, на який він посилається, більше не існує.
   Контрольна точка: запусти `terraform plan` — очікуй, що покаже план *створення* бакета, оскільки стан більше не відстежує його. НЕ застосовуй ще.
5. **Імпортуй реальний ресурс:** `terraform import aws_s3_bucket.this <new-bucket-id>` — приводить реальний поточний бакет під відстеження Terraform, використовуючи його реальний, поточний ID ресурсу.
   Контрольна точка: запусти `terraform plan` знову — очікуй мало чи жодного diff, якщо реальна конфігурація бакета відповідає задекларованій у коді; будь-який залишковий diff показує дрейф конфігурації понад просто ID ресурсу, що потребує окремого перегляду перед застосуванням.
...

### Перевірка
Коли план не показує неочікуваного diff, `terraform state show aws_s3_bucket.this` має відображати реальні атрибути нового бакета, підтверджуючи, що стан і реальність узгоджені без того, щоб apply торкнувся живого бакета.
```

## Поради та варіації
- Для повної втрати стану (не лише одного ресурсу) той самий крок 1 (резервна копія, якщо щось відновлюване) і патерн кроків 4-5 (контрольна точка плану перед будь-яким apply) все одно застосовні, просто повторені для набагато більшої кількості ресурсів — розглянь скриптування викликів `terraform import`, якщо обсяг великий, але тримай контрольну точку плану-й-перегляду перед першим реальним `apply` незалежно від масштабу.
- Після будь-якого відновлення стану варто розмова про кореневу причину, чому сталась ручна зміна поза процесом — відновлений стан не запобігає повторенню того самого дрейфу, якщо основна прогалина процесу (напр., доступ до консолі без Terraform-first робочого процесу) не вирішена.
- Цей промпт планує відновлення; завжди май другого інженера, що переглядає план перед виконанням команд, що змінюють стан, проти продакшену, зважаючи на те, наскільки легко неправильний вибір `state rm` проти `destroy` може спричинити реальну втрату даних.
