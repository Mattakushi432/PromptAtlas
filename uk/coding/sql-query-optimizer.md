## Опис
Переписує повільний SQL-запит на оптимізовану версію і рекомендує конкретні потрібні індекси, з урахуванням запиту та його схеми — конкретне виправлення, а не загальний пояснювач "як працюють індекси". Для реального повільного запиту, який комусь треба виправити.

## Коли використовувати
- Конкретний запит виходить за таймаут чи з'являється як найповільніший у логу повільних запитів бази даних і потребує конкретного виправлення.
- Рев'ю нового запиту перед релізом у продакшн, щоб рано виловити очевидний патерн повного сканування таблиці.
- Рішення, який індекс додати, без надлишкового індексування таблиці, що вже інтенсивна на запис.

## Промпт

```
Ти оптимізуєш повільний SQL-запит з урахуванням його схеми та (якщо доступно) плану виконання. Видай переписаний запит і конкретні рекомендації індексів, а не загальні поради.

Повільний запит: {{SLOW_QUERY}}
Відповідна схема (таблиці, колонки, наявні індекси, приблизна кількість рядків): {{SCHEMA}}
Вивід плану виконання, якщо доступний (EXPLAIN/EXPLAIN ANALYZE): {{EXECUTION_PLAN}}
Двигун бази даних: {{DATABASE_ENGINE}}

Інструкції:
1. Визнач конкретну(і) причину(и) повільності: відсутній індекс, що спричиняє послідовне сканування/сканування таблиці, non-sargable предикат (функція, обгорнута навколо індексованої колонки, що заважає використанню індексу), непотрібний підзапит, який міг би бути join'ом, SELECT *, що витягує непотрібні колонки/рядки, неявне перетворення типу, що ламає використання індексу, чи порядок join'у, який планувальник обирає погано.
2. Якщо надано план виконання, наводь конкретні докази з нього (напр., "Seq Scan on orders, cost=... rows=50000"), а не вгадуй причину.
3. Надай переписаний запит з тією самою семантикою результату — вивід має бути доведено еквівалентним оригіналу для коректних вхідних даних, а не просто швидшим і "достатньо близьким".
4. Рекомендуй конкретний(і) індекс(и): точні колонки, порядок (для композитних індексів порядок важливий для того, які патерни запитів отримають вигоду), і тип індексу, якщо двигун підтримує опції (B-tree проти partial проти покривного/included columns).
5. Зазнач вартість запису для кожного рекомендованого індексу (кожен індекс сповільнює INSERT/UPDATE/DELETE на цій таблиці) — не рекомендуй індекси без визнання цього компромісу, особливо на таблиці, інтенсивній на запис.
6. Якщо запит повільний з причини, яку жоден індекс чи переписування не можуть виправити (напр., він фундаментально агрегує забагато даних для OLTP-запиту), скажи про це і запропонуй архітектурну альтернативу (матеріалізоване представлення, попередня агрегація, кешування), а не форсуй виправлення на рівні запиту.
7. Якщо {{EXECUTION_PLAN}} не надано, скажи, що ти хотів би побачити в ньому для підтвердження діагнозу, але все одно дай найкращий діагноз лише із запиту та схеми.

Формат виводу: Markdown з розділами: Діагноз, Переписаний запит, Рекомендовані індекси (з компромісами), і (якщо застосовно) Архітектурна примітка.
```

## Змінні
- `{{SLOW_QUERY}}` — запит для оптимізації. Обов'язково.
- `{{SCHEMA}}` — відповідні визначення таблиць, наявні індекси, приблизні розміри таблиць. Обов'язково.
- `{{DATABASE_ENGINE}}` — напр. "PostgreSQL 16", "MySQL 8". Обов'язково — синтаксис індексів і поведінка оптимізатора різняться за двигуном.
- `{{EXECUTION_PLAN}}` — фактичний вивід EXPLAIN. Необов'язково, але перетворює вгадування на діагноз.

## Приклад
**Вхід:** `{{SLOW_QUERY}}` = `SELECT * FROM orders WHERE YEAR(created_at) = 2026`, `{{SCHEMA}}` = `orders(id, created_at, ...)`, немає індексу на `created_at`, `{{DATABASE_ENGINE}}` = "MySQL 8".

**Вихід (фрагмент):**
```
## Діагноз
`YEAR(created_at) = 2026` обгортає колонку-кандидата на індекс у функцію, роблячи предикат non-sargable — навіть з індексом на `created_at`, MySQL не може використати його для цього предиката і переходить до повного сканування таблиці.

## Переписаний запит
```sql
SELECT * FROM orders WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';
```

## Рекомендовані індекси
`CREATE INDEX idx_orders_created_at ON orders(created_at);` — простий B-tree індекс, тепер використовний предикатом діапазону. Компроміс: незначні накладні витрати запису на кожну вставку замовлення; прийнятно з урахуванням того, що замовлення читаються значно частіше, ніж записуються в цій таблиці.
```

## Поради та варіації
- Встав реальний вивід `EXPLAIN (ANALYZE, BUFFERS)` (Postgres) чи `EXPLAIN FORMAT=JSON` (MySQL) для значно точнішого діагнозу, ніж дозволяє сама схема.
- Для запиту, повільного через поганий порядок join'у, попроси також запропонувати хінт запиту чи реструктуризацію (напр., CTE, що матеріалізує проміжний результат), якщо планувальнику не можна довіряти хороший вибір.
