## Опис
Перевіряє вже написаний скрипт міграції бази даних на ризик блокувань і простою перед запуском у продакшн. Відрізняється від написання нової міграції з нуля — це рев'ю того, що вже існує, речення за реченням, з прив'язкою до реальної поведінки блокувань конкретного движка БД.

## Коли використовувати
- Рев'ю PR з міграцією перед мерджем, особливо для великої чи високонавантаженої таблиці.
- Міграція відпрацювала підозріло довго чи спричинила інцидент, і хочеш зрозуміти чому постфактум.
- Визначення, які міграції в команді потребують вікна обслуговування, а які безпечно запускати онлайн.

## Промпт

```
Ти проводиш аудит скрипта міграції бази даних на ризик блокувань і простою перед запуском у продакшні. Вважай, що міграція логічно коректна; твоє завдання — що станеться з живою, працюючою базою даних під час її виконання.

Скрипт міграції:
{{MIGRATION_SCRIPT}}

Движок бази даних і версія: {{DB_ENGINE}}

Контекст таблиці (необов'язково — приблизна кількість рядків, патерн читання/запису): {{TABLE_CONTEXT}}

Для кожного оператора в скрипті:
1. Вкажи, який тип блокування він бере на цьому конкретному движку/версії (наприклад, ACCESS EXCLUSIVE, лише метадані, без блокування завдяки підтримці online DDL) — обґрунтуй це реальною задокументованою поведінкою блокувань для {{DB_ENGINE}}, а не загальними припущеннями про SQL.
2. Вкажи, чи перезаписує він усю таблицю, чи це швидка зміна лише метаданих.
3. Оціни ризик (LOW / MEDIUM / HIGH) з обґрунтуванням, що враховує контекст таблиці, якщо він наданий (наприклад, повний перезапис таблиці — LOW ризик на порожній таблиці і HIGH на таблиці з 50 млн рядків під постійним навантаженням на запис).

Там, де ризик MEDIUM або HIGH, запропонуй безпечніший переписаний варіант — наприклад, розбиття "додати NOT NULL колонку" на додати nullable → backfill пакетами → додати обмеження, або використання нативної функції online/concurrent DDL движка, якщо така є.

Заверши загальним вердиктом (безпечно запускати будь-коли / потрібне вікно обслуговування / потрібно переписати перед запуском) і, якщо запропоновано переписаний варіант, повним безпечнішим скриптом.

Якщо скрипт не містить операторів зміни схеми (чисте маніпулювання даними), оціни натомість ризик конкуренції за row-lock і write-lock.
```

## Змінні
- `{{MIGRATION_SCRIPT}}` — скрипт міграції (SQL або файл міграції ORM) для перевірки. Обов'язково.
- `{{DB_ENGINE}}` — движок бази даних і версія (наприклад, "PostgreSQL 15", "MySQL 8.0"). Обов'язково — поведінка блокувань суттєво відрізняється між движками.
- `{{TABLE_CONTEXT}}` — приблизна кількість рядків і патерн навантаження таблиці(ь), що зачіпаються. Необов'язково, але суттєво покращує точність оцінки ризику.

## Приклад
**Вхід:** `{{MIGRATION_SCRIPT}}` = `ALTER TABLE orders ADD COLUMN priority INT NOT NULL DEFAULT 0;`, `{{DB_ENGINE}}` = "PostgreSQL 11", `{{TABLE_CONTEXT}}` = "таблиця orders, ~50 млн рядків, постійне навантаження на читання/запис".

**Вихід (фрагмент):**
```
Оператор: ALTER TABLE orders ADD COLUMN priority INT NOT NULL DEFAULT 0
- Блокування: ACCESS EXCLUSIVE на час перезапису. На PostgreSQL <11 додавання NOT NULL колонки з не-null значенням за замовчуванням змушує повний перезапис таблиці, тримаючи це блокування.
- Перезапис таблиці: так, на PG 11 цей конкретний випадок (постійне значення за замовчуванням) оптимізовано так, щоб уникнути перезапису — але блокування ACCESS EXCLUSIVE все одно береться коротко для оновлення каталогу, що може стати в чергу за довгими транзакціями на завантаженій таблиці.
- Ризик: MEDIUM — коротке блокування, але на таблиці з постійним трафіком воно все одно може спричинити накопичення черги очікування блокувань, якщо стане в чергу за вже виконуваною довгою транзакцією.

Рекомендація: запускати у вікні низького навантаження, або явно обмежити lock_timeout і робити retry, щоб блокування в черзі не застопорило весь потік трафіку.

Загальний вердикт: потрібне вікно обслуговування або захист через lock_timeout, а не переписування.
```

## Поради та варіації
- Для движків з потужними інструментами online-DDL (наприклад, MySQL з `pt-online-schema-change` чи нативним `ALGORITHM=INSTANT`) попроси явно перевірити, чи змінюють ці інструменти вердикт.
- Передай виведення `EXPLAIN` чи логи таймінгу міграції самого движка як додатковий `{{TABLE_CONTEXT}}`, якщо міграція вже відпрацювала і ти робиш постмортем, а не рев'ю перед мерджем.
