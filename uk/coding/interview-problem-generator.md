## Опис
Генерує практичну задачу для технічної співбесіди з рубрикою оцінювання, за темою і складністю — самодостатній практичний артефакт, відрізняється від «Ведучого мок-співбесіди» (що проводить живу сократівську співбесіду) і «Перекладача з дошки на код» (перекладає вже описаний алгоритм). Для побудови банку задач чи генерації свіжого практичного матеріалу.

## Коли використовувати
- Підготовка до технічних співбесід з бажанням отримати свіжі практичні задачі, націлені на конкретну тему/складність, а не перевикористовувати відомі задачі, розв'язки яких могли запам'ятати.
- Інтерв'юер чи команда будує внутрішній банк питань для співбесід з бажанням отримати нову задачу з готовою рубрикою.
- Практика конкретної слабкої області (напр., алгоритми графів, динамічне програмування) із задачами, згенерованими саме під цю прогалину.

## Промпт

```
Ти генеруєш практичну задачу для технічної співбесіди з рубрикою оцінювання — повну, самодостатню задачу, не опис того, яка задача була б хорошою.

Тема (необов'язково — напр., "динамічне програмування", "графи", "масиви/два вказівники"; якщо пропущено, обери поширену тему співбесід): {{TOPIC}}
Складність: {{DIFFICULTY}}
Цільова мова для еталонного розв'язку (необов'язково): {{LANGUAGE}}

Інструкції:
1. Напиши чітке, самодостатнє формулювання задачі: сценарій, точний формат вводу/виводу і явні обмеження (межі розміру вводу, діапазони значень) — задача для співбесіди з неоднозначними обмеженнями видає неоднозначні, важкі для оцінки розв'язки.
2. Включи 2-3 приклади з вводом, очікуваним виводом і однорядковим поясненням чому — достатньо, щоб той, хто розв'язує, міг перевірити своє розуміння задачі перед початком кодування.
3. Спроєктуй задачу так, щоб її заявлені обмеження дійсно розрізняли підходи різної складності — якщо brute-force розв'язок і оптимальний розв'язок обидва тривіально пройшли б з урахуванням заявлених обмежень, обмеження не роблять свою роботу; затягни їх так, щоб задумана оптимізація була дійсно необхідною.
4. Напиши рубрику оцінювання, що покриває: коректність (чи видає правильний вивід на типових вводах і крайових випадках), складність (чи відповідає очікуваній часовій/просторовій складності для цього рівня складності — сформулюй, якою є ця очікувана складність), і якість коду (читабельні назви змінних, без очевидно мертвого коду) як значно менш зважений третинний критерій.
5. Переліч конкретні крайові випадки, які повний розв'язок має обробляти (порожній ввід, ввід з одним елементом, усі однакові значення, максимальний розмір обмеження) — саме це фактично відрізняє робочий розв'язок від зламаного на практиці.
6. Надай еталонний розв'язок на {{LANGUAGE}} (чи поширеній мові, якщо не вказано), що відповідає очікуваній складності, щоб планка складності рубрики була конкретно продемонстрована, а не лише заявлена.
7. Зазнач поширені неправильні підходи чи помилки, специфічні для цієї задачі (класична помилка на одиницю, наївний підхід, що виглядає правильним, але падає на конкретному крайовому випадку), щоб оцінювач знав, на що звертати увагу, навіть не бачачи порушення саме цього пункту рубрики.

Формат виводу: Markdown з розділами: Формулювання задачі, Приклади, Обмеження, Рубрика оцінювання, Крайові випадки для обробки, Еталонний розв'язок, Поширені помилки.
```

## Змінні
- `{{DIFFICULTY}}` — напр. "легка", "середня", "важка" (чи конкретний рівень на кшталт "senior-інженер, суміжний з системним дизайном"). Обов'язково.
- `{{TOPIC}}` — алгоритмічна область для фокусу. Необов'язково — генератор може обрати збалансовану тему, якщо пропущено.
- `{{LANGUAGE}}` — мова для еталонного розв'язку. Необов'язково, за замовчуванням поширена мова співбесід (Python чи подібна).

## Приклад
**Вхід:** `{{TOPIC}}` = "sliding window", `{{DIFFICULTY}}` = "середня".

**Вихід (фрагмент):**
```markdown
## Формулювання задачі
Дано рядок `s` і ціле число `k`, знайти довжину найдовшого підрядка, що містить щонайбільше `k` різних символів.

## Обмеження
1 <= s.length <= 10^5, 0 <= k <= 26 (лише малі англійські літери) — розмір вводу виключає перевірку brute-force O(n²) кожного підрядка в розумний час, вимагаючи підходу sliding window.

## Рубрика оцінювання
- Коректність (60%): проходить типові випадки й крайові випадки нижче.
- Складність (30%): має виконуватися за O(n) часу — розв'язок brute-force O(n²) має бути позначений як такий, що не відповідає планці для цієї складності, навіть якщо коректний.
- Якість коду (10%): чіткі назви змінних для меж вікна й лічильників символів.

## Крайові випадки для обробки
- k = 0: відповідь має бути 0 (жоден підрядок не може мати 0 різних символів, хіба сам підрядок порожній).
- k >= кількості різних символів у s: відповідь — повна довжина рядка.
- Ввід порожнього рядка.
```

## Поради та варіації
- Для побудови банку питань, специфічного для компанії, попроси також згенерувати 2-3 природні наступні питання, які інтерв'юер міг би поставити, якщо кандидат швидко розв'язує базову задачу (поширена техніка калібрування сильнішого кандидата).
- Регенеруй з тією самою темою/складністю, але явно попроси інший конкретний сценарій, якщо перший вивід здається занадто близьким до дуже відомої наявної задачі.
