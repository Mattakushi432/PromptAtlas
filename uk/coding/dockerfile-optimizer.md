## Опис
Переписує Dockerfile для зменшення розміру образу і часу збірки — multi-stage збірки, порядок кешування шарів, вибір базового образу — зі збереженням тієї самої поведінки під час виконання. Для конкретного Dockerfile, що виріс повільним для збірки чи видає роздутий образ.

## Коли використовувати
- Docker-образ виріс достатньо, щоб сповільнити деплої чи час push/pull, і потребує конкретного зменшення розміру.
- Час збірки CI домінований Docker-збірками, що повторно завантажують/встановлюють незмінені залежності.
- Рев'ю нового Dockerfile перед тим, як він стане стандартом команди, щоб рано виловити очевидні неефективності.

## Промпт

```
Ти оптимізуєш Dockerfile для розміру образу і часу збірки, зберігаючи ідентичну поведінку під час виконання — результуючий контейнер має поводитися так само, лише збиратися швидше і бути меншим.

Dockerfile: {{DOCKERFILE}}
Контекст мови/фреймворку (необов'язково, якщо не очевидно з Dockerfile): {{APP_CONTEXT}}
Обмеження (необов'язково — напр., "має використовувати конкретний базовий образ для комплаєнсу", "не можна змінити інструмент збірки"): {{CONSTRAINTS}}

Інструкції:
1. Перевір порядок кешування шарів: чи файли маніфесту залежностей (package.json, requirements.txt, go.mod, Cargo.toml) копіюються і залежності встановлюються ПЕРЕД копіюванням решти вихідного коду застосунку? Якщо ні, кожна зміна коду непотрібно інвалідує шар кешу встановлення залежностей — переупорядкуй так, щоб повільно змінювані шари (залежності) йшли перед швидко змінюваними (вихідний код).
2. Рекомендуй multi-stage збірки, якщо ще не використовуються: етап збірки з повним інструментарієм (компілятори, dev-залежності), що видає артефакти, і тонкий фінальний runtime-етап, що копіює лише зібрані артефакти і runtime-залежності — це часто саме по собі суттєво зменшує розмір образу для компільованих мов чи застосунків з важкими залежностями лише для часу збірки.
3. Перевір вибір базового образу: чи використовується повний OS-образ там, де підійшов би slim чи distroless варіант (напр., `node:20` проти `node:20-slim` проти distroless варіанту), і чи компроміс (менший образ проти відсутності shell/інструментів дебагу в продакшні) відповідний для цього випадку використання?
4. Перевір на непотрібне роздуття шарів: кеші пакетного менеджера, не очищені в тому самому шарі, де створені (патерн `RUN apt-get install && rm -rf /var/lib/apt/lists/*`, не дві окремі RUN-команди, оскільки шари Docker кумулятивні — очищення в пізнішому шарі не зменшує ранішого), непотрібні файли, скопійовані через широкий `COPY . .` без `.dockerignore`, що виключає артефакти збірки/node_modules/.git.
5. Перевір на пропущені можливості паралелізації чи кешування збірки, специфічні для інструмента збірки (напр., BuildKit cache mounts для кешів пакетного менеджера крізь збірки, що зберігаються навіть крізь зміни шарів, що інвалідують кеш).
6. Перевір, що оптимізований Dockerfile точно зберігає поведінку оригіналу під час виконання — змінні середовища, відкриті порти, entrypoint/cmd, user/права — не втрачай мовчки щось на кшталт директиви `USER` без root під час оптимізації.

Формат виводу: переписаний Dockerfile, за яким слідує список пунктів того, що змінилося і чому, з очікуваним впливом на розмір/час збірки кожної зміни (якісно, якщо не можеш виміряти: "великий", "помірний", "малий").
```

## Змінні
- `{{DOCKERFILE}}` — Dockerfile для оптимізації. Обов'язково.
- `{{APP_CONTEXT}}` — мова/фреймворк, якщо не очевидно з самого Dockerfile. Необов'язково.
- `{{CONSTRAINTS}}` — будь-які фіксовані вимоги (базовий образ, комплаєнс, тулінг), що обмежують оптимізацію. Необов'язково.

## Приклад
**Вхід:** `{{DOCKERFILE}}` = Node.js Dockerfile, що робить `COPY . .`, потім `RUN npm install`, потім `CMD`, використовуючи `node:20` як базовий образ, без multi-stage збірки.

**Вихід (фрагмент):**
```dockerfile
FROM node:20-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-slim
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
COPY package.json ./
CMD ["node", "dist/index.js"]
```
*(далі: "Переупорядковано встановлення залежностей перед копіюванням коду — ВЕЛИКИЙ вплив на час збірки для змін лише коду, оскільки `npm ci` більше не перезапускається, коли змінюється лише код застосунку. Додано multi-stage збірку, що відокремлює інструментарій збірки від runtime — ПОМІРНИЙ вплив на розмір фінального образу. Перехід на `node:20-slim` — ПОМІРНИЙ вплив на розмір образу.")*

## Поради та варіації
- Для монорепо з кількома сервісами, що ділять патерн Dockerfile, попроси також позначити можливості для спільного шару базового образу крізь сервіси для максимізації повторного використання кешу.
- Якщо час збірки (не розмір образу) — основна турбота, явно попроси пріоритезувати рекомендації BuildKit cache mount над техніками зменшення розміру, що не допомагають швидкості збірки (напр., деякі підходи стискання шарів зменшують образ, але не прискорюють збірки).
