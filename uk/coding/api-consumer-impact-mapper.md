## Опис
Мапує, на яких внутрішніх споживачів реально вплине breaking change в API, до того, як вона вийде. Для сеньйора, що планує breaking change у внутрішньому/спільному API — відрізняється від `api-contract-consistency-reviewer` (перевіряє узгодженість між ендпоінтами, а не хто їх викликає) і `dependency-upgrade-impact-assessor` (оновлення зовнішніх бібліотек, а не власного внутрішнього API).

## Коли використовувати
- Плануєш breaking change у широко використовуваному внутрішньому API і треба знати, кого повідомити чи з ким скоординуватись перед випуском.
- Минулий breaking change спричинив несподіваний збій у команді, з якою не проконсультувались, і хочеш цього разу зробити це правильно.
- Вирішуєш, чи зміна реально безпечна для випуску без широкої координації, чи справді її потребує.

## Промпт

```
Ти мапуєш вплив запропонованого breaking change у внутрішньому API на його відомих і потенційно невідомих споживачів — до того, як зміна вийде, а не після того, як інцидент розкриє, хто реально постраждав.

Запропонована зміна (що змінюється в API): {{PROPOSED_CHANGE}}

Список відомих споживачів (команди/сервіси, відомі як такі, що викликають цей API, наскільки б неповним цей список не був): {{KNOWN_CONSUMER_LIST}}

Доступні методи виявлення (необов'язково — логи API-шлюзу, телеметрія service mesh, пошук коду в монорепо, каталог сервісів): {{DISCOVERY_METHODS_AVAILABLE}}

Для кожного відомого споживача:
1. Оціни, чи запропонована зміна реально впливає на їхнє використання — не кожен споживач API постраждає від кожної зміни в ньому; суди конкретно на основі того, від яких полів, ендпоінтів чи поведінки вони, за описом, залежать.
2. Познач споживачів, чий вплив справді невизначений з наданого опису і потребує прямого підтвердження від цієї команди, а не припущення ззовні.

Потім запропонуй конкретний план виявлення для споживачів поза відомим списком, використовуючи будь-які реально доступні методи виявлення — не пропускай цей крок, вважаючи відомий список обов'язково повним.

Виведи: таблицю впливу на кожного споживача (постраждав / не постраждав / потребує підтвердження, з обґрунтуванням для кожного), список "має бути підтверджено перед випуском" з невизначених пунктів, і план виявлення для невідомих.

Якщо список відомих споживачів взагалі не наданий, не переходь одразу до пропозиції методів виявлення з нуля — спочатку спитай, чи вже існує десь список споживачів, який просто не був включений (каталог сервісів, реєстр клієнтів API-шлюзу, попередня документація), перш ніж припускати, що його немає.
```

## Змінні
- `{{PROPOSED_CHANGE}}` — що змінюється в API. Обов'язково.
- `{{KNOWN_CONSUMER_LIST}}` — команди/сервіси, відомі як користувачі, наскільки відомо. Обов'язково.
- `{{DISCOVERY_METHODS_AVAILABLE}}` — який інструментарій існує для пошуку ще не відомих споживачів. Необов'язково; без нього пропонуються загальні підходи виявлення, позначені як такі, що потребують адаптації під конкретний інструментарій.

## Приклад
**Вхід:** `{{PROPOSED_CHANGE}}` = "видалення застарілого поля `legacy_status` з відповіді `/orders/{id}`, на користь наявного поля `status`", `{{KNOWN_CONSUMER_LIST}}` = "checkout-service (підтверджено використання `status`, не `legacy_status`), reporting-service (незрозуміло, яке поле він читає), партнерська інтеграція (немає прямого контакту, виявлена лише через логи API-шлюзу)", `{{DISCOVERY_METHODS_AVAILABLE}}` = "логи доступу API-шлюзу з тегуванням client ID, монорепо для внутрішніх сервісів".

**Вихід (фрагмент):**
```
checkout-service: НЕ ПОСТРАЖДАВ. Підтверджено, що вже використовує `status`, а не поле, що видаляється — дій не потрібно, але варто короткої примітки "для інформації, дій не потрібно", а не тиша, щоб вони не гадали, чи щось пропустили.

reporting-service: ПОТРЕБУЄ ПІДТВЕРДЖЕННЯ. Використання поля незрозуміле з наданого опису — не вважай на основі загального очікування, що звітний сервіс "напевно" використовує те поле, що зараз актуальне. Грепни репозиторій reporting-service у монорепо на `legacy_status` напряму (доступний метод виявлення), а не лише питай команду, оскільки пошук коду дасть остаточну відповідь швидше, ніж очікування відповіді.

Партнерська інтеграція: ПОТРЕБУЄ ПІДТВЕРДЖЕННЯ, найвищий ризик. Немає прямого каналу зв'язку, лише непряме виявлення через логи шлюзу — це споживач, найбільш ймовірно тихо зламаний цією зміною. Перед випуском перевір логи шлюзу конкретно на те, чи реальна обробка запиту/відповіді цього клієнта торкається `legacy_status` (якщо тіла запитів логуються), чи звернись через будь-який наявний канал партнерських стосунків, навіть якщо це не прямий інженерний контакт.

План виявлення невідомих: запитай логи API-шлюзу на всі окремі client ID, що звертались до `/orders/{id}` за останні 30 днів, звір з відомим списком споживачів вище, і поводься з будь-яким невідповідним client ID як з невідомим споживачем, що потребує того самого процесу підтвердження перед випуском зміни.
```

## Поради та варіації
- Якщо service mesh чи API-шлюз можуть згенерувати остаточний список усіх викликачів за нещодавній період, надавай перевагу цьому над покладанням на (часто застарілий) відомий список споживачів з документації чи пам'яті.
- Для справді низькоризикової зміни (наприклад, додавання нового необов'язкового поля, а не видалення) такий рівень мапування споживачів, ймовірно, надлишковий — резервуй його для змін, що реально є breaking, а не рутинних адитивних.
