## Опис
Рецензує потік автентифікації/авторизації — логін, управління сесіями, оновлення токенів, перевірки прав — на логічні слабкості, не ін'єкції чи секрети. Відрізняється від широкого проходу «Чекліста рев'ю коду на безпеку»: це глибоке рев'ю на рівні потоку однієї з областей системи з найвищими наслідками.

## Коли використовувати
- Рев'ю нового чи зміненого потоку логіну, сесії чи перевірки прав перед релізом.
- Аудит наявної системи автентифікації після виникнення занепокоєння безпекою, чи як частина періодичного рев'ю безпеки.
- Вивчення поширених патернів вразливостей автентифікації через їх перевірку на реальному коді потоку, а не абстрактне читання документації OWASP.

## Промпт

```
Ти рецензуєш потік автентифікації/авторизації на логічні слабкості — не ін'єкції, не управління секретами (для них є окремі рев'ю), а вади в самій логіці автентифікації.

Опис потоку та/або код (логін, обробка сесій, видача/оновлення токенів, перевірки прав — що в обсязі): {{AUTH_FLOW}}
Контекст системи (необов'язково — напр., "single-page app з JWT", "серверно-рендерений застосунок з серверними сесіями"): {{SYSTEM_CONTEXT}}

Інструкції:
1. Перевір логіку автентифікації: чи перевірка пароля/облікових даних стійка до атак на таймінг (порівняння за постійний час, не `==`/`.equals()` на секретах)? Чи є rate limiting чи блокування при повторних невдалих спробах (захист від brute-force)? Чи повідомлення про помилки при невдалому логіні достатньо загальні, щоб не розкривати існування імені користувача (ризик перерахунку користувачів)?
2. Перевір управління сесіями/токенами: як сесії інвалідуються при виході — на сервері (токен/сесія фактично відкликані) чи лише на клієнті (JWT, що лишається валідним до природного закінчення терміну навіть після "виходу")? Чи потік оновлення токена вразливий до того, що вкрадений refresh-токен використовується безкінечно (без ротації, без виявлення повторного використання)? Чи токени сесії передаються й зберігаються безпечно (флаги HttpOnly/Secure для cookie, не localStorage для чутливих токенів там, де XSS — реальний ризик)?
3. Явно перевір логіку авторизації/прав: чи авторизація перевіряється на кожній захищеній дії, чи лише іноді (напр., перевіряється при завантаженні сторінки, але не на базовому виклику API, дозволяючи прямий доступ до API для обходу перевірки на рівні UI)? Чи є місце, де авторизація покладається на надане клієнтом значення (роль чи ID користувача з тіла/параметрів запиту), а не на виведену на сервері ідентичність — це поширений вектор ескалації привілеїв (IDOR: Insecure Direct Object Reference).
4. Перевір на шляхи ескалації привілеїв: чи може користувач змінити запит, щоб діяти від імені іншого ID користувача, чи отримати доступ до ресурсів іншого користувача, вгадавши/перерахувавши ID, оскільки перевірка авторизації підтверджує "чи це валідний ресурс", а не "чи саме цей користувач володіє/має доступ до саме цього ресурсу"?
5. Перевір потік скидання пароля/відновлення акаунта, якщо в обсязі: чи токен скидання одноразовий, обмежений за часом і достатньо випадковий (не передбачуваний/короткий)? Чи сам потік/посилання скидання не витікає токен через заголовки referrer чи логи?
6. Перевір на фіксацію сесії: чи ідентифікатор сесії змінюється при зміні привілеїв (напр., при логіні чи ID сесії до логіну замінюється, а не повторно використовується після автентифікації)?
7. Для кожної знахідки опиши конкретний сценарій атаки, який вона уможливлює (конкретна послідовність дій зловмисника), і конкретне виправлення — не загальне "покращ свою автентифікацію".

Формат виводу: Markdown, один запис на знахідку, згруповано за категорією (Автентифікація / Управління сесіями та токенами / Авторизація / Ескалація привілеїв / Відновлення акаунта), кожен з критичністю, сценарієм атаки і виправленням.
```

## Змінні
- `{{AUTH_FLOW}}` — опис потоку чи код для рецензування. Обов'язково.
- `{{SYSTEM_CONTEXT}}` — архітектура (SPA/JWT, серверні сесії тощо), оскільки правильні патерни різняться. Необов'язково, але суттєво уточнює рев'ю.

## Приклад
**Вхід:** `{{AUTH_FLOW}}` = Express API, де `GET /api/orders/:id` отримує замовлення за ID і повертає його, якщо запитувач автентифікований, без перевірки, чи замовлення належить цьому користувачу.

**Вихід (фрагмент):**
```
### Авторизація — CRITICAL (IDOR)
`GET /api/orders/:id` перевіряє наявність валідної автентифікованої сесії, але не перевіряє, чи автентифікований користувач володіє запитаним замовленням — будь-який автентифікований користувач може переглянути замовлення будь-якого іншого користувача, вгадавши/інкрементуючи `:id`.
Сценарій атаки: Користувач A, залогінений, запитує `/api/orders/1`, `/api/orders/2`, `/api/orders/3`... і бачить деталі замовлень інших користувачів (потенційно включно з адресами, платіжною інформацією) без жодної відмови авторизації.
Виправлення: додай явну перевірку володіння: `if (order.userId !== req.user.id) return res.status(404).send()` (повертай 404, не 403, щоб уникнути підтвердження існування ресурсу для ID, якими користувач не володіє).
```

## Поради та варіації
- Для мультитенантної системи явно додай ізоляцію тенантів до обсягу рев'ю — доступ до даних крізь тенантів є варіантом IDOR з вищою типовою критичністю, і його легко пропустити, якщо рев'ювер думає лише в категоріях перевірок на рівні користувача.
- Якщо рецензуєш конкретно інтеграцію OAuth/SSO, попроси також перевірити валідацію параметра state (захист CSRF у потоці OAuth) і валідацію redirect URI (ризик open redirect) — поширені специфічні для OAuth слабкості, які чекліст цього загального промпту не покриває за замовчуванням.
