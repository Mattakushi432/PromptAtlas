## Опис
Пропонує, як розділити один великий файл чи модуль на менші, згуртовані, на основі його фактичної внутрішньої структури — план декомпозиції на рівні модулів, не пропозиція меж сервісів/мікросервісів і не виділення однієї функції. Для файлу, що виріс занадто великим для навігації, не обов'язково занадто складним логічно.

## Коли використовувати
- Один файл виріс до тисяч рядків, і знайти в ньому щось вимагає пошуку, а не пам'яті.
- Кілька людей постійно стикаються з конфліктами мерджу в тому самому гігантському файлі, бо непов'язані фічі живуть у ньому разом.
- Перед додаванням великої нової фічі до великого модуля, з бажанням спочатку розділити його, щоб додавання мало очевидне місце.

## Промпт

```
Ти плануєш, як розділити один великий файл/модуль на менші, згуртовані модулі на основі його фактичної внутрішньої структури — не пропонуєш мікросервіси чи повний архітектурний редизайн, і не просто виділяєш одну функцію.

Файл/модуль для декомпозиції:
{{FILE_CONTENTS}}

Обмеження (необов'язково — напр., "публічне API має залишитися тим самим", "не можна вводити циклічні імпорти", "команда віддає перевагу розділенню за фічами, а не за типами"): {{CONSTRAINTS}}

Інструкції:
1. Визнач окремі турботи/відповідальності, наразі змішані в цьому файлі — групуй функції/класи/константи за тим, що вони фактично роблять разом, на основі спільних даних, з якими вони працюють, і того, як часто вони викликають одна одну, а не лише за поверхневою схожістю.
2. Запропонуй набір нових модулів, кожен з: назвою, відповідальністю одним реченням, і які конкретні функції/класи/константи з оригінального файлу переходять у нього.
3. Визнач, що має залишитися спільним (типи, константи, невеликий набір утиліт, використовуваних кількома новими модулями), і де цей спільний код має жити, щоб не стати новим звалищем.
4. Зістав залежності між запропонованими новими модулями — якщо модулю A потрібно імпортувати з модуля B, скажи про це і познач, якщо це створює незграбний чи циклічний зв'язок, що натякає на неправильну межу.
5. Якщо {{CONSTRAINTS}} вказує, що публічне API має бути збережене, покажи, як публічні експорти оригінального файлу реекспортуються (напр., тонкий барель `index.ts`), щоб зовнішні споживачі не зламалися.
6. Впорядкуй фактичну міграцію як послідовність безпечних, незалежно-мерджованих кроків (не "зроби все в одному PR") — переміщуючи найізольованіший шматок першим, найзаплутаніший — останнім.
7. Якщо файл насправді не має роздільних турбот (це дійсно одна згуртована річ, яка просто довга), скажи про це, а не форсуй штучне розділення.

Формат виводу: Markdown з розділами: Запропоновані модулі (з відповідальностями та вмістом), Спільний код, Карта залежностей, Порядок міграції.
```

## Змінні
- `{{FILE_CONTENTS}}` — великий файл/модуль для декомпозиції. Обов'язково.
- `{{CONSTRAINTS}}` — сумісність API, обмеження імпортів чи вподобання команди, що формують розділення. Необов'язково.

## Приклад
**Вхід:** `{{FILE_CONTENTS}}` = 2000-рядковий `utils.ts`, що змішує форматування дат, хелпери API-клієнта та функції валідації форм без чіткої організації.

**Вихід (фрагмент):**
```
### Запропоновані модулі
1. **date-formatting.ts** — Форматування та парсинг дат для відображення. Містить: `formatDate`, `parseRelativeDate`, константу `DATE_FORMATS`.
2. **api-client-helpers.ts** — Формування запитів/відповідей для API-клієнта. Містить: `buildQueryString`, `parseApiError`, залежить від `date-formatting.ts` для серіалізації таймстемпів.
3. **form-validation.ts** — Правила валідації вводу. Містить: `validateEmail`, `validateRequired`. Без залежності від двох інших.

### Порядок міграції
1. Спочатку виділи `form-validation.ts` — нуль залежностей від інших груп, найбезпечніше перемістити.
2. Далі виділи `date-formatting.ts` — одна внутрішня залежність (api-client-helpers), але від нього нічого не залежить, що також не переміщується.
3. Виділи `api-client-helpers.ts` останнім, явно імпортуючи `date-formatting.ts`.
```

## Поради та варіації
- Для монорепо зі строгим лінтингом меж імпортів попроси також запропонувати конфігурацію правила лінтера/path alias, потрібну для примусового дотримання нових меж надалі.
- Якщо команда посеред міграції на інший архітектурний патерн (напр., папки за фічами), передай цей патерн як обмеження, щоб запропоновані модулі йому відповідали, а не розділенню за типами загального вигляду.
