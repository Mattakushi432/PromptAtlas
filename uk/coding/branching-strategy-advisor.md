## Опис
Рекомендує стратегію гілкування Git (trunk-based, Git Flow, GitHub Flow чи варіант) на основі фактичного розміру команди й темпу релізів — не загальне пояснення кожної моделі. Для реального рішення про процес команди, не туторіал з Git.

## Коли використовувати
- Налаштування конвенцій Git-воркфлоу для нової команди чи проєкту.
- Наявна стратегія гілкування спричиняє тертя (довгоживучі гілки застарівають, конфлікти мерджу накопичуються, релізи блокуються непов'язаною роботою в польоті) і потребує переоцінки.
- Пояснення команді, чому конкретна стратегія відповідає їхній ситуації, з обґрунтуванням, яке вони можуть оскаржити, якщо обмеження неправильні.

## Промпт

```
Ти рекомендуєш стратегію гілкування Git на основі конкретних наданих обмежень команди й релізу — не загальне порівняння всіх моделей.

Розмір і структура команди (необов'язково — напр., "5 інженерів, одна команда" проти "40 інженерів у 6 командах"): {{TEAM_STRUCTURE}}
Темп релізів (як часто код фактично виходить — безперервно, щотижня, щомісяця, чи прив'язаний до циклів рев'ю магазину застосунків): {{RELEASE_CADENCE}}
Обмеження (необов'язково — напр., "потрібно одночасно підтримувати кілька продакшн-версій", "мобільний застосунок із затримками рев'ю магазину застосунків"): {{CONSTRAINTS}}

Інструкції:
1. Зваж trunk-based розробку (короткоживучі гілки, часті мерджі в main, feature flags для незавершеної роботи) проти наданого розміру команди й темпу: вона добре підходить малим-середнім командам, що деплоять часто/безперервно, але вимагає або сильної дисципліни CI/тестування, або зрілості feature-flag'ів, щоб уникнути деплою напівготової роботи — явно зазнач цю передумову, а не припускай, що вона вже на місці.
2. Зваж Git Flow (структура гілок develop/release/hotfix/feature) проти обмежень: вона підходить ситуаціям, що потребують одночасної підтримки кількох випущених версій (напр., продукт у магазині застосунків із затримками рев'ю, чи ПЗ з версіями довгострокової підтримки), але додає реальні накладні витрати процесу, які марні для команди, що деплоїть безперервно без тягаря підтримки кількох версій.
3. Зваж GitHub Flow / просту модель feature-гілка-плюс-PR як середній варіант: короткі feature-гілки, замерджені через PR у main, деплой з main, без повної ієрархії гілок Git Flow — часто правильний варіант за замовчуванням для команди, що хоче PR-рев'ю, але не має обмеження підтримки кількох версій Git Flow.
4. Дай конкретну рекомендацію з основною причиною, прив'язаною до {{TEAM_STRUCTURE}} і {{RELEASE_CADENCE}} — не хедж, що перелічує плюси/мінуси кожної опції без висновку.
5. Якщо {{CONSTRAINTS}} включає щось, що сильно диктує відповідь (напр., "має підтримувати 3 паралельні продакшн-версії для enterprise-клієнтів з різними графіками оновлення"), дозволь цьому обмеженню керувати рекомендацією, навіть якщо воно конфліктує з тим, що передбачив би сам розмір команди/темп.
6. Зазнач конкретні частини процесу, які рекомендація передбачає на практиці: конвенцію іменування гілок, вимоги рев'ю PR, як вирізаються релізи, як обробляються hotfix'и — сама назва стратегії недієва без цього.
7. Якщо наявна стратегія спричиняє конкретну описану болючу точку, діагностуй, чи біль дійсно невідповідність стратегії, чи прогалина дисципліни/тулінгу в межах поточної стратегії (напр., trunk-based без feature flags насправді не є trunk-based), перш ніж рекомендувати повну зміну.

Формат виводу: Markdown з розділами: Рекомендована стратегія (з основним обґрунтуванням), Практичні деталі процесу, і (якщо застосовно) Діагноз поточної болючої точки.
```

## Змінні
- `{{TEAM_STRUCTURE}}` — розмір команди і як вона організована. Обов'язково.
- `{{RELEASE_CADENCE}}` — як часто і як фактично виходить код. Обов'язково — це зазвичай вирішальний фактор поряд з розміром команди.
- `{{CONSTRAINTS}}` — все, що могло б перевизначити рекомендацію за замовчуванням (підтримка кількох версій, затримки рев'ю, комплаєнс). Необов'язково, але може бути вирішальним.

## Приклад
**Вхід:** `{{TEAM_STRUCTURE}}` = "8 інженерів, одна команда", `{{RELEASE_CADENCE}}` = "деплой у продакшн кілька разів на день", `{{CONSTRAINTS}}` = "немає потреби підтримувати старі версії; веб-застосунок, без затримки магазину застосунків".

**Вихід (фрагмент):**
```
## Рекомендована стратегія
Trunk-based розробка. Маленька команда, що деплоїть кілька разів на день без тягаря підтримки кількох версій, близька до ідеального кейсу для trunk-based — накладні витрати гілок release/hotfix Git Flow додали б вартість процесу без відповідної вигоди тут, оскільки немає нічого для паралельної підтримки.

## Практичні деталі процесу
Короткоживучі feature-гілки (ідеально до 1-2 днів), замерджені в main через PR після рев'ю і проходження CI. Незавершені фічі, які не можуть вийти того самого дня, мають бути закриті за feature flag, а не залишені на довгоживучій гілці — це навантажена передумова для безпечної роботи trunk-based; без неї main стає нестабільним.
```

## Поради та варіації
- Для монорепо з кількома незалежно деплойованими сервісами зазнач, що різні сервіси в межах того самого репозиторію можуть розумно використовувати різні темпи релізів навіть за однієї загальної конвенції гілкування — не форсуй одноманітність там, де вона не потрібна.
- Якщо команда наразі на Git Flow і розглядає спрощення, попроси також окреслити шлях міграції (як згорнути довгоживучі гілки develop/release), а не просто рекомендувати цільовий стан.
