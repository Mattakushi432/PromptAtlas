## Опис
Проєктує поетапний план рол-ауту через feature flag — етапи, метрики для спостереження, умови kill-switch і критерії видалення флагу — для конкретної ризикованої зміни. Відрізняється від плану відкату на рівні деплою: тут йдеться про поступове відкриття зміни реальному трафіку за флагом, а не про скасування деплою.

## Коли використовувати
- Викочуєш зміну, достатньо ризиковану, щоб "переключити флаг на 100% і подивитись" було недостатньо.
- Пишеш секцію рол-ауту в плані запуску чи дизайн-документі.
- Вирішуєш, що насправді означає "безпечно видалити цей флаг", перш ніж флаг стане постійним техборгом.

## Промпт

```
Ти проєктуєш поетапний план рол-ауту через feature flag для конкретної зміни — не загальний план деплою чи відкату.

Зміна, що викочується: {{CHANGE_DESCRIPTION}}

Відомі фактори ризику (що правдоподібно може піти не так): {{RISK_FACTORS}}

Доступні сегменти користувачів для поетапності (необов'язково — наприклад, внутрішні користувачі, опт-ін бета, відсотковий рандомний спліт): {{USER_SEGMENTS}}

Створи:
1. Таблицю поетапного рол-ауту: кожен етап (наприклад, лише внутрішні → 1% → 10% → 50% → 100%), конкретну метрику чи сигнал для спостереження на цьому етапі (прив'язану до реальних наданих факторів ризику, а не загальне "моніторити помилки"), і мінімальний час утримання перед переходом далі.
2. Явні умови спрацювання kill-switch — яка метрика, перетнувши який поріг, має тригерити відкат, і чи це має бути автоматично, чи потребує рішення людини.
3. Критерії видалення флагу — як конкретно виглядає "повністю викочено і безпечно видалити цей флаг", щоб він не залишався постійним боргом.

Якщо зміна не має осмисленого способу сегментувати користувачів (наприклад, одноразова батчева джоба, міграція схеми, внутрішня cron-задача), явно скажи, що поетапний рол-аут через флаг не підходить для цієї зміни, і запропонуй інший механізм безпеки замість того, щоб насильно накидати структуру поетапного флага.
```

## Змінні
- `{{CHANGE_DESCRIPTION}}` — що викочується. Обов'язково.
- `{{RISK_FACTORS}}` — конкретні способи, якими ця зміна може піти не так. Обов'язково — без цього метрики для спостереження будуть загальними, а не прицільними.
- `{{USER_SEGMENTS}}` — які механізми поетапності реально доступні (внутрішні користувачі, бета-список, відсотковий рол-аут). Необов'язково; без нього мається на увазі стандартна відсоткова поетапність.

## Приклад
**Вхід:** `{{CHANGE_DESCRIPTION}}` = "новий платіжний процесор для оформлення замовлення, що замінює поточний", `{{RISK_FACTORS}}` = "збої платежів, неправильні суми списання, простій API провайдера", `{{USER_SEGMENTS}}` = "внутрішні співробітники, потім відсотковий рол-аут".

**Вихід (фрагмент):**
```
Етап 1 — лише внутрішні: спостерігати за відсотком успішних платежів і звіркою сум списання проти логів старого процесора для тих самих типів транзакцій. Утримання: доки не оброблено щонайменше 50 внутрішніх транзакцій з нульовими розбіжностями сум.
Етап 2 — 1% реального трафіку: спостерігати за дельтою відсотка успішних платежів проти контрольної групи (старий процесор на решті 99%), відсоток помилок API провайдера. Утримання: мінімум 48 годин, щоб охопити повний тижневий цикл трафіку.

Kill-switch: автоматичний відкат, якщо відсоток успішних платежів на новому процесорі падає більше ніж на 2 процентні пункти нижче контрольної групи протягом будь-якого 15-хвилинного вікна, або якщо виявлено будь-яку розбіжність суми списання (нульова толерантність — тут потрібен ручний розгляд людиною, а не лише моніторинг).

Критерії видалення флагу: 100% трафіку на новому процесорі протягом 2 повних тижнів без жодного ручного відкату, плюс код-шлях старого процесора явно видалено (а не просто вимкнено флагом), перш ніж це закривати.
```

## Поради та варіації
- Для зміни з добре відомим радіусом ураження (наприклад, суто UI-правка) секцію kill-switch можна звести до одного простого сигналу — не накидай важку структуру на низькоризиковану зміну.
- Поєднуй з `deployment-rollback-planner` для механіки відкату на рівні деплою, яку цей план рол-ауту передбачає як наявну.
