## Опис
Діагностує, чому цикл рев'ю PR команди повільний, на основі опису реального процесу — діагностика процесу на рівні команди для інженерного менеджера, відрізняється від `pr-review-assistant` (рецензує вміст одного PR) і `constructive-review-comment-rewriter` (покращує тон коментарів). Тут не розглядається вміст жодного PR — лише те, чому PR простоюють.

## Коли використовувати
- PR простоюють відкритими днями, і незрозуміло чому.
- Успадкував команду з процесом рев'ю, що здається повільним, не знаючи, яка частина реально є вузьким місцем.
- Готуєшся до ретро саме про швидкість рев'ю.

## Промпт

```
Ти діагностуєш вузьке місце на рівні команди у швидкості рев'ю коду — не рецензуєш вміст жодного конкретного PR і не пропонуєш загальну пораду "рецензуй швидше".

Опис процесу (як призначаються рецензенти, розмір команди, типовий розмір PR, будь-які доступні метрики типу медіанного часу до першого рев'ю): {{PROCESS_DESCRIPTION}}

Спостережувані симптоми (що реально відбувається — наприклад, PR лежать повністю без рев'ю днями, чи отримують початкове рев'ю швидко, але проходять багато повільних раундів обговорення): {{SYMPTOMS}}

1. Висуни гіпотези про ймовірну категорію вузького місця, ранговані за тим, наскільки кожна відповідає заявленим симптомам: неоднозначність призначення/відповідальності (немає чітко відповідального рецензента, тож усі вважають, що хтось інший підхопить), перевантаження рецензентів (замало людей роблять рев'ю відносно обсягу PR — проблема пропускної здатності, а не процесу), розмір PR (великі diff'и природно займають більше часу і отримують нижчий пріоритет на користь швидших перемог), розрив часових поясів/асинхронність (рецензент і автор рідко мають перетин робочих годин), чи відсутність норм/SLA рев'ю (немає спільного очікування, наскільки швидко має відбутись рев'ю).
2. Для кожної гіпотези запропонуй одну конкретну, перевірювану зміну процесу — не розпливчасте "спілкуйтесь краще", а щось достатньо конкретне, щоб реально спробувати (наприклад, автопризначення на основі ротації, м'який ліміт розміру PR з нормою "розбий це", явне SLA першої відповіді протягом 1 робочого дня).
3. Вкажи, яка метрика підтвердила б чи спростувала кожну гіпотезу, якби зміну спробували — щоб це стало перевірюваним діагнозом, а не просто здогадкою, яку треба прийняти на віру.

Якщо описаний процес звучить розумно сам по собі, але обсяг PR просто завеликий для розміру команди, чесно скажи це — це проблема штату/пропускної здатності, а не баг процесу, і жодна зміна процесу не виправить справжню нестачу пропускної здатності.
```

## Змінні
- `{{PROCESS_DESCRIPTION}}` — як реально працює процес рев'ю сьогодні, розмір команди і будь-які доступні метрики. Обов'язково.
- `{{SYMPTOMS}}` — конкретний, спостережуваний патерн повільності. Обов'язково — різні патерни симптомів вказують на різні вузькі місця.

## Приклад
**Вхід:** `{{PROCESS_DESCRIPTION}}` = "команда з 8 людей, немає формального призначення рецензента — автор обирає, кого вважає вільним, немає SLA", `{{SYMPTOMS}}` = "PR часто лежать повністю без рев'ю 2-3 дні, перш ніж хтось прокоментує".

**Вихід (фрагмент):**
```
Топ-гіпотеза: неоднозначність призначення/відповідальності. Без формального призначення й авторів, що обирають рецензента ситуативно, є реальний ризик розмиття відповідальності — якщо автор помиляється щодо того, хто вільний, PR може лежати невидимим для всіх, хто реально міг би його підхопити, оскільки жодна конкретна людина не повідомлена як "відповідальна".

Запропонована зміна для перевірки: автопризначення на основі ротації (наприклад, бот round-robin, що призначає рівно одного основного рецензента на PR), а не вгадування автором, хто вільний.

Метрика для перевірки: відстежуй медіанний час до першого коментаря до і після — якщо ця гіпотеза правильна, він має помітно впасти протягом 1-2 тижнів після старту ротації, оскільки PR більше не залежатимуть від правильного вгадування автором доступності.

(Другорядна гіпотеза, нижча відповідність: перевантаження рецензентів — варто перевірити обсяг PR відносно розміру команди, але патерн "лежить з нулем коментарів" конкретно вказує радше на те, що ніхто явно не відповідальний, ніж на те, що всі занадто зайняті, щоб дійти до нього.)
```

## Поради та варіації
- Якщо метрики реально недоступні (немає відстеженого часу до першого рев'ю), попроси порекомендувати одну найдешевшу метрику для початку відстеження перед будь-якою зміною процесу — діагностика без базової лінії ризикує не дізнатись, чи фікс реально спрацював.
- Для розподіленої/віддаленої команди зваж гіпотезу розриву часових поясів сильніше і попроси конкретно перевірити, чи `{{PROCESS_DESCRIPTION}}` взагалі згадує врахування перетину робочих годин.
