## Опис
Аудитує сторінку на вузькі місця Core Web Vitals (LCP, INP, CLS) з опису сторінки та/або даних профілювання, і дає конкретні виправлення, ранжовані за впливом — для сторінки з відомими чи підозрюваними проблемами продуктивності, відрізняється від планування бекенд-масштабованості.

## Коли використовувати
- Сторінка отримує погані оцінки Core Web Vitals (у Lighthouse, CrUX чи моніторингу реальних користувачів) і потребує пріоритезованого списку виправлень, не загального чекліста продуктивності.
- Рев'ю нової сторінки/фічі перед запуском, щоб рано виловити очевидні регресії Core Web Vitals.
- Пояснення стейкхолдерам, чому конкретна сторінка повільна, термінами, прив'язаними до фактичних метрик, що впливають на SEO/UX, а не розпливчастим "здається повільним".

## Промпт

```
Ти аудитуєш вузькі місця Core Web Vitals сторінки з наданого опису/даних, і надаєш конкретні, ранжовані виправлення — не загальний пояснювач Core Web Vitals.

Опис сторінки (що вона рендерить, ключові ресурси — зображення, шрифти, сторонні скрипти, основний контент): {{PAGE_DESCRIPTION}}
Дані профілювання, якщо доступні (звіт Lighthouse, дані CrUX, підсумок трасування продуктивності): {{PROFILING_DATA}}
Відомі/підозрювані проблемні області (необов'язково): {{SUSPECTED_ISSUES}}

Інструкції:
1. Для LCP (Largest Contentful Paint): визнач, який елемент, ймовірно, є кандидатом LCP (зазвичай hero-зображення, великий текстовий блок чи контент над згином) і що затримує його — блокуючі рендеринг ресурси перед ним, пізно виявлене зображення (не попередньо завантажене, завантажене через JS замість звичайного `<img>`), відсутній `fetchpriority="high"`, чи повільний час відповіді сервера (TTFB), якщо можна вивести.
2. Для INP (Interaction to Next Paint): визнач ймовірні джерела затримки вводу чи довгих завдань — важке виконання JS, що блокує головний потік при взаємодії, великі перерендери компонентів, неоптимізовані обробники подій, чи сторонні скрипти, що монополізують головний потік.
3. Для CLS (Cumulative Layout Shift): визнач елементи, що ймовірно спричиняють зсув — зображення/вбудовування без явних width/height, веб-шрифти, що спричиняють reflow FOIT/FOUT, контент, вставлений над наявним контентом (реклама, банери, повідомлення про cookie) без зарезервованого простору, чи динамічно завантажений контент без плейсхолдера/скелетона.
4. Для кожної знахідки наведи конкретний доказ (з {{PROFILING_DATA}}, якщо надано, чи виведений з {{PAGE_DESCRIPTION}}, якщо ні) і дай конкретне виправлення — зміну на рівні коду чи завантаження ресурсів, не розпливчасту директиву "оптимізуй зображення".
5. Ранжуй знахідки за очікуваним впливом на фактичну оцінку метрики, не лише за легкістю виправлення — велика перемога, що вимагає більше роботи, все одно має ранжуватися вище за тривіальне виправлення з незначним впливом, хоча зазнач обидва.
6. Якщо {{PROFILING_DATA}} не надано, дай найкращий заснований на міркуваннях діагноз з опису сторінки, і скажи, які конкретні дані профілювання (трасування Lighthouse, польові дані CrUX) підтвердили б чи виправили б його.

Формат виводу: Markdown з розділами на кожну метрику (LCP / INP / CLS), кожен з ранжованими знахідками: проблема, доказ, виправлення, очікуваний вплив.
```

## Змінні
- `{{PAGE_DESCRIPTION}}` — що рендерить сторінка і її ключові ресурси. Обов'язково.
- `{{PROFILING_DATA}}` — фактичні дані вимірювання (Lighthouse, CrUX, трасування). Необов'язково, але перетворює аудит з висновку на діагноз.
- `{{SUSPECTED_ISSUES}}` — відомі проблемні області для пріоритетного дослідження. Необов'язково.

## Приклад
**Вхід:** `{{PAGE_DESCRIPTION}}` = "сторінка товару з великим hero-зображенням, завантаженим через JS-керований компонент каруселі зображень, плюс три блокуючі рендеринг сторонні скрипти аналітики в `<head>`", `{{PROFILING_DATA}}` = "Lighthouse: LCP 4.2s, елемент LCP — hero-зображення".

**Вихід (фрагмент):**
```
## LCP (4.2s — ціль менше 2.5s)
1. **[Високий вплив] Hero-зображення завантажується через JS-компонент каруселі, не звичайний `<img>`**
   Доказ: Lighthouse визначає hero-зображення як елемент LCP; зображення, відрендерене через JS, виявляється сканером попереднього завантаження браузера значно пізніше, ніж звичайний `<img src>` у початковому HTML, суттєво затримуючи LCP.
   Виправлення: рендери hero-зображення-кандидата LCP як звичайний `<img>` (чи використай `<link rel="preload" as="image">`) у початковому HTML, з логікою каруселі, накладеною зверху після гідратації, а не блокуючою існування зображення.

2. **[Середній вплив] Три блокуючі рендеринг скрипти аналітики в `<head>`**
   Доказ: скрипти, що блокують рендеринг, затримують перший пейнт і, транзитивно, LCP.
   Виправлення: додай `async` чи `defer` до сторонніх скриптів аналітики — вони не мають блокувати рендеринг.
```

## Поради та варіації
- Встав фактичний JSON-звіт Lighthouse чи підсумок трасування продуктивності Chrome DevTools як `{{PROFILING_DATA}}` для значно точніших знахідок, ніж дозволяє сам опис сторінки.
- Для сайту з багатьма схожими сторінками (напр., каталог е-комерції) запусти це на одній репрезентативній сторінці і попроси позначити, які знахідки на рівні шаблону (виправити раз, застосувати всюди) проти специфічних для сторінки.
