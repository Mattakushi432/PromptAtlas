## Опис
Перевіряє конфігурацію CI-пайплайну на надлишкові, повільні чи погано кешовані кроки, що збільшують вартість build-хвилин і час очікування розробника. Відрізняється від `ci-pipeline-debugger`, що діагностує, чому пайплайн падає — це для пайплайну, що коректно працює, але дорогий чи повільний.

## Коли використовувати
- Вартість CI-хвилин помітно зросла, чи цикл фідбеку PR з часом помітно сповільнився без очевидної єдиної причини.
- Рецензуєш нову конфігурацію пайплайну перед тим, як вона стане типовою для команди, щоб зловити марнотратство рано.
- Періодичне рев'ю гігієни пайплайну, окремо від будь-якого конкретного розслідування збою.

## Промпт

```
Ти проводиш аудит конфігурації CI-пайплайну на марнотратство вартості і часу — пайплайн працює і проходить; твоє завдання — що робить його повільнішим чи дорожчим, ніж потрібно.

Конфігурація пайплайну: {{PIPELINE_CONFIG}}

Розбивка тривалості (необов'язково — таймінг по кожному кроку, якщо доступний): {{DURATION_BREAKDOWN}}

Перевір:
1. Відсутнє чи неефективне кешування — установка залежностей, артефакти збірки чи кешування шарів Docker, що повторюють ідентичну роботу на кожному запуску замість кешування і повторного використання, коли вхідні дані не змінились.
2. Надлишкова робота між паралельними джобами — кілька джобів, кожна незалежно повторює те саме налаштування (наприклад, окремо встановлює ті самі залежності у 5 паралельних джобах тестових шардів) замість спільного кешованого кроку налаштування чи попередньо зібраного артефакту.
3. Кроки, що виконуються безумовно, хоча могли б бути умовними чи пропущеними — наприклад, запуск повного тестового набору чи важкого кроку збірки на зміні, що торкнулась лише документації, коли умовне виконання на основі шляхів могло б безпечно це пропустити.
4. Невідповідності розміру раннера — непотрібно великий/дорогий тип раннера для легкого кроку, чи навпаки (недостатній раннер, що штучно сповільнює важкий крок).

Для кожної знахідки дай конкретне виправлення і приблизну оцінку впливу на час/вартість (порядок величини, не хибна точність), щоб знахідки можна було пріоритезувати за реальною окупністю, а не рецензувати в порядку файлу.

Якщо пайплайн уже добре оптимізований, чесно скажи це, замість того щоб вигадувати незначні знахідки, щоб виглядати ретельним, і зазнач, що моніторити надалі (наприклад, коефіцієнт влучань кешу, тренд тривалості кроків), щоб зловити майбутню регресію, перш ніж вона знову стане реальною проблемою вартості.
```

## Змінні
- `{{PIPELINE_CONFIG}}` — файл(и) конфігурації CI-пайплайну. Обов'язково.
- `{{DURATION_BREAKDOWN}}` — дані таймінгу по кожному кроку, якщо доступні. Необов'язково, але суттєво покращує точність того, які знахідки реально варто пріоритезувати, а не теоретично марнотратні, але практично мізерні.

## Приклад
**Вхід:** `{{PIPELINE_CONFIG}}` = GitHub Actions workflow з 5 паралельними джобами тестових шардів, кожна незалежно запускає `npm install` без налаштованого кешу, `{{DURATION_BREAKDOWN}}` = "кожен шард займає ~90с на install, ~3хв на тести".

**Вихід (фрагмент):**
```
Знахідка: кешування залежностей не налаштоване, і кожен з 5 паралельних шардів незалежно запускає `npm install` (~90с кожен). Загальний змарнований час: ~7.5 хвилин часу раннера на кожен запуск пайплайну витрачено на ідентичні, повторювані установки (5 × 90с), жодна з яких не мала відбуватись більше одного разу.
Виправлення: додай кешування залежностей, ключоване хешем lockfile (наприклад, `actions/cache` з ключем на хеш `package-lock.json`), щоб влучання в кеш майже повністю пропускало install на незмінних залежностях — це саме по собі має скоротити ~90с install кожного шарду до кількох секунд при влучанні в кеш.

Оцінка впливу: приблизно 85-90% зниження ~7.5 хвилин сумарного часу install на запуск (промахи кешу лише при змінах lockfile), що напряму перетворюється і на нижчі оплачувані хвилини, і на швидший фідбек PR, оскільки шарди виконуються паралельно, а найповільніший блокує завершення всього пайплайну.

Серйозність: HIGH — це дуже ймовірно найбільше джерело марнотратства в цій конфігурації з огляду на те, наскільки механічно повторювана робота між шардами.
```

## Поради та варіації
- Якщо `{{DURATION_BREAKDOWN}}` недоступна, попроси спочатку порекомендувати додати базовий таймінг/звітування по кожному кроку перед подальшою оптимізацією — аудит наосліп ризикує виправляти крок, що здавався повільним, але насправді не був вузьким місцем.
- Для монорепо конкретно поєднуй це з `monorepo-build-graph-bottleneck-finder` — той промпт охоплює структуру графа залежностей пакетів, що спричиняє непотрібні перезбірки, а це інша першопричина, ніж марнотратство конфігурації пайплайну, охоплене тут.
