## Опис
Перетворює технічний changelog чи diff на реліз-нотатки простою мовою для нетехнічної аудиторії — PM, керівника чи команди, що працює з клієнтами. Відрізняється від `pr-description-generator` (написано для інших розробників, що рецензують код) і `conventional-commit-writer` (історія git, а не комунікація зі стейкхолдерами).

## Коли використовувати
- Пишеш "що вийшло цього тижня" резюме для нетехнічного стейкхолдера чи команди, що працює з клієнтами.
- Готуєш клієнтські реліз-нотатки з технічного changelog.
- Керівнику потрібне резюме релізу простою мовою перед дзвінком з клієнтом.

## Промпт

```
Ти перекладаєш технічний changelog у реліз-нотатки для нетехнічної аудиторії — а не документуєш деталі реалізації для інших інженерів.

Технічні зміни (diff, список комітів чи технічний changelog): {{TECHNICAL_CHANGES}}

Аудиторія: {{AUDIENCE}}

Для кожної зміни:
1. Переклади її в те, що користувач чи бізнес реально відчуває інакше — не що змінилося в коді, а яка поведінка змінилась з їхньої точки зору.
2. Якщо зміна не має видимого користувачу чи бізнесу ефекту (чистий внутрішній рефакторинг, оновлення залежності, зміна лише тестів), не перелічуй її окремо — згрупуй усі такі зміни в один рядок "внутрішні покращення та підтримка" замість того щоб роздувати нотатки пунктами, що нічого не означають для цієї аудиторії.
3. Якщо зміна ризикована чи може бути видимою користувачу несподіваним чином (зміна поведінки, замаскована під фікс, депрекейшн), познач це явно і помітно, а не давай їй злитись зі звичайними пунктами — цій аудиторії треба знати, на що звертати увагу, а не просто що вийшло.

Підбери тон і структуру під {{AUDIENCE}}: внутрішнє резюме для керівника може бути стислішим і посилатись на метрики/цілі; клієнтські нотатки мають читатись природно, уникати внутрішнього жаргону і номерів тікетів, і фокусуватись суто на користі для користувача чи зміні поведінки.

Якщо технічний ввід занадто скупий, щоб зрозуміти, що реально змінилось з точки зору користувача (наприклад, повідомлення коміту без реального опису), скажи про це і попроси додатковий контекст, замість того щоб вигадувати правдоподібний, але сфабрикований опис впливу зміни.
```

## Змінні
- `{{TECHNICAL_CHANGES}}` — diff, список комітів чи технічний changelog для перекладу. Обов'язково.
- `{{AUDIENCE}}` — для кого призначені нотатки (внутрішнє резюме для керівника, клієнтські реліз-нотатки, конкретна команда). Обов'язково — це змінює і тон, і те, що вважається вартим згадки.

## Приклад
**Вхід:** `{{TECHNICAL_CHANGES}}` = "fix: виправлено обробку часового поясу в генерації запланованих звітів (використовувався UTC, тепер — часовий пояс акаунту); chore: оновлено lodash до 4.17.21; refactor: винесено сервіс звітів в окремий модуль", `{{AUDIENCE}}` = "команда підтримки, що працює з клієнтами".

**Вихід (фрагмент):**
```
**Заплановані звіти тепер використовують часовий пояс вашого акаунту.** Раніше заплановані звіти генерувались на основі часу UTC, що могло означати, що звіт, запланований на "9:00", приходив у інший локальний час, ніж очікувалось, залежно від того, де базується акаунт. Тепер звіти генеруються в реально налаштований час, у часовому поясі акаунту. Якщо клієнт повідомляє про звіт, що приходить у неочікуваний час, цей фікс, ймовірно, вирішує це надалі — але перевір, чи пояснює він минулий патерн, який вони описують.

**Інше:** внутрішні покращення та підтримка (без видимих клієнту змін).
```

## Поради та варіації
- Для клієнтських нотаток попроси також позначити, які зміни варто проактивно згадати клієнтам, що подавали пов'язані тікети підтримки, а які — тихі фікси.
- Якщо зміна — це реальна зміна поведінки, замаскована під "фікс" (як у прикладі), переконайся, що вона позначена як те, про що варто проінформувати підтримку, а не похована як звичайний пункт — це часто найцінніша частина результату.
