## Опис
Перевіряє diff пул-реквесту на відповідність його власному заявленому наміру та процесним конвенціям команди — обсяг змін, тести, документація, іменування — ще до того, як його побачить людина-рев'ювер. Це процесний фільтр, а не пошук багів: для глибокого аналізу безпеки чи коректності використовуй окремий промпт.

## Коли використовувати
- Перед тим як запросити рев'ю від людини — щоб самостійно виловити процесні прогалини (відсутні тести/документацію, нечіткий обсяг).
- Коли рецензуєш PR колеги і хочеш швидко пройтися структурно, перш ніж читати кожен рядок.
- Коли потрібно послідовно застосовувати чекліст команди для контрибуторів різного рівня досвіду.

## Промпт

```
Ти — рев'ювер пул-реквесту, який проводить перевірку процесу та обсягу змін, а не глибокий аудит коректності, безпеки чи продуктивності.

Заголовок і опис PR:
{{PR_TITLE_AND_DESCRIPTION}}

Пов'язаний тікет/вимоги (необов'язково):
{{LINKED_TICKET}}

Diff:
{{DIFF}}

Конвенції команди (необов'язково):
{{TEAM_CONVENTIONS}}

Інструкції:
1. На основі заголовка, опису та пов'язаного тікета сформулюй одним реченням, що саме, за заявою, робить цей PR.
2. Перевірка обсягу: познач будь-який фрагмент diff'у, який не служить заявленій меті ("розповзання обсягу"), і познач те, що заявлена мета передбачає, але diff цього не робить ("неповний обсяг").
3. Перевірка тестів: для кожної нової чи зміненої функції/гілки логіки перевір наявність відповідної зміни в тестах. Познач зміни логіки без відповідного покриття тестами.
4. Перевірка документації: познач будь-яку змінену публічну API, опцію конфігурації чи поведінку, видиму користувачу, без відповідного оновлення документації/README/коментарів.
5. Перевірка конвенцій: якщо задано {{TEAM_CONVENTIONS}}, познач вибір іменування, розташування файлів чи патернів у diff'і, що відхиляється від них.
6. Якщо помітиш щось схоже на серйозний баг чи проблему безпеки — коротко назви це, але прямо зазнач "потребує окремого рев'ю — тут детально не аналізувалося", замість того щоб досліджувати самостійно.
7. Якщо diff порожній, складається лише з пробілів, або опис не відповідає жодному коду в diff'і — прямо про це скажи, замість того щоб вигадувати знахідки.

Формат виводу: Markdown, згруповано під заголовками Scope / Tests / Documentation / Conventions / Other. Кожен позначений пункт — один рядок, PASS або FLAG, з реченням-поясненням. Заверши одним рядком-висновком: "Готовий до рев'ю" або "Потребує змін спочатку" з поясненням чому.
```

## Змінні
- `{{DIFF}}` — diff пул-реквесту (формат unified diff працює найкраще). Обов'язково.
- `{{PR_TITLE_AND_DESCRIPTION}}` — заголовок і опис самого PR. Обов'язково.
- `{{LINKED_TICKET}}` — текст тікета/issue, який PR нібито закриває. Необов'язково, але робить перевірку обсягу точнішою.
- `{{TEAM_CONVENTIONS}}` — правила команди, напр. "кожен новий ендпойнт потребує запису в OpenAPI; без default-експортів". Необов'язково.

## Приклад
**Вхід:** `{{PR_TITLE_AND_DESCRIPTION}}` = "Додати промокоди на відсоткову знижку при оформленні замовлення", `{{DIFF}}` = додає функцію `applyDiscountCode()` і підключає її до checkout, жоден тестовий файл не змінено.

**Вихід (фрагмент):**
```
## Tests
- FLAG: `applyDiscountCode()` — це нова бізнес-логіка (розрахунок відсотка, перевірка терміну дії) без відповідних змін у тестових файлах у diff'і.

## Scope
- PASS: усі змінені файли стосуються заявленої функції промокодів.

**Висновок:** Потребує змін спочатку — додай тести для `applyDiscountCode()`, перш ніж це буде готово до рев'ю.
```

## Поради та варіації
- Для інтеграції з CI-ботом попроси лише один рядок на кожен позначений пункт, без прози — так легше публікувати як коментар до PR.
- Якщо в команди ще немає письмових конвенцій, просто не заповнюй {{TEAM_CONVENTIONS}} — перевірки обсягу/тестів/документації все одно працюють самостійно.
- Поєднуй із «Асистент код-рев'ю» для глибини на рівні рядків, безпеки та продуктивності, яку цей промпт свідомо пропускає.
