## Опис
Оцінює радіус ураження запропонованої зміни у спільній дизайн-системі/бібліотеці компонентів серед команд і застосунків, що її споживають, перед публікацією нової версії. Фронтенд-аналог `api-consumer-impact-mapper` для бекенд API — застосований до prop API, візуальних значень за замовчуванням і контрактів поведінки замість контрактів ендпоінтів.

## Коли використовувати
- Змінюєш prop API спільного компонента, стиль за замовчуванням чи поведінку і треба знати, які застосунки-споживачі зламаються.
- Вирішуєш, чи зміна справді patch/minor версія, чи насправді прихована major breaking change.
- Публікуєш нову версію дизайн-системи і готуєш споживачів до того, що реально для них зміниться.

## Промпт

```
Ти оцінюєш радіус ураження запропонованої зміни у спільній бібліотеці компонентів серед команд/застосунків, що її споживають — ти не рецензуєш якість реалізації самої зміни.

Запропонована зміна (що змінюється в компоненті — перейменування/видалення prop, зміна значення за замовчуванням, зміна поведінки): {{PROPOSED_CHANGE}}

Відомі споживачі (застосунки/команди, відомі як користувачі цього компонента, і як саме, якщо відомо): {{KNOWN_CONSUMERS}}

Методи виявлення використання (необов'язково — пошук коду по всьому монорепо, власна аналітика використання бібліотеки компонентів, якщо є): {{USAGE_DISCOVERY_METHODS}}

1. Класифікуй зміну: patch-safe (жодної видимої споживачу зміни поведінки чи вигляду), потребує-minor-версії-з-шляхом-депрекейшену (адитивна чи має зворотно-сумісний перехід), чи справді-major/breaking (наявне використання споживачем видимо зламається чи виглядатиме неправильно без змін з їхнього боку).
2. Для кожного відомого споживача оціни, чи описаний патерн використання реально постраждає — зміна стилю за замовчуванням може бути невидимою для споживача, що завжди явно перевизначає саме цей prop, тоді як зламає того, хто покладається на значення за замовчуванням.
3. Конкретно познач категорію "лише-візуальна" breaking change, якщо релевантно — зсув відступів, кольору чи розміру часто відмахують як "не справжня зламана зміна", бо нічого не кидає помилку, але це все одно може зламати дизайн-намір команди-споживача, припущення про верстку чи контраст доступності. Розглядай це як реальну категорію breaking change, а не менш важливе занепокоєння, ніж функціональний злам.
4. Запропонуй план виявлення для споживачів поза відомим списком, використовуючи будь-які реально доступні методи виявлення, а не вважай відомий список обов'язково повним.

Виведи: класифікацію, оцінку впливу на кожного споживача, план виявлення для невідомих, і рекомендований приріст версії.

Якщо зміна справді адитивна (новий необов'язковий prop, новий варіант, що не змінює жодну наявну поведінку), чесно підтверди це, а не вважай, що кожна зміна бібліотеки компонентів заслуговує на цей повний рівень уваги — надмірне застосування важкого рев'ю до тривіально безпечних змін витрачає час рецензента і привчає людей пропускати рев'ю для того, що реально важливо.
```

## Змінні
- `{{PROPOSED_CHANGE}}` — що змінюється в компоненті. Обов'язково.
- `{{KNOWN_CONSUMERS}}` — застосунки/команди, відомі як користувачі компонента, і як саме. Обов'язково.
- `{{USAGE_DISCOVERY_METHODS}}` — доступний інструментарій для пошуку ще не відомих споживачів. Необов'язково; без нього пропонуються загальні підходи виявлення.

## Приклад
**Вхід:** `{{PROPOSED_CHANGE}}` = "зміна значення за замовчуванням prop `size` компонента Button з 'medium' на 'small'", `{{KNOWN_CONSUMERS}}` = "застосунок Checkout (широко використовує Button, не перевизначає `size` у ~80% використань, за швидким грепом), застосунок Admin Dashboard (явно встановлює `size` на кожному використанні Button, підтверджено рев'ю коду)".

**Вихід (фрагмент):**
```
Класифікація: справді-major/breaking, попри те, що виглядає "просто правкою значення за замовчуванням". Зміна значення за замовчуванням функціонально невидима на поверхні API компонента, але візуально зламана для будь-якого споживача, що покладається на старе значення за замовчуванням — це саме категорія "лише-візуальна breaking change", яку легко недокласифікувати.

Застосунок Checkout: ПОСТРАЖДАВ, суттєво. ~80% використань Button не перевизначають `size`, тобто більшість кнопок у цьому застосунку тихо зменшаться — це реальна візуальна регресія на великій поверхні, а не незначний нюанс стилю, і, ймовірно, потребує явного рев'ю/схвалення цієї команди перед випуском, а не лише примітки в changelog.

Застосунок Admin Dashboard: НЕ ПОСТРАЖДАВ. Явно встановлює `size` на кожному використанні за рев'ю коду — зміна за замовчуванням тут не має жодного видимого ефекту. Варто короткого повідомлення для інформації, щоб не насторожились через запис у changelog, але дій з їхнього боку не потрібно.

Рекомендований приріст версії: major, не minor чи patch — навіть якщо жоден prop не видалено чи перейменовано, видима зміна поведінки для споживача з більшістю використань (Checkout) відповідає планці breaking change за реальним наміром semver (зміна, що обґрунтовано могла б зламати того, хто покладається на поточну поведінку), а не лише буквальному визначенню форми API.
```

## Поради та варіації
- Для бібліотеки компонентів з уже налаштованим візуальним регресійним тестуванням (наприклад, Chromatic, Percept) попроси явно зазначити, що набір регресійних тестів — найшвидший спосіб отримати остаточну, індивідуальну для кожного споживача відповідь на "чи це реально виглядає інакше", а не покладатись лише на ручні міркування про значення за замовчуванням.
- Якщо бібліотека публікує аналітику використання (які застосунки реально рендерять які компоненти, з реальної телеметрії), надавай їй перевагу над виявленням на основі пошуку коду — вона фіксує динамічні патерни використання, які статичний греп пропустить.
