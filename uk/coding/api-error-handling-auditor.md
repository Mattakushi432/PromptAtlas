## Опис
Аудитує гарантії ідемпотентності API та узгодженість обробки помилок — конкретно, чи безпечні повтори дійсно безпечні, і чи передбачувані відповіді про помилки — для API, який клієнти реально викликатимуть через ненадійні мережі. Відрізняється від «Радника з версіонування API» і «Дизайнера REST-ендпойнтів»: це аудит коректності поведінки під час відмов, а не промпт для дизайну з нуля.

## Коли використовувати
- Перед релізом API, який клієнти повторюватимуть при відмові, щоб підтвердити, що повтори не спричинять дубльовані побічні ефекти (подвійні списання, дубльовані записи).
- Розслідування звіту про баг з дублюванням даних, який підозрюють як наслідок поведінки повторів клієнта.
- Стандартизація форми відповідей про помилки в API, що розросся органічно і тепер має неузгоджені формати помилок по ендпойнтах.

## Промпт

```
Ти аудитуєш поведінку ідемпотентності API та узгодженість обробки помилок — не загальний дизайн ендпойнтів чи іменування.

Ендпойнти API та їхня реалізація (чи опис поведінки): {{API_DETAILS}}
Відома поведінка повторів клієнта (необов'язково — напр., "мобільний клієнт повторює POST-запити до 3 разів при таймауті"): {{RETRY_BEHAVIOR}}

Інструкції:
1. Для кожного ендпойнта, що змінює стан (POST, PUT, PATCH, DELETE), визнач, чи він дійсно ідемпотентний у реалізації — не лише чи HTTP-метод конвенційно ідемпотентний (PUT/DELETE мають бути, але погана реалізація все одно може це зламати).
2. Конкретно для POST-ендпойнтів (не ідемпотентних за конвенцією HTTP) перевір, чи є механізм ідемпотентності (наданий клієнтом ключ ідемпотентності, природний ключ дедуплікації) — познач будь-який POST, що створює ресурс без способу запобігти дублюванню повторним запитом.
3. Для кожного ендпойнта простеж, що станеться, якщо клієнт надішле той самий запит двічі через мережевий таймаут, де перший запит фактично успішно виконався на сервері, але відповідь було втрачено: чи друга спроба видасть корисну помилку, тихо продублює ефект, чи поверне оригінальний результат?
4. Аудитуй узгодженість відповідей про помилки: чи всі ендпойнти використовують ту саму форму тіла помилки (код помилки, повідомлення, деталі валідації на рівні поля)? Познач будь-який ендпойнт, що повертає інакше сформовану помилку, голий рядок, чи неструктурований 500 для випадку, що мав би бути обробленим 4xx.
5. Перевір коректність статус-кодів: помилка валідації, що повертає 500 замість 400/422, чи випадок "не знайдено", що повертає 200 з порожнім тілом замість 404 — це ламає логіку обробки помилок клієнта, що перемикається за статус-кодом.
6. Якщо надано {{RETRY_BEHAVIOR}}, конкретно простеж, чи описаний патерн повторів безпечний з урахуванням фактичної ідемпотентності ендпойнтів, і познач будь-яку комбінацію, що на практиці призвела б до дубльованих ефектів.

Формат виводу: Markdown з розділами: Знахідки ідемпотентності (за ендпойнтом), Знахідки узгодженості відповідей про помилки, і виноска "Найвищий ризик" для будь-якої знахідки, що могла б спричинити реальне дублювання чи пошкодження даних під час повтору.
```

## Змінні
- `{{API_DETAILS}}` — ендпойнти та як вони реалізовані, чи поведінковий опис, якщо код недоступний. Обов'язково.
- `{{RETRY_BEHAVIOR}}` — як клієнти фактично повторюють невдалі запити. Необов'язково, але робить аналіз ідемпотентності конкретним, а не теоретичним.

## Приклад
**Вхід:** `{{API_DETAILS}}` = "POST /orders створює замовлення і списує кошти з методу оплати; без підтримки ключа ідемпотентності", `{{RETRY_BEHAVIOR}}` = "клієнт повторює будь-який запит, що вийшов за таймаут, до 2 разів".

**Вихід (фрагмент):**
```
### Знахідки ідемпотентності
**POST /orders — НАЙВИЩИЙ РИЗИК**
Не існує механізму ключа ідемпотентності. Якщо початковий запит успішно виконується на сервері (замовлення створено, платіж списано), але відповідь втрачається через мережевий таймаут, повтор клієнта створить друге замовлення і друге списання — це реальний ризик подвійного списання з урахуванням заявленої поведінки повторів, а не теоретичний.
Рекомендація: приймай наданий клієнтом заголовок `Idempotency-Key`; при повторному запиті з уже баченим ключем повертай оригінальну відповідь замість повторного виконання списання.
```

## Поради та варіації
- Для платіжних чи інших фінансових ендпойнтів зокрема трактуй будь-яку знахідку ідемпотентності як автоматично НАЙВИЩИЙ РИЗИК незалежно від заявленої поведінки повторів — сама серйозність наслідків це виправдовує.
- Якщо аудитуєш GraphQL API замість REST, адаптуй питання ідемпотентності конкретно до мутацій, оскільки запити GraphQL за конвенцією за своєю природою лише для читання/ідемпотентні.
