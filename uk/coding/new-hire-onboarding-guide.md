## Опис
Генерує гід онбордингу нового співробітника для конкретного репозиторію — налаштування середовища розробки, орієнтація в кодовій базі, практики команди — ширше за обсяг швидкого старту README. Для підготовки реального документа онбордингу, не загального шаблону "як онбордити інженерів".

## Коли використовувати
- Приєднується новий інженер, а структурованого документа онбордингу немає, чи наявний застарілий.
- Стандартизація онбордингу в команді, що росте, щоб розгін не залежав повністю від усного знання того, хто випадково вільний того тижня.
- Аудит того, чи наявні матеріали онбордингу дійсно покривають те, що новому співробітнику потрібно в перший тиждень.

## Промпт

```
Ти пишеш гід онбордингу нового співробітника для конкретного репозиторію/команди — документ першого тижня, не повний архітектурний довідник.

Опис репозиторію/кодової бази (що він робить, технологічний стек, архітектура на високому рівні): {{REPO_DESCRIPTION}}
Кроки налаштування середовища розробки (фактичні потрібні команди/інструменти): {{SETUP_STEPS}}
Практики команди (необов'язково — процес код-рев'ю, темп деплою, норми комунікації, чергування, якщо релевантно): {{TEAM_PRACTICES}}
Наявний документ онбордингу для перегляду, якщо є (необов'язково): {{EXISTING_DOC}}

Інструкції:
1. Упорядкуй контент за тим, що новому співробітнику дійсно потрібне послідовно: спочатку налаштування середовища й запуск кодової бази (перед тим як щось інше матиме значення), потім орієнтація в кодовій базі (основні компоненти, де що знайти), потім процес команди (як тут насправді працює код-рев'ю/деплой), потім куди звертатися за допомогою.
2. Напиши кроки налаштування як точні, виконувані команди з очікуваними результатами на кожному кроці ("тепер ти маєш побачити X"), щоб новий співробітник міг самостійно діагностувати, коли щось не збігається, а не суцільну стіну прози.
3. Для орієнтації в кодовій базі не намагайся пояснити все — покрий жменю концепцій/компонентів, що відкривають розуміння решти (базова доменна модель, основний потік запиту, де живе бізнес-логіка проти того, де ні), а не вичерпний тур файл-за-файлом.
4. Включи конкретне перше завдання чи два, якщо можна вивести (пропозицію типу "good first issue" чи конкретну малу область для першої малої зміни) — гід онбордингу, що закінчується на "тепер ти налаштований" без наступного кроку, витрачає імпульс першого дня.
5. Документуй практики команди як конкретні, дієві норми ("PR потребують одного схвалення перед мерджем, використовуй канал #eng-reviews, щоб пінгнути на рев'ю"), а не розпливчасті заяви ("ми цінуємо якість коду").
6. Зазнач, до кого/куди звертатися за допомогою для різних видів питань (конкретний Slack-канал, область експертизи конкретної людини), а не загальне "питай, якщо є питання".
7. Якщо надано {{EXISTING_DOC}}, збережи точні частини і познач/виправ усе застаріле, а не повне переписування з нуля.

Формат виводу: Markdown з розділами: Налаштування середовища, Орієнтація в кодовій базі, Практики команди, Отримання допомоги, Запропоноване перше завдання.
```

## Змінні
- `{{REPO_DESCRIPTION}}` — що робить кодова база і її архітектура на високому рівні. Обов'язково.
- `{{SETUP_STEPS}}` — фактичні команди налаштування середовища розробки. Обов'язково.
- `{{TEAM_PRACTICES}}` — як команда фактично працює (рев'ю, деплой, комунікація). Необов'язково, але суттєво покращує реальну корисність.
- `{{EXISTING_DOC}}` — наявний документ онбордингу для перегляду. Необов'язково.

## Приклад
**Вхід:** `{{REPO_DESCRIPTION}}` = "моноліт Django, що обслуговує сайт е-комерції, з окремим репозиторієм фронтенду на React", `{{SETUP_STEPS}}` = "docker-compose up, потім python manage.py migrate && python manage.py runserver", `{{TEAM_PRACTICES}}` = "PR потребують 1 схвалення, деплої відбуваються автоматично при мерджі в main через CI".

**Вихід (фрагмент):**
```markdown
## Налаштування середовища
1. `docker-compose up` — запускає Postgres і Redis. Ти маєш побачити, як обидва сервіси логують "ready to accept connections" протягом ~30 секунд.
2. `python manage.py migrate` — застосовує схему бази даних. Очікуй список назв міграцій, що прокручуються, без помилок.
3. `python manage.py runserver` — запускає застосунок на http://localhost:8000. Ти маєш побачити сторінку логіну.

## Орієнтація в кодовій базі
Базова доменна модель живе в `apps/orders/models.py` і `apps/inventory/models.py` — почни звідти, а не намагайся читати кожен app. Бізнес-логіка ціноутворення/знижок централізована в `apps/orders/services/pricing.py`, не розкидана по view — якщо шукаєш "де обчислюється X", перевір спочатку там.

## Практики команди
- PR вимагають 1 схвалення перед мерджем.
- Мердж у `main` запускає автоматичний продакшн-деплой через CI — немає окремого ручного кроку деплою, тож замерджений PR живий протягом хвилин.
```

## Поради та варіації
- Для розподіленої/віддаленої команди додай розділ конкретно про норми комунікації (очікування щодо часу відповіді, які канали синхронні проти асинхронних), оскільки це часто найбільше незаявлене припущення, на якому спотикаються нові співробітники.
- Якщо команда веде структуровану програму баді/ментора онбордингу, зазнач, де людино-керовані частини вписуються відносно цього самообслуговуваного документа, щоб гід не дублював те, що баді має покрити в розмові.
