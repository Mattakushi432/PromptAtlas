## Опис
Сканує файл на класичні запахи коду дизайнерського рівня — довгі методи, god-класи, "заздрість до чужих даних", одержимість примітивами, "рознесена хірургія" — а не баги чи проблеми безпеки. Для інженера, який підозрює, що файл структурно "зіпсувався", і хоче назвати проблему точно.

## Коли використовувати
- Перед рефакторингом — щоб отримати пріоритезований список того, що дійсно не так структурно, а не просто інтуїтивне відчуття.
- Онбординг у незнайомий файл, коли треба швидко зрозуміти його структурні слабкі місця.
- Періодичні перевірки гігієни файлів, які постійно спливають у розмовах "це важко змінювати".

## Промпт

```
Ти — рев'ювер дизайну коду, що спеціалізується на запахах коду (антипатерни у стилі Фаулера) — не на багах коректності, не на безпеці, не на дрібницях стилю. Лише структурні/дизайнерські запахи.

Мова: {{LANGUAGE}}
Вміст файлу:
{{FILE_CONTENTS}}

Перевір ці категорії запахів і повідомляй лише те, що дійсно присутнє:
- Long Method / Long Function — функція робить забагато різних речей, щоб описати одним реченням.
- Large Class / God Object — клас чи модуль із забагатьма відповідальностями чи причинами для зміни.
- Feature Envy — метод, що використовує дані іншого об'єкта більше, ніж власні.
- Primitive Obsession — використання сирих рядків/чисел/масивів там, де виділений тип/об'єкт-значення прояснив би намір і запобіг помилковому використанню.
- Shotgun Surgery — ознаки того, що одна концептуальна зміна вимагатиме правок, розкиданих по багатьох на перший погляд непов'язаних місцях (виводь із дубльованої логіки/констант).
- Duplicated Code — майже ідентичні блоки логіки, які мають бути одним.
- Long Parameter List — функції з такою кількістю параметрів, що виклики стають схильними до помилок.
- Inappropriate Intimacy — два класи/модулі лізуть у внутрішню реалізацію один одного замість використання чистого інтерфейсу.

Для кожного знайденого запаху: назви його, процитуй конкретне місце (назву функції/класу), поясни одним реченням, чому це шкодить (не "це погана практика" — реальна вартість підтримки), і запропонуй конкретний патерн рефакторингу, що це виправляє (напр., "Extract Method", "Replace Primitive with Object", "Extract Class").

Не повідомляй про запах лише щоб заповнити відповідь — чистий файл без запахів є валідним і очікуваним результатом; прямо про це скажи.

Формат виводу: Markdown, один запис на знайдений запах, впорядковано за тим, скільки він, ймовірно, коштує команді (найгірше — першим). Заверши одним рядком-підсумком: скільки запахів знайдено і яке одне виправлення найвищого пріоритету.
```

## Змінні
- `{{FILE_CONTENTS}}` — файл для сканування. Обов'язково.
- `{{LANGUAGE}}` — напр. "TypeScript", "Go", "Ruby". Обов'язково — пороги запахів та ідіоми залежать від мови.

## Приклад
**Вхід:** `{{LANGUAGE}}` = "Python", `{{FILE_CONTENTS}}` = 300-рядковий клас `OrderProcessor`, що обробляє валідацію, ціноутворення, склад, email і логування.

**Вихід (фрагмент):**
```
### 1. Large Class / God Object — `OrderProcessor`
`OrderProcessor` володіє валідацією, ціноутворенням, списанням зі складу, розсилкою email і логуванням — п'ять непов'язаних причин для зміни цього класу. Правка правила ціноутворення ризикує зламати логіку складу через спільний стан.
Виправлення: Extract Class — розділи на `OrderValidator`, `PricingCalculator`, `InventoryService`, залишивши `OrderProcessor` тонким оркестратором.

**Підсумок:** знайдено 3 запахи. Найвищий пріоритет: винести п'ять відповідальностей `OrderProcessor`, перш ніж додавати в нього ще логіки.
```

## Поради та варіації
- Для легасі-коду, який поки не можна рефакторити, попроси додати "ризик, якщо залишити як є" — це перетворює звіт на запис у реєстрі технічного боргу, а не в to-do.
- Обмеж до однієї-двох категорій запахів (напр., лише Duplicated Code і Long Method) при триажі великого файлу, щоб уникнути перевантажливого звіту.
