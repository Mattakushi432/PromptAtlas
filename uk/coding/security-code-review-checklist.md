## Опис
Проганяє фрагмент коду через фіксований чекліст класів вразливостей (ін'єкції, автентифікація, криптографія, десеріалізація, SSRF та інші) замість довільного рев'ю — для інженера чи рев'ювера, якому потрібне систематичне покриття безпеки, а не загальна перевірка якості.

## Коли використовувати
- Рев'ю коду, що працює з користувацьким вводом, автентифікацією чи чутливими даними перед релізом.
- Аудит стороннього чи легасі-модуля, якому не довіряєш і потребуєш структурованого проходу.
- Підготовка доказів для security sign-off, де "ми перевірили X, Y, Z явно" важливіше за вільну думку.

## Промпт

```
Ти — рев'ювер безпеки застосунків. Оціни код нижче за цим фіксованим чеклістом класів вразливостей — не пропускай категорію, навіть якщо вона здається очевидно нерелевантною; замість цього напиши "N/A: <причина одним реченням>".

Мова/стек: {{LANGUAGE_OR_STACK}}
Код:
{{CODE_SNIPPET}}

Чекліст (оціни кожен пункт):
1. Ін'єкції — SQL, NoSQL, командні, LDAP, шаблонні чи ін'єкції в логи через несанітизований ввід.
2. Порушена автентифікація/сесії — слабкі токени сесій, відсутність терміну дії, витік облікових даних.
3. Порушений контроль доступу — відсутні перевірки авторизації, небезпечні прямі посилання на об'єкти (IDOR).
4. Криптографічні недоліки — слабкі/застарілі алгоритми, зашиті ключі, недостатня випадковість, секрети у відкритому вигляді.
5. Небезпечна десеріалізація — недовірені дані передаються в десеріалізатор, здатний виконувати код.
6. Server-side request forgery (SSRF) — URL, на які впливає користувач, запитуються сервером без валідації.
7. Прогалини валідації вводу — відсутні перевірки довжини/типу/діапазону, що можуть призвести до подальших проблем.
8. Витік чутливих даних — секрети, PII чи внутрішні деталі в логах, повідомленнях про помилки чи відповідях.
9. Неправильна конфігурація безпеки — надто дозвільні значення за замовчуванням, докладні помилки, відсутні security-заголовки (якщо застосовно до цього фрагмента).

Для кожної ЗНАХІДКИ: процитуй точний вразливий рядок(и), назви категорію чекліста, наведи конкретний сценарій експлуатації (реальний зловмисний ввід і його ефект — а не "зловмисник може це використати"), оціни критичність (CRITICAL/HIGH/MEDIUM/LOW) і дай конкретне виправлення у вигляді фрагмента коду.

Якщо фрагмент занадто малий чи поза контекстом, щоб впевнено оцінити категорію (наприклад, немає видимої перевірки авторизації, бо вона відбувається деінде), скажи про це, а не вгадуй.

Формат виводу: Markdown, один підрозділ на пункт чекліста в порядку вище, кожен позначений FINDING(S) або N/A. Заверши одним рядком загальної оцінки ризику.
```

## Змінні
- `{{CODE_SNIPPET}}` — код для рев'ю. Обов'язково.
- `{{LANGUAGE_OR_STACK}}` — напр. "Node.js / Express", "Java / Spring". Обов'язково — патерни вразливостей залежать від мови.

## Приклад
**Вхід:** `{{LANGUAGE_OR_STACK}}` = "PHP", `{{CODE_SNIPPET}}` = ендпойнт, що десеріалізує значення cookie, надане користувачем, напряму.

**Вихід (фрагмент):**
```
### 5. Небезпечна десеріалізація
FINDING — `unserialize($_COOKIE['session_data'])` передає повністю контрольований зловмисником ввід у unserialize() PHP.
Експлуатація: зловмисник створює серіалізований об'єкт, що відповідає класу з гаджетом `__wakeup()`/`__destruct()`, наявним деінде в застосунку, для віддаленого виконання коду.
Критичність: CRITICAL.
Виправлення: заміни на `json_decode($_COOKIE['session_data'], true)` з валідацією отриманої структури, або підпиши cookie (HMAC) і перевіряй перед використанням.

**Загальна оцінка ризику:** CRITICAL — не релізити, доки не виправлено знахідку №5.
```

## Поради та варіації
- Для аудиторського сліду при комплаєнсі попроси вказувати відповідний CWE ID біля кожної знахідки (напр., CWE-502 для небезпечної десеріалізації).
- Звузь чекліст до підмножини (напр., лише пункти 1, 3, 4), коли рецензуєш фрагмент, де інші категорії доведено поза контекстом — це заощадить час на шумі N/A.
