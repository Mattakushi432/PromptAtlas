## Опис
Проєктує клієнтський досвід вирішення конфліктів синхронізації в офлайн-first мобільному застосунку — доповнення на рівні UX до «Дизайнер офлайн-синхронізації» (coding, вже випущений) з технічною стратегією синхронізації на рівні даних: той промпт проєктує, як конфлікти виявляються й зливаються на рівні даних; цей — що користувач реально бачить і робить, коли конфлікт потребує його вводу.

## Коли використовувати
- Спроєктував (чи використовуєш) технічну стратегію вирішення конфліктів (last-write-wins, злиття CRDT тощо), але не спроєктував, що відбувається, коли конфлікт справді потребує людського судження для вирішення.
- Користувачі плутаються чи втрачають дані, бо конфлікти мовчки авторозв'язуються способом, що їх дивує, і потрібен UX-підхід, що доречно показує конфлікти.
- Додаєш офлайн-підтримку до фічі й хочеш продумати UX конфліктів перед реалізацією, не допрацьовувати після того, як користувачі почнуть натрапляти на заплутані граничні випадки.

## Промпт

```
Ти проєктуєш клієнтський досвід вирішення конфліктів синхронізації в офлайн-first мобільному застосунку. Ти проєктуєш для конкретного типу даних і сценаріїв конфліктів, описаних — ти не пропонуєш загальне рішення «покажи діалог злиття», не пов'язане з тим, що реально редагується і як конфлікти реально виникають тут.

Фіча/дані, що синхронізуються: {{FEATURE}}
Технічний(і) сценарій(ї) конфлікту, що можуть трапитись: {{CONFLICT_SCENARIOS}}
Поточна чи запланована технічна стратегія вирішення: {{TECHNICAL_STRATEGY}}

Інструкції:
1. Для кожного сценарію в {{CONFLICT_SCENARIOS}} визнач, чи безпечно авторозв'язати мовчки (напр., неперекривні редагування різних полів, адитивні зміни на кшталт додавання елементів до списку з двох пристроїв), чи це справді потребує вводу користувача (напр., те саме поле відредаговано по-різному на двох пристроях, видалення на одному пристрої конфліктує з редагуванням на іншому) — не став за замовчуванням завжди показувати конфлікти користувачу, оскільки надмірний показ тривіальних конфліктів привчає користувачів ігнорувати UI без читання.
2. Для сценаріїв, що потребують вводу користувача, спроєктуй конкретний UI вирішення конфлікту: що показується (обидві версії поруч? вид diff? просто вибір «залиш мою» / «залиш їхню»?), калібрований під реальний тип даних {{FEATURE}} — конфлікт текстової нотатки потребує іншого UI, ніж конфліктуюче числове значення чи конфліктуючий булевий перемикач.
3. Спроєктуй для випадку, коли користувач знову офлайн саме тоді, коли UI вирішення конфлікту мав би показатись — чи можна відкласти вирішення до повернення онлайн, і якщо так, як виглядає проміжний стан (яку версію користувач бачить/редагує тим часом)?
4. Спроєктуй явний резерв «без втрати даних»: навіть при авторозв'язанні, чи програшна версія коли-небудь повністю відкидається, чи є спосіб її відновити (напр., історія версій, вікно скасування) — мовчазна, невідновна втрата даних від авторозв'язаного конфлікту — один із найшкідливіших режимів відмови офлайн-синхронізації, і дизайн має явно це вирішити, не залишати неявним.
5. Розглянь сповіщення/таймінг: чи має користувача перервати одразу, коли конфлікт виявлено (напр., саме коли він повертається онлайн), чи вирішення може почекати, доки він природно перейде до зачепленого контенту — негайне переривання для низькоризикового конфлікту може відчуватись більш деструктивним, ніж сам конфлікт.
6. Якщо {{TECHNICAL_STRATEGY}} вже зобов'язується завжди авторозв'язувати без будь-якого клієнтського UI конфлікту взагалі, перевір, чи це реально доречно, зважаючи на {{CONFLICT_SCENARIOS}} — познач будь-який сценарій у цьому списку, де мовчазне авторозв'язання правдоподібно спричинило б видиму користувачу, заплутуючу втрату даних, оскільки це невідповідність між технічною стратегією і UX-потребами.

Формат виводу: Markdown, окремий запис на кожен сценарій конфлікту: вердикт авторозв'язати проти потребує-вводу-користувача, і (для випадків вводу користувача) опис конкретного UI/флоу, плюс секція `### Запобіжна сітка від втрати даних`, що звертається до відновлення для авторозв'язаних випадків.
```

## Змінні
- `{{FEATURE}}` — конкретна фіча/тип даних, що синхронізується (напр., «вміст нотатки в застосунку особистих нотаток», «список товарів кошика покупок»). Обов'язково.
- `{{CONFLICT_SCENARIOS}}` — конкретні способи, якими конфлікт технічно може виникнути для цієї фічі. Обов'язково.
- `{{TECHNICAL_STRATEGY}}` — поточний чи запланований підхід вирішення на рівні даних. Обов'язково — дизайн UX має працювати з (чи проти) того, що реально робить технічний шар.

## Приклад
**Вхід:** `{{FEATURE}}` = «Застосунок особистого списку завдань — назва завдання, статус завершення, дата виконання» `{{CONFLICT_SCENARIOS}}` = «Назву того самого завдання відредаговано по-різному на двох офлайн-пристроях; завдання позначено завершеним на одному пристрої, поки на іншому змінено дату виконання; завдання видалено на одному пристрої, поки відредаговано на іншому» `{{TECHNICAL_STRATEGY}}` = «Наразі last-write-wins для всіх полів, без клієнтського UI конфлікту»

**Вихід (уривок):**
```
### Сценарій: назва відредагована по-різному на двох пристроях
Вердикт: Потребує вводу користувача — дві справді різні задумані назви не можна безпечно злити автоматично без ризику втрати задуманого редагування користувача на одному з пристроїв.
UI: Простий вибір із двох опцій («Залишити '[Назва пристрою А]'» / «Залишити '[Назва пристрою Б]'»), а не складний вид diff — назви завдань достатньо короткі, щоб повний текст поруч читався краще за diff.

### Сценарій: завершено на одному пристрої, дата виконання змінена на іншому
Вердикт: Авторозв'язати — це неперекривні редагування полів (статус завершення проти дати виконання) і можуть бути безпечно злиті застосуванням обох змін, а не вибором повного стану одного пристрою.
Примітка: поточна стратегія last-write-wins неправильно відкинула б одне з цих двох легітимних редагувань — познач це як невідповідність: тут потрібне злиття на рівні поля (не last-write-wins цілого запису) конкретно для цього сценарію.

### Сценарій: видалено на одному пристрої, відредаговано на іншому
Вердикт: Потребує вводу користувача — конфлікт видалення-проти-редагування — класичний випадок, де авторозв'язання в будь-якому напрямку ризикує несподіваним, невідновним результатом (або редагування користувача мовчки зникає, або завдання, яке він мав намір видалити, повертається).
UI: Показати як «Це завдання видалено на іншому пристрої, але тут є незбережені зміни — відновити його, чи підтвердити видалення?», а не мовчки обирати одну сторону.

### Запобіжна сітка від втрати даних
Зважаючи, що поточна стратегія last-write-wins не має механізму відновлення, рекомендуй додати щонайменше короткочасний (напр., 30-денний) м'яке-видалення/знімок-версії, щоб неправильно авторозв'язаний конфлікт усе одно можна було вручну відновити користувачем чи підтримкою, навіть для випадків авторозв'язання вище.
```

## Поради та варіації
- Лінія «авторозв'язати проти потребує-вводу-користувача» — єдине найвпливовіше дизайнерське рішення тут — помились у цій класифікації в будь-якому напрямку (надмірний показ тривіальних конфліктів чи мовчазне авторозв'язання справді неоднозначних) — і решта дизайну UI цього не компенсує.
- Поєднуй із «Дизайнер офлайн-синхронізації» (coding, вже випущений) рано в тому самому проході дизайну, а не після того, як технічна стратегія вже зафіксована — UX-потреби, виявлені тут (напр., потреба в злитті на рівні поля, а не цілого запису), можуть і мають інформувати технічний дизайн, не лише адаптуватись навколо нього постфактум.
- Для B2B/спільного контексту (кілька користувачів редагують спільні дані, не лише власні пристрої одного користувача), а не персональна мультипристроєва синхронізація, той самий підхід класифікації сценаріїв застосовний, але UI також потребує повідомляти, *хто* зробив конфліктну зміну, чого цей однокористувацький приклад не потребує звертати.
