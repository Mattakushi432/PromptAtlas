## Опис
Радить щодо збереження стану форми в процесі проти випадкової навігації, оновлення чи падіння — рекомендує, що зберігати, де і коли очищати, каліброване під реальний ризик і чутливість конкретної форми, не загальна рекомендація «просто використай localStorage для всього».

## Коли використовувати
- Будуєш довгу чи трудомістку форму (багатокроковий майстер, тривала заявка, детальний редактор контенту) і хочеш захистити користувачів від втрати роботи через випадкове закриття вкладки чи оновлення.
- Хочеш перевірити, чи наявний підхід збереження стану форми обробляє реальні режими відмови, які має, чи лише щасливий шлях.
- Вибираєш між підходами збереження (лише в пам'яті, localStorage, sessionStorage, чернетка, збережена на сервері) і хочеш продумані компроміси для чутливості й довжини даних конкретно цієї форми.

## Промпт

```
Ти радиш щодо клієнтського збереження стану форми для захисту від випадкової втрати. Ти каліброєш рекомендацію під довжину, чутливість даних і реалістичні режими відмови конкретної форми — ти не переходиш за замовчуванням на «просто зберігай усе в localStorage» без перевірки, чи це реально доречно для даних цієї форми.

Опис форми (поля, довжина, типовий час заповнення): {{FORM_DESCRIPTION}}
Чутливість даних (напр., містить паролі, платіжну інформацію, чи низькоризикова): {{DATA_SENSITIVITY}}
Режими відмови для захисту (оновлення, закриття вкладки, падіння, таймаут сесії): {{FAILURE_MODES}}

Інструкції:
1. Рекомендуй, чи взагалі варте додавання збереження, зважаючи на довжину/час заповнення {{FORM_DESCRIPTION}} — двополева форма зазвичай не варта складності збереження; багатокрокова форма, що займає кілька хвилин, зазвичай варта. Вкажи обґрунтування, не лише вердикт.
2. Рекомендуй механізм зберігання, доречний {{DATA_SENSITIVITY}}: ніколи не зберігай чутливі поля (паролі, повні номери платіжних карток, номери соцстрахування) у localStorage чи sessionStorage у відкритому тексті, оскільки обидва доступні будь-якому скрипту, що виконується на сторінці (ризик XSS), і зберігаються довше, ніж користувач може очікувати; для чутливих форм рекомендуй або повністю виключити ці конкретні поля зі збереження, або підхід чернетки на сервері замість клієнтського сховища.
3. Для нечутливих даних форми рекомендуй localStorage проти sessionStorage проти лише-в-пам'яті на основі {{FAILURE_MODES}}: sessionStorage переживає оновлення, але не нову вкладку/вікно чи перезапуск браузера; localStorage переживає все це, але зберігається невизначено довго, якщо явно не очищено, що потребує продуманої стратегії закінчення терміну/прибирання, щоб уникнути затримки застарілих чернеток.
4. Спроєктуй, коли збережений стан очищається: при успішному поданні (завжди), і розглянь розумне закінчення терміну для покинутих чернеток (напр., збережений стан старший за N днів імовірно застарілий і має бути відкинутий чи позначений як стара чернетка, а не мовчки відновлений, ніби актуальний).
5. Спроєктуй UX відновлення: чи має форма користувача, що повертається, мовчки заповнитись зі збереженого стану, чи він має побачити явну підказку «продовжити чернетку?» — мовчазне відновлення ризикує заплутати користувача, що навмисно покинув форму чи заповнює її зараз для іншої мети (напр., друге, непов'язане подання).
6. Якщо {{FORM_DESCRIPTION}} передбачає кілька екземплярів форми, що можуть існувати одночасно (напр., користувач може мати дві різні чернетки того самого типу форми відкритими в різних вкладках, чи редагувати два різні записи з тією самою формою), познач, що єдиний фіксований ключ сховища спричинив би взаємне перезаписування екземплярів — рекомендуй ключувати сховище за стабільним ідентифікатором (напр., ID чернетки чи запис, що редагується), а не один глобальний ключ на тип форми.

Формат виводу: Markdown із `## Рекомендація збереження` (варте додавання чи ні, і чому), `## Механізм зберігання` (з винятками, зумовленими чутливістю, якщо є), `## Стратегія очищення`, і `## UX відновлення`.
```

## Змінні
- `{{FORM_DESCRIPTION}}` — поля форми, довжина, і типовий час заповнення. Обов'язково.
- `{{DATA_SENSITIVITY}}` — чи є будь-які поля чутливими (облікові дані, платежі, персональні ідентифікатори) проти низькоризикового контенту. Обов'язково — напряму визначає, що безпечно зберігати на клієнті.
- `{{FAILURE_MODES}}` — які конкретні сценарії втрати найважливіші для цієї форми (випадкове оновлення значно частіше за повне падіння браузера, і правильний механізм різниться). Обов'язково.

## Приклад
**Вхід:** `{{FORM_DESCRIPTION}}` = «Форма заявки на роботу з 4 кроків: особиста інформація, історія роботи, поле супровідного листа, крок перегляду. Типовий час заповнення 10-15 хвилин.» `{{DATA_SENSITIVITY}}` = «Особиста інформація включає ім'я/email/телефон (помірно чутливо, не рівня облікових даних); платіжних даних немає» `{{FAILURE_MODES}}` = «Випадкове закриття вкладки/оновлення — основне занепокоєння на основі повідомлень користувачів»

**Вихід (уривок):**
```
## Рекомендація збереження
Варте додавання — форма на 10-15 хвилин, 4 кроки, представляє значні зусилля користувача, і втрата через випадкове оновлення — реальна, повідомлена проблема, не гіпотетичний граничний випадок.

## Механізм зберігання
localStorage, не sessionStorage — основний режим відмови (випадкове закриття вкладки) означає, що користувач може повторно відкрити форму в новій вкладці, чого sessionStorage не пережив би. Ім'я/email/телефон помірно чутливі, але не рівня облікових даних; зберігання їх на клієнті прийнятне тут, на відміну від гіпотетичної версії цієї форми, що також збирала б номер соцстрахування чи платіжну інформацію, що потребувало б виключення з клієнтського сховища.

## Стратегія очищення
Очищати при успішному поданні. Додати 7-денне закінчення терміну на збережені чернетки — чернетка заявки старша за тиждень імовірно покинута чи застаріла (напр., вакансія могла змінитись), тож трактуй її як застарілу, а не мовчки відновлюй як актуальну.

## UX відновлення
Явна підказка, не мовчазне заповнення: «У тебе є незавершена заявка від [дата] — продовжити з того місця, де зупинився, чи почати заново?» — мовчазне відновлення ризикує заплутати заявника, що повернувся й навмисно почав заново, чи здивувати старими даними, які він не одразу впізнає своїми.

Також позначено: якщо користувач правдоподібно міг би подавати заявку на більш ніж одну вакансію, використовуючи той самий компонент форми, ключуй збережену чернетку за ID вакансії, не одним фіксованим ключем — інакше друга заявка в процесі мовчки перезаписала б першу чернетку.
```

## Поради та варіації
- Для форми зі справді високоцінним кейсом використання з високим ризиком покинення (напр., довга заявка з відомо низьким рівнем завершення) варто розглянути збереження чернетки на сервері (не лише клієнтське збереження), навіть для нечутливих даних — лише клієнтське збереження не допомагає користувачу, що перемикає пристрої посередині.
- Якщо квота сховища браузера реалістичне занепокоєння (дуже великі форми, завантаження файлів, закодовані як дані), зазнач, що localStorage має практичні ліміти розміру (зазвичай кілька МБ), у які великий збережений чернетковий проєкт міг би влучити — явно познач це, а не припускай необмежену місткість сховища.
- Цей промпт покриває стратегію збереження, не механіку реалізації бібліотеки форм конкретного фронтенд-фреймворку — поєднання рекомендації з реальним тулінгом стану форм твого фреймворку окремий, специфічний для фреймворку крок.
