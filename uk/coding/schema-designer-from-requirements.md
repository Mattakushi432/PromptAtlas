## Опис
Проєктує схему реляційної бази даних — таблиці, колонки, типи, зв'язки, обмеження — з опису фічі простою мовою. Для старту нового моделювання даних з нуля, відрізняється від оптимізації наявного запиту чи аудиту рівня нормалізації.

## Коли використовувати
- Старт нової фічі чи сервісу з потребою в чорновій схемі перед написанням будь-якої міграції.
- Переклад документа вимог продукту в конкретну модель даних, яку команда може розглянути перед фіксацією.
- Рев'ю того, чи запропонована схема дійсно підтримує всі патерни доступу, потрібні фічі.

## Промпт

```
Ти проєктуєш схему реляційної бази даних з опису фічі. Видавай конкретну деталізацію на рівні DDL, а не абстрактний список сутностей.

Опис фічі: {{FEATURE_DESCRIPTION}}
Відомі патерни доступу (як дані фактично будуть запитуватися — необов'язково, але дуже цінно): {{ACCESS_PATTERNS}}
Двигун бази даних: {{DATABASE_ENGINE}}
Обмеження (необов'язково — напр., "має інтегруватися з наявною таблицею users", "очікується високий обсяг запису на X"): {{CONSTRAINTS}}

Інструкції:
1. Визнач сутності, що випливають з фічі, і спроєктуй таблицю на кожну сутність, з колонками, типами і nullability — обирай типи свідомо (не роби все за замовчуванням загальним рядком/текстом) і обґрунтуй будь-який неочевидний вибір типу.
2. Моделюй зв'язки явно: зовнішні ключі з правильною кардинальністю (один-до-багатьох, багато-до-багатьох через таблицю-зв'язку тощо), і вкажи поведінку ON DELETE (CASCADE, RESTRICT, SET NULL) на основі того, що має сенс для фактичних даних — не роби CASCADE усюди за замовчуванням без розгляду, чи це безпечно.
3. Додай обмеження понад лише зовнішні ключі: NOT NULL там, де поле дійсно обов'язкове, UNIQUE там, де цього вимагає бізнес-правило, обмеження CHECK для простих інваріантів (напр., ціна має бути невід'ємною), а не залишай валідацію повністю коду застосунку.
4. Якщо надано {{ACCESS_PATTERNS}}, перевір, що схема дійсно ефективно їх підтримує — познач, якщо описаний патерн доступу вимагав би повного сканування чи незграбного join'у з урахуванням запропонованого дизайну, і скоригуй (напр., додай денормалізовану колонку, композитний індекс), а не залиш це як відому проблему.
5. Рекомендуй індекси для наданих патернів доступу, понад ті, що випливають лише з первинних/зовнішніх ключів.
6. Познач будь-яку вимогу в описі фічі, неоднозначну щодо кардинальності чи володіння (напр., "проєкт має учасників" — чи може користувач належати кільком проєктам, і чи є роль на кожне членство?), замість того щоб мовчки обирати інтерпретацію.
7. Якщо {{CONSTRAINTS}} згадує інтеграцію з наявними таблицями, не перепроєктовуй ці таблиці — проєктуй лише нове, і покажи точно, як нові таблиці посилаються на наявні.

Формат виводу: Markdown з таблицею на кожну сутність (колонки, типи, обмеження) у формі, близькій до DDL, за якою слідує підсумок зв'язків та рекомендації індексів.
```

## Змінні
- `{{FEATURE_DESCRIPTION}}` — що фіча має зберігати і як сутності пов'язані. Обов'язково.
- `{{DATABASE_ENGINE}}` — напр. "PostgreSQL 16", "MySQL 8". Обов'язково — назви типів і синтаксис обмежень різняться.
- `{{ACCESS_PATTERNS}}` — як дані будуть запитуватися на практиці. Необов'язково, але різко покращує рішення щодо індексів/денормалізації.
- `{{CONSTRAINTS}}` — точки інтеграції чи міркування масштабу. Необов'язково.

## Приклад
**Вхід:** `{{FEATURE_DESCRIPTION}}` = "користувачі можуть створювати проєкти і запрошувати інших користувачів як учасників із роллю (owner/editor/viewer)", `{{DATABASE_ENGINE}}` = "PostgreSQL 16".

**Вихід (фрагмент):**
```
### projects
| Колонка | Тип | Обмеження |
|---|---|---|
| id | uuid | PRIMARY KEY |
| owner_id | uuid | NOT NULL, FK -> users(id) ON DELETE RESTRICT |
| name | text | NOT NULL |
| created_at | timestamptz | NOT NULL DEFAULT now() |

### project_members (таблиця-зв'язка)
| Колонка | Тип | Обмеження |
|---|---|---|
| project_id | uuid | NOT NULL, FK -> projects(id) ON DELETE CASCADE |
| user_id | uuid | NOT NULL, FK -> users(id) ON DELETE CASCADE |
| role | text | NOT NULL, CHECK (role IN ('owner','editor','viewer')) |
| PRIMARY KEY | (project_id, user_id) | — гарантує, що користувача не можна додати до того самого проєкту двічі |

**Примітка:** `projects.owner_id` використовує `ON DELETE RESTRICT`, а не CASCADE — видалення користувача, що володіє проєктами, не має мовчки видаляти ці проєкти; володіння спочатку варто передати.
```

## Поради та варіації
- Для NoSQL/документного сховища замість цього моделювання таблиць-зв'язків цього промпту не переноситься напряму — попроси явно про компроміси embedded-vs-referenced дизайну документів.
- Коли схему затверджено, передай її в «Укладач безпечних міграційних скриптів» для генерації фактичної міграції, а не вручну пиши DDL з цієї чернетки.
