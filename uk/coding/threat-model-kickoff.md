## Опис
Створює перший прохід моделі загроз у стилі STRIDE з опису фічі до написання будь-якого коду — сесія на етапі дизайну, яку проводить команда, орієнтована на безпеку, щоб закласти пом'якшення з першого дня. Відрізняється від сканування вже написаного коду на вразливості: тут працюємо з описом того, що будується, а не з diff'ом.

## Коли використовувати
- Старт дизайну фічі, що торкається чутливих даних, автентифікації, платежів чи нової межі довіри.
- Підготовка тез для реальної зустрічі з командою з моделювання загроз.
- Легка заміна повного security-рев'ю, коли воно ще не виправдане, але питання "а ми взагалі про це думали" вже актуальне.

## Промпт

```
Ти фасилітуєш перший прохід моделі загроз для фічі, яку ще не побудовано, за методологією STRIDE. Працюй з наданим описом — не вигадуй деталі реалізації, яких там немає.

Опис фічі (що будується, залучені актори, потоки даних і відомі межі довіри): {{FEATURE_DESCRIPTION}}

Чутливість даних (необов'язково — який тип даних задіяний, наприклад PII, платіжні дані, жодних): {{DATA_SENSITIVITY}}

Кроки:
1. Переформулюй межі довіри і потоки даних, які можеш визначити з опису — хто/що з ким спілкується, і де змінюється рівень довіри (наприклад, клієнт до сервера, сервер до стороннього API).
2. Для кожного елемента застосуй STRIDE — Spoofing (підміна), Tampering (втручання), Repudiation (відмова від авторства), Information disclosure (розкриття інформації), Denial of service (відмова в обслуговуванні), Elevation of privilege (підвищення привілеїв) — і перелічи конкретні, правдоподібні загрози, специфічні для реальних акторів і потоків з опису, а не типові приклади з підручника ("зловмисник може підмінити особу" — надто розпливчасто; назви яку саме особу, на якій межі і як).
3. Оціни кожну загрозу за ймовірністю × впливом (LOW/MEDIUM/HIGH для кожного).
4. Запропонуй одне найбільш ефективне пом'якшення для кожної загрози MEDIUM+ — дизайнерське рішення, що запобігає їй, а не просто "додати валідацію".

Виведи: резюме меж довіри, потім таблицю загроз STRIDE, потім список "топ пом'якшень для закладання з першого дня", впорядкований за пріоритетом.

Якщо опис надто розпливчастий, щоб визначити реальні межі довіри чи акторів, не вгадуй — перелічи конкретні питання, на які треба отримати відповіді перед тим, як моделювання загроз стане можливим.
```

## Змінні
- `{{FEATURE_DESCRIPTION}}` — що будується: актори, потоки даних і відомі межі довіри. Обов'язково.
- `{{DATA_SENSITIVITY}}` — тип задіяних даних, якщо є. Необов'язково, але суттєво покращує оцінку Information Disclosure та впливу.

## Приклад
**Вхід:** `{{FEATURE_DESCRIPTION}}` = "Публічний API-ендпоінт дозволяє авторизованому користувачу завантажити фото профілю, яке зберігається в S3 і віддається через CDN URL, повернутий клієнту.", `{{DATA_SENSITIVITY}}` = "зображення, завантажені користувачами, деякі можуть містити ідентифікуючу інформацію".

**Вихід (фрагмент):**
```
Межі довіри: клієнт (недовірений ввід) → API-сервер (валідує, автентифікує) → S3 (зберігання) → CDN (публічна доставка, без авторизації).

Tampering: ендпоінт завантаження приймає файл із content-type/іменем файлу, заданими клієнтом — зловмисник може завантажити файл, що насправді є HTML/SVG-навантаженням, замаскованим під зображення, яке пізніше віддається з origin-домену CDN, уможливлюючи stored XSS, якщо CDN віддає його inline. Ймовірність: MEDIUM, Вплив: HIGH.
Пом'якшення: валідувати реальний вміст файлу (magic bytes, а не лише розширення чи заголовок content-type) і віддавати завантажені зображення з окремого домену без кукі, щоб виконання будь-якого скрипта не мало доступу до сесії основного застосунку.

Elevation of privilege: на шляху завантаження не видно перевірки власності — якщо ендпоінт приймає ID цільового користувача, а не визначає його з сесії, користувач може перезаписати фото іншого користувача. Ймовірність: MEDIUM, Вплив: MEDIUM.
```

## Поради та варіації
- Для вже спроєктованої фічі, коли потрібне ретроспективне покриття замість вхідних даних на етапі дизайну, передай як `{{FEATURE_DESCRIPTION}}` дизайн-документ чи опис архітектурної діаграми — процес той самий.
- Поєднуй із `secure-coding-checklist-generator`, коли починається реалізація: цей промпт визначає пом'якшення для закладання, а той перетворює їх на чекліст для етапу реалізації.
