## Опис
Оцінює стійкість коду, що звертається до зовнішнього, стороннього API — таймаути, повтори, поведінку резервного варіанту — відносно того, наскільки цей виклик реально критичний для флоу користувача, частиною якого він є. Для інженера, що інтегрує нову зовнішню залежність, а не рев'ю контракту/дизайну API.

## Коли використовувати
- Додаєш нову інтеграцію з платіжним процесором, службою доставки, email-сервісом чи будь-яким зовнішнім API.
- Минулий інцидент простежувався до повільного чи недоступного зовнішнього API, що потягнув за собою твій власний сервіс.
- Перевіряєш, чи обробка помилок інтеграції відповідає тому, наскільки виклик реально критичний.

## Промпт

```
Ти оцінюєш стійкість коду, що звертається до стороннього API — конкретно те, як він обробляє повільність, помилки чи повну недоступність цієї зовнішньої залежності. Вважай, що щаслива логіка інтеграції коректна; твоє завдання — що відбувається, коли зовнішня сторона поводиться неправильно.

Код інтеграції: {{INTEGRATION_CODE}}

Критичність цього зовнішнього виклику (він на критичному шляху ключового користувацького флоу, який має завершитись успішно, чи це best-effort/неблокуюче): {{EXTERNAL_API_CRITICALITY}}

Перевір:
1. Таймаут — чи встановлено явний, розумний таймаут на виклик, замість покладання на значення за замовчуванням бібліотеки/платформи, яке може бути надто довгим чи фактично нескінченним?
2. Стратегію повторів — чи існує логіка повторів для тимчасових збоїв, і чи використовує вона backoff (а не щільний цикл повторів, що може посилити навантаження на вже проблемний зовнішній сервіс)?
3. Circuit-breaker чи резервний варіант — при затяжному зовнішньому збої, чи є механізм припинити бомбардувати сервіс, що впав, і або швидко відмовити, або віддати резервний варіант, замість того щоб кожен запит окремо чекав повний таймаут?
4. Поширення збою — коли зовнішній виклик остаточно провалюється, що відбувається із запитом, що його зробив? Він провалює всю дію користувача, чи м'яко деградує (наприклад, пропускає неважливий крок збагачення даних і продовжує)? Оціни, чи це відповідає заявленій {{EXTERNAL_API_CRITICALITY}} — best-effort виклик, що обвалює ключовий флоу при збої, — розбіжність, варта уваги, навіть якщо код "працює".

Для кожної знайденої прогалини запропонуй конкретне виправлення (значення таймауту з обґрунтуванням, стратегію backoff чи резервну поведінку), а не просто зафіксуй, що прогалина існує.

Якщо заявлена критичність — best-effort, але рев'ю виявляє, що виклик насправді структурований так, що блокує/провалює ключовий флоу, явно назви цю розбіжність топ-знахідкою — зазвичай вона важливіша за будь-який окремий відсутній таймаут.
```

## Змінні
- `{{INTEGRATION_CODE}}` — код, що звертається до зовнішнього API. Обов'язково.
- `{{EXTERNAL_API_CRITICALITY}}` — чи цей виклик на критичному шляху обов'язкового флоу, чи best-effort/неблокуючий. Обов'язково — вимоги до стійкості оцінюються відносно цього, а не в абстракції.

## Приклад
**Вхід:** `{{INTEGRATION_CODE}}` = флоу оформлення замовлення, що синхронно викликає сторонній API оцінки шахрайства без встановленого таймауту і провалює все оформлення замовлення, якщо виклик кидає виняток, `{{EXTERNAL_API_CRITICALITY}}` = "best-effort — оцінка шахрайства це приємний бонус, а не жорстка вимога для завершення оформлення замовлення".

**Вихід (фрагмент):**
```
Знахідка (топ): заявлена критичність — best-effort, але код провалює все оформлення замовлення, якщо виклик fraud API кидає виняток — це розбіжність критичності. Best-effort виклик збагачення ніколи не має мати можливості заблокувати ключовий flow доходу. Серйозність: HIGH.
Виправлення: обгорни виклик оцінки шахрайства так, щоб збій чи таймаут логували попередження й продовжували оформлення замовлення зі станом "не оцінено" за замовчуванням, замість поширення винятку вгору, що провалює транзакцію.

Знахідка: на HTTP-клієнті для цього виклику не встановлено явного таймауту — покладання на значення за замовчуванням бібліотеки ризикує тим, що повільний fraud API застопорить запити оформлення замовлення на невизначений час. Серйозність: MEDIUM.
Виправлення: встанови явний таймаут (наприклад, 500мс, з огляду на те, що це best-effort сигнал, на очікування якого не варто витрачати багато часу) і обробляй таймаут так само, як будь-який інший збій у резервному шляху вище.
```

## Поради та варіації
- Для справді критичного виклику (наприклад, самого платіжного процесора) рекомендація резервного варіанту змінюється з "м'яко деградувати" на "швидко відмовити з чітким повідомленням для користувача і опцією повтору" — явно скажи, якщо виклик дійсно не можна зробити best-effort.
- Поєднуй з `caching-strategy-advisor`, якщо зовнішні дані змінюються повільно — короткоживучий кеш часто краще виправлення стійкості, ніж глибша логіка повторів.
