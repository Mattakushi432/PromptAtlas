## Опис
Позначає feature flags, які безпечно видалити, бо код більше не має реальної варіації за ними — детектор мертвих флагів на рівні коду, відмінний від «Побудова матриці пріоритизації техборгу» (coding, вже випущений) із загальним плануванням погашення за ROI і від «Планувальник поетапного рол-ауту через feature flag» (coding, вже випущений) із дизайном стадій рол-ауту: цей промпт конкретно про пошук флагів, чиї обидві гілки зійшлись чи чия перевірка флага тепер недосяжна.

## Коли використовувати
- Твоя кодова база накопичила feature flags із часом, і підозрюєш, що кілька повністю розкачені (чи повністю вбиті), але перевірки флагів так і не видалили.
- Хочеш систематичний прохід перед спринтом прибирання, а не ручний пошук застарілих флагів по одному.
- Новий інженер постійно запитує, що робить конкретний флаг, і ніхто не впевнений, чи він досі щось значуще перемикає.

## Промпт

```
Ти аудитуєш feature flags у кодовій базі на ті, що безпечно видалити — флаги, де код більше не має реальної варіації за ними, бо одна гілка мертва, недосяжна, чи значення флага ефективно було константним тривалий час. Ти позначаєш кандидатів на видалення; ти сам не видаляєш код.

Місця використання флагів (результати grep чи фрагменти коду): {{FLAG_USAGES}}
Конфігурація флагів/поточні значення (якщо доступно): {{FLAG_CONFIG}}
Вік флага/історія рол-ауту (якщо відомо): {{FLAG_HISTORY}}

Інструкції:
1. Для кожного флага перевір, чи обидві гілки (true й false) його перевірки все ще досяжні на практиці, чи одна гілка — мертвий код (напр., false-гілка робить щось, більше неможливе, зважаючи на інший стан застосунку, чи флаг був на 100% рол-ауту задокументований період за {{FLAG_HISTORY}}).
2. Познач кандидата як «безпечно видалити, лишити код true-гілки», коли флаг ефективно завжди true, зважаючи на {{FLAG_CONFIG}}/{{FLAG_HISTORY}} — вкажи, яка гілка виживає, а яку варто видалити.
3. Познач кандидата як «безпечно видалити, лишити код false-гілки», коли флаг був повністю відкачений чи ніколи повністю не запущений і тепер ефективно завжди false — це випадок, який найлегше пропустити, оскільки флаг, доданий для запуску, що пізніше відкотили, часто забувають, а не прибирають.
4. Не позначай флаг як видалюваний лише тому, що він виглядає застарілим за віком — перевіряй на реальні докази фіксованої/зійшлої поведінки (100% рол-аут без запланованого продовження експерименту, явну нотатку «повністю запущено», чи буквально недосяжні гілки), а не вгадуй за віком. Якщо {{FLAG_HISTORY}}/{{FLAG_CONFIG}} не надано, явно скажи, що видалюваність не можна підтвердити лише з місць використання.
5. Розрізняй справді мертвий флаг від навмисного постійного вимикача екстреного випадку (напр., флаг екстреного вимкнення, задуманий лишатись у стані «увімкнено» невизначено довго, але існувати для реагування на інциденти) — стабільне значення kill-switch флага не є доказом його смерті; явно познач цю різницю, а не рекомендуй видалення навмисного механізму безпеки.
6. Для кожного флага, позначеного видалюваним, вкажи кожне місце файлу, де з'являється його перевірка, щоб обсяг видалення був конкретно видимим перед тим, як хтось зобов'яжеться до прибирання.

Формат виводу: Markdown, окремий запис на кожен флаг: назва, вердикт (безпечно видалити / лишити — причина / потрібно більше інформації), яка гілка виживає, якщо видалюваний, і всі місця файлів, де з'являється перевірка.
```

## Змінні
- `{{FLAG_USAGES}}` — результати grep чи фрагменти коду, що показують кожне місце перевірки конкретного флага. Обов'язково.
- `{{FLAG_CONFIG}}` — поточне сконфігуроване значення/відсоток рол-ауту флага, якщо доступно із системи управління флагами. Рекомендовано — без цього вердикти лишаються попередніми.
- `{{FLAG_HISTORY}}` — коли флаг було введено і будь-які відомі віхи рол-ауту. Необов'язково, але значно покращує впевненість у вердикті.

## Приклад
**Вхід:** `{{FLAG_USAGES}}` = "`if (flags.newCheckoutFlow) { renderNewCheckout() } else { renderLegacyCheckout() }` — з'являється в CheckoutPage.tsx, CheckoutAnalytics.ts" `{{FLAG_CONFIG}}` = «newCheckoutFlow: 100% рол-аут, наразі немає прикріпленого експерименту» `{{FLAG_HISTORY}}` = «Введено 14 місяців тому для запуску редизайну чекауту»

**Вихід (уривок):**
```
### Флаг: newCheckoutFlow
Вердикт: Безпечно видалити — лишити код true-гілки (`renderNewCheckout()`).
Обґрунтування: 100% рол-аут без прикріпленого експерименту, стабільний тривалий період за історією — false-гілка (`renderLegacyCheckout()`) ефективно мертвий код на цей момент.
Локації для оновлення: CheckoutPage.tsx (умовний рендер), CheckoutAnalytics.ts (аналітична подія, прив'язана до флага).
Примітка: підтверди з командою чекауту, що `renderLegacyCheckout()` не тримається навмисно як резервний kill-switch перед видаленням — сам по собі 100% рол-аут не виключає навмисної запобіжної сітки, хоча нічого в наданій історії не натякає на такий намір тут.
```

## Поради та варіації
- Запускай це періодично (напр., щоквартально), а не лише під час спеціального спринту прибирання — розростання флагів накопичується поступово, і виявлення рано тримає кожен прохід прибирання невеликим.
- Для флага, позначеного «потрібно більше інформації», це саме по собі корисний сигнал — зазвичай означає, що власність чи статус рол-ауту флага десь чітко не відстежується, що є прогалиною процесу, вартою виправлення незалежно від долі цього конкретного флага.
- Поєднуй із «Пошук мертвого коду» (coding, вже випущений) для ширшого проходу мертвого коду, коли гілки, пов'язані з флагами, підтверджені й видалені — цей промпт сфокусований конкретно на коді, огородженому флагами, не на мертвому коді загалом.
