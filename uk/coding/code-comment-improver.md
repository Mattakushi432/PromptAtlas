## Опис
Перетворює нечисленні, відсутні чи некорисні коментарі коду на дійсно корисні — пояснюючи ЧОМУ, не переказуючи ЩО код уже й так каже — для конкретного файлу. Вузький обсяг лише щодо коментарів, відрізняється від «Аудитора конвенцій іменування» (назви) і загальних промптів код-рев'ю.

## Коли використовувати
- Успадкував файл із заплутаною логікою і без коментарів, що пояснюють неочевидні частини.
- Рев'ю PR, де коментарі або відсутні, або просто переказують код рядок за рядком ("// increment i" над `i++`).
- Підготовка файлу для нового контриб'ютора з бажанням, щоб коментарі несли більше тягаря пояснення.

## Промпт

```
Ти покращуєш коментарі коду — додаєш дійсно корисні там, де їх бракує, виправляєш ті, що просто переказують код, і видаляєш ті, що не додають цінності. Ти не чіпаєш логіку коду.

Код: {{CODE}}
Мова: {{LANGUAGE}}

Інструкції:
1. Визнач місця, що потребують коментаря, бо ЧОМУ коду не очевидне з читання: неочевидне бізнес-правило, обхідний шлях для конкретного бага/обмеження, вибір алгоритму, що не самоочевидний, тонкий інваріант, який майбутній редактор міг би легко зламати, мотивований продуктивністю патерн, що виглядає незвично (розгорнутий цикл, нетрадиційна структура даних), що інакше виглядав би помилкою.
2. НЕ додавай коментар, що просто переказує те, що код уже й так каже іншими словами (`// loop through users` над `for user in users:`) — якщо видалення коментаря не заплутало б читача, коментар не має там бути.
3. Познач і видали/перепиши наявні коментарі, що активно неправильні чи застарілі (описують поведінку, якої код більше не має) — неправильний коментар гірший за відсутність коментаря, оскільки він активно вводить в оману.
4. Для публічних API (експортовані функції/класи, особливо в бібліотеці) напиши doc-коментар за стандартною конвенцією мови (JSDoc, docstring, Javadoc тощо), що покриває параметри, значення, що повертається, і будь-які кинуті помилки/винятки — але тримай пропорційно; простий getter не потребує абзацу.
5. Для будь-якого коментаря, що позначає обхідний шлях (виправлення конкретного бага в залежності, особливість браузера/платформи), включи достатньо деталей, щоб майбутній читач міг визначити, коли безпечно видалити (номер версії, посилання на issue, умову для перевірки).
6. Зберігай фактичну логіку коду точно — це прохід лише по коментарях. Якщо помітиш баг під час читання, не виправляй мовчки; зазнач це окремо поза виводом покращення коментарів.
7. Тримай коментарі лаконічними — коментар, що вимагає більше часу читання, ніж код, який він описує, зазвичай зайшов задалеко; одне-два речення типово, залишай довші пояснення для дійсно складних інваріантів.

Вивід: код з покращеними коментарями, за яким слідує короткий список будь-яких видалених коментарів і чому, і (окремо) будь-які помічені, але не виправлені баги.
```

## Змінні
- `{{CODE}}` — файл/код для покращення коментарів. Обов'язково.
- `{{LANGUAGE}}` — мова програмування, оскільки конвенції doc-коментарів різняться (JSDoc проти docstrings проти Javadoc). Обов'язково.

## Приклад
**Вхід:** `{{LANGUAGE}}` = "Python", `{{CODE}}` = функція з `retries = 3  # set retries to 3` над циклом повторів, і без коментаря на рядку, що пропускає повтор для конкретного коду помилки.

**Вихід (фрагмент):**
```python
retries = 3  # обрано емпірично: вікно rate-limit вищерозташованого API на практиці скидається за ~2 повтори; більше додає затримку без виміряної вигоди

if error.code == 429:
    break  # не повторюй помилки rate-limit — негайний повтор погіршує backoff rate-limit на боці вищерозташованого сервісу (див. INCIDENT-204)
```
*(далі: "Видалено оригінальний коментар `# set retries to 3` — він лише переказував присвоєння без доданої інформації.")*

## Поради та варіації
- Для кодової бази, що впроваджує строгіший стандарт документації (напр., вимагає doc-коментарі на всіх експортованих функціях для згенерованого довідника API), явно попроси позначати будь-яку публічну функцію, що досі бракує doc-коментаря, як окремий пункт для подальшої роботи.
- Якщо рецензуєш дуже великий файл, запускай це по кожному логічному розділу окремо, а не весь файл одразу, щоб тримати судження про якість коментарів відкаліброваним до локального контексту, а не розбавленим по непов'язаному коду.
