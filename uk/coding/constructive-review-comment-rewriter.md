## Опис
Переписує різкі, розпливчасті чи грубі коментарі код-рев'ю на конкретні, дієві та шанобливі — для рев'ювера, який знає, що щось не так, але чий перший чернетковий варіант прозвучить погано, або для команди, що стандартизує добрішу культуру рев'ю.

## Коли використовувати
- Перед публікацією коментаря до рев'ю, яким не пишаєшся, але думку все одно треба донести.
- Коучинг молодшого рев'ювера, чий фідбек технічно правильний, але звучить зневажливо.
- Приведення пачки лаконічних коментарів ("це неправильно", "погана назва") до вигляду, з яким контриб'ютор дійсно може щось зробити.

## Промпт

```
Ти переписуєш коментарі код-рев'ю так, щоб вони були конструктивними: конкретними, об'єктивними та дієвими, зберігаючи оригінальну технічну суть. Не пом'якшуй коментар до розпливчастості — конструктивний коментар усе одно прямо каже, що треба змінити.

Оригінальний(і) коментар(і):
{{ORIGINAL_COMMENTS}}

Контекст коду (необов'язково, рядок(и), яких стосується коментар):
{{CODE_CONTEXT}}

Бажаний тон (необов'язково, за замовчуванням: колегіальний і прямий): {{TONE}}

Інструкції:
1. Для кожного оригінального коментаря визнач основну технічну проблему — навіть якщо оригінальне формулювання є просто образою чи однослівним відкиданням, виведи реальну проблему з контексту, якщо можливо.
2. Перепиши за такою структурою: спостереження (що ти помітив, сформульоване про код, а не про людину) + чому це важливо (конкретний наслідок) + запропонований напрямок (не обов'язково єдине виправлення, але відправна точка).
3. Постав перед кожним переписаним коментарем мітку, що відображає його реальну вагу: `nit:` для незначного/необов'язкового, `question:` для того, у чому ти не впевнений, а не точно знаєш, що не так, `suggestion:` для рекомендованої зміни, `blocking:` для того, що обов'язково треба виправити перед мерджем.
4. Якщо оригінальний коментар занадто розпливчастий, щоб відновити з нього технічну суть (напр., просто "ні"), скажи про це і запитай, що саме малося на увазі, замість того щоб вигадувати правдоподібну, але сфабриковану проблему.
5. Ніколи не додавай сарказм, пом'якшення, що стирає суть ("можливо, варто розглянути можливість..."), чи непов'язану похвалу як пом'якшення.

Формат виводу: один переписаний коментар на кожен оригінальний, у тому ж порядку, як нумерований список.
```

## Змінні
- `{{ORIGINAL_COMMENTS}}` — різкий(і) коментар(і) для переписування, по одному в рядку. Обов'язково.
- `{{CODE_CONTEXT}}` — код, якого стосується коментар. Необов'язково, але покращує точність, коли оригінальний коментар лаконічний.
- `{{TONE}}` — напр. "прямий, для senior-колеги" чи "особливо м'який, для новачка-контриб'ютора". Необов'язково.

## Приклад
**Вхід:** `{{ORIGINAL_COMMENTS}}` = "ця функція — суцільний хаос", `{{CODE_CONTEXT}}` = 90-рядкова функція, що змішує парсинг вводу, бізнес-логіку та запис у БД.

**Вихід (фрагмент):**
```
1. suggestion: Наразі ця функція обробляє парсинг, бізнес-логіку і запис у базу даних в одному блоці, що ускладнює тестування бізнес-логіки окремо. Розглянь розділення на `parseInput()`, `calculateResult()` і `saveResult()` — це дозволить юніт-тестувати обчислення без бази даних.
```

## Поради та варіації
- Для анонімних/асинхронних інструментів рев'ю попроси тримати всі коментарі в другій особі про код ("ця функція..."), а не про автора ("ти написав...").
- Для команди, що впроваджує Conventional Comments, явно вимагай мітки `nit:`/`question:`/`suggestion:`/`blocking:` щоразу, як показано вище.
