## Опис
Виявляє шляхи коду та залежності, які, ймовірно, не використовуються, на основі доказів у наданому контексті — досяжність, експорти, які ніколи не імпортуються, feature flag'и, назавжди застряглі увімкненими/вимкненими — з чесним рівнем впевненості для кожної знахідки. Для прибирання кодової бази, відрізняється від загального проходу запахів коду: це конкретно про "чи можна це видалити".

## Коли використовувати
- Підозрюєш, що модуль, функція чи залежність більше не використовується, і хочеш другу думку перед видаленням.
- Прибирання після того, як фіча була повністю розкочена (чи повністю відкочена), і її логіка флага/гілки тепер назавжди однобока.
- Онбординг у кодову базу і бажання знати, що безпечно ігнорувати, а що несе навантаження.

## Промпт

```
Ти шукаєш ймовірно мертвий код — код, що виглядає недосяжним, невикористаним чи назавжди замкнутим коротко — на основі лише наданих доказів. Чесно вказуй рівень впевненості; статичний аналіз фрагмента коду не може довести, що щось дійсно мертве, так, як це може реальний інструмент трасування використання.

Код/модуль для аналізу: {{CODE}}
Додатковий контекст (необов'язково — напр., інші файли, що можуть посилатися на це, відомі стани feature flag'ів, package.json/імпорти деінде в репозиторії): {{ADDITIONAL_CONTEXT}}

Шукай:
1. Недосяжний код — код після безумовного return/throw/break, чи всередині умови, яка завжди хибна з урахуванням видимих констант.
2. Невикористані експорти/функції — визначені, але, на основі наданого контексту, ніколи ніде видимо не імпортуються чи не викликаються.
3. Назавжди однобокі feature flag'и/умови — перевірка флага, де всі видимі докази свідчать, що він тепер завжди true чи завжди false (напр., флаг з назвою `enableLegacyFlow`, який кожен викликач встановлює в `false`).
4. Невикористані залежності — імпорти, що присутні, але чиї експортовані члени ніколи не згадуються у видимому коді.
5. Закоментовані блоки коду — познач їх окремо як проблему документації/прибирання, не те саме, що дійсно мертвий виконуваний код.

Для кожної знахідки вкажи ВПЕВНЕНІСТЬ (HIGH: сильні, прямі докази в наданому; MEDIUM: наводить на думку, але не можеш виключити невидимого викликача; LOW: спекулятивно) — не подавай знахідки MEDIUM/LOW з тією ж впевненістю, що й HIGH.

Для знахідок з впевненістю MEDIUM/LOW скажи точно, яка додаткова перевірка підвищила б чи знизила б твою впевненість (напр., "прогреп весь репозиторій на `oldPricingLogic`, щоб підтвердити відсутність решти викликачів").

Ніколи не стверджуй, що щось мертвий код, лише тому що ти особисто не бачиш його використання — розрізняй "не використовується в тому, що я бачу" і "точно невикористовується".

Формат виводу: Markdown, згруповано за типом знахідки, кожна з рівнем впевненості та перевіркою, яка б це підтвердила.
```

## Змінні
- `{{CODE}}` — код/модуль для аналізу. Обов'язково.
- `{{ADDITIONAL_CONTEXT}}` — інший контекст репозиторію, що впливає на впевненість (інші файли, конфігурації флагів, маніфести пакетів). Необов'язково, але суттєво покращує точність.

## Приклад
**Вхід:** `{{CODE}}` = модуль, що експортує `formatLegacyDate()`, `{{ADDITIONAL_CONTEXT}}` = "греп по всьому репозиторію показує відсутність решти імпортів formatLegacyDate".

**Вихід (фрагмент):**
```
### Невикористаний експорт — `formatLegacyDate` — ВИСОКА впевненість
Жоден імпорт `formatLegacyDate` не з'являється ніде в наданих результатах грепу по репозиторію, і він не є частиною публічної API-поверхні цього модуля, що декларується (не знайдено реекспорту в `index.ts`).
Підтверджуюча перевірка вже зроблена: греп по репозиторію на ідентифікатор. Рекомендую видалення після фінальної перевірки будь-яких динамічних/рядкових імпортів (напр., `require(variableName)`), які греп не може виловити.
```

## Поради та варіації
- Поєднуй з реальним виводом інструмента статичного аналізу (ts-prune, knip, vulture, deadcode) як `{{ADDITIONAL_CONTEXT}}` — цей промпт найсильніший у поясненні/підтвердженні виводу інструмента та виловлюванні того, що прості інструменти досяжності пропускають (як-от назавжди однобокі флаги), а не в повній заміні інструмента.
- Для великого PR на видалення попроси також позначати будь-яку знахідку, експортовану з публічної API пакета (проти суто внутрішньої), як ризикованішу для видалення, оскільки зовнішні споживачі можуть існувати поза видимою кодовою базою.
