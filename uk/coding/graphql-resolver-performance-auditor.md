## Опис
Перевіряє код реалізації GraphQL-резолверів на проблеми продуктивності часу виконання — відсутній батчинг, надлишкові запити до бази даних на поле, відсутнє кешування. Відрізняється від `graphql-schema-reviewer`, що критикує саме визначення схеми (SDL) на ризик N+1 і форму over-fetching на етапі дизайну: тут рецензується реальний код резолверів, що виконується під час рантайму, де добре спроєктована схема все ще може бути погано реалізована, чи навпаки.

## Коли використовувати
- GraphQL API повільне під реальним навантаженням запитів, попри розумний дизайн схеми.
- Рецензуєш новий код резолвера перед мерджем, щоб зловити проблему продуктивності до випуску.
- Розслідуєш, чому конкретний тип запиту непропорційно повільний.

## Промпт

```
Ти проводиш аудит коду реалізації GraphQL-резолверів на продуктивність рантайму — не форму схеми (вважай, що сам дизайн схеми розумний; твоє завдання — як резолвери реально виконуються проти неї).

Код резолверів: {{RESOLVER_CODE}}

Контекст схеми (необов'язково — релевантні визначення типів, якщо корисно для розуміння ролі резолвера): {{SCHEMA_CONTEXT}}

Перевір:
1. Виконання N+1 — будь-який резолвер, що отримує пов'язані/вкладені дані окремим запитом до бази даних на кожного батька, що виконується один раз для кожного елемента списку (наприклад, резолвер `Post.author`, що запитує базу даних окремо для кожного поста у списку з 50, замість батчингу всіх 50 пошуків автора в один запит).
2. Коректність батчингу — якщо механізм батчингу (DataLoader чи еквівалент) використовується, перевір, що він реально коректно проскоупований: новий інстанс на кожен запит, а не спільний/на рівні модуля інстанс, що витікав би кешовані дані між непов'язаними запитами (тонкий баг, який легко внести і легко пропустити при рев'ю).
3. Можливості кешування — дорогі чи часто повторювані обчислення всередині резолвера, які не кешуються, коли базові дані не змінюються в межах запиту чи короткого TTL.
4. Обмеження складності/глибини запиту — чи існує будь-який захист від того, щоб один глибоко вкладений чи широко розгалужений запит був катастрофічно дорогим для виконання, зловмисно чи просто через ненавмисно дорогий клієнтський запит.

Для кожної знахідки процитуй конкретний резолвер і опиши конкретний патерн запиту, що спричинить проблему (наприклад, "запит `posts { author { name } }` для списку зі 100 постів спричинить 100 окремих пошуків автора"), а не загальну "це може бути повільним".

Якщо бібліотека батчингу вже використовується, не вважай саму її наявність достатньою — перевір, що скоупінг реально коректний, оскільки неправильно налаштований DataLoader (наприклад, інстанційований один раз при завантаженні модуля замість на кожен запит) — реальний і поширений режим збою, а не гіпотетичний.
```

## Змінні
- `{{RESOLVER_CODE}}` — код реалізації резолвера для аудиту. Обов'язково.
- `{{SCHEMA_CONTEXT}}` — релевантні визначення типів, якщо це допомагає прояснити роль резолвера. Необов'язково.

## Приклад
**Вхід:** `{{RESOLVER_CODE}}` = резолвер `Post.author`, що напряму виконує `db.users.findById(post.authorId)`, без DataLoader чи батчингу десь у мапі резолверів.

**Вихід (фрагмент):**
```
Знахідка: виконання N+1 у `Post.author`. Патерн, що спричиняє: будь-який запит зі списком постів та їхніми авторами — `posts { author { name } }` — виконає один виклик `findById` на кожен пост у результаті, тож список зі 50 постів спричинить 50 окремих звернень до бази даних замість одного батчованого запиту. Серйозність: HIGH, масштабується лінійно з розміром списку і, ймовірно, домінуюча вартість будь-якого запиту зі списком постів.

Виправлення: введи DataLoader для пошуку користувачів, що батчить виклики `findById`, зроблені в межах одного такту виконання GraphQL, в один запит `WHERE id IN (...)`, і інстанціюй його заново на кожен запит (наприклад, у фабриці контексту GraphQL) — не як синглтон на рівні модуля, що витікав би кешованих користувачів одного запиту у відповідь іншого.
```

## Поради та варіації
- Для федеративного/subgraph GraphQL-налаштування попроси конкретно перевірити патерни N+1, введені на рівні шлюзу/композиції, а не лише всередині резолверів одного subgraph — федерація може вносити власні прогалини батчингу.
- Поєднуй з `n-plus-one-detector`, якщо базовий доступ до бази даних йде через ORM — той промпт ловить патерни N+1 на рівні ORM загалом, а цей саме калібрований під модель виконання GraphQL-резолверів (порезультатне вирішення поля).
