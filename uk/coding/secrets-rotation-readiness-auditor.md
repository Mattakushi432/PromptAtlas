## Опис
Перевіряє, чи сервіс реально може ротувати credential (API-ключ, пароль бази даних, сертифікат) без простою. Відрізняється від `secrets-leak-detector`, що шукає розкриті чи захардкожені секрети — не те, чи ротація належно керованого секрету операційно можлива без збою.

## Коли використовувати
- Встановлюєш політику ротації credential і треба перевірити, чи сервіси реально можуть її підтримати на практиці, а не лише на папері.
- Спроба ротації спричинила збій, і хочеш зрозуміти конкретну прогалину для наступного разу.
- Вимога комплаєнсу передбачає періодичну ротацію, і ти перевіряєш реальну операційну готовність.

## Промпт

```
Ти перевіряєш, чи сервіс може ротувати конкретний credential без простою — не те, чи credential зараз розкритий чи витік, це окреме питання; вважай, що сам credential належно керований, і зосередься виключно на тому, чи його ротація операційно безпечна.

Код сервісу чи конфігурація (як credential завантажується і використовується — env-змінна, прочитана один раз при старті vs. періодично перечитувана, чи сервіс може тримати одну активну credential чи кілька): {{SERVICE_CODE_OR_CONFIG}}

Тип credential (API-ключ, пароль бази даних, TLS-сертифікат тощо — механіка ротації суттєво відрізняється за типом): {{CREDENTIAL_TYPE}}

Перевір:
1. Таймінг завантаження — чи credential завантажується один раз при старті процесу (тобто ротація вимагає повного перезапуску/редеплою для набуття чинності, а не живої ротації), чи може бути перезавантажена з джерела без перезапуску процесу?
2. Підтримка подвійної валідності — чи може сервіс приймати і коректно використовувати два валідні credential одночасно протягом перехідного вікна? Це ключовий механізм для ротації з нульовим простоєм: створи новий credential у джерелі, поки старий все ще валідний, дай обом коротко працювати, перемкни сервіс, потім виведи старий credential з експлуатації — замість жорсткого перемикання, що вимагає ідеального таймінгу.
3. Послідовність низхідних систем — для типів credential із залежностями (база даних, де новий пароль має бути створений і надано права до того, як застосунок перемкнеться на нього; TLS-сертифікат, якому клієнти мають довіряти до того, як він стане єдиним обслуговуваним сертифікатом) перевір, чи план ротації реально правильно впорядковує це, а не вважає одноатомарний обмін.

Виведи вердикт готовності: може ротувати живцем з нульовим простоєм / потребує короткого перезапуску сервісу, але без повного збою / потребує запланованого вікна простою — з конкретною прогалиною(ами), що спричиняє будь-що коротше за живу ротацію, і що потрібно змінити, щоб досягти ротації з нульовим простоєм, якщо це реальна мета.

Якщо тип credential не має підтримки подвійної валідності на рівні провайдера (деякі legacy чи сторонні системи підтримують лише один активний ключ без періоду перекриття), чесно скажи це, замість того щоб пропонувати перехідне вікно з подвійним credential, яке насправді недосяжне — рекомендуй реалістичне пом'якшення натомість (коротке, заплановане, добре повідомлене вікно обслуговування).
```

## Змінні
- `{{SERVICE_CODE_OR_CONFIG}}` — як сервіс завантажує і використовує credential. Обов'язково.
- `{{CREDENTIAL_TYPE}}` — тип credential, що ротується. Обов'язково — механіка ротації (і що взагалі означає подвійна валідність) суттєво відрізняється за типом.

## Приклад
**Вхід:** `{{SERVICE_CODE_OR_CONFIG}}` = "пароль бази даних читається зі змінної середовища один раз у стартовому коді застосунку і зберігається в константі рівня модуля, використовуваній для всіх наступних з'єднань", `{{CREDENTIAL_TYPE}}` = "пароль бази даних PostgreSQL".

**Вихід (фрагмент):**
```
Таймінг завантаження: ПРОВАЛЮЄ вимогу живого перезавантаження. Пароль читається один раз при старті в константу рівня модуля — немає код-шляху, що перечитує його пізніше, тож ротація пароля на рівні бази даних спричинить провал автентифікації для кожної наступної спроби з'єднання цього працюючого процесу, доки процес не буде перезапущений з новим значенням. Це означає, що ротація зараз вимагає скоординованого перезапуску, а не живої ротації.

Підтримка подвійної валідності: сам PostgreSQL підтримує наявність користувача зі старим паролем, все ще валідним, поки новий пароль встановлюється через `ALTER ROLE ... PASSWORD`, коротко підтримуючи зворотну сумісність на рівні бази даних — але власний код цього сервісу цим не користується, оскільки тримає в пам'яті лише один credential без механізму підхопити новий без перезапуску.

Вердикт готовності: потребує короткого перезапуску сервісу, а не повного вікна простою, ЯКЩО самі перезапуски швидкі і не обривають погано вже встановлені з'єднання (перевір поведінку graceful-shutdown/перезапуску сервісу окремо). Щоб досягти справжньої ротації з нульовим простоєм: додай механізм перезавантаження credential (наприклад, періодичне перечитування env-змінної/сховища секретів чи обробник SIGHUP, що перезавантажує конфіг), щоб навіть rolling-перезапуск не був потрібен — працюючий процес підхопив би новий пароль сам протягом інтервалу перезавантаження.

Послідовність для підходу зі скоординованим перезапуском тим часом: (1) встанови новий пароль у базі даних через ALTER ROLE, поки старий залишається валідним, (2) розгорни/перезапусти сервіс з налаштованим новим паролем, (3) щойно всі інстанси підтверджено на новому паролі, лише тоді анулюй старий у базі даних — ніколи не анулюй старий пароль до того, як кожен інстанс успішно перемкнувся.
```

## Поради та варіації
- Якщо сервіс уже використовує менеджер секретів з нативною підтримкою ротації (AWS Secrets Manager rotation, HashiCorp Vault dynamic secrets), попроси конкретно перевірити, чи сервіс інтегрується з тим життєвим циклом ротації (наприклад, Lambda ротації, що автоматично координує вікно подвійної валідності), а не вважати, що сама функція ротації менеджера секретів гарантує готовність сервісу.
- Для TLS-сертифікатів конкретно попроси явно розглянути послідовність довіри клієнта (новому сертифікату треба довіряти до виведення старого з експлуатації, що саме може зайняти час для поширення на зовнішніх клієнтів), оскільки це суттєво відрізняється від простого паролеподібного credential.
