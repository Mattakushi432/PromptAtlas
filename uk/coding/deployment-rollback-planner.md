## Опис
Генерує конкретний, покроковий план відкату для конкретної зміни деплою — коду, конфігурації чи інфраструктури — до релізу, щоб відкат не імпровізувався під час інциденту. Відрізняється від «Укладача безпечних міграційних скриптів» (специфічно для БД) і «Оцінки ризику перед мерджем» (загальний рівень ризику, не покроковий план).

## Коли використовувати
- Підготовка до деплою зміни з будь-яким ризиком потреби відкату, з бажанням записати процедуру відкату перед деплоєм, а не з'ясовувати її під тиском під час інциденту.
- Деплой пов'язаний з іншими змінами (міграція, конфігураційний флаг, стороння інтеграція), де "просто відкоти код" не є повним відкатом.
- Написання запису runbook для повторюваного типу деплою, щоб процедуру відкату не потрібно було винаходити щоразу.

## Промпт

```
Ти пишеш конкретний, покроковий план відкату для деплою — вважай, що йому потрібно слідувати комусь під тиском часу під час інциденту, а не читати як загальний документ політики.

Опис деплою (що змінюється — код, конфігурація, інфраструктура, feature flag): {{DEPLOYMENT_DESCRIPTION}}
Пов'язані зміни (необов'язково — напр., "цей деплой також вимагає міграції БД", "конфігураційний флаг має перемкнутися одночасно"): {{COUPLED_CHANGES}}
Тулінг деплою (необов'язково — напр., "Kubernetes з ArgoCD", "простий CI/CD-пайплайн зі скриптом деплою"): {{DEPLOY_TOOLING}}

Інструкції:
1. Вкажи конкретний механізм відкату для основної зміни: `kubectl rollout undo`, попередній тег образу контейнера для повторного деплою, повернення feature flag назад у off, відкат Terraform і повторний apply — точну команду чи дію, не "відкоти деплой".
2. Якщо {{COUPLED_CHANGES}} включає щось нетривіально відновлюване (міграцію бази даних, зміну схеми черги повідомлень, зміну стану стороннього API), адресуй це явно: чи можна це чисто відкотити, чи план відкату має натомість враховувати зворотну сумісність (старий код має продовжувати працювати проти нової схеми/стану, оскільки саму міграцію не можна скасувати)?
2a. Якщо пов'язану зміну дійсно не можна скасувати, прямо про це скажи і опиши фактичне пом'якшення (напр., "міграція одностороння; якщо потрібен відкат, попередню версію коду потрібно підтвердити сумісною з новою схемою ПЕРЕД відкатом — перевір це ДО деплою, а не під час інциденту").
3. Вкажи кроки перевірки, щоб підтвердити, що відкат дійсно спрацював — не просто "задеплой стару версію", а що перевірити після (частота помилок повернулася до базового рівня, конкретна перевірка здоров'я проходить, метрика canary відновилася) і скільки чекати перед оголошенням відкату успішним.
4. Зазнач будь-який ручний крок, який не можна автоматизувати (очищення кешу, повідомлення нижчерозташованої команди, ручне повернення значення конфігурації в дашборді), оскільки саме ці кроки найімовірніше забудуть під тиском.
5. Вкажи власний ризик відкату: чи сам відкат повністю безпечний, чи має побічні ефекти (напр., запити в польоті, оброблені новою версією, але не старою, спричиняючи короткочасну неузгодженість)? Не подавай відкат як безризиковий, якщо це не так.
6. Якщо надано {{DEPLOY_TOOLING}}, використовуй його фактичний механізм (конкретні команди/кроки UI), а не загальний опис.

Формат виводу: Markdown з розділами: Критерії тригера відкату (коли фактично відкочувати, коротко), Кроки відкату (пронумеровано, по порядку), Перевірка, Відомі обмеження.
```

## Змінні
- `{{DEPLOYMENT_DESCRIPTION}}` — що деплоїться. Обов'язково.
- `{{COUPLED_CHANGES}}` — все, що має змінитися разом з основним деплоєм. Необов'язково, але критично, коли присутнє — це найпоширеніше джерело неповного плану відкату.
- `{{DEPLOY_TOOLING}}` — фактичний механізм/платформа деплою. Необов'язково, але робить план напряму виконуваним, а не загальним.

## Приклад
**Вхід:** `{{DEPLOYMENT_DESCRIPTION}}` = "новий процес оформлення замовлення за feature flag, задеплоєний через Kubernetes", `{{COUPLED_CHANGES}}` = "нове обов'язкове поле додано до таблиці orders через зворотно-сумісну міграцію (nullable) перед цим деплоєм", `{{DEPLOY_TOOLING}}` = "Kubernetes зі стандартним пайплайном деплою".

**Вихід (фрагмент):**
```
## Кроки відкату
1. Переверни feature flag `new-checkout-flow` назад у `false` в системі управління флагами — це найшвидше пом'якшення, що не вимагає повторного деплою, тож зроби це ПЕРШИМ, якщо проблема ізольована в логіці нового процесу.
2. Якщо проблема не вирішується перемиканням флага (напр., краш у коді, що виконується незалежно від флага), відкоти деплой: `kubectl rollout undo deployment/checkout-service`.

## Відомі обмеження
Міграція таблиці orders (нове nullable поле) НЕ відкочується цією процедурою — вона зворотно-сумісна за задумом, тож стара версія коду продовжує нормально працювати з новою схемою (вона просто ігнорує нове nullable поле). Відкат міграції не потрібен і не має бути спробуваний.
```

## Поради та варіації
- Для деплою без feature flag (прямий деплой коду) план спрощується лише до кроку 2+ — не форсуй крок перемикання флага, якого немає.
- Передай вивід у шаблон runbook інциденту команди, якщо він є, щоб цей план відкату був знаходимим під час реального інциденту, а не жив лише в описі PR.
