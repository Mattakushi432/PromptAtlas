## Опис
Допомагає розробнику перетворити грубе кодингове завдання на добре сформований промпт для AI-кодинг агента (Claude Code, Cursor, Copilot Chat тощо) — мета-промпт, що покращує наступний промпт, не сам документ специфікації. Відрізняється від «Специфікації з розпливчастого запиту» (видає артефакт специфікації): цей промпт коучить навичку написання промптів і видає готовий до надсилання промпт.

## Коли використовувати
- Ось-ось попросиш AI-кодинг агента про щось нетривіальне і хочеш, щоб перший промпт дійсно спрацював, замість того щоб ітерувати п'ять разів, щоб дійти до цього.
- Попередня сесія з AI-кодингом пройшла погано (неправильні припущення, розповзання обсягу, галюциновані API), і ти хочеш зрозуміти, що в промпті це спричинило.
- Навчання команди ефективнішому промптингу AI-кодинг інструментів через перероблення їхнього фактичного завдання, а не читання загальних порад з промптингу.

## Промпт

```
Ти допомагаєш мені перетворити грубе кодингове завдання на ефективний промпт для AI-кодинг агента — видаючи готовий до надсилання промпт, не лише загальну пораду з промптингу.

Мій грубий опис завдання: {{ROUGH_TASK}}
Цільовий AI-інструмент (необов'язково — напр., "Claude Code з доступом до репозиторію", "ChatGPT без доступу до кодової бази", "Cursor"): {{TARGET_TOOL}}
Відповідний контекст кодової бази, який я міг би включити (необов'язково — шляхи файлів, наявні патерни, обмеження): {{AVAILABLE_CONTEXT}}

Інструкції:
1. Визнач, що недостатньо специфіковане в {{ROUGH_TASK}}, через що AI-агент вгадав би неправильно: відсутні критерії прийняття (як виглядає "готово"), відсутні обмеження (які наявні патерни/бібліотеки мають використовуватися проти уникатися), неоднозначний обсяг (чи це включає тести? міграцію? лише happy path?).
2. Якщо {{TARGET_TOOL}} має доступ до репозиторію/кодової бази, рекомендуй, на який конкретний контекст його спрямувати (конкретні файли, наявну схожу реалізацію для дотримання як патерна), а не переказувати все прозою, яку агент міг би просто прочитати з коду.
3. Якщо {{TARGET_TOOL}} не має доступу до кодової бази, визнач, який контекст треба вставити вбудовано, оскільки агент не може виявити його самостійно (відповідний наявний код, фактичне повідомлення про помилку, конкретна версія бібліотеки) — промпт для сліпого до контексту інструменту має бути самодостатнішим.
4. Додай явні межі: що НЕ змінювати (не чіпай непов'язані файли, не рефактор понад завдання, не додавай нові залежності без запитання), якщо завдання такого типу, де агент міг би розумно перевищити обсяг — це поширене джерело небажаних розлогих diff'ів.
5. Вкажи крок перевірки, який ти хочеш, щоб агент зробив перед вважанням завдання завершеним (запусти тести, перевір конкретну поведінку), щоб взаємодія включала самоперевірку, а не закінчувалася на "я зробив зміну".
6. Якщо завдання достатньо велике, що єдиний промпт ризикує несфокусованим результатом, запропонуй розбити на послідовність менших промптів натомість, і покажи перший з них.
7. Видай фактичний покращений текст промпту, готовий до вставки — не опис того, що містив би хороший промпт.

Формат виводу: Markdown з розділами: Що було недостатньо специфіковане, Покращений промпт (у блоці коду, готовий до використання), і (якщо релевантно) Запропоновані наступні промпти.
```

## Змінні
- `{{ROUGH_TASK}}` — завдання так, як ти природно його б описав, неполіроване. Обов'язково.
- `{{TARGET_TOOL}}` — конкретний AI-кодинг інструмент, для якого цей промпт, оскільки доступ до контексту різниться. Необов'язково, але сильно впливає на те, що потрібно включити вбудовано.
- `{{AVAILABLE_CONTEXT}}` — відповідні деталі кодової бази, які ти міг би включити. Необов'язково.

## Приклад
**Вхід:** `{{ROUGH_TASK}}` = "додай кешування до ендпойнта профілю користувача, він повільний", `{{TARGET_TOOL}}` = "Claude Code з доступом до репозиторію".

**Вихід (фрагмент):**
```
## Що було недостатньо специфіковане
Немає критеріїв прийняття для "повільний" (наскільки повільний, і яка прийнятна ціль?), не вказана стратегія кешування (TTL? інвалідація при оновленні профілю?), немає межі, які файли ендпойнта чіпати, якщо є кілька схожих ендпойнтів.

## Покращений промпт
Додай кешування до ендпойнта `GET /api/users/:id/profile` у `src/routes/users.ts` — наразі він займає ~800мс через join кількох таблиць. Використай наявний патерн кешування Redis, уже встановлений у `src/routes/orders.ts` (cache-aside, TTL 5 хвилин), а не вводь новий підхід до кешування. Інвалідуй запис кешу, коли профіль оновлюється через `PUT /api/users/:id/profile` у тому самому файлі. Не чіпай інші ендпойнти. Після реалізації запусти наявний тестовий набір для цього маршруту і додай тест, що підтверджує інвалідацію кешу при оновленні.
```

## Поради та варіації
- Для агента з автономним багатокроковим виконанням (здатного виконувати команди, читати кілька файлів) явно зазнач, що йому варто самостійно дослідити наявний патерн перед реалізацією, а не припускати, що опис патерну в промпті вичерпний.
- Веди невелику особисту бібліотеку промптів, що добре спрацювали для повторюваних типів завдань (додати ендпойнт, додати міграцію, додати тест), і перевикористовуй/адаптуй їх замість того щоб починати з нуля щоразу.
