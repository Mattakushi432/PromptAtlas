## Опис
Діагностує падаючий CI-пайплайн з виводу його логу — розрізняючи реальну відмову коду/тесту від проблеми середовища, кешування чи нестабільності — і дає конкретне виправлення. Для реального падаючого пайплайну, відрізняється від загальної «Діагностики "на моїй машині працює"» (яка покриває будь-який міжсередовищний баг, не конкретно CI).

## Коли використовувати
- Запуск CI впав, і вивід логу довгий/шумний, що ускладнює знаходження фактичної відмови серед шуму setup/teardown.
- Крок пайплайну падає періодично, і потрібно розрізнити "це реальний баг" від "це нестабільність CI" перед витратою часу на дебаг непошкодженого коду.
- Пайплайн, що працював вчора, падає сьогодні без жодної зміни коду, і потрібно знайти, що змінилося в середовищі (версія залежності, оновлення образу раннера, кеш).

## Промпт

```
Ти діагностуєш падаючий CI-пайплайн з виводу його логу — розрізняючи реальні проблеми коду/тестів від причин, специфічних для середовища CI, а не автоматично припускаючи, що це баг коду.

Вивід логу CI (відповідна падаюча секція, плюс навколишній контекст, якщо доступний): {{CI_LOG}}
Платформа/конфіг CI (необов'язково, напр., YAML воркфлоу GitHub Actions, конфіг CircleCI): {{CI_CONFIG}}
Що нещодавно змінилося, якщо відомо (diff коду, оновлення залежності, немає відомої зміни): {{RECENT_CHANGES}}

Інструкції:
1. Ізолюй фактичну відмову від навколишнього шуму логу — процитуй конкретну помилку, не весь лог, і визнач, у якому кроці пайплайну вона сталася.
2. Класифікуй тип відмови: справжня відмова тесту/коду (код дійсно неправильний), різниця середовища CI (інша ОС/версія залежності/локаль/часовий пояс, ніж локальна розробка), проблема кешування (застарілий кеш видає застарілі залежності чи артефакти збірки), патерн нестабільності (тест, залежний від таймінгу, залежність від зовнішнього сервісу, конкуренція за ресурси на спільному раннері), чи проблема конфігурації CI (неправильно налаштований крок, відсутній секрет/env-змінна, неправильна робоча директорія).
3. Якщо надано {{CI_CONFIG}}, перевір його на типові неправильні конфігурації, релевантні відмові: відсутні чи неправильні ключі кешування, кроки, що виконуються в неправильному порядку/директорії, змінні середовища, не передані належно падаючому кроку, чи конфігурація matrix/паралелізму, що спричиняє конкуренцію за ресурси.
4. Якщо {{RECENT_CHANGES}} показує відсутність зміни коду, але пайплайн почав падати, зосередься конкретно на тому, що могло змінитися в самому середовищі CI: транзитивне оновлення залежності (без lock-файлу, чи lock-файл не враховується), оновлення базового образу платформи CI, зміна поведінки зовнішнього сервісу, від якого залежить CI.
5. Розрізняй "нестабільно, потребує карантину чи виправлення стабільності" від "постійно зламано, потребує реального виправлення" на основі наданих доказів (одна відмова проти описаного патерну періодичних відмов) — не рекомендуй карантинувати тест, що насправді надійно виловлює реальний баг.
6. Дай конкретне виправлення: зміну коду, зміну конфігурації CI, крок очищення кешу, чи фіксацію версії залежності — не розпливчасту директиву "перевір свою конфігурацію CI".

Формат виводу: Markdown з розділами: Ізольована відмова, Класифікація, Першопричина, Виправлення.
```

## Змінні
- `{{CI_LOG}}` — відповідний вивід логу CI. Обов'язково.
- `{{CI_CONFIG}}` — файл конфігурації пайплайну. Необов'язково, але часто потрібне для діагностики відмов, спричинених середовищем/конфігурацією.
- `{{RECENT_CHANGES}}` — що змінилося (чи ні) перед тим, як пайплайн почав падати. Необов'язково, але дуже цінне для розрізнення багів коду від дрейфу середовища.

## Приклад
**Вхід:** `{{CI_LOG}}` = крок `npm ci`, що падає з помилкою невідповідності цілісності lock-файлу, `{{RECENT_CHANGES}}` = "без зміни коду, працювало вчора".

**Вихід (фрагмент):**
```
## Ізольована відмова
`npm ci` падає з "Invalid: lock file's X does not satisfy Y" під час кроку встановлення залежностей.

## Класифікація
Проблема середовища CI/залежностей, не баг коду — `npm ci` падає на етапі встановлення, до виконання будь-якого тестового коду.

## Першопричина
Цей патерн помилки зазвичай означає, що `package-lock.json` розсинхронізований з `package.json` (хтось відредагував `package.json` напряму без регенерації lock-файлу, чи lock-файл не був закомічений після локального `npm install`), АБО — оскільки ти повідомляєш про відсутність зміни коду і що воно працювало вчора — метадані реєстру транзитивної залежності змінилися так, що зламали раніше закешоване розв'язання.

## Виправлення
Запусти `npm install` локально, щоб регенерувати `package-lock.json`, перевір, що diff виглядає розумно (без неочікуваних мажорних стрибків версій), закоміть це, і повторно запусти CI. Якщо повторюється без жодної локальної зміни, перевір, чи ключ кешу CI включає хеш lock-файлу — застарілий кеш, що видає старий lock-файл проти нового стану реєстру, — ймовірна вторинна причина.
```

## Поради та варіації
- Конкретно для нестабільного тесту (не проблеми конфігурації пайплайну) передай у «Дослідник нестабільних тестів» для глибшого розслідування по тесту, коли цей промпт уже підтвердив, що відмова є нестабільністю, а не реальним багом.
- Встав логи кількох падаючих запусків разом, якщо відмова періодична — патерн у запусках (той самий крок падає проти різних щоразу) сам по собі діагностичний.
