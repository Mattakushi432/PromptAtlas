## Опис
Пише скрипт міграції бази даних (up та down) з явною увагою до безпеки продакшену — поведінка блокування, стратегія backfill, відновлюваність — для зміни схеми, що має вийти без простою. Для написання фактичної міграції, відрізняється від проєктування цільової схеми («Дизайнер схем із вимог») чи оцінки загального ризику diff'у («Оцінка ризику перед мерджем»).

## Коли використовувати
- Написання міграції для таблиці зі значним продакшн-трафіком/кількістю рядків, де наївна міграція могла б заблокувати таблицю чи спричинити простій.
- Додавання NOT NULL колонки, нового обмеження чи індексу до наявної великої таблиці.
- Потрібна міграція, що дійсно відновлювана, а не така, що має порожній чи деструктивний метод `down`.

## Промпт

```
Ти пишеш скрипт міграції бази даних з безпекою продакшену як основною турботою — не лише коректністю самої зміни схеми.

Бажана зміна схеми: {{SCHEMA_CHANGE}}
Контекст розміру/трафіку таблиці (необов'язково, але важливо — напр., "таблиця orders, ~40 млн рядків, постійно читається/записується"): {{TABLE_CONTEXT}}
Двигун бази даних і інструмент міграції (необов'язково, напр., "PostgreSQL, використовуючи Rails migrations" чи "MySQL, використовуючи Flyway"): {{ENGINE_AND_TOOL}}

Інструкції:
1. Визнач, чи бажана зміна вимагає блокування на рівні таблиці в цьому двигуні/версії, і на скільки відносно розміру таблиці — якщо так, розбий зміну на кілька безпечніших кроків замість одного блокуючого оператора (напр., спочатку додай колонку як nullable, зроби backfill пакетами, потім додай обмеження NOT NULL окремо; додай індекс CONCURRENTLY, а не блокуючу побудову індексу).
2. Якщо потрібен backfill, напиши його як пакетну операцію (не єдиний UPDATE, що торкається мільйонів рядків одразу), і зазнач компроміс розміру пакета (занадто малий = повільна міграція, занадто великий = довге блокування/лаг).
3. Напиши справжню міграцію `down`/відкату, що дійсно скасовує зміну — якщо повне скасування неможливе (напр., дані видаленої колонки втрачені), прямо про це скажи, замість того щоб писати метод `down`, який мовчки нічого не робить чи видає помилку.
4. Познач будь-який крок, що не може виконуватися в транзакції на цьому двигуні (напр., деякий DDL у MySQL, чи операції CONCURRENTLY в Postgres, які не можуть виконуватися в блоці транзакції), і структуруй міграцію відповідно.
5. Зазнач обмеження порядку деплою, якщо міграція і зміна коду застосунку пов'язані (напр., "задеплой цю міграцію перед кодом, що починає писати в нову колонку, інакше отримаєш помилки запису під час роловту") — це поширене джерело інцидентів з міграціями.
6. Якщо {{TABLE_CONTEXT}} не надано, за замовчуванням обирай найбезпечніший багатокроковий підхід, а не припускай, що таблиця маленька, і скажи, що робиш саме так.

Вивід: скрипт міграції (up та down), за яким слідує коротка примітка про порядок деплою, якщо релевантно.
```

## Змінні
- `{{SCHEMA_CHANGE}}` — зміна для виконання (додати колонку, додати обмеження, додати індекс, перейменувати тощо). Обов'язково.
- `{{ENGINE_AND_TOOL}}` — двигун бази даних і фреймворк міграцій, оскільки поведінка блокування і синтаксис суттєво різняться. Обов'язково.
- `{{TABLE_CONTEXT}}` — розмір таблиці і патерн трафіку. Необов'язково, але сильно впливає на те, чи безпечна наївна одностадійна міграція.

## Приклад
**Вхід:** `{{SCHEMA_CHANGE}}` = "додати NOT NULL колонку `status` зі значенням за замовчуванням 'pending' до таблиці orders", `{{TABLE_CONTEXT}}` = "40 млн рядків, постійно записується", `{{ENGINE_AND_TOOL}}` = "PostgreSQL 16".

**Вихід (фрагмент):**
```sql
-- Крок 1: додай колонку як nullable, без значення за замовчуванням (швидко, лише метадані в PG 11+)
ALTER TABLE orders ADD COLUMN status text;

-- Крок 2: backfill пакетами (виконуй поза єдиною транзакцією, напр., через скрипт)
-- UPDATE orders SET status = 'pending' WHERE status IS NULL AND id BETWEEN :batch_start AND :batch_end;

-- Крок 3: додай обмеження NOT NULL після завершення backfill (валідується окремо, щоб уникнути блокування повного сканування таблиці)
ALTER TABLE orders ADD CONSTRAINT orders_status_not_null CHECK (status IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_status_not_null;
```
*(далі: "Порядок деплою: викотіть кроки 1-3 цієї міграції повністю перед деплоєм коду застосунку, що припускає, що `status` завжди присутній, щоб уникнути читання застосунком NULL посеред backfill.")*

## Поради та варіації
- Для інструменту міграцій із вбудованим лінтером "безпечних міграцій" (напр., strong_migrations для Rails) попроси також позначити, які з його кроків цей лінтер позначив би, щоб вивід був заздалегідь перевірений.
- Поєднуй з «Оцінкою ризику перед мерджем» для ширшого фреймінгу ризику деплою, коли сам скрипт міграції вже написаний.
