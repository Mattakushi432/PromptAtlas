## Опис
Виловлює патерни запитів N+1 у коді ORM (Active Record, Django ORM, Sequelize, Prisma тощо) на рівні коду застосунку — відрізняється від аналізу форми схеми в «Рев'ювері схем GraphQL» і від налаштування одного запиту в «Оптимізаторі SQL-запитів». Для кодової бази, де проблема — патерн запитів, а не сам запит.

## Коли використовувати
- Сторінка чи ендпойнт повільні, і ти підозрюєш, що вони видають один запит на рядок у циклі замість єдиного батчованого запиту.
- Рев'ю PR, що додає цикл над зв'язком ORM, перед релізом, до того як це спричинить сповільнення продакшену під реальним обсягом даних.
- Аудит шару контролера/сервісу на патерни N+1, які юніт-тести не виловили б (оскільки тестові фікстури зазвичай замалі, щоб проявити проблему).

## Промпт

```
Ти виявляєш патерни запитів N+1 у коді ORM — код, що видає один додатковий запит на елемент колекції, замість єдиного батчованого запиту — і показуєш виправлення за допомогою фактичного механізму батчингу ORM.

Код: {{CODE}}
ORM/фреймворк: {{ORM_FRAMEWORK}}

Інструкції:
1. Простеж кожен цикл (явний `for`/`each`, чи неявний через рендеринг шаблону/серіалізацію), що звертається до зв'язку чи асоційованого поля на кожному елементі — це основна сигнатура N+1: нормально ізольовано, один зайвий запит на ітерацію сукупно.
2. Для кожного знайденого N+1 вкажи конкретний патерн, що спричиняє (напр., "звернення до `.author` всередині циклу над `posts` без eager-loading") і оціни зростання кількості запитів (напр., "1 запит для posts + N запитів для authors, де N = кількість постів").
3. Розрізняй реальні N+1 від запитів, що лише схожі, але ними не є (напр., єдиний запит, що вже використовує join, чи цикл, що фактично не звертається до бази даних на кожній ітерації) — хибні спрацьовування підривають довіру до рев'ю.
4. Надай виправлення за допомогою фактичного механізму eager-loading/батчингу ORM для цього фреймворку (напр., `.includes()` в Active Record, `select_related`/`prefetch_related` у Django, `include` у Sequelize, `include` у Prisma) — не загальну заяву "батчуй свої запити".
5. Якщо eager-loading усього призвів би до over-fetch даних, які рідко потрібні, зазнач цей компроміс і запропонуй цілеспрямованіше виправлення (напр., виділений запит лише потрібних полів) замість сліпого eager-loading усього зв'язку.
6. Перевір менш очевидний варіант: N+1, прихований за викликом методу чи серіалізатором, що сам робить запит на елемент, не лише напряму видимий цикл над зверненням до зв'язку.
7. Якщо патерну N+1 немає, прямо про це скажи, а не вигадуй його.

Формат виводу: Markdown, один запис на знайдений N+1: місце, патерн, що спричиняє, оцінка зростання запитів, і конкретне виправлення з виправленим кодом.
```

## Змінні
- `{{CODE}}` — код контролера/сервісу/view для перевірки. Обов'язково.
- `{{ORM_FRAMEWORK}}` — напр. "Ruby on Rails / Active Record", "Django ORM", "Prisma". Обов'язково — механізм виправлення специфічний для фреймворку.

## Приклад
**Вхід:** `{{ORM_FRAMEWORK}}` = "Ruby on Rails / Active Record", `{{CODE}}` = `@posts.each { |post| render partial: 'post', locals: { author_name: post.author.name } }`.

**Вихід (фрагмент):**
```
### N+1: `post.author` викликається в циклі — місце: блок `.each`
Патерн, що спричиняє: `post.author.name` викликається раз на пост без eager-loading `author`. Оцінка зростання: 1 запит для `@posts` + N запитів (по одному на пост) для `author`.

Виправлення:
```ruby
@posts = Post.includes(:author)
@posts.each { |post| render partial: 'post', locals: { author_name: post.author.name } }
```
`.includes(:author)` батчує всіх авторів в єдиний додатковий запит замість одного на пост.
```

## Поради та варіації
- Поєднуй з реальними логами запитів (напр., вивід гема `bullet` для Rails, чи сирий SQL-лог із запиту) як додатковий доказ — реальні логи підтверджують, що N+1 стається на практиці, а не лише теоретично.
- Для шару резолверів GraphQL замість традиційного контролера цей промпт усе одно застосовний до власних викликів ORM резолвера, але також див. «Рев'ювер схем GraphQL» для версії того самого ризику на рівні форми схеми.
