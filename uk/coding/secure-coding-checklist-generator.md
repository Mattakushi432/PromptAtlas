## Опис
Генерує чекліст безпечного кодування, підлаштований під конкретну мову/фреймворк — довідковий документ для проактивного використання командою, відрізняється від «Чекліста рев'ю коду на безпеку» (що рецензує фактичний код проти фіксованого чекліста). Для встановлення стандартів команди, онбордингу чи шаблону PR, не для аудиту конкретного шматка коду.

## Коли використовувати
- Онбординг команди в нову мову/фреймворк з бажанням отримати конкретний довідник безпечного кодування саме для неї, не загальний список OWASP.
- Побудова чекліста рев'ю PR чи розділу гайду контриб'юції для практик безпеки, специфічних для стеку проєкту.
- Встановлення базового стандарту безпечного кодування для нового проєкту до того, як усталяться звички код-рев'ю.

## Промпт

```
Ти генеруєш чекліст безпечного кодування, підлаштований під конкретну мову й фреймворк — конкретне, специфічне для фреймворку керівництво, не переказ загального OWASP Top 10.

Мова/фреймворк: {{LANGUAGE_AND_FRAMEWORK}}
Тип застосунку (необов'язково — напр., "REST API", "серверно-рендерений веб-застосунок", "CLI-інструмент, що обробляє дані користувача"): {{APP_TYPE}}
Рівень досвіду команди (необов'язково — впливає на те, скільки пояснення потребує кожен пункт): {{TEAM_LEVEL}}

Інструкції:
1. Покрий категорії вразливостей, релевантні для цієї конкретної мови/фреймворку/типу застосунку — пропускай категорії, що дійсно не застосовні (напр., пропусти специфічне для XSS керівництво для суто бекенд CLI-інструменту без рендерингу HTML), а не наповнюй чекліст заради повноти.
2. Для кожного пункту чекліста назви КОНКРЕТНИЙ механізм фреймворку для використання, не загальний принцип: "використовуй параметризовані запити ORM Django; уникай `.raw()` і `.extra()` з несанітизованим вводом" замість "запобігай SQL-ін'єкції". Загальний пункт недостатньо дієвий, щоб бути реальним чеклістом.
3. Включи специфічні для фреймворку "пастки": відомі патерни саме в цьому фреймворку, що виглядають безпечними, але ними не є (поширене джерело реальних вразливостей саме в цій екосистемі), а не лише підручникові класи вразливостей.
4. Організуй за областю (обробка вводу, автентифікація, авторизація, зберігання даних, управління залежностями, обробка помилок/логування, конфігурація деплою), а не за абстрактними назвами категорій OWASP, щоб це читалося як практичне керівництво, до якого розробник дійсно звертатиметься.
5. Для кожного пункту зазнач, чи це щось, що фреймворк обробляє за замовчуванням (і як уникнути випадкового вимкнення цього захисту) проти того, що розробник має явно реалізувати — ця різниця дуже важлива для пріоритезації.
6. Якщо {{TEAM_LEVEL}} вказує на менший досвід, додай рядок "чому це важливо" для кожного пункту; для досвідченої команди тримай пункти лаконічними і у форматі чекліста без розширеного пояснення.
7. Тримай список реалістичного розміру (цілься в дійсно навантажені пункти, не вичерпну енциклопедію) — чекліст на 200 пунктів не використовується; сфокусований на 20-30 пунктів використовується.

Формат виводу: Markdown-чекліст, згруповано за областю, кожен пункт як чекбокс з названим конкретним механізмом/патерном.
```

## Змінні
- `{{LANGUAGE_AND_FRAMEWORK}}` — напр. "Python / Django", "Node.js / Express", "Go / net/http". Обов'язково.
- `{{APP_TYPE}}` — який це тип застосунку, для обмеження релевантних категорій. Необов'язково, але покращує релевантність.
- `{{TEAM_LEVEL}}` — junior/змішана/senior, впливає на глибину пояснення. Необов'язково.

## Приклад
**Вхід:** `{{LANGUAGE_AND_FRAMEWORK}}` = "Node.js / Express", `{{APP_TYPE}}` = "REST API, що обслуговує мобільний застосунок".

**Вихід (фрагмент):**
```markdown
## Обробка вводу
- [ ] Валідуй тіла запитів бібліотекою схем (напр., Zod, Joi) на межі маршруту — не покладайся лише на типи TypeScript, які зникають у рантаймі й нічого не валідують з фактичного HTTP-запиту.
- [ ] Використовуй параметризовані запити через свій драйвер БД/ORM; ніколи не будуй SQL конкатенацією рядків/шаблонними літералами з даних запиту.

## Автентифікація
- [ ] Використовуй `bcrypt`/`argon2` для хешування паролів, ніколи швидкий хеш (лише MD5/родину SHA) — сам Express тут нічого не робить за тебе, це повністю на твоїй реалізації.
- [ ] Явно встановлюй cookie з флагами `httpOnly`, `secure` і `sameSite`, якщо використовуєш сесії на основі cookie — налаштування cookie Express за замовчуванням не безпечні за замовчуванням.
```

## Поради та варіації
- Після генерації перетвори це на фактичний шаблон чекліста PR чи пов'язаний документ у `CONTRIBUTING.md`, щоб його дійсно використовували, а не прочитали раз і забули.
- Для контексту, керованого комплаєнсом (SOC 2, HIPAA), попроси додати розділ, що зіставляє пункти чекліста з конкретними контролями комплаєнсу, яким вони допомагають відповідати.
