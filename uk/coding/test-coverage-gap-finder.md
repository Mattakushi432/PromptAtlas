## Опис
Порівнює функцію/модуль з наявними тестами, щоб знайти непокриті гілки, крайові випадки та шляхи обробки помилок — звіт про прогалини, а не повноцінна заміна тестового набору. Для розробника, який уже має тести і хоче знати, що досі відкрито.

## Коли використовувати
- Перед мерджем PR — перевірити, чи нові тести дійсно покривають гілки нової логіки, а не просто виконують happy path.
- Аудит тестового набору наявного модуля перед тим, як покладатися на нього як на страховку при рефакторингу.
- Пріоритезація обмеженого часу на тестування шляхом пошуку найризикованіших непокритих шляхів першими.

## Промпт

```
Ти порівнюєш код з наявними тестами, щоб знайти прогалини в покритті — не пишеш повний новий тестовий набір і не просто звітуєш числовий відсоток покриття.

Код:
{{CODE}}

Наявні тести:
{{EXISTING_TESTS}}

Інструкції:
1. Переліч кожну окрему логічну гілку в коді: кожен `if`/`else`, кожен випадок циклу з нуль/один/багато ітерацій, кожен ранній return, кожен шлях catch/обробки помилки, кожне використання параметра/значення за замовчуванням.
2. Для кожної гілки визнач, чи наявні тести дійсно її виконують — не просто чи функція десь викликається, а чи конкретний тестовий ввід веде виконання саме через цю гілку і робить асерт на результаті.
3. Звітуй лише про гілки, які НЕ покриті, кожну з: який ввід би її виконав і що тест має перевіряти (assert).
4. Окремо познач будь-яку гілку, яка "покрита" тестом, що її викликає, але не робить змістовний assert на результаті (напр., викликає функцію і лише перевіряє, що вона не кинула виняток) — це прогалина покриття на практиці, навіть якщо інструмент покриття позначить рядок як виконаний.
5. Пріоритезуй прогалини: познач, які з них найризикованіше залишати непокритими (напр., шлях обробки помилки платежу) проти менш ризикованих (рідко досяжна гілка форматування).
6. Якщо наявні тести вже змістовно покривають усе, прямо про це скажи, а не вигадуй незначні прогалини для звіту.

Формат виводу: Markdown, один запис на прогалину, впорядковано за ризиком (найвищий — першим). Кожен запис: гілка/умова, чому не покрита, конкретний ввід, що б її виконав, і що перевіряти (assert).
```

## Змінні
- `{{CODE}}` — функція/модуль для перевірки. Обов'язково.
- `{{EXISTING_TESTS}}` — наявний тестовий файл(и) для цього коду. Обов'язково.

## Приклад
**Вхід:** `{{CODE}}` = функція `parseConfig(raw)` зі значенням за замовчуванням, коли поле відсутнє, `{{EXISTING_TESTS}}` = тести, що покривають лише випадок, коли всі поля присутні.

**Вихід (фрагмент):**
```
### Прогалина: шлях значення за замовчуванням для відсутнього поля — ВИСОКИЙ ризик
`parseConfig` повертається до значення за замовчуванням, коли `raw.timeout` є undefined, але жоден тест не виконує цей шлях.
Ввід для виконання: `parseConfig({ ...validConfig, timeout: undefined })`.
Перевірити: значення `timeout` у поверненому конфігу дорівнює задокументованому значенню за замовчуванням, а не `undefined`.
```

## Поради та варіації
- Встав реальний звіт про покриття рядків/гілок від інструмента покриття поряд з `{{EXISTING_TESTS}}` для гібридної перевірки — покриття рядків показує, що виконувалося, цей промпт показує, що було змістовно перевірено.
- Для перевірки-гейта перед мерджем попроси завершити одним рядком PASS/FAIL залежно від того, чи залишилася прогалина з ВИСОКИМ ризиком.
