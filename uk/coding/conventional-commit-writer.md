## Опис
Пише повідомлення коміту у форматі Conventional Commits (type(scope): subject, плюс тіло) з diff'у — повідомлення одного коміту, не повний опис PR. Для конкретного, частого завдання написання хорошого повідомлення коміту зі staged-змін.

## Коли використовувати
- Коміт зміни з бажанням отримати правильно типізоване, добре обмежене повідомлення коміту без написання з нуля щоразу.
- Впровадження Conventional Commits у репозиторії (для автоматизованого changelog/semver тулінгу) з потребою в допомозі правильно класифікувати зміну.
- Прибирання неохайного повідомлення коміту перед пушем, щоб відповідати конвенціям комітів команди.

## Промпт

```
Ти пишеш повідомлення коміту у форматі Conventional Commits з diff'у — повідомлення одного коміту, не опис PR чи запис changelog.

Diff: {{DIFF}}
Додатковий контекст (необов'язково — напр., пов'язаний номер тікета, чому зроблено зміну, якщо не очевидно з diff'у): {{CONTEXT}}

Інструкції:
1. Визнач правильний type: `feat` (нова видима для користувача можливість), `fix` (виправлення бага), `refactor` (без зміни поведінки), `perf` (покращення продуктивності), `test` (зміни лише в тестах), `docs` (лише документація), `chore` (зміни тулінгу/збірки/залежностей без впливу на вихідний код), `style` (лише форматування, без зміни логіки). Якщо diff змішує типи (напр., виправлення плюс непов'язаний рефакторинг), обери домінуючий тип і зазнач у тілі, що коміт також включає вторинну зміну — чи познач, що ідеально було б розділити на окремі коміти.
2. Визнач scope, якщо конвенція кодової бази його використовує (назва модуля/компонента в дужках, напр. `feat(auth):`) — виведи його зі шляхів змінених файлів, якщо не вказано.
3. Напиши рядок subject: наказовий спосіб ("add", не "added"/"adds"), без крапки в кінці, до ~50 символів де можливо, достатньо конкретний, щоб бути корисним при перегляді `git log --oneline`.
4. Напиши тіло (якщо зміна не тривіально пояснюється лише subject'ом), що покриває: що змінилося і чому — "чому" важливіше за переказ diff'у, оскільки diff уже показує, що змінилося.
5. Якщо diff вносить ламаючу зміну, додай footer `BREAKING CHANGE:`, що описує, що ламається і як споживачам адаптуватися — не ховай це в тілі, де тулінг changelog це не знайде.
6. Якщо {{CONTEXT}} посилається на номер тікета/issue, включи його в footer за конвенцією проєкту (напр., `Refs: PROJ-123` чи `Closes #123`), якщо конвенцію можна вивести чи вона вказана.
7. Якщо diff занадто великий/змішаний, щоб підсумувати як один цілісний коміт, прямо про це скажи і запропонуй, як його можна розділити, замість того щоб писати штучно розпливчасте повідомлення, що вільно покриває все.

Вивід: повідомлення коміту, відформатоване точно так, як воно має бути написане (рядок subject, порожній рядок, тіло, порожній рядок, footer, якщо є) — готове до вставки в `git commit`.
```

## Змінні
- `{{DIFF}}` — diff, для якого написати повідомлення коміту. Обов'язково.
- `{{CONTEXT}}` — посилання на тікет чи неочевидна мотивація. Необов'язково.

## Приклад
**Вхід:** `{{DIFF}}` = додає перевірку на null і ранній return у `calculateDiscount()` для виправлення краша, коли `user.membershipTier` є undefined.

**Вихід (фрагмент):**
```
fix(checkout): guard against undefined membershipTier in discount calc

calculateDiscount() crashed when user.membershipTier was undefined
(e.g., for guest checkouts). Add an early return with the default
(no-discount) behavior in that case.
```

## Поради та варіації
- Для воркфлоу squash-merge, де заголовок PR стає повідомленням коміту, попроси вивід лише одним рядком (лише subject, без тіла), що відповідає обмеженням довжини заголовка PR.
- Якщо команда використовує строгіший варіант Conventional Commits з примусовим списком scope, передай цей список як частину {{CONTEXT}}, щоб scope обирався з валідних опцій, а не вигадувався.
