## Опис
Проводить через безпечне розв'язання конкретного конфлікту мерджу — пояснюючи, що змінила кожна сторона, чому вони конфліктують, і правильне розв'язання — а не сліпо обирає одну сторону. Для реального конфлікту перед тобою, відрізняється від «Археолога історії git» (пояснює наявний закомічений код, не активний конфлікт).

## Коли використовувати
- Застряг на конфлікті мерджу/ребейзу, де не очевидно, яка сторона "правильна" чи як об'єднати обидві зміни.
- Рев'ю чужого розв'язання конфлікту для перевірки, чи випадково не втратили намір однієї сторони.
- Навчання читати маркери конфлікту і систематично міркувати про них замість вгадування.

## Промпт

```
Ти проводиш через розв'язання конкретного конфлікту мерджу — поясни намір обох сторін і видай коректне розв'язання, не просто обери одну сторону.

Секція файлу з конфліктом (включно з маркерами `<<<<<<<`/`=======`/`>>>>>>>`): {{CONFLICT}}
Контекст щодо кожної сторони, якщо відомий (необов'язково — напр., "наша — це release-гілка, їхня — feature-гілка, що перейменувала цю функцію"): {{SIDE_CONTEXT}}
Навколишній код для контексту (необов'язково): {{SURROUNDING_CODE}}

Інструкції:
1. Поясни, чого намагалася досягти кожна сторона (`ours`/`HEAD` і `theirs`/вхідна гілка) — не лише що каже текст, а очевидний намір за зміною, виведений із самого коду та будь-якого наданого {{SIDE_CONTEXT}}.
2. Визнач, чи це справжній логічний конфлікт (обидві сторони змінили ту саму поведінку несумісними способами — потрібне реальне рішення) чи хибний конфлікт (обидві сторони зробили сумісні чи навіть ідентичні зміни, що просто торкаються тих самих рядків, напр., обидві перейменували змінну на ту саму нову назву, чи зміна однієї сторони є строгою надмножиною іншої).
3. Для справжнього конфлікту запропонуй розв'язання, що зберігає намір ОБОХ сторін там, де можливо (напр., якщо одна сторона додала новий параметр, а інша — нову перевірку валідації, розв'язання, ймовірно, потребує обох), а не за замовчуванням "залиш ours" чи "залиш theirs".
4. Якщо збереження наміру обох сторін дійсно неможливе (вони ухвалили взаємовиключні рішення щодо тієї самої поведінки), прямо про це скажи, поясни компроміс між двома опціями, і рекомендуй одну з обґрунтуванням — не обирай мовчки одну без позначення, що було ухвалене реальне рішення.
5. Випиши точний розв'язаний код (з видаленими маркерами конфлікту), щоб його можна було напряму використати, не лише опис того, що робити.
6. Познач будь-що в навколишньому коді (якщо надано), що також може потребувати оновлення для узгодженості з розв'язанням — розв'язання конфлікту, що виправляє позначені рядки, але залишає пов'язаний непозначений рядок тепер неузгодженим, є поширеним джерелом тонких багів після мерджу.
7. Рекомендуй, що перевірити після розв'язання (конкретний тест для запуску, поведінку для ручної перевірки) з урахуванням того, що змінилося на обох сторонах.

Формат виводу: Markdown з розділами: Що змінила кожна сторона, Справжній чи хибний конфлікт, Розв'язаний код, Що перевірити після.
```

## Змінні
- `{{CONFLICT}}` — секція з конфліктом і маркерами. Обов'язково.
- `{{SIDE_CONTEXT}}` — що представляє кожна гілка/сторона чи що намагалася зробити. Необов'язково, але дуже допомагає для оцінки наміру.
- `{{SURROUNDING_CODE}}` — код поруч з конфліктом для ширшого контексту. Необов'язково.

## Приклад
**Вхід:** `{{CONFLICT}}` = ours додає параметр `timeout` до функції зі значенням за замовчуванням 30, theirs додає валідацію вводу для наявного параметра тієї самої функції, обидва торкаються сигнатури/тіла функції.

**Вихід (фрагмент):**
```
## Що змінила кожна сторона
Ours: додано новий параметр `timeout` (за замовчуванням 30с) для контролю таймауту запиту, не пов'язаний з валідацією.
Theirs: додано перевірку валідації наявного параметра `url` для відхилення порожніх рядків.

## Справжній чи хибний конфлікт
Хибний конфлікт — обидві зміни незалежні й сумісні; вони перетинаються лише тому, що обидві торкаються тієї самої області сигнатури/тіла функції. Обидві мають бути збережені.

## Розв'язаний код
```js
function fetchData(url, timeout = 30) {
  if (!url) throw new Error('url is required');
  // ...
}
```

## Що перевірити після
Запусти наявний тестовий набір для цієї функції, і додай тест, що поєднує обидві нові поведінки: виклик з порожнім url все одно має кидати виняток незалежно від переданого значення timeout.
```

## Поради та варіації
- Для конфлікту в lock-файлі чи згенерованому файлі (а не написаному вручну коді) правильна відповідь зазвичай "регенеруй файл, не мерджи вручну" — явно познач це, якщо конфлікт виглядає таким, що в згенерованому артефакті.
- Для довгоживучої feature-гілки з багатьма конфліктами проти швидкозмінюваного main розглянь ребейз поступово і розв'язання конфліктів коміт-за-комітом, а не один гігантський конфлікт мерджу — згадай це як пропозицію процесу, якщо конфлікт виглядає незвично великим/заплутаним.
