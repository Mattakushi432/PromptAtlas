## Опис
Перевіряє, чи запланований трафік і тривалість A/B тесту реально можуть досягти статистичної значущості для цільового розміру ефекту — перевірка на стадії планування, відмінна від «Рев'ю інструментації A/B-тестів» (coding, вже випущений) із фокусом на рівні коду трекінгу/інструментації: цей промпт запускається до старту тесту, перевіряючи, чи він взагалі статистично життєздатний як спроєктований.

## Коли використовувати
- Плануєш A/B тест і хочеш перевірити, чи доступний трафік реально може виявити розмір ефекту, який тебе цікавить, перед вкладанням інженерного часу в його побудову.
- Минулий тест повернувся «невизначеним», і хочеш ретроспективно перевірити, чи він взагалі мав достатню потужність для виявлення ефекту, на який сподівався.
- Вирішуєш між тестуванням на малотрафіковій сторінці проти високотрафікової, і хочеш конкретне порівняння, скільки часу реально потребувала б кожна.

## Промпт

```
Ти перевіряєш, чи запланований трафік і тривалість A/B тесту реально можуть досягти статистичної значущості для цільового розміру ефекту. Ти міркуєш на основі наданих чисел — ти не проводиш реальний розрахунок потужності з точністю понад те, що виправдовують вводи, і явно позначаєш, коли ввід — приблизна оцінка, а не точна цифра.

Базова метрика й поточний рівень: {{BASELINE}}
Доступний трафік (відвідувачі/події на день чи тиждень): {{TRAFFIC}}
Мінімальний розмір ефекту, вартий виявлення: {{MIN_EFFECT}}
Запланована тривалість тесту: {{PLANNED_DURATION}}

Інструкції:
1. Використовуючи стандартну оцінку розміру вибірки для тесту двох пропорцій (чи доречний тип тесту для наданої метрики), оціни приблизно, скільки трафіку/конверсій потрібно було б на варіант, щоб надійно виявити {{MIN_EFFECT}} на конвенційних рівнях значущості/потужності (95% довіри, 80% потужності) — покажи оцінку як приблизну цифру із заявленими припущеннями, не як хибно точне число.
2. Порівняй цю оцінку з {{TRAFFIC}} і {{PLANNED_DURATION}}, щоб прямо сказати, чи запланований тест адекватно потужний, недостатньо потужний, чи надто потужний (більше трафіку/часу, ніж строго потрібно) для заявленого мінімального розміру ефекту.
3. Якщо недостатньо потужний, конкретно вкажи, що потрібно змінити для виправлення: довшу тривалість (дай приблизну оцінку наскільки довше), більший мінімальний розмір ефекту, який тест реально зміг би виявити при поточному трафіку/тривалості, чи більше трафіку (напр., тестування на високотрафіковій поверхні).
4. Познач конкретний ризик усе одно запускати недостатньо потужний тест: нульовий/невизначений результат не означає «немає ефекту», він може просто означати «недостатньо даних для виявлення ефекту, навіть якщо він існує» — це розрізнення часто губиться при інтерпретації результатів, і варто заявити його явно на стадії планування до запуску тесту.
5. Якщо метрика не проста конверсійна ставка (напр., безперервна метрика на кшталт доходу на користувача, що має інші міркування дисперсії, ніж бінарна конверсія), познач, що стандартна оцінка двох пропорцій — груба апроксимація, і що точніший розрахунок потужності для цього типу метрики потребував би реальної дисперсії метрики, не лише її середнього.
6. Не подавай це як заміну ретельного розрахунку потужності, зробленого з реальним статистичним тулінгом, якщо рішення високоризикове — цей промпт швидка перевірка на здоровий глузд, щоб рано зловити явно недостатньо потужний план, не заміна ретельного попередньо зареєстрованого аналізу для значущого тесту.

Формат виводу: Markdown із `## Оцінена вимога`, `## Порівняння з планом` (адекватно потужний / недостатньо потужний / надто потужний), і `## Рекомендація` (конкретне коригування, якщо недостатньо потужний).
```

## Змінні
- `{{BASELINE}}` — поточне значення метрики/конверсійна ставка до тесту. Обов'язково.
- `{{TRAFFIC}}` — реалістичний доступний трафік/обсяг подій для тесту. Обов'язково.
- `{{MIN_EFFECT}}` — найменша зміна, яку реально вартувало б діяти на основі (напр., «приріст на 2 процентні пункти»). Обов'язково — без цього неможливо судити, чи «достатньо» трафіку відносно чогось конкретного.
- `{{PLANNED_DURATION}}` — як довго планується запускати тест. Обов'язково.

## Приклад
**Вхід:** `{{BASELINE}}` = «Поточна конверсія реєстрації: 3%» `{{TRAFFIC}}` = «~2000 відвідувачів на тиждень на сторінку реєстрації» `{{MIN_EFFECT}}` = «Приріст на 1 процентний пункт (3% -> 4%) вартувало б випустити» `{{PLANNED_DURATION}}` = «2 тижні»

**Вихід (уривок):**
```
## Оцінена вимога
Виявлення приросту з 3% до 4% (відносне збільшення ~33%) на 95% довіри / 80% потужності приблизно вимагає порядку кількох тисяч відвідувачів на варіант (приблизна оцінка, стандартні припущення двох пропорцій) — малі абсолютні конверсійні ставки з помірним абсолютним приростом зазвичай потребують більших розмірів вибірки, ніж підказує інтуїція.

## Порівняння з планом
При ~2000 відвідувачів/тиждень, розділених між 2 варіантами (~1000/варіант/тиждень), 2 тижні дають приблизно ~2000 відвідувачів на варіант загалом — ймовірно недостатньо потужно для надійного виявлення приросту на 1 пункт при цьому базовому рівні, хоча це приблизна оцінка, не точний розрахунок.

## Рекомендація
Варіанти: (а) продовж тривалість тесту — приблизно в 2-3 рази довше за поточно заплановане, як груба порядкова оцінка, щоб наблизитись до адекватної потужності; (б) прийми, що тест реально може надійно виявити лише більший ефект за 1 пункт при поточному трафіку/тривалості, і трактуй менший спостережений ефект як невизначений, а не «немає ефекту», якщо повернувся нульовим; (в) якщо доступна високотрафікова сторінка для запуску цього тесту натомість, це суттєво скоротило б необхідну тривалість.
```

## Поради та варіації
- Якщо ця перевірка постійно повертається «недостатньо потужною» для тестів, які реально хочеш запускати, це вартий ескалації сигнал — можливо, команді потрібна нижча планка для «вартих виявлення» ефектів, спосіб об'єднувати трафік між сторінками, чи прийняття, що деякі ідеї потрібно випускати без повного A/B тесту й оцінювати інакше (напр., через менш масштабну якісну перевірку).
- Для тесту, що вже пройшов і повернувся невизначеним, використай цей промпт ретроспективно з реальним трафіком/тривалістю тесту, щоб перевірити, чи він взагалі був адекватно потужним — це переформульовує «тест не знайшов ефекту» на точніше «тест, можливо, не мав достатньо даних, щоб знайти ефект», що змінює наступні кроки.
- Цей промпт дає орієнтовну перевірку на здоровий глузд, не публікаційний аналіз потужності — для тесту з реальними бізнес-ставками, що спираються на статистичну строгість, використовуй спеціалізоване статистичне ПЗ чи консультуйся з кимось із формальною експертизою в дизайні експериментів.
