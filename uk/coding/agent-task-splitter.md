## Опис
Розділяє фічу на підзавдання розміру агента для мультиагентного кодинг-воркфлоу — послідовні, обмежені, з чіткими межами й точками передачі — для оркестрації кількох AI-агентів (чи кількох послідовних сесій агента) над однією фічею. Відрізняється від промптів типу «аудит архітектури агента»: це декомпозиція завдань, не дизайн архітектури.

## Коли використовувати
- Фіча достатньо велика, що одна сесія AI-агента, що працює над усім цим, ризикує втратити фокус чи видати несфокусований, важкий для рев'ю diff.
- Використання мультиагентного воркфлоу (паралельні чи послідовні агенти, кожен з обмеженим завданням) з потребою в фактичному розбитті завдань перед розсиланням роботи.
- Рішення, які частини фічі безпечно паралелізувати між агентами проти тих, що мають залежності, які вимагають послідовного виконання.

## Промпт

```
Ти розділяєш фічу на підзавдання розміру агента для мультиагентного (чи послідовного багатосесійного) кодинг-воркфлоу — конкретні, обмежені завдання з чіткими межами, не загальний проєктний план.

Опис фічі: {{FEATURE_DESCRIPTION}}
Контекст кодової бази (необов'язково — відповідна наявна структура/патерни): {{CODEBASE_CONTEXT}}
Модель виконання (необов'язково — "паралельні агенти, що працюють одночасно" проти "послідовні сесії, по одній за раз"): {{EXECUTION_MODEL}}

Інструкції:
1. Розклади фічу на підзавдання, обмежені тим, що одна сесія агента може завершити цілісно: достатньо сфокусовані, щоб видати рецензований diff з однією метою, не настільки гранулярні, що накладні витрати координації перевищують вигоду від розділення.
2. Визнач справжні залежності між підзавданнями (підзавдання B потребує тип/інтерфейс/міграцію, яку створює підзавдання A) проти хибних залежностей (підзавдання, що лише здаються пов'язаними, але фактично не блокують одне одного) — послідовно упорядковуй лише те, що дійсно має бути послідовним.
3. Якщо {{EXECUTION_MODEL}} паралельна, явно визнач, які підзавдання можуть безпечно виконуватися паралельно без конфліктів файлів/мерджу (торкаються непересічних файлів/модулів), і познач будь-яку пару, ризиковану для паралелізації (обидві ймовірно торкаються того самого файлу), навіть якщо не строго залежні.
4. Для кожного підзавдання визнач чітку межу: які файли/області воно має торкатися, і явно чого воно НЕ має торкатися — це найважливіша річ для збереження мерджабельності diff'ів, вироблених агентом, оскільки недообмежений опис завдання — найпоширеніша причина блукання агента непов'язаним кодом.
5. Визнач інтерфейс/контракт, який кожне підзавдання передає наступному (сигнатуру функції, форму даних, контракт API) ПЕРЕД тим, як будь-яке з підзавдань розіслано, якщо підзавдання послідовні/залежні — узгодження контракту наперед уникає того, що вибір реалізації одного агента мовчки ламає припущення наступного агента.
6. Для кожного підзавдання сформулюй, як конкретно виглядає "готово" (конкретний тест проходить, конкретна поведінка демонстровна), щоб координуючий процес (людина чи агент) міг перевірити завершення перед розсиланням залежної роботи.
7. Познач будь-яку частину фічі, достатньо неоднозначну, що агент підзавдання, ймовірно, потребуватиме зробити судження — розв'яжи цю неоднозначність у самому розбитті завдань, а не залишай агенту вгадувати непослідовно по підзавданнях.

Формат виводу: Markdown, один запис на підзавдання, у порядку залежності/виконання: назва, обсяг (торкається/не торкається), вводи, потрібні з попередніх підзавдань, визначення готовності. За яким слідує опис графа залежностей (які підзавдання блокують які, які можуть виконуватися паралельно).
```

## Змінні
- `{{FEATURE_DESCRIPTION}}` — повна фіча для декомпозиції. Обов'язково.
- `{{CODEBASE_CONTEXT}}` — відповідна наявна структура, у яку мають вписатися підзавдання. Необов'язково, але покращує точність обмеження.
- `{{EXECUTION_MODEL}}` — паралельне чи послідовне виконання агента. Необов'язково, але змінює, що потрібно позначати (безпека паралелізації проти лише послідовності).

## Приклад
**Вхід:** `{{FEATURE_DESCRIPTION}}` = "додати фічу 'збережені пошуки': користувачі можуть зберігати пошуковий запит, переглядати свої збережені пошуки, і отримувати сповіщення, коли нові результати збігаються", `{{EXECUTION_MODEL}}` = "послідовні сесії".

**Вихід (фрагмент):**
```
### Підзавдання 1: Модель даних і API для збереження/перегляду пошуків
Обсяг: нова таблиця/міграція `saved_searches`, ендпойнти `POST /api/saved-searches` і `GET /api/saved-searches`. НЕ торкається логіки сповіщень чи фронтенду.
Визначення готовності: ендпойнти протестовані й функціональні; збережений пошук можна створити й отримати через API.

### Підзавдання 2: UI фронтенду для збереження й перегляду пошуків
Залежить від: контракту API підзавдання 1 (точна форма запиту/відповіді).
Обсяг: кнопка "зберегти цей пошук" на сторінці результатів пошуку, сторінка списку "збережені пошуки". НЕ торкається бекенду чи логіки сповіщень.
Визначення готовності: користувач може зберегти пошук з UI і побачити його у своєму збереженому списку.

### Підзавдання 3: Завдання сповіщень для нових відповідних результатів
Залежить від: моделі даних підзавдання 1 (потребує запиту збережених пошуків).
Обсяг: фонове завдання, що порівнює нові результати зі збереженими пошуками й запускає сповіщення. НЕ торкається UI, окрім показу сповіщення, якщо він ще не існує.
Визначення готовності: тест, що демонструє, що новий відповідний результат запускає сповіщення для відповідного збереженого пошуку.

**Примітка щодо паралелізації:** Підзавдання 2 і Підзавдання 3 можуть виконуватися паралельно, коли Підзавдання 1 завершене — вони не торкаються тих самих файлів, і жодне не залежить від виводу іншого.
```

## Поради та варіації
- Для дійсно новаторської/неоднозначної фічі спочатку запусти менший прохід планування (чи використай виділеного агента планування) перед цією декомпозицією — цей промпт працює найкраще, коли загальна форма фічі вже достатньо зрозуміла.
- Якщо використовуєш буквально паралельних агентів, явно попроси запропоновану мапу володіння файлами (яке підзавдання "володіє" якими файлами) як додатковий захід уникнення колізій понад сам аналіз залежностей.
