## Опис
Критикує схему GraphQL конкретно на ризик N+1-запитів, дизайн over-fetching/under-fetching та необмежені list-поля — рев'ю якості дизайну схеми, відмінне від загального проходу дизайну API і повністю відмінне від дизайну REST-ендпойнтів. Для схеми до чи після реалізації, коли турбує продуктивність резолверів.

## Коли використовувати
- Проєктування нової схеми GraphQL з бажанням виловити ризики N+1 ще до написання резолверів.
- API GraphQL має проблеми з продуктивністю, і ти підозрюєш, що сама форма схеми, а не лише відсутність батчингу DataLoader, є першопричиною.
- Рев'ю PR зі схемою, де рев'ювери постійно пропускають наслідки для продуктивності резолверів, бо рецензують типи, а не патерни доступу.

## Промпт

```
Ти рецензуєш схему GraphQL конкретно на проблеми дизайну, релевантні продуктивності — ризик N+1, over/under-fetching, необмежені списки — не загальний дизайн типів чи іменування.

Схема (SDL): {{SCHEMA}}
Відомі патерни запитів, які фактично використовують клієнти (необов'язково, але дуже цінно): {{QUERY_PATTERNS}}
Деталі реалізації резолверів (необов'язково, якщо доступні): {{RESOLVER_DETAILS}}

Інструкції:
1. Для кожного поля, що повертає список типу з власними резолвабельними полями, визнач, чи розв'язання цих вкладених полів по всьому списку ризикує патерном N+1 (один запит на елемент списку), а не єдиним батчованим запитом — познач це навіть якщо батчинг у стилі DataLoader вже може бути на місці, оскільки саму форму схеми варто оцінювати незалежно від пом'якшень реалізації.
2. Познач будь-яке list-поле без аргументів пагінації (без `first`/`after` чи `limit`/`offset`) — необмежений список є і ризиком продуктивності, і потенційним вектором DoS, якщо клієнт може запросити довільно великий набір результатів.
3. Визнач ризик over-fetching: тип, що завжди повертає велике/дороге поле (напр., повний текст документа), навіть коли більшість запитів цього не потребують — порекомендуй, чи має воно стати окремим полем за явним opt-in, чи використовувати патерни в стилі `@defer`, якщо схема це підтримує.
4. Визнач ризик under-fetching / "балакучих" запитів: форма схеми, що змушує клієнтів робити кілька round-trip запитів для збирання того, що концептуально є даними одного екрана, коли один добре спроєктований запит міг би це обслужити.
5. Перевір на циклічні/глибоко вкладені зв'язки, що могли б дозволити зловмисному чи наївному клієнту сконструювати надзвичайно дорогий запит (напр., `friends { friends { friends { ... } } }`) — познач, якщо немає обмеження глибини/складності запиту чи воно не очевидне.
6. Для кожної знахідки вкажи конкретну форму запиту, що спричинила б проблему, а не лише абстрактний ризик.

Формат виводу: Markdown, один запис на знахідку, згруповано за категорією (Ризик N+1 / Необмежені списки / Over-fetching / Under-fetching / Складність запиту), кожен зі спричиняючим патерном запиту та запропонованою зміною схеми.
```

## Змінні
- `{{SCHEMA}}` — GraphQL SDL для рецензування. Обов'язково.
- `{{QUERY_PATTERNS}}` — реальні чи очікувані клієнтські запити до цієї схеми. Необов'язково, але різко покращує релевантність — теоретичні проблеми схеми, які жоден клієнтський запит ніколи не спричинить, мають нижчий пріоритет.
- `{{RESOLVER_DETAILS}}` — як поля фактично розв'язуються (батчовано, по-елементні виклики БД тощо). Необов'язково.

## Приклад
**Вхід:** `{{SCHEMA}}` = тип `Post` з полем `comments: [Comment!]!` (без аргументів пагінації), і кожен `Comment` має поле `author: User!`.

**Вихід (фрагмент):**
```
### Ризик N+1
`Comment.author` — для будь-якого запиту, що отримує коментарі поста і автора кожного коментаря, розв'язання `author` для кожного коментаря ризикує одним запитом на коментар, якщо не батчовано (напр., через DataLoader). Спричиняючий запит: `{ post(id: "1") { comments { author { name } } } }`. Рекомендую підтвердити, що батчинг DataLoader на місці для `Comment.author`, і явно зазначити це в документації резолверів, оскільки це не видно з самої схеми.

### Необмежені списки
`Post.comments: [Comment!]!` не має аргументів пагінації — пост із 10 000 коментарів поверне їх усі в одній відповіді. Рекомендую перетворити на патерн connection: `comments(first: Int, after: String): CommentConnection!`.
```

## Поради та варіації
- Передай реальні логи запитів чи `.graphql`-файли запитів клієнта як `{{QUERY_PATTERNS}}` — це перетворює рев'ю з теоретичного на "ось конкретні запити, які виконують ваші користувачі, і ось що ламається".
- Для схеми, що використовує конкретний серверний фреймворк (Apollo, GraphQL Yoga тощо), попроси зазначити доступні пом'якшення, специфічні для фреймворку (напр., automatic persisted queries Apollo, обмеження складності запиту на основі вартості), а не лише загальні поради.
