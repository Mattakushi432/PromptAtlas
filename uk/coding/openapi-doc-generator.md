## Опис
Укладає документацію OpenAPI/Swagger з наявного коду ендпойнтів — зворотне документування API, побудованого без специфікації, чи такого, що від неї відхилилося. Для того, щоб отримати специфікацію з реального коду, а не проєктувати нові ендпойнти (для цього див. «Дизайнер REST-ендпойнтів»).

## Коли використовувати
- API було побудовано без специфікації OpenAPI, і тепер вона потрібна для генератора клієнтського SDK, API-шлюзу чи партнерської документації.
- Наявна специфікація OpenAPI розсинхронізувалася з фактичним кодом і потребує регенерації/узгодження.
- Онбординг нової команди-споживача, якій потрібна документація, а єдине джерело істини — сама реалізація.

## Промпт

```
Ти генеруєш специфікацію OpenAPI 3.x з наявного коду реалізації ендпойнтів. Документуй те, що код фактично робить, а не те, що він мав би ідеально робити — якщо реалізація має неузгодженості, документуй їх сумлінно, а не мовчки "виправляй" у специфікації.

Код ендпойнта: {{ENDPOINT_CODE}}
Наявна специфікація OpenAPI для оновлення, якщо узгоджуєш розсинхронізацію (необов'язково): {{EXISTING_SPEC}}
Метадані API (назва, версія, базовий шлях — необов'язково): {{API_METADATA}}

Інструкції:
1. Для кожного ендпойнта виведи: шлях, HTTP-метод, параметри шляху/запиту/заголовка (з типами і чи обов'язкові), схему тіла запиту, і кожну відповідь, яку код фактично може видати (не лише успішний випадок), з точними статус-кодами.
2. Виводь типи схеми й обмеження з коду настільки точно, наскільки можливо: nullable-поля, enum'и (з логіки валідації чи визначень типів), формати рядків (email, date-time, uuid) там, де код дійсно їх валідує, а не лише там, де назва поля на це натякає.
3. Там, де фактична поведінка коду неоднозначна чи неузгоджена (напр., поле іноді присутнє у відповідях, а іноді пропущене, неузгоджені форми помилок у схожих ендпойнтах), познач це як коментар/примітку, а не вгадуй чисту форму — це документує технічний борг, а не приховує його.
4. Включи визначення схем автентифікації/безпеки, якщо код показує, як перевіряється автентифікація (bearer-токен, заголовок API-ключа тощо).
5. Напиши короткий, але дійсно корисний `description` для кожного ендпойнта і кожного неочевидного поля — не переказ назви поля (поле з назвою `status` потребує документування фактичних можливих значень і значення, а не "Статус").
6. Якщо надано {{EXISTING_SPEC}}, узгодь її: залиш вручну написані описи/приклади там, де вони досі точні, але виправ будь-який параметр, схему чи відповідь, що розсинхронізувалися з тим, що код тепер фактично робить, і познач кожну зроблену корекцію.

Вивід: валідний OpenAPI 3.x YAML, плюс короткий список будь-яких неоднозначностей чи неузгодженостей, позначених під час генерації.
```

## Змінні
- `{{ENDPOINT_CODE}}` — реалізація маршруту/хендлера для документування. Обов'язково.
- `{{EXISTING_SPEC}}` — попередня специфікація для узгодження, якщо існує. Необов'язково.
- `{{API_METADATA}}` — назва, версія, сервери/базовий шлях для info-блоку специфікації. Необов'язково.

## Приклад
**Вхід:** `{{ENDPOINT_CODE}}` = Express-хендлер для `GET /users/:id`, що повертає об'єкт користувача чи 404 з `{ error: string }`, і валідує, що `id` є UUID перед запитом.

**Вихід (фрагмент):**
```yaml
/users/{id}:
  get:
    summary: Get a user by ID
    parameters:
      - name: id
        in: path
        required: true
        schema:
          type: string
          format: uuid
    responses:
      '200':
        description: The requested user
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/User'
      '404':
        description: No user exists with the given ID
        content:
          application/json:
            schema:
              type: object
              properties:
                error:
                  type: string
```

## Поради та варіації
- Для великої кодової бази запускай це по одному файлу маршрутів за раз, а не на все API одразу, потім зливай отримані специфікації — це тримає кожну генерацію точною і уникає обрізання.
- Прогони згенеровану специфікацію через реальний валідатор OpenAPI після цього (напр., Spectral), щоб виловити будь-які структурні проблеми, які міг внести YAML-вивід моделі.
