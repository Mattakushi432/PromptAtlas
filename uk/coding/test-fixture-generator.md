## Опис
Генерує реалістичні мок/фікстурні дані за заданою схемою — для тестів, seed-скриптів чи локальної розробки — замість ручного написання зразкових об'єктів один за одним. Для розробника, якому потрібні правдоподібні дані, а не налаштування бібліотеки генерації даних.

## Коли використовувати
- Написання тесту, якому потрібно кілька реалістичних записів (користувачі, замовлення, товари), а ручне створення кожного — виснажливе.
- Наповнення локальної dev-бази даними, що виглядають достатньо реальними, щоб виловити баги UI/форматування.
- Навмисна потреба в крайових фікстурах (порожні рядки, граничні числа, юнікод-імена) для стрес-тестування логіки валідації.

## Промпт

```
Ти генеруєш реалістичні тестові фікстурні дані за схемою. Дані мають виглядати так, ніби вони могли б правдоподібно існувати в продакшні — різноманітні, не очевидно фейкові чи повторювані — при цьому строго відповідаючи типам і обмеженням схеми.

Схема (JSON Schema, TypeScript-інтерфейс, DDL бази даних чи опис): {{SCHEMA}}
Кількість записів: {{RECORD_COUNT}}
Особливі вимоги (необов'язково — напр., "включи 2 записи з крайовими значеннями", "дати мають охоплювати останній рік", "імена мають включати нелатинські алфавіти"): {{SPECIAL_REQUIREMENTS}}

Інструкції:
1. Строго дотримуйся схеми: правильні типи, поважай обов'язкові/необов'язкові поля, поважай будь-які enum, min/max чи обмеження формату (формат email, формат UUID тощо).
2. Роби дані різноманітними та реалістичними — різні імена, правдоподібні діапазони значень, без очевидно послідовних/фейкових патернів (уникай "Test User 1", "Test User 2", якщо явно не попросили дані у стилі плейсхолдерів).
3. Підтримуй будь-які неявні референційні зв'язки (напр., якщо поле явно є зовнішнім ключем, що посилається на інший тип сутності, який також генерується, тримай ID узгодженими).
4. Якщо {{SPECIAL_REQUIREMENTS}} просить крайові випадки, генеруй їх як чітко позначену окрему підмножину, а не змішуй непомітно зі "звичайними" записами.
5. Ніколи не генеруй дані, що виглядають як реальні PII справжніх людей (використовуй явно вигадані, але правдоподібно звучні імена, не реальних знаменитостей чи публічних осіб).
6. Виводь у форматі, що випливає з типу схеми (JSON-масив для JSON Schema/TS-інтерфейсу, SQL INSERT-запити для DDL), якщо не запитано інший формат виводу.
```

## Змінні
- `{{SCHEMA}}` — форма даних, за якою генерувати. Обов'язково.
- `{{RECORD_COUNT}}` — скільки записів генерувати. Обов'язково.
- `{{SPECIAL_REQUIREMENTS}}` — крайові випадки, розподіли чи обмеження понад саму схему. Необов'язково.

## Приклад
**Вхід:** `{{SCHEMA}}` = TypeScript-інтерфейс `{ id: string; email: string; age: number; plan: 'free' | 'pro' }`, `{{RECORD_COUNT}}` = 3, `{{SPECIAL_REQUIREMENTS}}` = "включи один крайовий випадок з віком на мінімально дозволеному значенні (13)".

**Вихід (фрагмент):**
```json
[
  { "id": "usr_4f1a2c", "email": "priya.nandan@example.com", "age": 34, "plan": "pro" },
  { "id": "usr_9b7e10", "email": "marcus.oduya@example.com", "age": 13, "plan": "free" },
  { "id": "usr_2d88f3", "email": "lena.vogt@example.com", "age": 61, "plan": "free" }
]
```

## Поради та варіації
- Для навантажувального/perf-тестування попроси значно більший `{{RECORD_COUNT}}` з явною приміткою тримати вивід компактним JSON (без pretty-printing), щоб вкластися в ліміти відповіді.
- Зафіксуй набір `{{SPECIAL_REQUIREMENTS}}` з ворожими вхідними даними (рядки максимальної довжини, SQL-спецсимволи, емоджі), коли мета — фазинг логіки валідації, а не реалістичні seed-дані.
