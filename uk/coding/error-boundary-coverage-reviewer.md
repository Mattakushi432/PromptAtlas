## Опис
Перевіряє фронтенд-застосунок на прогалини у покритті error boundary і fallback UI — де необроблена помилка компонента обвалила б цілу сторінку/застосунок замість м'якої деградації. Відрізняється від `accessibility-auditor` і `frontend-performance-auditor`, що перевіряють зовсім інші аспекти.

## Коли використовувати
- Баг у непов'язаному компоненті обвалив цілу сторінку для користувачів.
- Додаєш error boundaries навмисно як прохід з підвищення стійкості, а не реактивно після інциденту.
- Рецензуєш нову область фічі на ізоляцію помилок перед випуском.

## Промпт

```
Ти проводиш аудит покриття error boundary у фронтенд-застосунку — де необроблена помилка рантайму в одному компоненті поширилась би і обвалила б більшу частину застосунку, ніж мала б, замість того щоб бути ізольованою і м'яко деградованою.

Структура застосунку (дерево компонентів чи структура маршрутизації, і де зараз існують error boundaries, якщо є): {{APP_STRUCTURE}}

Фреймворк: {{FRAMEWORK}}

Зроби наступне:
1. Визнач ділянки застосунку без error boundary між ними і коренем застосунку — тобто помилка будь-де в цьому піддереві обвалила б увесь застосунок, а не лише цю секцію.
2. Рекомендуй розміщення boundary, що ізолює незалежні, некритичні секції від решти застосунку — сторонній віджет, одну картку дашборду, неважливу фічу бічної панелі — а не покладання на один-єдиний boundary верхнього рівня, що все одно обвалює всю сторінку, коли щось падає.
3. Для наявних boundary перевір, чи мають вони справді корисний fallback UI (не просто порожній div, і не просто загальне "щось пішло не так" без жодного шляху відновлення — дія повтору чи посилання назад до робочого стану помітно краще) і чи спіймана помилка реально десь звітується (логування, моніторинг помилок), а не тихо ковтається, що приховало б реальні баги від того, щоб їх колись помітили.

Виведи: знахідки, організовані за секціями застосунку, кожна з серйозністю (наскільки критична ця секція, і наскільки великий зараз радіус ураження від необробленої помилки там) і конкретною рекомендацією (додай boundary тут, покращ fallback цього boundary, підключи catch цього boundary до звітування про помилки).

Якщо фреймворк чи бібліотека у використанні не підтримує error boundaries на рівні компонента так само, як React, не вважай, що точний патерн React застосовний — запропонуй найближчий еквівалентний механізм, реально доступний у {{FRAMEWORK}}.
```

## Змінні
- `{{APP_STRUCTURE}}` — дерево компонентів чи структура маршрутизації, і наявне розміщення error boundary, якщо є. Обов'язково.
- `{{FRAMEWORK}}` — фронтенд-фреймворк у використанні. Обов'язково — механізми і ідіоми error boundary суттєво різняться між фреймворками.

## Приклад
**Вхід:** `{{APP_STRUCTURE}}` = "застосунок-дашборд: AppRoot > DashboardPage > [SummaryCard, ChartWidget (сторонній embed), RecentActivityList] — існує лише один error boundary на AppRoot", `{{FRAMEWORK}}` = "React".

**Вихід (фрагмент):**
```
Знахідка: єдиний boundary лише на AppRoot. Будь-яка помилка в ChartWidget (сторонній embed, за своєю природою найменш надійна частина цього дерева) зараз обвалює всю DashboardPage — SummaryCard і RecentActivityList також зникнуть, хоча жоден з них не залежить від роботи ChartWidget. Серйозність: HIGH саме для цього випадку, оскільки сторонні embed'и статистично ймовірне джерело несподіваних помилок порівняно з власним кодом.

Рекомендація: додай спеціальний error boundary напряму навколо ChartWidget, з fallback типу "Графік тимчасово недоступний" плюс кнопкою повтору, щоб збій там деградував до відсутнього графіка, а не порожнього дашборду. Зроби те саме для RecentActivityList, якщо він залежить від окремого, незалежно здатного відмовити джерела даних.

Перевірка якості fallback: наявний boundary рівня AppRoot — перевір, що реально рендерить його fallback. Якщо це порожній екран чи нестильоване повідомлення про помилку без шляху назад до робочого стану, це погана остання лінія захисту навіть після додавання більш гранулярних boundary вище; він має щонайменше пропонувати дію перезавантаження/повтору.

Звітування про помилки: підтверди, що `componentDidCatch` (чи еквівалент) boundary AppRoot реально надсилає помилку в сервіс моніторингу — якщо він лише логує в консоль, реальні продакшн-помилки залишаються непоміченими замість того, щоб бути спійманими і виправленими.
```

## Поради та варіації
- Для фреймворка без вбудованого примітиву error boundary попроси запропонувати найближчий робочий патерн (наприклад, обгортковий компонент з еквівалентом try/catch для релевантного життєвого циклу, чи специфічний для фреймворка хук обробки помилок), а не насильно накидати React-подібну відповідь на інший фреймворк.
- Пріоритезуй розміщення boundary навколо всього, що застосунок не повністю контролює — сторонні embed'и, реклама, віджети — перед власним кодом, оскільки їх і важче гарантовано зробити безбаговими, і легше виправдати ізоляцію.
