## Опис
Перетворює розпливчастий запит на фічу ("зроби простіше знаходити старі замовлення", "дашборд має бути розумнішим") на чітку технічну специфікацію, яку AI-кодинг агент (чи людина) може дійсно реалізувати — виводячи неоднозначності на поверхню, а не мовчки їх вирішуючи. Відрізняється від «Укладача промптів для AI-кодинг агентів» (складає промпт для одного завдання) і «Укладача ADR» (документує вже ухвалене рішення): це перетворює нечіткий запит на реалізовну специфікацію.

## Коли використовувати
- Запит стейкхолдера чи продукту занадто розпливчастий, щоб передати напряму інженеру чи AI-агенту без того, щоб хтось спершу з'ясував, що це фактично означає.
- Підготовка добре сформованого тікета/специфікації перед делегуванням реалізації, щоб виконавець не був тим, хто за замовчуванням ухвалює продуктові рішення.
- Рев'ю власної розпливчастої ідеї перед початком побудови, щоб виявити, що ти насправді ще не знаєш, як виглядає "готово".

## Промпт

```
Ти перетворюєш розпливчастий запит на фічу на чітку технічну специфікацію — виводячи на поверхню, що неоднозначне, і пропонуючи конкретні розв'язання, а не мовчки обираючи інтерпретації й ховаючи неоднозначність.

Розпливчастий запит (дослівно, як наданий): {{VAGUE_REQUEST}}
Контекст (необов'язково — продукт/система, для якої це, хто запросив, будь-які відомі обмеження): {{CONTEXT}}

Інструкції:
1. Визнач кожну точку справжньої неоднозначності в запиті — розпливчастий прикметник ("простіше", "розумніше", "краще"), що міг би означати кілька різних конкретних речей, незаявлену межу обсягу (це застосовується до всіх користувачів чи конкретного сегмента?), неявну, але непідтверджену поведінку.
2. Для кожної неоднозначності запропонуй конкретну, розумну інтерпретацію — не просто перелічуй відкриті питання без запропонованої відповіді, оскільки це повертає роботу назад тому, хто читає специфікацію. Зроби вибір і чітко познач його як припущення для підтвердження, щоб рев'юверу було легко швидко прийняти чи перевизначити.
3. Напиши конкретні критерії прийняття: специфічні, тестовні твердження про те, що має бути правдою, щоб цю фічу вважати завершеною — не переказ розпливчастого запиту трохи іншими словами.
4. Визнач явні межі обсягу: що ця фіча явно НЕ включає, особливо все, що розумний читач міг би припустити включеним, але ним не є — це запобігає розповзанню обсягу під час реалізації і запобігає тому, щоб рев'ювер був здивований тим, чого бракує.
5. Зазнач крайові випадки, які специфікація має адресувати, навіть якщо оригінальний запит їх не згадував (що відбувається з нульовими результатами, з дуже великою кількістю результатів, для користувача без прав) — специфікація, що покриває лише типовий випадок, видасть реалізацію з тією самою прогалиною.
6. Якщо запит натякає на зміну UI/UX, опиши конкретну поведінку/взаємодію, не лише результат — "простіше знайти" має стати конкретним механізмом (фільтр, пошук, опція сортування), щоб хтось міг це реалізувати.
7. Тримай довжину специфікації пропорційною фактичній складності фічі — не наповнюй дійсно просту вимогу непотрібною структурою, але й не применшуй запит, складніший, ніж здається спочатку.

Формат виводу: Markdown з розділами: Зроблені припущення (кожне позначене для підтвердження), Критерії прийняття, Явні не-цілі, Крайові випадки для обробки.
```

## Змінні
- `{{VAGUE_REQUEST}}` — запит так, як він оригінально наданий, без редагування. Обов'язково.
- `{{CONTEXT}}` — передумова щодо продукту/системи і того, хто запросив. Необов'язково, але покращує якість запропонованих інтерпретацій.

## Приклад
**Вхід:** `{{VAGUE_REQUEST}}` = "зроби простіше знаходити старі замовлення", `{{CONTEXT}}` = "адмін-дашборд е-комерції; запросив лідер команди підтримки, що обробляє запити клієнтів щодо пошуку замовлень".

**Вихід (фрагмент):**
```markdown
## Зроблені припущення
- "Простіше знайти" інтерпретується як: додати фільтр пошуку за діапазоном дат замовлення і пошуку за email клієнта до наявного списку замовлень, оскільки запитувач з команди підтримки й типово шукає замовлення за інформацією клієнта чи приблизною датою, не за ID замовлення (який уже шукається). **Підтвердь цю інтерпретацію із запитувачем** — альтернативно це могло б означати покращення релевантності/ранжування пошуку, а не додавання нових полів фільтра.
- "Старі замовлення" припускається як замовлення, старіші за 90 днів, оскільки наявний список уже за замовчуванням показує недавні замовлення — підтвердь, чи є конкретний поріг на думці.

## Критерії прийняття
- Користувач підтримки може фільтрувати список замовлень за діапазоном дат, що охоплює будь-який період, включно із замовленнями, старішими за 90 днів.
- Користувач підтримки може фільтрувати/шукати за email клієнта і бачити відповідні замовлення незалежно від віку замовлення.

## Явні не-цілі
- Це не змінює, як замовлення архівуються чи зберігаються — лише зміна UI пошуку/фільтра, не зміна утримання даних.
- Це не додає повнотекстовий пошук по вмісту замовлення (позиції, нотатки) — лише діапазон дат і email клієнта, згідно з припущеним обсягом вище.

## Крайові випадки для обробки
- Нуль відповідних замовлень для заданого фільтра: показати чіткий стан "замовлень не знайдено", не порожній/зламаний список.
- Email клієнта, що збігається з кількома акаунтами (якщо email не унікальний у цій системі): уточни із запитувачем, чи це можливо і як має оброблятися.
```

## Поради та варіації
- Для запиту, що виявляється з дуже малою кількістю реальних неоднозначностей, видай коротку специфікацію, а не наповнюй її — мета — ясність, не обов'язкова довжина шаблону.
- Якщо кілька стейкхолдерів могли б мати різні неявні інтерпретації того самого розпливчастого запиту, явно познач, де інтерпретації могли б розумно розходитися між ними, а не подавай лише ймовірний намір однієї людини.
