## Опис
Діагностує помилки невідповідності SSR/гідратації (React'івське «Text content did not match», попередження гідратації Vue та еквіваленти), розрізняючи кілька реальних першопричин — недетермінований вивід рендеру, доступ до браузерних API під час серверного рендеру й розбіжність даних сервер/клієнт — за текстом помилки й кодом компонента, а не через загальний дебаг компонентів.

## Коли використовувати
- Бачиш попередження/помилку невідповідності гідратації в серверно-рендереному React, Vue чи подібному застосунку і треба швидко знайти, яка з небагатьох реальних причин це є, замість вгадування компонент за компонентом.
- Невідповідність гідратації відтворюється лише зрідка чи лише в продакшні, і підозрюєш недетермінований джерело рендеру, а не пряму помилку.
- Мігруєш клієнт-only компонент на серверний рендер і хочеш проактивно перевірити його на патерни, що зазвичай спричиняють невідповідності, перед випуском.

## Промпт

```
Ти діагностуєш невідповідність гідратації серверного рендерингу, визначаючи її конкретну першопричину серед відомого набору причин, а не пропонуючи загальний рефакторинг компонента.

Фреймворк: {{FRAMEWORK}}
Повідомлення помилки/попередження про невідповідність, дослівно: {{ERROR_MESSAGE}}
Задіяні компоненти, включно з будь-якою логікою отримання даних/рендеру: {{COMPONENT_CODE}}

Інструкції:
1. Спершу перевір на недетермінований вивід рендеру, оскільки це найпоширеніша причина: `Date.now()`, `new Date()`, `Math.random()` чи будь-яке значення, що може відрізнятись між проходом рендеру сервера й клієнта — включно з форматуванням, залежним від локалі/часового поясу (напр., `toLocaleDateString()`), яке могло б розв'язатись по-різному, якщо сервер і клієнт мають різну конфігурацію локалі/часового поясу.
2. Перевір на доступ до браузерного API під час коду рендеру, що мав би бути безпечним для сервера: `window`, `document`, `localStorage`, `navigator`, чи неправильно використана умова на кшталт `typeof window !== 'undefined'` — усе це дає різний вивід (чи кидає помилку, якщо неохороняється) на сервері проти клієнта.
3. Перевір на розбіжність даних сервер/клієнт: чи серверно-рендерений HTML використовує дані з одного джерела (напр., серверний fetch у момент запиту), тоді як прохід гідратації клієнта використовує інше чи застаріле джерело (напр., кешовані дані/localStorage, чи клієнтський fetch, що розв'язується після початкового монтування)? Це поширено з контентом, залежним від автентифікації чи персоналізованим, який недоступний послідовно в обох точках рендеру.
4. Перевір на невалідну вкладеність HTML, яку браузер мовчки «виправляє» під час початкового парсингу (напр., `<div>` всередині `<p>`, чи `<table>` без потрібних структурних елементів) — DOM, який браузер реально будує з серверного HTML, може відрізнятись від того, що очікує віртуальний DOM фреймворку, спричиняючи невідповідність, навіть якщо серверний вивід був побайтово коректним, як написано.
5. Перевір на втручання розширення браузера чи стороннього скрипта, лише якщо про невідповідність повідомляється як таку, що трапляється виключно в браузерах конкретних користувачів і не відтворюється локально — це реальна, але значно рідша причина, і не має бути першою гіпотезою.
6. Зіставте знахідку з конкретним текстом/локацією {{ERROR_MESSAGE}}, якщо помилка фреймворку їх містить (напр., помилки невідповідності React часто називають конкретний текст чи елемент).

Формат виводу: Markdown. Найімовірніша причина першою, з конкретним рядком/патерном у {{COMPONENT_CODE}}, відповідальним за це, чому воно розходиться між сервером і клієнтом, і конкретним виправленням (зроби детермінованим, обгороди для клієнт-only рендеру, чи узгодь джерело даних). Перерахуй вторинні гіпотези, лише якщо основна не пояснює {{ERROR_MESSAGE}} повністю.
```

## Змінні
- `{{FRAMEWORK}}` — використовуваний SSR-фреймворк/бібліотека (React/Next.js, Vue/Nuxt, SvelteKit тощо), оскільки точні API й ідіоми охорони клієнт-only різняться. Обов'язково.
- `{{ERROR_MESSAGE}}` — текст помилки чи попередження про невідповідність, дослівно, включно з будь-якими деталями елемента/тексту, які повідомляє фреймворк. Обов'язково.
- `{{COMPONENT_CODE}}` — задіяні компоненти, включно з їхньою логікою отримання даних і рендеру. Обов'язково.

## Приклад
**Вхід:** `{{FRAMEWORK}}` = «Next.js (React)» `{{ERROR_MESSAGE}}` = «Text content did not match. Server: "Posted 3 hours ago" Client: "Posted 3 hours ago" (невідповідність повідомляється при пере-рендері, не початковому відображенні — текст елемента змінюється невдовзі після завантаження)» `{{COMPONENT_CODE}}` = «`<span>{formatRelativeTime(post.createdAt)}</span>`, де `formatRelativeTime` обчислює рядок на кшталт "X годин тому" з `Date.now() - post.createdAt`.»

**Вихід (уривок):**
```
### Найімовірніша причина: недетермінований вивід рендеру через Date.now()
`formatRelativeTime` обчислює свій вивід, використовуючи `Date.now()` у момент рендеру. Сервер рендерить у момент запиту (скажімо, 14:00:00), даючи "3 години тому"; клієнт гідратує через кілька сотень мілісекунд — кілька секунд пізніше, і `Date.now()` на клієнті вже може відрізнятись достатньо — чи, ймовірніше, відносний час перетинає межу округлення — щоб дати інший вивід уже на наступному рендері, що React потім повідомляє як невідповідність, хоча це не справжня невідповідність контенту SSR/CSR — це компонент, що пере-рендерюється в інший рядок майже одразу.

Виправлення: для відображення відносного часу рендери стабільне, детерміноване значення при першому рендері (напр., сирий ISO timestamp, чи обчисли рядок відносного часу один раз, використовуючи значення, передане з сервера й заморожене для цього рендеру), і почни живо оновлювати відносний час на клієнті лише після завершення гідратації (напр., у `useEffect`, який потім тригерить наступні пере-рендери) — це уникає ситуації, коли серверний і клієнтський рендер дають різний текст для того самого початкового відображення.

Це варіант загального патерну «недетермінований вивід рендеру», але специфічний для форматування відносного часу: реальна розбіжність — не незгода сервера й клієнта про «зараз», а пере-рендер компонента в інший рядок у самому вікні гідратації.
```

## Поради та варіації
- Якщо першопричина — доступ до браузерного API, виправлення майже завжди — обгородити доступ так, щоб він виконувався лише після монтування (напр., читай `window`/`localStorage` всередині `useEffect`/`onMounted` і рендери безпечний для сервера fallback на початковому проході), а не намагатись змусити API «працювати» на сервері.
- Відрізняється від «Дебагера чутливої верстки» (coding, вже випущений): той промпт діагностує поломку верстки/CSS на конкретних розмірах екрана; цей — незгоду виводу рендеру сервер/клієнт, що не пов'язана з розміром вʼюпорту.
- Якщо {{ERROR_MESSAGE}} відтворюється лише в продакшні, а не в локальній розробці, спершу перевір саме на значення, залежні від середовища (часовий пояс/локаль сервера відрізняються від регіону деплою, чи CDN/edge-кешована HTML-відповідь віддає застарілий серверний вивід проти клієнта, що отримав свіжі дані), перш ніж припускати, що це взагалі баг рендеру на рівні коду.
