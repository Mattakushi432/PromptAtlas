## Опис
Аудитує таблицю маршрутів deep link/universal link мобільного застосунку на прогалини покриття й небезпечну обробку параметрів — перевіряє конкретно шар роутингу, не самі екрани, і позначає маршрути, що можуть впасти, неправильно навігувати чи бути експлуатовані через недовірене зовнішнє посилання.

## Коли використовувати
- Додаєш новий deep link і хочеш перевірити його проти наявної таблиці маршрутів на конфлікти чи прогалини перед релізом.
- Аудитуєш повну поверхню deep link застосунку перед перевіркою безпеки, оскільки deep links — поширена точка входу недовіреного вводу, про яку легко забути, що вона зовнішня.
- Користувач повідомив про падіння чи неправильний екран при переході за посиланням, і підозрюєш баг роутингу/обробки параметрів, а не баг рівня екрана.

## Промпт

```
Ти аудитуєш таблицю маршрутів deep link/universal link мобільного застосунку на прогалини покриття й небезпечну обробку параметрів. Ти рев'юїш шар роутингу — як вхідні посилання зіставляються, парсяться й диспетчеризуються — не власну логіку екранів призначення.

Таблиця маршрутів / код лінкінгу: {{ROUTE_CODE}}
Платформа(и): {{PLATFORM}}
Приклади deep links, що зараз підтримуються: {{EXAMPLE_LINKS}}

Інструкції:
1. Перевір кожен патерн маршруту на параметри, що використовуються без валідації перед передачею на екран (напр., ID, використаний напряму у виклику бази даних/API, URL, використаний напряму в WebView) — deep link за визначенням недовірений зовнішній ввід, і неваlідовані параметри — найпоширеніше джерело падінь чи ін'єкцій із неправильно сформованих/зловмисних посилань.
2. Перевір на неоднозначність маршрутів: патерни, що можуть зіставитись більш ніж з одним маршрутом, чи catch-all/резервний маршрут, надто поблажливий, що може поглинути посилання, призначені для конкретнішого маршруту.
3. Перевір, що кожен маршрут має явну резервну поведінку для відсутніх чи неправильно сформованих обов'язкових параметрів (напр., посилання без очікуваного параметра `id`) — режим відмови має бути плавним перенаправленням чи екраном помилки, не падінням чи екраном невизначеного стану.
4. Перевір на прогалини автентифікації/авторизації: чи будь-який маршрут, що має вимагати авторизованого користувача чи конкретний дозвіл, реально забезпечує цю перевірку на рівні роутингу, чи навігує спершу і перевіряє пізніше (що може спричинити спалах неавторизованого контенту чи неузгоджений стан)?
5. Звір {{EXAMPLE_LINKS}} проти таблиці маршрутів, щоб підтвердити, що кожне справді розв'язується в задуманий маршрут і екран — таблиця маршрутів може виглядати правильною ізольовано, але все одно неправильно обробляти реальне посилання через тонкий баг зіставлення патернів.
6. Познач маршрути, що є в таблиці маршрутів, але не мають відповідного прикладу/тестового посилання, і навпаки — незадокументований маршрут — поширене джерело дрейфу між тим, що реально випущено, і тим, що реально тестується.

Формат виводу: Markdown, окремий запис на кожну знахідку: патерн маршруту, конкретна проблема, і виправлення. Заверши підсумком покриття (перевірені маршрути, маршрути без прикладу посилання, будь-які знайдені неоднозначні зіставлення).
```

## Змінні
- `{{ROUTE_CODE}}` — таблиця маршрутів deep link/конфігурація і логіка парсингу/диспетчеризації. Обов'язково.
- `{{PLATFORM}}` — iOS, Android чи обидва (механізми й конвенції роутингу різняться). Обов'язково.
- `{{EXAMPLE_LINKS}}` — набір реальних чи репрезентативних deep links, які застосунок має обробляти. Обов'язково — без конкретних прикладів неоднозначність і прогалини покриття значно важче перевірити проти реальної поведінки.

## Приклад
**Вхід:** `{{ROUTE_CODE}}` = «Патерни маршрутів: `/product/:id`, `/user/:userId/settings`, `/*` (catch-all → головний екран). `:id` передається напряму в `fetchProduct(id)` без валідації.» `{{PLATFORM}}` = «iOS (Universal Links)» `{{EXAMPLE_LINKS}}` = «myapp.com/product/123, myapp.com/user/456/settings»

**Вихід (уривок):**
```
### Знахідка: неваlідований параметр `:id`, переданий у `fetchProduct`
Маршрут: `/product/:id`. `id` береться напряму з URL і передається в `fetchProduct(id)` без перевірки типу чи формату. Неправильно сформоване посилання (напр., `/product/../../admin` чи нечисловий ID залежно від обробки бекенду) могло б спричинити неочікуваний виклик API чи падіння замість контрольованої помилки.
Виправлення: валідуй, що `id` відповідає очікуваному формату (напр., числовий), перед викликом `fetchProduct`; при невідповідності направляй у стан «контент не знайдено» замість виклику API з неваlідованим вводом.

### Знахідка: catch-all маршрут може поглинути неправильно сформовані посилання призначеного маршруту
Маршрут: `/*` → головний екран. Неправильно сформований `/product/` (без ID) чи `/user//settings` (без userId) провалився б у catch-all замість того, щоб проявитись як чіткий стан «неправильне посилання», мовчки приховуючи, що конкретний маршрут був задуманий, але зламаний.
Виправлення: розглянь конкретнішу резервну поведінку для неправильно сформованих версій відомих префіксів маршрутів (напр., `/product/*` без дійсного ID → «продукт не знайдено», а не загальна головна).

Підсумок покриття: перевірено 3 маршрути. `/user/:userId/settings` не має явної перевірки автентифікації, видимої в наданому коді — підтвердь, що це навмисно, чи додай перевірку «потрібен вхід» на рівні маршруту. Знайдено 0 неоднозначних зіставлень патернів.
```

## Поради та варіації
- Для великої таблиці маршрутів запускай цей промпт секціями, згрупованими за областю фічі, а не всю таблицю одразу — полегшує перегляд знахідок і призначення правильній відповідальній команді.
- Поєднуй із набором тестів фаззингу/неправильно сформованих посилань після виправлення знахідок — цей промпт виявляє ймовірні проблеми з читання коду, але не виконує маршрути, щоб підтвердити, що виправлення реально працює як задумано.
- Для Android зважай, що intent filters можуть мати додаткові тонкощі зіставлення (комбінації хост/схема/шлях) понад те, що ловить простий перегляд рядків-патернів — познач усе, що потребує тесту на рівні пристрою для повного підтвердження.
