## Опис
Рефакторить одну довгу функцію на кілька менших, добре названих із ідентичною поведінкою — видає реальний рефакторений код, а не лише список того, що не так. Для розробника, який вирішив виправити довгу функцію і хоче конкретний перший чернетковий варіант розділення.

## Коли використовувати
- Функція виросла до того, що вже нечитабельна одним поглядом, і потребує розділення.
- Готуєшся додати нову фічу до довгої функції і хочеш спочатку спростити її структуру, перш ніж додавати ще.
- Рецензуєш чиюсь довгу функцію і хочеш запропонувати конкретне виділення замість того, щоб просто сказати "це занадто довго".

## Промпт

```
Ти рефакториш довгу функцію на менші, добре названі функції з ІДЕНТИЧНОЮ зовнішньою поведінкою — однакові вхідні дані дають однакові результати, однакові побічні ефекти в тому ж порядку, однакові помилки за тих самих умов. Це рефакторинг Extract Method, а не переписування.

Функція для рефакторингу:
{{FUNCTION_CODE}}

Мова: {{LANGUAGE}}
Конвенції іменування/стилю для дотримання (необов'язково): {{STYLE_CONVENTIONS}}

Інструкції:
1. Визнач природні межі виділення: блок, що обчислює одну окрему річ, має описувану мету, незалежну від решти, і не ділить настільки багато змінного локального стану з оточенням, що виділення вимагало б повертати п'ять значень назад.
2. Для кожної виділеної функції дай їй назву, що описує, що вона робить (не "helper1", "part2") — назва має зробити оригінальну функцію читабельною майже як прозу, коли виділення завершено.
3. Тримай виділені функції на однаковому рівні абстракції одна відносно одної в новому тілі оригінальної функції — не залишай один гігантський inline-блок поряд із п'ятьма однорядковими виділеними викликами.
4. Зберігай поведінку точно: якщо в оригіналі є ранні return'и, побічні ефекти в конкретному порядку чи обробка помилок, рефакторена версія має видавати ідентичну спостережувану поведінку для кожного вхідного значення, включно з крайовими випадками.
5. Не "покращуй" логіку під час виділення (виправлення підозрюваного бага, зміна алгоритму) — якщо помітиш щось схоже на баг, зазнач це окремо після рефакторингу, не виправляй мовчки.
6. Покажи фінальний результат: нове коротке тіло оригінальної функції плюс усі виділені функції, готові до вставки.
7. Коротко поясни обґрунтування межі кожного виділення — чому саме цей блок заслуговує власної функції.

Вивід: рефакторений код (усі функції), за яким слідує коротке обґрунтування для кожного виділення.
```

## Змінні
- `{{FUNCTION_CODE}}` — довга функція для рефакторингу. Обов'язково.
- `{{LANGUAGE}}` — напр. "Python", "Java", "TypeScript". Обов'язково.
- `{{STYLE_CONVENTIONS}}` — конвенції іменування/форматування для дотримання (напр., "приватні методи з префіксом _"). Необов'язково.

## Поради та варіації
- Для мов/кодових баз, що не заохочують багато малих вільних функцій (напр., строгий ООП-стиль), попроси виділення в приватні методи того ж класу замість самостійних функцій.
- Якщо функція заплутана в занадто багато спільного змінного стану для чистого виділення, попроси прямо про це сказати і запропонувати ширшу реструктуризацію (напр., введення малого об'єкта стану), а не форсувати незграбне розділення.
