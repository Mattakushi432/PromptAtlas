## Опис
Пояснює міркування, що стоять за коментарями код-рев'ю, які джуніор-розробник отримав на свій PR, щоб він засвоїв принцип, а не просто виконав вказівку. Відрізняється від `constructive-review-comment-rewriter`, що допомагає рецензенту писати кращі коментарі — тут йдеться про того, хто їх отримав і намагається реально зрозуміти чому.

## Коли використовувати
- Отримав коментарі рев'ю, які зрозумілі як інструкції, але незрозуміло, чому рецензент хоче саме такої зміни.
- Хочеш засвоїти патерн, а не просто застосувати фікс і забути, щоб він не виринав знову в наступному PR.
- Готуєшся обговорити фідбек рев'ю з ментором і хочеш прийти з реальними питаннями, а не просто "гаразд, зміню".

## Промпт

```
Ти допомагаєш джуніор-розробнику зрозуміти міркування за коментарями код-рев'ю, які він отримав — не переписуєш коментарі і не просто переказуєш те, що вони вже кажуть.

Отримані коментарі рев'ю (встав як є): {{REVIEW_COMMENTS}}

Контекст коду (достатньо навколишнього коду, щоб зрозуміти, до чого стосуються коментарі): {{CODE_CONTEXT}}

Для кожного коментаря:
1. Поясни базовий принцип чи ризик, від якого він захищає — на один рівень глибше за сам коментар. Якщо коментар каже "виведи це в окрему функцію", поясни чому: читабельність, тестованість, уникнення дублювання чи щось інше конкретне для цього коду — а не загальне визначення "чому функції — це добре".
2. Наведи конкретний приклад режиму збою, який цей принцип запобігає — конкретний спосіб, яким код міг би піти не так чи стати важким у підтримці, якщо коментар проігнорувати, прив'язаний до реального показаного коду, а не підручниковий приклад.
3. Класифікуй коментар або як майже універсальне правило (те, що майже будь-який досвідчений інженер позначив би незалежно від команди), або як команда/рецензент-специфічну стилістичну перевагу — вкажи яке саме, і зазнач, що друге варто дотримуватись заради узгодженості, але це не глибокий принцип для засвоєння так само.

Якщо коментар насправді просто особиста перевага чи незначний bikeshedding без реального базового ризику (наприклад, перевага в неймінгу без різниці у зрозумілості), чесно скажи це, замість того щоб вигадувати переконливо звучне обґрунтування для того, чого немає — джуніор-розробники калібруються швидше, коли можуть відрізнити реальні принципи від стилю команди.
```

## Змінні
- `{{REVIEW_COMMENTS}}` — отримані коментарі рев'ю, як написані. Обов'язково.
- `{{CODE_CONTEXT}}` — достатньо навколишнього коду, щоб коментарі мали сенс поза контекстом. Обов'язково.

## Приклад
**Вхід:** `{{REVIEW_COMMENTS}}` = "Тут краще використати Map замість об'єкта для кешу — в об'єктів є проблеми з prototype pollution.", `{{CODE_CONTEXT}}` = функція, що використовує звичайний об'єкт `{}` як in-memory кеш, ключований наданими користувачем строковими ID.

**Вихід (фрагмент):**
```
Базовий принцип: звичайний JS-об'єкт успадковує від Object.prototype, тож такі ключі як "constructor", "__proto__" чи "toString" поводяться особливо замість звичайних записів кешу — у Map немає таких успадкованих ключів, тож кожен ключ поводиться однаково.

Режим збою, якому це запобігає: оскільки ключ кешу тут походить з наданих користувачем ID, користувач (випадково чи навмисно), надіславши ID "__proto__", міг би взаємодіяти з ланцюжком прототипу об'єкта замість того щоб бути збереженим як звичайний запис — у деяких патернах коду це навіть можна використати для атак prototype pollution. З Map той самий ключ — просто звичайний ключ без особливої поведінки.

Класифікація: майже універсальне правило, а не стилістична перевага. Використання Map для кешу, ключованого недовіреним/динамічним строковим вводом, — стандартна практика саме через цей конкретний клас багів — це не вибір house-style.
```

## Поради та варіації
- Якщо кілька коментарів виявляються проявом одного й того ж базового принципу, попроси явно зазначити це наприкінці — розпізнання одного повторюваного принципу в п'яти коментарях корисніше для навчання, ніж п'ять окремих пояснень.
- Для коментаря, який підозрюєш просто house-style, спитай прямо, а не вважай так — перевірка на чесність у цьому промпті налаштована саме на те, щоб реально це сказати, а не роздувати важливість кожного коментаря.
