## Опис
Діагностує, чому конкретне правило CSS не застосовується (чи перевизначається), простежуючи специфічність, порядок джерела і каскадні шари — і виправляє це без звернення до `!important` за замовчуванням. Для конкретного бага "чому мій стиль не застосовується", відмінного від багів адаптивності/макета.

## Коли використовувати
- Правило CSS, що виглядає коректним, не застосовується візуально, і ти підозрюєш, що інше правило перемагає в битві специфічності/каскаду.
- Успадкував таблицю стилів з розкиданими деклараціями `!important` і хочеш зрозуміти й розплутати фактичну війну специфічності під ними.
- Дебаг стилю, що ламається лише в одному конкретному контексті (напр., всередині конкретного батьківського компонента) через неочікувано вищого-специфічність правило предка.

## Промпт

```
Ти діагностуєш, чому конкретне правило CSS не набуває чинності, простежуючи фактичну механіку каскаду — специфічність, порядок джерела, `!important` і каскадні шари, якщо використовуються — а не звертаєшся до `!important` як виправлення за замовчуванням.

CSS-правила в грі (те, що має застосовуватися, і будь-які інші, що можуть конкурувати): {{CSS_RULES}}
Відповідний HTML елемента (наявні класи/ID/атрибути): {{ELEMENT_HTML}}
Що очікується проти того, що фактично відбувається: {{SYMPTOM}}

Інструкції:
1. Обчисли специфічність кожного конкуруючого правила, використовуючи стандартне зважування (inline, ID, клас/атрибут/псевдоклас, елемент/псевдоелемент), і покажи обчислення, а не лише переможця — це основний діагностичний крок.
2. Якщо специфічності рівні, тайбрейкер — порядок джерела (пізніше перемагає) — перевір фактичний порядок появи правил у таблиці(ях) стилів і зазнач, чи процес збірки/бандлінгу міг переупорядкувати їх неочікувано (напр., CSS Modules, порядок інжекції styled-components).
3. Перевір на `!important` у будь-якому конкуруючому правилі — якщо присутній, зазнач, що жодне збільшення специфічності правила "що має застосовуватися" не переможе, і `!important` у програючому правилі (якщо ти його контролюєш) чи на задуманому правилі (як останній засіб, позначений як технічний борг) — єдині способи це обійти.
4. Якщо використовуються каскадні шари CSS (`@layer`), врахуй це: порядок шарів повністю перевизначає специфічність для правил у різних шарах, тож правило з низькою специфічністю в пізнішому шарі перемагає правило з високою специфічністю в ранішому шарі — перевір це перед висновком, що проблема саме в специфічності.
5. Рекомендуй виправлення, що адресує першопричину з найменшим необхідним збільшенням специфічності — надавай перевагу коригуванню специфічності програючого селектора, щоб ледь перемогти, чи реструктуризації, щоб уникнути конфлікту (напр., використання каскадного шару, чи видалення надто широкого конкуруючого селектора), над зверненням до `!important`.
6. Якщо наявні декларації `!important` є частиною проблеми, зазнач, які з них несуть навантаження (їх видалення зламало б щось інше) проти тих, що видаляються як частина виправлення.

Формат виводу: Markdown з розділами: Розбір специфічності (кожне конкуруюче правило з обчисленою специфічністю), Першопричина, Виправлення.
```

## Змінні
- `{{CSS_RULES}}` — конкуруючі CSS-правила, у фактичному порядку джерела, якщо можливо. Обов'язково.
- `{{ELEMENT_HTML}}` — класи, ID і відповідні атрибути елемента. Обов'язково — обчислення специфічності залежить від того, що саме збігається з селекторами.
- `{{SYMPTOM}}` — який стиль очікується і що фактично рендериться. Обов'язково.

## Приклад
**Вхід:** `{{CSS_RULES}}` = `.card .title { color: blue; }` і `#sidebar .card-title { color: red; }`, `{{ELEMENT_HTML}}` = `<h2 id="sidebar" class="card-title">...</h2>`, вкладений у `.card`, `{{SYMPTOM}}` = "очікується синій, отримується червоний".

**Вихід (фрагмент):**
```
## Розбір специфічності
- `.card .title` — два класи → специфічність (0,2,0). Примітка: цей селектор насправді взагалі не збігається з елементом — елемент має клас `card-title`, не `title`, тож це правило навіть не конкурує (невідповідність назв, а не програш специфічності).
- `#sidebar .card-title` — один ID + один клас → специфічність (1,1,0), вища за будь-який лише-клас селектор.

## Першопричина
Це насправді не війна специфічності — `.card .title` не збігається з елементом через невідповідність назви класу (`title` проти `card-title`). `#sidebar .card-title` — єдине правило, що збігається, тому червоний.

## Виправлення
Виправ задуманий селектор на `.card .card-title` (чи перейменуй клас елемента), щоб він фактично таргетив елемент; потім знову порівняй специфічність — (0,2,0) проти (1,1,0) все одно надає перевагу ID-селектору, тож також розглянь, чи `#sidebar` взагалі має бути ID-селектором тут, чи має бути обмежений інакше.
```

## Поради та варіації
- Встав фактичний вивід панелі обчислених стилів з DevTools браузера (що показує переможне правило і ті, що воно перемогло, закреслені) як додатковий контекст `{{CSS_RULES}}` — це дає базову істину, а не вимагає, щоб модель симулювала розв'язання каскаду з нуля.
- Для налаштування CSS-in-JS (styled-components, Emotion) зазнач, що порядок інжекції (який може залежати від рантайму) важливий так само, як специфічність — познач це як окремий режим відмови, якщо симптом непослідовний між завантаженнями сторінки.
