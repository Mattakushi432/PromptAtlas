## Опис
Перетворює розпливчастий, неповний баг-репорт на мінімальний, виконуваний план відтворення — для тріажу вхідного тікета до того, як ти взагалі торкнешся коду. Не для діагностики бага, який ти вже вмієш відтворити.

## Коли використовувати
- Тікет підтримки чи репорт користувача каже, що щось зламалось, без чітких кроків.
- Триажиш беклог баг-репортів і треба зрозуміти, що спитати перед тим, як розслідувати.
- Передаєш баг комусь іншому і хочеш дати конкретну відправну точку замість розпливчастого опису.

## Промпт

```
Ти робиш тріаж баг-репорту, щоб зрозуміти, як його відтворити — ти ще нічого не дебажиш і не виправляєш.

Баг-репорт (як подано, яким би розпливчастим він не був): {{BUG_REPORT}}

Контекст системи (необов'язково — що робить система, важливе для інтерпретації репорту): {{SYSTEM_CONTEXT}}

Зроби наступне:
1. Перелічи, чого бракує в репорті для реального відтворення: точні кроки, середовище (браузер/ОС/версія застосунку), стан акаунту чи даних, очікуваний vs. фактичний результат.
2. Запропонуй найменший набір уточнювальних питань до автора репорту — не більше 5, у порядку, який найшвидше звузить пошук.
3. Склади план мінімального відтворення на основі найімовірніших відповідей на ці питання, чітко позначений як гіпотеза для перевірки, а не підтверджений репро.

Якщо репорт вже містить усе необхідне для відтворення (чіткі кроки, середовище, очікуваний vs. фактичний результат), скажи це прямо і просто акуратно переформулюй кроки відтворення — не вигадуй питання про відсутню інформацію, якщо вона насправді є.
```

## Змінні
- `{{BUG_REPORT}}` — сирий текст баг-репорту чи тікета, як подано. Обов'язково.
- `{{SYSTEM_CONTEXT}}` — короткий опис того, що робить система/фіча, щоб допомогти інтерпретувати неоднозначні формулювання репорту. Необов'язково.

## Приклад
**Вхід:** `{{BUG_REPORT}}` = "оформлення замовлення зламане, пробував двічі, просто не працює", `{{SYSTEM_CONTEXT}}` = "флоу оформлення замовлення в інтернет-магазині: кошик → доставка → оплата → підтвердження".

**Вихід (фрагмент):**
```
Чого бракує: на якому кроці саме зламано (доставка, оплата, підтвердження), що означає "не працює" (повідомлення про помилку, порожній екран, зависання, неправильний результат), браузер/пристрій, чи були товари в кошику, чи оплата взагалі була спробувана.

Питання для уточнення (за пріоритетом):
1. На якому саме екрані все зупиняється — доставка, оплата чи підтвердження?
2. Бачиш повідомлення про помилку, чи сторінка просто не реагує?
3. Яким браузером і пристроєм користуєшся?

Мінімальний репро-план (гіпотеза — перевір перед глибоким дебагом): додати товар у кошик → перейти до кроку оплати → відправити з тестовою карткою → подивитись, чи сторінка зависає чи видає помилку. Найімовірніші кандидати з огляду на "пробував двічі, просто не працює": застряглий стан завантаження або тихий збій виклику API оплати.
```

## Поради та варіації
- Для внутрішніх баг-репортів від колег, яких можна прямо спитати уточнення, одразу переходь до списку питань і пропускай секцію гіпотези.
- Якщо репорт містить скріншот чи фрагмент логу, додай його прямо в `{{BUG_REPORT}}` — список відсутньої інформації підлаштується і позначить лише те, чого справді ще бракує.
