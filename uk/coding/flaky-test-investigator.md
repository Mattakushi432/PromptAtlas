## Опис
Генерує ранжований список гіпотез, чому конкретний тест падає періодично, а не стабільно — таймінг, спільний стан, порядок, зовнішні залежності — для інженера, який втомився перезапускати CI і хоче реального плану розслідування.

## Коли використовувати
- Тест падає приблизно раз на 20 запусків без жодної зміни коду, а перезапуск "виправляє" його.
- Тест падає лише при запуску в певному порядку чи паралельно з іншими тестами, ніколи ізольовано.
- Рішення, чи карантинувати нестабільний тест, чи дійсно виправити його, і потрібно знати, що ймовірніше.

## Промпт

```
Ти розслідуєш нестабільний (періодично падаючий) тест. Мета — ранжований список гіпотез і як перевірити кожну — а не гарантований діагноз лише зі статичного аналізу, оскільки нестабільність за природою потребує доказів під час виконання.

Код тесту: {{TEST_CODE}}
Код, що тестується (необов'язково): {{CODE_UNDER_TEST}}
Патерн падіння (напр., "падає ~5% запусків", "падає лише в CI, ніколи локально", "падає лише після тесту X"): {{FAILURE_PATTERN}}
Вивід падіння/стек-трейс з падаючого запуску (якщо є): {{FAILURE_OUTPUT}}

Розглянь ці категорії нестабільності і підтверди/виключи кожну на основі наданих доказів:
1. Гонки станів / асинхронний таймінг — асерти виконуються до завершення асинхронної роботи, відсутні await, довільні sleep(), що маскують реальні очікування.
2. Спільний змінний стан — глобальні змінні, синглтони чи спільна база даних/фікстура, що передає стан між тестами, особливо якщо падіння корелює з порядком тестів.
3. Порушення ізоляції тестів — setup/teardown не повністю скидає стан (файли, моки, час, random seed) між запусками.
4. Зовнішні залежності — мережеві виклики, реальний годинник (`Date.now()`, `time.time()`), випадковість чи поведінка файлової системи, що не замокані/зафіксовані, тому результати різняться від запуску до запуску.
5. Конкуренція за ресурси — навантаження CPU/пам'яті в CI, через яке чутливі до таймінгу асерти (таймаути, порядок) падають лише під навантаженням.
6. Недетермінований порядок — сам тест чи код, що тестується, покладається на порядок ітерації (напр., hash map/set), який не гарантований.

Для кожної гіпотези, яку оцінюєш як правдоподібну, поясни конкретні докази, що на неї вказують, і дай конкретний спосіб її підтвердити (напр., "додай лог фактичного проти очікуваного timestamp", "запусти тест 100 разів ізольовано проти 100 разів у повному наборі і порівняй частоту падінь", "запусти з фіксованим random seed").

Ранжуй гіпотези за тим, наскільки добре вони відповідають заявленому патерну падіння — "падає лише в CI" сильно вказує на конкуренцію за ресурси чи різницю середовищ, "падає лише після тесту X" сильно вказує на спільний стан тощо. Не подавай усі гіпотези як однаково ймовірні, якщо патерн явно віддає перевагу одній.

Якщо інформації недостатньо, щоб щось підтвердити чи виключити, скажи, які конкретні дані (логи падінь за N запусків, спосіб відтворити локально) дозволили б звузити пошук.
```

## Змінні
- `{{TEST_CODE}}` — вихідний код нестабільного тесту. Обов'язково.
- `{{FAILURE_PATTERN}}` — як проявляється нестабільність (частота, умови, за яких вона стається/не стається). Обов'язково — це найсильніший сигнал для ранжування.
- `{{CODE_UNDER_TEST}}` — функція/модуль, що тестується. Необов'язково, але часто потрібне для виявлення гонок станів.
- `{{FAILURE_OUTPUT}}` — реальна помилка/провалений асерт з реального падаючого запуску. Необов'язково, але дуже цінно.

## Приклад
**Вхід:** `{{FAILURE_PATTERN}}` = "падає лише при запуску після `test_creates_user`, ніколи ізольовано", `{{TEST_CODE}}` = тест, що робить запит `SELECT COUNT(*) FROM users` і перевіряє, що результат дорівнює 1.

**Вихід (фрагмент):**
```
### 2. Спільний змінний стан — ВИСОКА впевненість
Патерн падіння (лише після `test_creates_user`) майже підручниковий приклад спільного стану: `test_creates_user`, ймовірно, вставляє рядок у `users`, який не очищується, тому асерт цього тесту `COUNT(*) = 1` падає, бо фактична кількість — 2.
Підтвердження: перевір, чи обидва тести діляться базою даних/транзакцією без відкату між ними, і перевір teardown у `test_creates_user`.
```

## Поради та варіації
- Якщо є CI-логи з кількох падаючих запусків, встав декілька зразків `{{FAILURE_OUTPUT}}` — патерн у падіннях (той самий асерт проти різних щоразу) сам по собі діагностичний.
- Для рішення "карантин чи виправлення" явно попроси також оцінити зусилля на виправлення для кожної гіпотези, щоб зважити вартість проти цінності тесту.
