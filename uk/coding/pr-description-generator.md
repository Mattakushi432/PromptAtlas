## Опис
Генерує чіткий, повний опис PR з diff'у й пов'язаного тікета — підсумок, зміни, план тестування — документ, який рев'ювер читає перед зануренням у код. Відрізняється від «Укладача Conventional Commits» (повідомлення одного коміту) і «Асистента рев'ю пул-реквестів» (рецензує PR, не пише його опис).

## Коли використовувати
- Відкриття PR з бажанням отримати опис, що дійсно допомагає рев'юверу, а не однорядкове "fixes bug" без жодного контексту.
- PR виріс і торкається кількох файлів, потребуючи опису, що прив'язує зміни назад до заявленої мети, щоб рев'ювер не залишався вгадувати, чому зроблена кожна зміна.
- Стандартизація якості опису PR у команді без потреби всім тримати той самий шаблон у пам'яті.

## Промпт

```
Ти пишеш опис пул-реквесту з diff'у і (якщо доступний) пов'язаного тікета — документ, призначений допомогти рев'юверу швидко зрозуміти зміну, не запис changelog.

Diff: {{DIFF}}
Пов'язаний тікет/issue (необов'язково — вимога чи звіт про баг, який адресує цей PR): {{TICKET}}
Шаблон PR для дотримання, якщо в репозиторії є свій (необов'язково): {{PR_TEMPLATE}}

Інструкції:
1. Напиши підсумок (2-4 речення), що заявляє, що робить цей PR і чому — "чому" має прив'язуватися назад до {{TICKET}}, якщо надано, не просто переказувати, які файли змінилися.
2. Переліч конкретні зроблені зміни, згруповані логічно (не просто плоский список файлів) — напр., "Бекенд: додано валідацію до ендпойнта X" / "Фронтенд: оновлено форму для показу нового стану помилки" — щоб рев'ювер міг навігувати diff з мапою замість читання файлів у якомусь порядку появи.
3. Виокрем усе, на що рев'юверу варто звернути особливу увагу: ризиковану зміну, неочевидне дизайнерське рішення, місце, де ти конкретно невпевнений і хочеш фідбек — не ховай це в diff для рев'ювера, щоб відкрити самостійно без спонукання.
4. Напиши план тестування: що фактично тестувалося (конкретні сценарії, не "тестувалося вручну"), і що рев'ювер міг би перевірити сам, щоб підтвердити, що зміна працює — конкретні кроки чи команди, не розпливчасте запевнення.
5. Якщо diff включає щось поза заявленим обсягом {{TICKET}} (опортуністичне прибирання, непов'язане виправлення, включене разом), явно виокрем це як окрему примітку, щоб рев'юверу не довелося самому з'ясовувати, чи це було навмисно.
6. Якщо надано {{PR_TEMPLATE}}, заповни його точно, а не використовуй іншу структуру, навіть якщо розділи цього промпту за замовчуванням організували б інформацію інакше.
7. Тримайся чесно: якщо щось не тестувалося, скажи про це, а не натякай на покриття, якого не існує — роздутий план тестування активно шкодить якості рев'ю, даючи хибну впевненість.

Формат виводу: Markdown за {{PR_TEMPLATE}}, якщо надано, інакше: Підсумок, Зміни, Примітки для рев'юверів, План тестування.
```

## Змінні
- `{{DIFF}}` — diff PR. Обов'язково.
- `{{TICKET}}` — текст пов'язаної вимоги/звіту про баг. Необов'язково, але різко покращує розділ "чому".
- `{{PR_TEMPLATE}}` — шаблон PR репозиторію, якщо є. Необов'язково.

## Приклад
**Вхід:** `{{DIFF}}` = додає middleware обмеження частоти запитів до ендпойнта `/api/login`, `{{TICKET}}` = "Звіт про баг: зловмисники можуть підбирати пароль brute-force, звертаючись до ендпойнта тисячі разів без обмеження".

**Вихід (фрагмент):**
```markdown
## Підсумок
Додає обмеження частоти запитів до `/api/login`, щоб запобігти атакам brute-force credential stuffing, адресуючи заявлений баг, де необмежені спроби логіну дозволялися без обмеження.

## Зміни
- Бекенд: додано `rateLimitMiddleware` до маршруту логіну, обмеження 5 спроб на IP за 15 хвилин.
- Бекенд: додано відповідь `429 Too Many Requests` із заголовком `Retry-After` при перевищенні ліміту.

## Примітки для рев'юверів
Вікно ліміту частоти (5/15хв) — перший прохід на основі типових патернів brute-force — познач, якщо вважаєш, що це має бути конфігуроване через env-змінну, а не захардкоджене, оскільки, можливо, захочемо налаштувати це після запуску.

## План тестування
- Перевірено вручну: 6 швидких спроб логіну з того самого IP коректно повертають 429 на 6-й.
- Перевірено вручну: спроби з іншого IP не впливають на ліміт частоти іншого IP.
- Ще не тестовано: поведінка під розподіленою/ротуючою-IP атакою — саме обмеження частоти не повністю адресує це; зазначаю як відоме обмеження, не блокую цей PR.
```

## Поради та варіації
- Для репозиторію зі squash-merge, де опис PR стає частиною постійної історії комітів, попроси трохи компактнішу версію, оптимізовану для цієї аудиторії (майбутні читачі git-log), а не лише для аудиторії живого рев'ю.
- Якщо diff дуже великий, попроси також позначити, які конкретні файли найвартіше рецензувати першими (найризикованіша логіка) проти механічних (перейменування, оновлення згенерованих файлів).
