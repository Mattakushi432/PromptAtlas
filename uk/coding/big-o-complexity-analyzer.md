## Опис
Виводить фактичну часову та просторову складність заданої функції через ретельний аналіз коду — вкладеність циклів, рекурсія, вартість операцій структур даних — з детально відпрацьованим міркуванням, а не просто заявленим ярликом Big-O. Для аналізу реального, можливо неочевидного коду, відрізняється від пояснення концепції складності абстрактно.

## Коли використовувати
- Рев'ю характеристик продуктивності функції перед релізом, особливо такої, що працює з даними, які можуть значно вирости.
- Підозра, що шматок коду повільніший, ніж виглядає, з бажанням отримати ретельне виведення, а не здогадку.
- Порівняння двох реалізацій тієї самої логіки для визначення, яка дійсно краще масштабується, коли це не очевидно з простого читання.

## Промпт

```
Ти виводиш фактичну часову та просторову складність наданого коду через покроковий аналіз — покажи міркування, а не лише фінальний ярлик Big-O.

Функція/код: {{CODE}}
Мова: {{LANGUAGE}}
Відповідний контекст (необов'язково — напр., "n — довжина масиву, m — окремий розмір вводу"): {{CONTEXT}}

Інструкції:
1. Визнач домінуючу(і) вхідну(і) змінну(і) і явно назви їх (n, m тощо) — якщо є кілька незалежних вводів, що по-різному впливають на вартість (напр., вкладений цикл над двома різними колекціями різних розмірів), використовуй окремі змінні, а не згортай усе в одну n.
2. Пройдися по коду структурно: для кожного циклу вкажи його кількість ітерацій у термінах вхідних змінних; для кожного вкладеного циклу — перемнож; для кожного виклику функції підстав її власну складність (рекурсивно аналізуючи викликані допоміжні функції, а не вважаючи їх безкоштовними).
3. Для будь-якої операції структури даних (додавання до списку, пошук у dict/hash, перевірка належності множині, вставка в масив за індексом) використовуй її ФАКТИЧНУ складність для даної мови/реалізації, а не припущену O(1) для всього — `.insert(0, x)` списку Python — це O(n), не O(1); неіндексований пошук поля, що вимагає повного сканування таблиці, не є O(1), навіть якщо виглядає як простий пошук.
4. Для рекурсивного коду встанови й розв'яжи (чи чітко проміркуй) рекурентне співвідношення — сформулюй саме рекурентне співвідношення, не лише фінальну відповідь, щоб виведення можна було перевірити.
5. Розрізняй складність найкращого, середнього і найгіршого випадку там, де вони дійсно різняться (напр., середній проти найгіршого випадку quicksort), і вкажи, який випадок найрелевантніший для позначення як практична турбота.
6. Аналізуй просторову складність окремо від часової, включно з будь-яким допоміжним простором (хеш-мапа, побудована під час алгоритму, глибина стеку викликів рекурсії) — не просто звітуй часову складність і не припускай, що простір очевидно такий самий.
7. Якщо складність коду гірша за добре відомий оптимальний підхід для цієї задачі, назви кращий підхід і його складність, але не переписуй код, якщо не попросили — мета тут — точний аналіз, не автоматична оптимізація.

Формат виводу: Markdown з розділами: Використані змінні, Покрокове виведення, Часова складність (найкращий/середній/найгірший, якщо різняться), Просторова складність, і (якщо релевантно) примітка про краще відомий підхід.
```

## Змінні
- `{{CODE}}` — функція/код для аналізу. Обов'язково.
- `{{LANGUAGE}}` — мова програмування, оскільки вартість операцій структур даних специфічна для реалізації. Обов'язково.
- `{{CONTEXT}}` — уточнення, що представляють вхідні змінні, якщо не очевидно з коду. Необов'язково, але допомагає для функцій з кількома вводами.

## Приклад
**Вхід:** `{{LANGUAGE}}` = "Python", `{{CODE}}` = функція, що для кожного елемента списку розміром n перевіряє належність іншому списку (не set) розміром m.

**Вихід (фрагмент):**
```
## Покрокове виведення
Зовнішній цикл виконується n разів (раз на елемент першого списку). Всередині нього `x in other_list` на Python `list` (не `set`) — це лінійне сканування O(m), не O(1) — поширена помилка, оскільки `in` на set було б O(1) у середньому випадку, але тут список.
Всього: n ітерацій × O(m) на ітерацію = O(n × m).

## Часова складність
O(n·m) — найгірший і середній випадок тут однакові, оскільки перевірка належності списку лінійна незалежно від того, де в середньому знайдено збіг.

## Просторова складність
O(1) допоміжного простору — жодні додаткові структури даних, пропорційні розміру вводу, не будуються.

## Примітка
Якщо `other_list` перетворити на `set` один раз перед циклом (одноразова вартість O(m)), перевірка належності стане O(1) у середньому випадку, знижуючи загальну складність до O(n + m) — суттєве покращення, якщо ця функція викликається з великими списками.
```

## Поради та варіації
- Для рекурсивних функцій з мемоізацією явно попроси проаналізувати складність З і БЕЗ мемоізації, щоб зробити покращення конкретним, а не аналізувати лише оптимізовану версію.
- Якщо порівнюєш дві реалізації, встав обидві і попроси паралельне виведення, що завершується прямою порівняльною таблицею, а не запускай цей промпт двічі окремо.
