## Опис
Рекомендує кросплатформену (React Native, Flutter) чи нативну (Swift/Kotlin) розробку з урахуванням фактичних обмежень проєкту — навички команди, потреби продуктивності, вимоги специфічних для платформи фіч — а не загальний список плюсів/мінусів. Для реального рішення build-or-choose на старті проєкту.

## Коли використовувати
- Старт нового мобільного застосунку з вибором підходу фреймворку до написання будь-якого коду.
- Наявний нативний застосунок розглядає кросплатформене переписування (чи навпаки) і потребує обґрунтованого кейсу, а не хайпу фреймворків.
- Обґрунтування вибору мобільного стеку стейкхолдерам з міркуваннями, прив'язаними до реального проєкту, а не посиланням на порівняльний блог-пост.

## Промпт

```
Ти рекомендуєш кросплатформену чи нативну мобільну розробку на основі наданих конкретних обмежень — не загальне порівняння фреймворків.

Опис застосунку (що він робить, ключові фічі): {{APP_DESCRIPTION}}
Обмеження команди (наявні навички, розмір команди, терміни): {{TEAM_CONSTRAINTS}}
Специфічні для платформи вимоги (необов'язково — напр., "потрібна глибока інтеграція з HealthKit/Health Connect", "важкі кастомні анімації", "AR-фічі"): {{PLATFORM_REQUIREMENTS}}

Інструкції:
1. Визнач будь-яку жорстку вимогу, що форсує (чи сильно надає перевагу) нативу: глибоку інтеграцію специфічного для ОС API без зрілого кросплатформеного мосту, критичну для продуктивності роботу (складна графіка в реальному часі, важка фонова обробка), чи ексклюзивну для платформи фічу. Якщо жодної немає, прямо про це скажи, замість того щоб вигадувати причину надати перевагу нативу.
2. Зважуй обмеження команди суттєво: команда з сильними навичками web/JS/Dart без досвіду нативної мобільної розробки має реальну вартість переходу на натив (наймання, час розгону), яку загальне порівняння ігнорує; команда з наявною сильною експертизою iOS/Android втрачає менше, переходячи на натив, і може отримати менше з головної обіцянки кросплатформи (спільна кодова база), якщо їй все одно доведеться вивчати новий фреймворк.
3. Якщо рекомендуєш кросплатформу, назви конкретний фреймворк (React Native проти Flutter) на основі обмежень — наявна знайомість команди з мовою (JS/TS надає перевагу React Native, нічого конкретно не надає перевагу Flutter, хіба команда знає Dart чи хоче послідовніший рушій рендерингу між платформами) важливіша за те, який фреймворк популярніший абстрактно.
4. Будь чесним щодо реальних витрат кросплатформи, навіть рекомендуючи її: періодична потреба заглиблюватися в нативні модулі для специфічних для платформи фіч, потенційне відставання в прийнятті найновіших фіч ОС, і різниця в розмірі застосунку/часі старту — не переоцінюй її як строго еквівалентну нативу.
5. Будь чесним щодо реальних витрат нативу, навіть рекомендуючи його: дві кодові бази для підтримки, дві експертизи платформи потрібні, повільніша швидкість розробки фіч для прямолінійних CRUD-екранів, що не потребують специфічного для платформи полірування.
6. Дай конкретну рекомендацію з єдиною найсильнішою причиною, що випливає із заявлених обмежень, не хедж, що перелічує кожен розгляд без висновку.

Формат виводу: Markdown з розділами: Аналіз вимог, Відповідність команді, Рекомендація (з основним обґрунтуванням), Витрати, які варто прийняти.
```

## Змінні
- `{{APP_DESCRIPTION}}` — що робить застосунок і його ключові фічі. Обов'язково.
- `{{TEAM_CONSTRAINTS}}` — наявні навички команди, розмір і терміни. Обов'язково — це зазвичай вирішальний фактор.
- `{{PLATFORM_REQUIREMENTS}}` — будь-які специфічні для платформи технічні потреби. Необов'язково, але може бути жорстким обмеженням, якщо є.

## Приклад
**Вхід:** `{{APP_DESCRIPTION}}` = "соціальний застосунок зі стрічкою, повідомленнями і стандартними CRUD-екранами, без важкої графіки", `{{TEAM_CONSTRAINTS}}` = "3 веброзробники з сильним досвідом React/TypeScript, без попереднього мобільного досвіду, 4-місячний термін", `{{PLATFORM_REQUIREMENTS}}` = "нічого специфічного для жодної платформи".

**Вихід (фрагмент):**
```
## Аналіз вимог
Ніщо в описі застосунку не форсує натив — стрічка, повідомлення і CRUD-екрани добре підтримуються обома основними кросплатформеними фреймворками без потреби в екзотичній інтеграції з ОС.

## Відповідність команді
Сильний бекграунд команди в React/TypeScript — значний аргумент на користь саме React Native над Flutter — вони можуть бути продуктивними майже одразу, використовуючи наявні знання JS/React, проти розгону з нуля на Dart і моделі віджетів Flutter однаково для обох фреймворків, якщо йти в кросплатформу, чи значно більшої вартості розгону, якщо йти повністю на натив (вивчення Swift/Kotlin з нуля для команди з 3 осіб і 4-місячного проєкту — реальний ризик для термінів).

## Рекомендація
React Native. Основна причина: наявний навичковий набір цієї команди напряму переноситься, що тут важливіше за будь-який технічний компроміс на рівні фреймворку з урахуванням прямолінійного набору фіч застосунку і жорсткого 4-місячного терміну.

## Витрати, які варто прийняти
Очікуй написання невеликої кількості нативних модулів, якщо пізніше захочеться специфічного для платформи полірування (напр., кастомна обробка push-сповіщень); закладай незначний додатковий час QA на специфічні для платформи крайові випадки, які React Native не абстрагує ідеально.
```

## Поради та варіації
- Якщо оцінюєш переписування наявного нативного застосунку, додай болючі точки наявного застосунку (швидкість розробки, складність найму) як явне обмеження — розрахунок суттєво відрізняється від рішення для greenfield-проєкту.
- Для команди, вже розділеної між нативними iOS- і Android-розробниками без інтересу вивчати новий фреймворк, явно попроси зважити "залишитися на нативі, але ділити більше логіки через спільний бекенд/шар API" як компромісну опцію.
