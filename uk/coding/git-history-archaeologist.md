## Опис
Пояснює, чому конкретний рядок чи блок коду, ймовірно, існує, з урахуванням контексту `git blame`/`git log` — реконструюючи намір з повідомлень комітів, навколишньої історії й форми коду. Для розуміння незнайомого, на вигляд дивного наявного коду, відрізняється від «Гіда розв'язання конфліктів мерджу» (активний конфлікт) і «Модернізатора легасі-коду» (міграція відомого патерну, не дослідження незрозумілого).

## Коли використовувати
- Зустрів дивний на вигляд рядок коду (незвичайний окремий випадок, магічне число, обхідний шлях) і хочеш зрозуміти, чому він там, перед тим як його чіпати.
- Рішення, чи безпечно видалити/змінити щось, спочатку зрозумівши, чому це було додано насамперед.
- Онбординг у незнайомий код з використанням його історії як швидшого способу зрозуміти намір, ніж читання коду наосліп.

## Промпт

```
Ти реконструюєш, чому конкретний шматок коду, ймовірно, існує, використовуючи докази з історії git — міркування з повідомлень комітів, навколишніх змін і форми коду, не лише опис того, що код зараз робить.

Код у питанні: {{CODE}}
Вивід git blame/log для цього коду (повідомлення комітів, дати, можливо diff'и коміту, що вводить код): {{GIT_HISTORY}}
Пов'язаний контекст (необов'язково — номери пов'язаних тікетів, знайдені в повідомленнях комітів, суміжний код): {{RELATED_CONTEXT}}

Інструкції:
1. Визнач коміт, що ввів цей конкретний код (чи його поточну форму, якщо він змінювався відтоді), і виведи, що повідомлення коміту каже про намір — спочатку прийми заявлену причину за чисту монету, потім перевір, чи форма коду узгоджується з цією заявленою причиною.
2. Якщо повідомлення коміту некорисне (загальне на кшталт "fix bug" чи "update code"), поглянь на навколишні докази: що ще змінилося в тому самому коміті (коміт з виправленням бага, що також торкається тестового файлу, натякає, який баг виправлявся і як), дату коміту відносно інших пов'язаних змін, посилання на номери тікетів/issue.
3. Розрізняй різні ймовірні категорії "чому": обхідний шлях для конкретного зовнішнього бага/обмеження (часто має коментар поруч чи повідомлення коміту, що згадує назву бібліотеки/API), окремий випадок, зумовлений бізнес-вимогою (конкретний клієнт/крайовий випадок), захисна перевірка проти бага, що стався в продакшні (часто вводиться разом з тестом, що відтворює саме цей баг), чи дійсно мертвий/застарілий код, що пережив свою початкову причину.
4. Якщо код торкалися кілька комітів з часом, простеж еволюцію — початкова причина може вже не бути поточною причиною, якщо пізніші коміти перепризначили чи розширили початковий код.
5. Вкажи свою впевненість: HIGH (повідомлення коміту + форма коду + навколишні докази всі вказують в одному напрямку), MEDIUM (правдоподібна історія, але деяка неоднозначність), LOW (історія не дає достатньо для впевненої реконструкції наміру — скажи, чого бракує, напр., пов'язаного тікета, що прояснив би це).
6. Якщо неявно чи явно запитано, чи цей код тепер безпечно видалити/змінити, дай відповідь на основі реконструйованого наміру: якщо початкова причина (напр., баг у відтоді оновленій залежності) підтверджено більше не застосовна, скажи про це; якщо причина все ще правдоподібно релевантна, познач, що видалення несе реальний ризик.

Формат виводу: Markdown з розділами: Коміт-джерело і заявлений намір, Підтримуючі/суперечливі докази, Ймовірна категорія, Впевненість, і (якщо релевантно) Оцінка безпеки видалення.
```

## Змінні
- `{{CODE}}` — код, чия історія досліджується. Обов'язково.
- `{{GIT_HISTORY}}` — фактичний вивід `git blame`/`git log -p` чи еквівалент для цього коду. Обов'язково — без реальних даних історії це вироджується в спекуляцію лише з коду.
- `{{RELATED_CONTEXT}}` — посилання на тікети, суміжний код чи інші підтримуючі докази. Необов'язково, але допомагає підтвердити гіпотезу.

## Приклад
**Вхід:** `{{CODE}}` = `if (userId === 'user_4471') { skipValidation = true; }`, `{{GIT_HISTORY}}` = повідомлення коміту "hotfix: unblock acme-corp signup, ticket SUPPORT-892, remove after their data is cleaned up".

**Вихід (фрагмент):**
```
## Коміт-джерело і заявлений намір
Повідомлення коміту напряму заявляє, що це тимчасовий hotfix для конкретного клієнта (натякнутого через "acme-corp") для обходу проблеми даних, явно позначений для видалення, коли їхні дані буде очищено (SUPPORT-892).

## Ймовірна категорія
Захисний/обхідний окремий випадок для конкретної відомої проблеми — явно тимчасовий за власним визнанням коміту, не постійна бізнес-вимога.

## Впевненість
HIGH — повідомлення коміту незвично явне і щодо причини, і щодо задуманого терміну життя цього коду.

## Оцінка безпеки видалення
Цей код мав бути явно тимчасовим. Перевір поточний статус тікета SUPPORT-892 — якщо він вирішений/закритий, цей окремий випадок дуже ймовірно безпечно видалити зараз; якщо все ще відкритий, підтверди з тим, хто володіє цим тікетом, перед видаленням, оскільки базова проблема даних може ще не бути дійсно вирішена.
```

## Поради та варіації
- Для коду взагалі без корисного повідомлення коміту (поширена проблема зі старою squashed історією) будь явним, що впевненість буде обмежена MEDIUM/LOW, і запропонуй запитати оригінального автора напряму, якщо він досі досяжний, замість того щоб подавати спекулятивну історію з невиправданою впевненістю.
- Поєднуй з виводом `git blame -w -C` (ігноруючи пробіли, відстежуючи переміщення коду між файлами) для коду, що переміщувався/рефакторився, оскільки наївний blame на переміщеному рядку часто вказує на коміт рефакторингу, а не оригінальний авторський намір.
