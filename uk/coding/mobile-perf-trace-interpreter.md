## Опис
Інтерпретує сирий вивід мобільного профайлера — таймінги кадрів, пропущені кадри, розбивку CPU/GPU — і визначає пріоритет, що виправляти першочергово. Відрізняється від діагностики розряду батареї чи інтерпретації краш-логу: це для застосунку, що працює, але гальмує чи фризить, а не падає чи жере батарею.

## Коли використовувати
- Зняв трейс (Xcode Instruments, Android Studio Profiler, Perfetto, Flipper), але сирий вивід щільний і незрозуміло, з чого почати.
- Конкретний екран чи взаємодія відчуваються фризливо, є дані профайлера, але немає чіткого наступного кроку.
- Триаж кількох знахідок з профайлера, щоб зрозуміти, яку виправляти першою.

## Промпт

```
Ти — інженер з продуктивності мобільних застосунків, який інтерпретує вивід профайлера, щоб визначити пріоритети виправлень — код ти ще не пишеш.

Вивід трейсу (сирий текст профайлера, зведена статистика чи розбивка за методами): {{TRACE_OUTPUT}}

Платформа: {{PLATFORM}}

Заявлений симптом (що реально спостеріг користувач/тестувальник — наприклад, "скрол смикається", "екран завантажується 3 секунди"): {{SYMPTOM}}

З даних трейсу:
1. Визнач топ-3–5 факторів, що спричиняють заявлений симптом, цитуючи конкретні докази з трейсу для кожного (назва методу і його частка часу, сплеск часу кадру, конкретна кількість пропущених кадрів).
2. Класифікуй кожен як CPU-bound, GPU-bound, блокування головного потоку, чи I/O-bound (диск/мережа) — це визначає, який тип виправлення застосовний.
3. Розстав пріоритети за (оціночним впливом на симптом) × (приблизна складність виправлення: швидка перемога чи структурна зміна).
4. Для кожного дай один конкретний наступний крок — конкретну зміну чи більш прицільне зняття профілю для підтвердження гіпотези, а не загальну пораду "оптимізуй це".

Якщо трейс не показує нічого явно аномального щодо заявленого симптому, чесно скажи це, замість того щоб натягувати знахідку, і запропонуй, який додатковий трейс (інший сценарій, довший запис, інший інструмент) реально покаже проблему.
```

## Змінні
- `{{TRACE_OUTPUT}}` — вивід профайлера: сирий текст трейсу, експортоване зведення чи розбивка таймінгів за методами. Обов'язково.
- `{{PLATFORM}}` — iOS чи Android (і інструмент профайлінгу, якщо релевантно — впливає на те, як читати дані). Обов'язково.
- `{{SYMPTOM}}` — проблема продуктивності, помітна користувачу, що розслідується. Обов'язково — без неї все в трейсі виглядає однаково "вартим оптимізації".

## Приклад
**Вхід:** `{{TRACE_OUTPUT}}` = зведення Android Studio Profiler, що показує `RecyclerView.onBindViewHolder` на рівні 40% часу кадру під час скролу, з повторюваними викликами декодування bitmap, `{{PLATFORM}}` = "Android", `{{SYMPTOM}}` = "скрол списку смикається на пристроях середнього рівня".

**Вихід (фрагмент):**
```
1. `onBindViewHolder` займає 40% часу кадру — CPU-bound, блокування головного потоку. Доказ: повторювані синхронні виклики декодування bitmap всередині bind, по одному на кожен видимий рядок на кожному кадрі скролу.
   Пріоритет: HIGH вплив, LOW-MEDIUM складність (швидка перемога) — декодування майже напевно повторюється для рядків, що вже проскролили повз, замість використання кешу.
   Наступний крок: перевір, чи bitmap не кешуються (пошукай бібліотеку завантаження зображень з налаштованим диск/пам'ять кешем); якщо не кешуються — це і є фікс, а не привід для глибшого профілювання.

Порядок пріоритетів: виправляти #1 першим — це і найбільший фактор, і найдешевший фікс.
```

## Поради та варіації
- Для трейсів iOS/Instruments попроси явно розрізняти докази "CPU hotspot з Time Profiler" від "пропуск кадру Core Animation" — вони вказують на різні категорії виправлень.
- Якщо симптом — час холодного старту, а не фриз при скролі, скажи це прямо — категорії I/O-bound і блокування головного потоку домінують по-різному на старті порівняно з трейсами взаємодії.
