## Опис
Зіставляє ідіоми та патерни кодбейзу з мови-джерела з їхніми еквівалентами в цільовій мові перед початком портування — плановий артефакт, який команда пише, щоб уникнути дослівного, неідіоматичного перекладу. Відрізняється від модернізації патерну в межах однієї мови: це саме для планування портування між мовами.

## Коли використовувати
- Плануєш переписування/портування сервісу чи модуля з однієї мови на іншу.
- Онбордиш команду, що вільно володіє цільовою мовою, але не мовою-джерелом, щоб вони розуміли, на що дивляться.
- Заздалегідь вирішуєш, які частини портування потребують редизайну, а не просто перекладу.

## Промпт

```
Ти плануєш портування між мовами. Твоє завдання — зіставити ідіоми і патерни з мови-джерела зі справді ідіоматичними еквівалентами в цільовій мові — а не зробити дослівний, механічно перекладений порт.

Мова-джерело: {{SOURCE_LANGUAGE}}
Цільова мова: {{TARGET_LANGUAGE}}
Репрезентативний код чи список патернів у використанні (наприклад, обробка помилок через винятки, декоратори, duck typing, goroutines, null coalescing): {{CODE_SAMPLE_OR_PATTERNS}}

Для кожного патерну чи ідіоми:
1. Вкажи найближчий справді ідіоматичний еквівалент у {{TARGET_LANGUAGE}} — не механічну транслітерацію, яка просто компілюється.
2. Познач будь-який патерн без чистого еквіваленту 1:1 — вони потребують реального дизайнерського рішення під час портування, а не заміни синтаксису. Поясни, які реально є варіанти.
3. Познач ідіоми та конвенції цільової мови, які команді варто прийняти, але вона може не подумати про це, прийшовши з {{SOURCE_LANGUAGE}} (наприклад, перехід з Python на Go: немає винятків, тож обробку помилок треба закладати явними значеннями повернення з самого початку, а не прикручувати пізніше; немає дизайну "класи насамперед" — думай маленькими інтерфейсами).

Виведи: таблицю зіставлення ідіом (патерн-джерело → цільовий еквівалент → примітки), потім секцію "патерни, що потребують переосмислення, а не перекладу", потім короткий список "топ пасток для розробника з {{SOURCE_LANGUAGE}}, що пише на {{TARGET_LANGUAGE}}".

Якщо мова-джерело і цільова мова близькі родичі (наприклад, Java до Kotlin, JavaScript до TypeScript), явно познач, де майже дослівне портування дійсно нормальне, а де воно скомпілюється, але читатиметься неідіоматично — не вважай "компілюється" синонімом "ідіоматично".
```

## Змінні
- `{{SOURCE_LANGUAGE}}` — мова, з якої портуємо. Обов'язково.
- `{{TARGET_LANGUAGE}}` — мова, на яку портуємо. Обов'язково.
- `{{CODE_SAMPLE_OR_PATTERNS}}` — репрезентативний код або просто список патернів/ідіом, реально використовуваних у кодбейзі-джерелі. Обов'язково — зіставлення корисне, лише якщо прив'язане до того, що там насправді є.

## Приклад
**Вхід:** `{{SOURCE_LANGUAGE}}` = "Python", `{{TARGET_LANGUAGE}}` = "Go", `{{CODE_SAMPLE_OR_PATTERNS}}` = "обробка помилок через винятки з кастомними класами винятків; duck-typed аргументи функцій; базовий клас з кількома підкласами, що перевизначають один метод".

**Вихід (фрагмент):**
```
Патерн: обробка помилок через винятки → еквівалент у Go: явні значення повернення `(result, error)`, з обгортанням помилок через `fmt.Errorf("...: %w", err)` для ролі кастомних класів винятків у передачі контексту вгору по стеку викликів.
Потребує переосмислення, а не перекладу: ієрархія класів з перевизначенням методів не має прямого еквіваленту в Go — у Go немає успадкування. Реальні варіанти — (а) інтерфейс, реалізований окремими типами, чи (б) вбудовування структур (embedding), якщо мета — справжнє повторне використання коду (не поліморфізм). Який саме варіант залежить від того, чи потрібно викликачам працювати з екземплярами поліморфно (→ інтерфейс), чи просто уникнути дублювання полів (→ embedding).

Топ пастка: у Python duck typing означає, що типи аргументів рідко проєктуються заздалегідь; у Go доведеться визначати інтерфейси рано, бо додавати їх заднім числом до вже написаних конкретних типів у великому кодбейзі — дорого.
```

## Поради та варіації
- Для пари з однієї родини мов (наприклад, Java → Kotlin) попроси окремо перелічити, які патерни Java стають антипатернами в Kotlin (як багатослівна перевірка на null замість `?.`), навіть якщо Java-версія все одно скомпілюється.
- Запускай це перед `legacy-code-modernizer`, а не замість нього — цей промпт задає цільові ідіоми; той застосовує отримані патерни до конкретного коду під час самого портування.
