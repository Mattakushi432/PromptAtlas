## Опис
Переносить конкретний застарілий патерн коду на його сучасний ідіоматичний еквівалент (callback'и на async/await, class-компоненти на hooks, старий синтаксис ORM на актуальний) з поясненням, що змінилося і чому це безпечно. Для розробника, що свідомо модернізує легасі-код, а не робить широке переписування.

## Коли використовувати
- Кодова база досі використовує застарілий патерн (callback hell, застаріле API, старий синтаксис фреймворку), і ти модернізуєш поступово.
- Онбординг у старий код і бажання побачити сучасний еквівалент поруч, щоб зрозуміти швидше.
- Підготовка до оновлення версії фреймворку/мови і потреба перенести патерни, що зламаються чи стануть застарілими.

## Промпт

```
Ти модернізуєш конкретний застарілий патерн коду до його актуального ідіоматичного еквівалента — цілеспрямована міграція, а не повне переписування чи редизайн. Зберігай поведінку точно; змінюється лише патерн/синтаксис.

Легасі-код:
{{LEGACY_CODE}}

Вихідний патерн/версія (необов'язково, якщо відомо): {{SOURCE_VERSION}}
Цільовий патерн/версія: {{TARGET_VERSION}}
Обмеження (необов'язково — напр., "має залишатися сумісним з X", "не можна вводити нові залежності"): {{CONSTRAINTS}}

Інструкції:
1. Визнач конкретний(і) застарілий(і) патерн(и) у коді (напр., вкладені callback'и, використання `var`, class-компонент з lifecycle-методами, застарілі виклики API) і назви кожен.
2. Перепиши, використовуючи сучасний еквівалент для {{TARGET_VERSION}}, зберігаючи точну поведінку — той самий потік керування, ту саму семантику обробки помилок, той самий порядок побічних ефектів.
3. Не додавай мовчки нові фічі, не виправляй непов'язані баги і не змінюй публічний інтерфейс/сигнатуру, якщо модернізація саме цього не вимагає (напр., перетворення callback на promise неминуче змінює конвенцію виклику — явно познач це як зміну, що ламає сумісність для викликачів).
4. Якщо застарілий патерн має тонкість, яку наївний сучасний еквівалент не відтворює (напр., callback, що теоретично міг спрацювати кілька разів, чого один `await` не може представити), познач це, а не мовчки видавай відмінну поведінку.
5. Якщо {{CONSTRAINTS}} виключає найідіоматичніший сучасний підхід, використай найкращий доступний підхід у межах обмеження і скажи, чим довелося пожертвувати.
6. Перелічи кожне місце виклику чи споживача, якому знадобиться зміна внаслідок цієї міграції, якщо це можна вивести з контексту.

Вивід: модернізований код, за яким слідує короткий список того, що змінилося, і будь-які зміни, що ламають сумісність для викликачів.
```

## Змінні
- `{{LEGACY_CODE}}` — старий патерн для міграції. Обов'язково.
- `{{TARGET_VERSION}}` — на що мігрувати, напр. "async/await (ES2017+)", "функціональні компоненти React з hooks (React 18)", "стиль SQLAlchemy 2.0". Обов'язково.
- `{{SOURCE_VERSION}}` — старий патерн/версія, якщо не очевидно з коду. Необов'язково.
- `{{CONSTRAINTS}}` — обмеження сумісності чи залежностей, що обмежують модернізацію. Необов'язково.

## Приклад
**Вхід:** `{{LEGACY_CODE}}` = функція Node.js із вкладеними callback'ами для трьох послідовних викликів БД, `{{TARGET_VERSION}}` = "async/await".

**Вихід (фрагмент):**
```js
async function getUserOrders(userId) {
  const user = await db.getUser(userId);
  const orders = await db.getOrders(user.id);
  const items = await db.getOrderItems(orders.map(o => o.id));
  return items;
}
```
*(далі: "Зміна, що ламає сумісність для викликачів: оригінал приймав callback у Node-стилі `(err, result)` як останній аргумент; ця версія натомість повертає Promise. Викликачів зі старою callback-сигнатурою потрібно оновити чи обгорнути через `util.callbackify`.")*

## Поради та варіації
- Для масштабної міграції запускай цей промпт по одній функції за раз і попроси також позначати, чи функція — хороший кандидат для codemod (механічна, за патерном) чи потребує ручного судження.
- При модернізації коду фреймворку (напр., React class → hooks) явно попроси зберегти будь-які тонкощі таймінгу lifecycle (напр., умови `componentDidUpdate`) як окрему примітку, оскільки таймінг ефектів у hooks не є точною відповідністю 1:1.
