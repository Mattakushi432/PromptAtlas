## Опис
Генерує структурований план розвідувального аналізу даних (EDA) з опису датасету та мети аналізу — інструмент планування того, що перевірити перед зануренням у хаотичне дослідження, не сам аналіз: він видає чек-лист/послідовність речей для дослідження, адаптований під реальну форму даних і питання.

## Коли використовувати
- Ти щойно отримав новий датасет і хочеш систематичний план дослідження, а не тицяння навмання з ризиком пропустити щось важливе.
- Онбордиш когось іншого на датасет і хочеш задокументований, повторюваний підхід EDA, якому можна слідувати.
- Хочеш перевірити, чи власне хаотичне дослідження досі покрило основи (пропущені значення, розподіли, очевидні проблеми якості даних), перш ніж робити висновки.

## Промпт

```
Ти генеруєш план розвідувального аналізу даних з опису датасету й мети аналізу. Ти адаптуєш план під реальну форму даних і питання — ти не видаєш загальний чек-лист EDA, не пов'язаний із тим, що реально описано.

Опис датасету (стовпці, типи, розмір, джерело): {{DATASET_DESCRIPTION}}
Мета аналізу: {{GOAL}}
Відомі проблеми якості даних (якщо є): {{KNOWN_ISSUES}}

Інструкції:
1. Почни з перевірок якості даних, специфічних для описаного: патерни пропущених значень (не просто «перевір на null» — які стовпці найімовірніше мають змістовну проти структурну відсутність значень, зважаючи на джерело), очевидні викиди чи неможливі значення, зважаючи на описані типи стовпців, і дублікати записів, якщо структура даних робить це правдоподібним.
2. Запропонуй одновимірні перевірки (розподіли, зведена статистика) спершу для стовпців, найрелевантніших {{GOAL}}, не недиференційований прохід через кожен стовпець — пріоритезуй на основі того, що реально потрібно меті.
3. Запропонуй дво- та багатовимірні/реляційні перевірки конкретно між змінними, що правдоподібно пов'язані з {{GOAL}} — вкажи, чому кожна запропонована перевірка релевантна меті, не просто «перевір кореляції між усім».
4. Якщо надано {{KNOWN_ISSUES}}, переконайся, що план явно звертається до того, як обійти чи квантифікувати вплив цієї проблеми, а не загальний план, що ігнорує відому проблему.
5. Познач будь-яку перевірку, що потребує зовнішнього контексту, відсутнього в самому датасеті (напр., доменні знання про те, як виглядає «нормальний» діапазон для змінної) — перевірка корисніша, коли зрозуміло, який результат був би несподіваним проти очікуваного.
6. Послідовно впорядкуй план логічно: спершу якість даних, потім одновимірне, потім дво-/багатовимірне/зв'язки, потім (якщо релевантно меті) початкова генерація гіпотез — не переходь до аналізу кореляцій до перевірки базових проблем якості даних, що можуть дати оманливі результати.

Формат виводу: Markdown, пронумерований, послідовний чек-лист, згрупований під `## Якість даних`, `## Одновимірне`, `## Дво-/багатовимірне/зв'язки`, і (якщо релевантно) `## Початкові гіпотези для перевірки`, кожен пункт із однорядковою нотаткою чому це важливо для {{GOAL}}.
```

## Змінні
- `{{DATASET_DESCRIPTION}}` — стовпці, типи, приблизний розмір і джерело/метод збору. Обов'язково — розпливчастіші описи дають розпливчастіші плани.
- `{{GOAL}}` — на що аналіз зрештою намагається відповісти чи що підтримати. Обов'язково — без цього план не може пріоритезувати.
- `{{KNOWN_ISSUES}}` — будь-які вже відомі проблеми якості даних. Необов'язково — пропусти, якщо ще невідомо.

## Приклад
**Вхід:** `{{DATASET_DESCRIPTION}}` = «Таблиця транзакцій клієнтів: customer_id, transaction_date, amount, product_category, signup_source. ~500 тис. рядків, з експорту продакшн бази даних.» `{{GOAL}}` = «Зрозуміти, що зумовлює вищу довічну цінність клієнта» `{{KNOWN_ISSUES}}` = «Деякі транзакції мають amount = 0, незрозуміло, чи це помилка даних, чи легітимна безкоштовна транзакція»

**Вихід (уривок):**
```
## Якість даних
1. Дослідити рядки amount = 0 конкретно (за відомою проблемою) — перевір, чи вони скупчуються за product_category чи signup_source, що вказало б на легітимний патерн (напр., безкоштовні пробні періоди) проти розкиданого випадково, що вказало б на помилку пайплайну даних. Це напряму впливає на те, чи ці рядки мають включатись у розрахунки LTV.
2. Перевір на дублікати транзакцій (той самий customer_id + transaction_date + amount) — продакшн-експорти іноді мають дублювання від логіки повтору/replay; дублікати завищили б цифри LTV.
3. Перевір діапазон дат і шукай прогалини — несподівана прогалина може означати неповний експорт, а не реальну бізнес-неактивність.

## Одновимірне
1. Розподіл amount (виключаючи/позначаючи питання нульового значення вище) — релевантно LTV, оскільки це основна агрегована цінність.
2. Розподіл транзакцій на customer_id — релевантно, оскільки LTV — функція і частоти транзакцій, і суми.

## Дво-/багатовимірне/зв'язки
1. Amount і частота за signup_source — напряму релевантно меті: якщо певні джерела залучення корелюють із вищим LTV, це дієво для стратегії залучення.
...
```

## Поради та варіації
- Запусти секцію «Якість даних» спершу окремим проходом і виріши знахідки там, перш ніж переходити до одновимірних/багатовимірних перевірок — продовження з невирішеними проблемами якості даних (як неоднозначні рядки нульового значення вище) ризикує будувати аналіз на хиткій основі.
- Для дуже великого чи високовимірного датасету план цього промпту — стартовий обсяг, не вичерпний — очікуй ітерувати сам план, коли початкові знахідки підкажуть нові релевантні питання.
- Поєднуй із «chart-type-recommender-for-a-dataset-shape» (data-and-analysis), коли план визначить, які конкретні зв'язки варто візуалізувати.
