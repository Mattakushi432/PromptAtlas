## Опис
Складає SQL-запит із питання природною мовою проти описаної схеми, з явно позначеними припущеннями — відмінний від «sql-query-performance-reviewer» (data-and-analysis, ще в бэклозі), який критикує продуктивність уже написаного запиту, а не складає новий із запиту простою мовою.

## Коли використовувати
- Знаєш, на яке питання хочеш отримати відповідь, але не хочеш писати SQL вручну, особливо для запиту з кількома джойнами чи умовами.
- Прототипуєш запит проти незнайомої схеми й хочеш першу чернетку для перевірки й коригування, а не починати з нуля.
- Хочеш перевірити, чи власна чернетка запиту реально відповідає задуманому питанню, отримавши незалежно виведений запит із формулювання простою мовою.

## Промпт

```
Ти складаєш SQL-запит із питання природною мовою, зважаючи на опис схеми. Ти явно вказуєш кожне припущення, яке довелось зробити — ти не вгадуєш мовчки неоднозначну бізнес-логіку (напр., що вважається «активним» користувачем) і подаєш запит так, ніби визначення було точним.

Схема (таблиці, стовпці, зв'язки): {{SCHEMA}}
Питання: {{QUESTION}}
Діалект SQL: {{DIALECT}}

Інструкції:
1. Визнач кожен неоднозначний термін чи рішення бізнес-логіки в {{QUESTION}}, яке сама схема не вирішує (напр., «недавній» — останні 7 днів? 30? «активний» — коли заходив? робив покупку?), і вкажи конкретне припущення, яке робиш для кожного, замість мовчазного вибору одного.
2. Пиши запит, використовуючи лише таблиці/стовпці, що існують у {{SCHEMA}} — якщо відповідь на питання потребує даних, відсутніх у схемі, скажи це прямо, а не вигадуй правдоподібно звучну назву стовпця.
3. Використовуй джойни, доречні до описаних зв'язків (не cross join чи припущений зв'язок, не заявлений у схемі) — якщо зв'язок між двома потрібними таблицями неясний із {{SCHEMA}}, познач це, а не вгадуй умову джойну.
4. Пиши запит у синтаксисі, доречному {{DIALECT}} (напр., функції дат, конкатенація рядків, `LIMIT` проти `TOP` суттєво різняться між PostgreSQL/MySQL/SQL Server/BigQuery), а не загальним SQL, що реально може не запуститись.
5. Для агрегатних запитів будь явним щодо гранулярності результату (один рядок на що?), оскільки тонко неправильний `GROUP BY` — одне з найпоширеніших джерел технічно робочого, але неправильного запиту.
6. Якщо питання справді досить неоднозначне, що дві по-різному сформульовані відповіді могли б на нього відповісти, коротко подай обидва, а не мовчки зобов'язуйся до одного — краще виявити розгалуження, ніж вгадати й помилитись.

Формат виводу: SQL-запит у блоці коду, перед ним короткий список «Припущення» для всього неоднозначного, і після нього однорядкова нотатка про гранулярність результату (що представляє один рядок).
```

## Змінні
- `{{SCHEMA}}` — назви таблиць, стовпці, типи, і як таблиці зв'язуються (зовнішні ключі чи описані зв'язки). Обов'язково — розпливчастий опис схеми дає запит, повний здогадок.
- `{{QUESTION}}` — питання простою мовою, на яке треба відповісти. Обов'язково.
- `{{DIALECT}}` — конкретний діалект SQL (PostgreSQL, MySQL, BigQuery, SQL Server тощо). Обов'язково — синтаксичні відмінності важливі для запиту, що реально запускається.

## Приклад
**Вхід:** `{{SCHEMA}}` = «users(id, email, created_at, country); orders(id, user_id, amount, created_at, status)» `{{QUESTION}}` = «У яких країнах найвища середня сума замовлення від активних клієнтів цього року?» `{{DIALECT}}` = «PostgreSQL»

**Вихід (уривок):**
```sql
-- Припущення:
-- 1. «активні клієнти» інтерпретовано як користувачі з хоча б одним замовленням статусу 'completed' цього року (у схемі немає явного прапорця «активний»)
-- 2. «цього року» інтерпретовано як поточний календарний рік (використовуючи CURRENT_DATE)
-- 3. «середню суму замовлення» розраховано лише по замовленнях статусу 'completed', щоб виключити скасовані/повернуті замовлення з викривлення середнього

SELECT
  u.country,
  AVG(o.amount) AS avg_order_value
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.status = 'completed'
  AND o.created_at >= DATE_TRUNC('year', CURRENT_DATE)
GROUP BY u.country
ORDER BY avg_order_value DESC;
```
Гранулярність: один рядок на країну.
```

## Поради та варіації
- Завжди переглядай список «Припущення» перед запуском запиту — це та частина, що найімовірніше розходиться з тим, що ти реально мав на увазі, особливо для бізнес-термінів на кшталт «активний», що не мають одного універсального визначення.
- Для повторюваного звітного запиту, а не одноразового, коли припущення підтверджені, збережи фіналізований запит, а не перевиводь його щоразу — цей промпт найкращий для чернетки й дослідження, не заміна підтримуваного звітного запиту.
- Якщо згенерований запит повільний чи виглядає структурно дивно при запуску на реальному обсязі даних, поєднуй із «sql-query-performance-reviewer» (data-and-analysis, бэклог) для окремого проходу продуктивності — цей промпт оптимізує на коректність і ясність, не продуктивність запиту.
